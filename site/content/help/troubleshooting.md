# 문제 해결

Tasty를 쓰다가 막혔다면 아래에서 증상에 맞는 항목을 찾아보세요. 설치와 권한, 터미널 연결, 알림 문제를 확인하는 방법을 안내합니다. 해결되지 않으면 페이지 아래의 문제 신고 방법을 참고하세요.

## 먼저 볼 파일

모두 `~/.tasty/` 아래에 있습니다 (Windows 는 `%USERPROFILE%\.tasty\`).

| 파일 | 내용 |
|---|---|
| `config.toml` | 설정. 설정 윈도우에서 저장한 값이 여기 들어갑니다 |
| `tasty.port` | 실행 중인 Tasty 의 IPC 포트 번호. Tasty 가 뜰 때 만들어집니다 |
| `debug.log` | 직전 실행의 경고 이상 로그. Tasty 를 다시 켜면 비워집니다 |
| `crash-reports/crash-*.log` | 크래시 리포트 — 버전 · OS · 위치 · 메시지 · backtrace |
| `crash-reports/hang-*.log` | 윈도우가 5초 넘게 멈췄을 때 자동으로 남는 기록 |
| `launch.log` | 이미 실행 중인 Tasty 가 있을 때 다시 실행한 기록과 결과 |
| `hook-failures.log` | Claude / Codex 훅이 Tasty 에 닿지 못한 기록 |
| `plugins-logs/<플러그인 id>.log` | 플러그인별 로그. `tasty plugin logs <id>` 로도 봅니다 |
| `state.db` | 최근 파일 등 앱이 자동으로 관리하는 데이터 |

더 자세한 로그가 필요하면 터미널에서 로그 레벨을 올려 실행합니다. `RUST_LOG` 가 아니라 `TASTY_LOG` 입니다.

```sh
TASTY_LOG=debug tasty 2> tasty.log
```

## 설치 · 첫 실행

- **Windows: "Windows 의 PC 보호" 경고가 뜹니다** — 코드 서명이 없어서입니다. **추가 정보 → 실행** 을 누릅니다.
- **macOS: "확인되지 않은 개발자" 라며 열리지 않습니다** — Gatekeeper 입니다. **시스템 설정 > 개인정보 보호 및 보안** 에서 허용하거나, 터미널에서 `xattr -dr com.apple.quarantine /Applications/Tasty.app` 을 실행합니다.
- **Linux: AppImage 가 실행되지 않습니다** — 실행 권한이 없거나 FUSE 가 없습니다. `chmod +x Tasty-*.AppImage` 를 먼저 하고, 그래도 안 되면 `./Tasty-*.AppImage --appimage-extract-and-run` 으로 실행합니다.
- **Linux: `GLIBC_2.39 not found` 로 실행되지 않습니다** — Ubuntu 20.04 · Debian 11 처럼 빌드 기준(Ubuntu 24.04)보다 오래된 배포판입니다. 구배포판용 빌드는 없습니다.
- **Linux `.tar.gz`: 라이브러리가 없다며 종료됩니다** — `tasty` 가 빠진 공유 라이브러리 파일 이름을 나열하고 끝납니다. 함께 나오는 검색 명령(`apt-file search` · `dnf provides` · `zypper what-provides` · `pacman -F` 중 배포판에 맞는 것)으로 그 라이브러리를 제공하는 패키지를 찾아 설치하세요. 필요한 라이브러리를 자동으로 설치하려면 `.deb` / `.rpm` 을 사용하세요.
- **윈도우가 뜨지 않고 바로 종료되며 로그에 "GPU 어댑터를 찾을 수 없음" 이 남습니다** — 사용할 수 있는 GPU 어댑터(Vulkan / DirectX 12 / Metal)를 찾지 못했습니다. 이 오류는 화면에 따로 표시되지 않고 `~/.tasty/debug.log` 와 터미널 출력(터미널에서 실행했을 때)에만 남습니다. 드라이버를 설치·업데이트합니다. Linux 는 `libvulkan1` / `vulkan-loader` 가 있으면 Vulkan 으로, 없으면 OpenGL 로, 그것도 안 되면 소프트웨어 렌더링으로 뜹니다. 그래픽 화면 없이 서버 · VM에서 실행하려면 [headless 빌드](../getting-started/install.md#headless-빌드)를 사용하세요.
- **Windows: "Git Bash를 찾을 수 없습니다"** — Tasty 는 Windows 에서 Git Bash 를 셸로 씁니다. Git for Windows 를 설치하거나 **설정** <!-- en: Settings --> > **터미널** <!-- en: Terminal --> > **셸** <!-- en: Shell --> 에서 bash 경로를 직접 지정합니다. 첫 실행이면 터미널 대신 **셸 선택** <!-- en: Choose a shell --> 화면이 뜹니다. 그 화면에 bash.exe 경로를 입력하고 **이 셸 사용** <!-- en: Use this shell --> 을 누르거나, **종료** <!-- en: Quit --> 로 닫고 Git for Windows 를 설치한 뒤 다시 실행합니다.
- **설정한 셸이 아닌 다른 셸이 열립니다** — 설정의 셸 경로에 파일이 없으면(Windows 는 bash · zsh 가 아닌 파일이어도) Tasty 는 찾아낸 다른 셸(Windows 는 Git Bash, macOS · Linux 는 로그인 셸이나 `$SHELL`)로 터미널을 엽니다. 설정 파일의 셸 값은 바꾸지 않으므로 경로를 고치거나 그 셸을 다시 설치하면 새 터미널부터 원래 셸로 돌아옵니다. 어떤 셸로 대신했는지는 `~/.tasty/debug.log` 에 남고, **설정** <!-- en: Settings --> > **터미널** <!-- en: Terminal --> 탭에도 안내가 뜹니다(Windows 는 "Git Bash를 찾을 수 없습니다", macOS · Linux 는 "설정한 경로에서 셸을 찾을 수 없습니다").
- **시작하자마자 "터미널을 시작할 수 없음" 화면이 뜹니다** — 첫 터미널을 열지 못했습니다. 본문의 "자세한 내용" 에 원인이 나옵니다. 설정한 셸 경로에 파일은 있지만 실행할 수 없을 때(macOS · Linux 에서 실행 권한이 없는 파일 등)가 대표적입니다. `config.toml` 의 `general.shell` 을 고친 뒤 다시 실행합니다. 이미 실행 중일 때 새 윈도우를 열다 같은 원인으로 실패하면 **새 윈도우를 열 수 없음** <!-- en: Could not open a new window --> 안내에 원인이 나오고, 열려 있던 윈도우는 그대로 동작합니다.
- **알림에 "최근 목록과 튜토리얼 진행이 저장되지 않습니다" 가 있습니다** — 최근 파일 목록과 튜토리얼 진행을 담는 `~/.tasty/state.db` 를 열지 못했습니다. Tasty 는 그대로 쓸 수 있고 터미널과 레이아웃 복원에는 영향이 없지만, 이전에 저장한 최근 목록과 튜토리얼 진행을 불러오지 못하고 이번 실행에서 바뀐 내용도 저장되지 않습니다. 이번 실행에서 Explorer로 이동한 폴더는 실행 중 그 윈도우의 최근 목록에 보일 수 있지만 다음 실행에는 남지 않습니다. 알림 본문에 원인이 나옵니다. "DB가 잠겨 있습니다" 면 다른 Tasty 가 이미 떠 있습니다. "손상되었습니다" / "스키마 버전이 맞지 않습니다" 면 Tasty 를 끄고 `~/.tasty/state.db` 를 백업한 뒤 지우면 다음 실행부터 새로 시작됩니다. 원인을 해소한 뒤 Tasty 를 다시 실행해야 저장이 다시 됩니다.
- **"Tasty를 시작하지 못했습니다" 화면이 뜨고 터미널이 열리지 않습니다** — 첫 윈도우를 준비하는 중에 Tasty 내부 단계가 실패했습니다. "자세한 내용" 에 원인이 나옵니다. **종료** <!-- en: Quit --> 를 누르거나 Esc · Enter 로 닫으면 Tasty 가 끝납니다. 다시 실행하고, 계속 반복되면 데이터 폴더(`TASTY_HOME`, 기본값 `~/.tasty`)를 쓸 수 있는지와 `~/.tasty/debug.log` 를 확인합니다. 화면을 띄울 수 없는 환경에서는 같은 내용이 메시지 상자(Linux 에서 zenity 가 없으면 데스크톱 알림)로 나옵니다.
- **Tasty 터미널 안에서 `tasty` 를 쳤는데 새 윈도우가 안 뜹니다** — Tasty 안에서 인자 없이 실행하면 새 윈도우 대신 도움말을 보여줍니다. 새 윈도우는 `tasty new window` 로 엽니다(보던 윈도우의 포커스는 그대로 둡니다).

설치 절차 자체는 [설치](../getting-started/install.md) 에 있습니다.

## macOS 권한 프롬프트

**증상** — 작업 도중에 권한 프롬프트가 떠서 하던 일이 멈춥니다. 터미널 안의 명령(과 그 안의 에이전트)이 새 폴더를 처음 건드릴 때마다 생깁니다.

**원인** — 터미널 안에서 실행한 명령이 파일을 읽으면 macOS 는 그 접근을 Tasty 의 것으로 봅니다(Terminal.app · iTerm2 도 같습니다). macOS 는 실제로 접근하는 그 순간에만 묻기 때문에, 미리 받아두지 않으면 프롬프트가 작업 한가운데에서 뜹니다.

**해결 — 미리 한 번에 받아둡니다.** **설정** > **일반** <!-- en: General --> > **권한** <!-- en: Permissions --> 에서 **모든 권한 요청하기** <!-- en: Request all permissions --> 를 누르면 다운로드 · 문서 · 데스크탑 폴더 → (연결돼 있으면) 외장 · 네트워크 볼륨 → 화면 기록 순으로 하나씩 물어봅니다. 앞의 것에 답해야 다음이 뜨고, 프롬프트가 떠 있는 동안에도 윈도우는 정상 동작합니다. 이미 허용하거나 거부한 항목은 다시 뜨지 않으므로 몇 번을 눌러도 괜찮습니다. 볼륨을 새로 연결한 뒤 다시 누르면 그 볼륨만 추가로 물어봅니다.

Tasty 는 시작할 때 프롬프트를 **자동으로 띄우지 않습니다.** 앱을 처음 켠 사람에게 이유를 알 수 없는 프롬프트가 줄줄이 뜨는 것을 없애기 위해서입니다. 대신 허용되지 않은 권한이 남아 있으면 시작할 때 안내가 떠서 이 화면으로 데려갑니다.

**어떻게 답하나**

| 권한 | 허용하지 않으면 | 나중에 바꾸려면 |
|---|---|---|
| 폴더 접근 (다운로드 · 문서 · 데스크탑 · 볼륨) | 그 폴더를 읽거나 쓰는 명령이 실패할 수 있습니다 | 시스템 설정 > 개인정보 보호 및 보안 > 파일 및 폴더 |
| 화면 기록 | `Ctrl+Alt+S` 스크린샷 → 클립보드 기능이 "화면 기록 권한이 필요합니다" 안내만 띄웁니다. 한 번 거부하면 다시 묻지 않습니다 | 시스템 설정 > 개인정보 보호 및 보안 > 화면 및 시스템 오디오 기록 |

현재 상태도 같은 탭에서 볼 수 있습니다(macOS 에서만 보입니다). 전체 디스크 접근 권한은 앱이 요청할 수 없어 이 버튼에 포함되지 않습니다. 전체 디스크 접근 권한 행의 **시스템 설정 열기** <!-- en: Open System Settings --> 로 시스템 설정을 열어 직접 추가하세요. 폴더 권한은 자동으로 확인할 수 없어 "자동 확인 불가" <!-- en: Cannot check automatically --> 으로 표시됩니다.

- **"허용되지 않은 권한이 있습니다" 안내가 떴습니다** — 전체 디스크 접근 권한이나 화면 기록 권한이 없어 보이는 동안 시작할 때마다 뜹니다. 어떤 권한이 어떤 상태인지는 **설정** > **일반** > **권한** 탭에서 봅니다. **권한 설정 열기** <!-- en: Open permission settings --> 를 누르면 Tasty 의 권한 화면이 열립니다. 전체 디스크 접근 권한은 앱이 직접 요청할 수 없어, 그 화면의 전체 디스크 접근 권한 행에 있는 **시스템 설정 열기** <!-- en: Open System Settings --> 로 시스템 설정을 열고 Tasty 를 목록에 직접 추가해야 합니다. 이 권한을 주면 파일 접근 프롬프트(다른 앱의 데이터 · 다운로드 · 문서 · 데스크탑 · 볼륨)가 사라집니다. 다만 다른 앱 제어(Automation) · 화면 기록은 별개 권한이라 그대로 남습니다. 권한을 주면 다음 시작부터 안내가 뜨지 않습니다. 안내를 끄는 설정은 없습니다. 껐다는 기록을 남기면 나중에 권한이 초기화됐을 때 알려줄 방법이 없어지기 때문입니다.
- **권한을 다 줬는데 폴더 접근 프롬프트는 여전히 뜹니다** — 시작 안내는 확인할 수 있는 권한만 봅니다. 다운로드 · 문서 · 데스크탑 · 볼륨 같은 폴더 권한은 확인하려고 폴더에 접근하면 권한 요청 대화상자가 뜰 수 있어 안내 판정에 넣지 않습니다. 전체 디스크 접근 권한을 주면 이 폴더들에도 접근할 수 있습니다.
- **권한을 줬는데도 안내가 다시 뜹니다** — 내려받은 배포본과 직접 빌드한 Tasty 모두 ad-hoc 서명이라, 업데이트하거나 다시 빌드하면 macOS 가 다른 앱으로 봅니다. 그러면 시스템 설정의 전체 디스크 접근 권한 목록에 Tasty 가 켜진 채 남아 있어도 그 항목은 더 이상 적용되지 않을 수 있습니다. 권한이 있는 상태로 Tasty 를 시작한 적이 있으면 안내가 이 경우를 알아보고, 목록에서 Tasty 를 지운 뒤 다시 추가하라고 알려 줍니다. 앱은 그대로인데 권한이 꺼진 경우에는 다시 켜라고 알려 주고, `tccutil reset` 등으로 목록에서 Tasty 가 사라졌다면 다시 추가하라고 알려 줍니다. **설정** > **일반** > **권한** 의 전체 디스크 접근 권한 행도 상태는 "허용 안 됨" 으로 두고 그 아래 한 줄에 같은 처방(켜져 보여도 적용되지 않으니 지우고 다시 추가, 또는 다시 켜기, 목록에서 사라졌으면 + 로 다시 추가)을 적습니다. 직접 빌드한다면 `./scripts/macos-codesign-identity.sh --create` 로 "Tasty Dev" 인증서를 한 번 만들고 이후 빌드에 같은 인증서를 사용하세요. 인증서를 사용해도 권한 유지가 보장되지는 않으므로 시스템 설정에서 상태를 함께 확인하세요. 인증서로 바꾼 직후에도 목록에서 기존 Tasty 를 빼고 다시 추가하세요.
- **전체 디스크 접근 권한 상태가 "확인 불가" 로 나옵니다** <!-- en: The Full Disk Access status shows "Unknown" --> — 이 상태는 macOS 에 묻는 API 가 없어 추정으로 구합니다. 추정에 쓰는 파일이 이 macOS 버전에 없으면 허용 여부를 판단할 근거가 없어 확인 불가로 표시하고, 이 권한을 이유로 시작 안내를 띄우지도 않습니다(화면 기록이 미승인이면 그 이유로는 뜹니다). 이 값으로 막히는 기능은 없습니다.
- **"Tasty이(가) 다른 앱의 데이터에 접근하려고 합니다" 가 앱 폴더마다 계속 뜹니다** — `~/Library/Application Support/<앱>` 같은 경로는 앱별로 따로 물어서 **모든 권한 요청하기** 로도 미리 받아둘 수 없습니다. 위의 전체 디스크 접근 권한을 주면 사라집니다.
- **`osascript` 를 쓸 때 "다른 앱을 제어하려고 합니다" 가 뜹니다** — Automation 권한은 대상 앱마다 승인해야 하며 전체 디스크 접근 권한으로도 덮이지 않습니다. Tasty 가 미리 해둘 수 있는 것이 없습니다.

## 윈도우가 멈추거나 갑자기 종료될 때

- **윈도우가 클릭 · 키 입력 · CLI 에 전혀 반응하지 않습니다** — 5초 넘게 멈추면 `~/.tasty/crash-reports/hang-*.log` 가 자동으로 남습니다. 파일의 `Render phase`가 `acquire` / `submit` / `present`이면 해당 렌더링 단계에서 멈춘 기록입니다. GPU 드라이버 문제일 수 있으므로 드라이버 업데이트도 확인하세요. Tasty 는 스스로 복구하지 않으므로 강제 종료하고 다시 띄웁니다.
- **갑자기 종료됐습니다** — `~/.tasty/crash-reports/crash-*.log` 를 봅니다. 문제를 신고할 때 이 파일을 함께 붙입니다.

## 설정이나 윈도우 구성이 초기화된 것처럼 보일 때

- **설정이 기본값으로 돌아갔습니다** — `~/.tasty/config.toml` 이 TOML 로 해석되지 않으면 기본값으로 시작합니다. 원래 파일은 지워지지 않습니다. 그대로 두었다가, 설정을 저장해 파일을 새로 쓰는 순간 같은 폴더의 `config.toml.bak` 으로 옮겨집니다. 그 파일을 열어 고친 뒤 `config.toml` 로 되돌리면 설정이 복원됩니다. 어느 줄이 문제인지는 `~/.tasty/debug.log` 에 적힙니다.
- **저장해둔 윈도우 구성이 복원되지 않았습니다** — 먼저 **설정** > **일반** > **시작 시 레이아웃 복원** <!-- en: Restore layout on startup --> 이 켜져 있는지 확인하세요. 워크스페이스 · 페인 · 탭 배치는 `~/.tasty/structure/journal.db` 에 저장됩니다. 이전 버전이 쓰던 `~/.tasty/layouts/` 의 `01.json` 같은 파일은 새 저장소로 처음 한 번 옮겨 올 때만 읽으므로, 그 뒤에는 이 파일을 고치거나 지워도 복원되는 배치가 바뀌지 않습니다. 저장소를 열지 못하면 Tasty 는 새 기본 워크스페이스로 시작하고, 오류 알림과 함께 윈도우 오른쪽 위에 **마지막 세션을 복원하지 못했습니다** <!-- en: Couldn't restore your last session --> 안내를 띄웁니다. 안내에는 원인과 저장소 위치가 적히고, 같은 내용이 `~/.tasty/debug.log` 에 남습니다. 저장소 파일은 바꾸거나 옮기거나 지우지 않습니다. 이번 실행에서 바꾼 워크스페이스 · 탭 · 레이아웃 배치는 Tasty 를 종료하면 사라지며(터미널에서 바꾼 파일에는 영향이 없습니다), 다음 실행은 저장소를 다시 읽습니다. 읽기 권한을 되돌리면 원래 배치가 복원됩니다. 안내는 **계속** <!-- en: Continue --> 이나 × 로 닫으며, 떠 있는 동안에도 터미널 입력은 그대로 됩니다. 다른 Tasty 가 같은 데이터 폴더를 쓰고 있을 때는 시작하지 않고 원인 화면을 보여 줍니다. 문제를 신고할 때 로그를 함께 붙여 주세요. <!-- TODO verify: 손상된 journal.db 에서 사용자가 배치를 되살리는 절차가 있는지 -->
- **"이전 레이아웃 파일을 가져오지 못했습니다" 알림이 떴습니다** <!-- en: "An old layout file could not be imported" --> — 이전 버전이 쓰던 `~/.tasty/layouts/01.json` 같은 파일을 레이아웃으로 읽지 못한 경우입니다. 그 윈도우는 새 기본 워크스페이스로 시작하고 파일은 그대로 남습니다. 파일을 읽을 권한이 없을 때는 오류 알림과 함께 윈도우 오른쪽 위에 안내가 뜹니다. 한 번 새 레이아웃으로 시작한 뒤에는 파일을 고쳐도 다시 가져오지 않습니다.
- **"터미널 내용 일부를 복원하지 못했습니다" 알림이 떴습니다** <!-- en: "Some terminal contents were not restored" --> — 이전 버전 파일을 가져올 때 일부 터미널의 저장된 내용 파일이 없거나 읽히지 않은 경우입니다. 배치는 그대로 복원되고 그 터미널만 이전 출력 없이 시작합니다.
- **"선택했던 탭을 복원하지 못했습니다" 알림이 떴습니다** <!-- en: "Selected tabs could not be restored" --> — 워크스페이스와 탭 배치는 복원했지만 마지막으로 선택했던 워크스페이스·탭 기록을 읽지 못한 경우입니다. 첫 워크스페이스와 탭이 선택된 채 시작합니다. 읽지 못한 기록은 알림에 적힌 위치(보통 `~/.tasty/structure/damaged/`)에 남겨 두며 자동으로 지우지 않습니다.
- **"저장된 레이아웃 일부를 복원하지 못했습니다" 알림이 떴습니다** <!-- en: "Part of the saved layout could not be restored" --> — 윈도우 하나의 저장 기록을 읽지 못한 경우입니다. 그 윈도우만 복원하지 않고 새 레이아웃으로 시작하며, 다른 윈도우는 그대로 복원됩니다. 읽지 못한 기록은 지우지 않고 남겨 둡니다. 알림에 레이아웃 번호와 원인이 적힙니다.
- **"이전 저장 시점으로 복원했습니다" 알림이 떴습니다** <!-- en: "Restored from an earlier save point" --> — 가장 최근 저장 시점을 읽지 못해 이전 저장 시점과 그 뒤 기록으로 레이아웃을 다시 만든 경우입니다. 그 뒤 기록을 모두 다시 적용하므로 레이아웃은 그대로입니다.
- **탭 하나가 빈 터미널로 열렸고 "탭 하나를 복원하지 못했습니다" 알림이 떴습니다** <!-- en: A tab opened as an empty terminal with "A tab could not be restored" --> — 그 탭에 저장된 내용(작업 폴더 · 이전 출력 · 복원 명령)을 읽지 못한 경우입니다. 다른 탭과 워크스페이스는 그대로 복원되고, 그 탭은 현재 셸 설정으로 새로 시작합니다. 읽지 못한 원본은 저장소에 그대로 남겨 두며 지우지 않습니다. 알림에 어느 워크스페이스의 어느 탭인지와 원인이 적힙니다.
- **"저장되지 않는다, `.bak` 파일을 옮기거나 지워라" 는 알림이 떴습니다** — 설정 파일(`config.toml`)의 원본을 옆으로 옮기려 했지만 `.bak` 부터 `.bak.9` 까지 아홉 자리가 이미 차 있어 더 둘 곳이 없는 경우입니다. 원본을 지우지 않으려고 저장 자체를 멈춘 상태이며, 그 세션 동안은 계속 저장되지 않습니다. 쌓인 `.bak` 파일 중 필요 없는 것을 옮기거나 지운 뒤 다시 켜면 정상으로 돌아옵니다.
- **"설정 파일을 읽지 못했다" 는 알림이 떴습니다** — 파일이 있는데 **읽지 못한** 경우입니다(권한 문제나 디스크 오류). 이때 Tasty 는 그 파일을 건드리지 않고 저장도 하지 않습니다 — 그대로 두면 지금 화면의 기본값이 원래 설정을 덮어쓰지 않습니다. 권한을 고치거나 파일을 다른 이름으로 옮긴 뒤 다시 켭니다.

  ```sh
  ls -l ~/.tasty/config.toml
  ```

## Tasty 를 다시 실행했을 때

- **앱 메뉴 · 실행기로 다시 실행했더니 새 윈도우 대신 이미 떠 있던 윈도우가 앞으로 옵니다** — 같은 데이터 폴더(`~/.tasty/`, 또는 `TASTY_HOME` 으로 지정한 폴더)를 쓰는 Tasty 는 하나만 실행됩니다. 다시 실행하면 새 프로세스를 만들지 않고 실행 중인 Tasty 에 넘깁니다. 트레이로 숨겼거나 최소화한 윈도우도 다시 보이고, 마지막으로 쓰던 윈도우가 앞으로 옵니다. 실제로 앞으로 올지는 OS 가 정하므로, 작업 표시줄 깜빡임으로 끝나는 환경도 있습니다. Wayland 에서 데스크톱 환경이 윈도우 활성화 요청을 지원하지 않으면 떠 있던 윈도우 대신 새 윈도우가 열립니다.
- **터미널에서 `tasty` 를 실행했더니 새 윈도우 하나만 열립니다** — Tasty 밖의 터미널 · 스크립트 · 에이전트에서 인자 없이 실행하면 `tasty new window` 와 같은 결과입니다. Tasty 가 띄운 터미널 안에서는 새 윈도우 대신 도움말이 나옵니다. 보던 윈도우의 포커스와 숨긴 윈도우는 그대로 둡니다. Windows 에서는 지금 쓰고 있는(앞에 있는) 터미널에서 실행하면 OS 가 앞으로 가져올 권한을 넘겨주므로, 앱 메뉴로 실행했을 때처럼 떠 있던 윈도우가 앞으로 올 수 있습니다.
- **"이미 실행 중인 Tasty가 있습니다." 상자가 뜹니다** — 실행 중인 Tasty 에 요청을 넘기지 못했고, 실행 중인 Tasty 가 응답하지 않습니다. 요청이 전달됐지만 처리가 늦을 때는 상자 없이 잠시 뒤 윈도우가 열립니다. 상자는 실행 중인 Tasty 가 아직 시작하는 중이었거나, Linux 에서 세션 버스에 연결하지 못한 경우가 대부분입니다. 원인은 데이터 폴더의 `launch.log`(`~/.tasty/launch.log`)에 남습니다. 다시 실행할 때마다 진행 단계별로 여러 줄이 기록됩니다. Linux 에서 `zenity` 가 없으면 상자 대신 데스크톱 알림으로 뜹니다.
- **방금 강제 종료한 Tasty 를 다시 실행하면 조금 늦게 뜹니다** — 남은 잠금이 풀리기를 2초까지 기다린 뒤 시작합니다.
- **Tasty 를 두 개 따로 띄워야 합니다** — 하나를 다른 `TASTY_HOME` 으로 실행합니다.

  ```sh
  TASTY_HOME=~/tasty-second tasty
  ```

## `tasty` 명령이 연결되지 않을 때

- **`No running tasty instance found (port file not found at …)`** — CLI가 확인한 경로에 포트 파일이 없습니다. 메시지에 적힌 경로가 `~/.tasty/tasty.port` 가 아니면 다른 홈 디렉토리(`TASTY_HOME`)를 보고 있는 것입니다. 이 메시지는 설정 언어(`general.language`, 기본값 영어)를 따르므로 한국어로 설정했다면 "실행 중인 tasty 인스턴스를 찾을 수 없습니다" 로 나옵니다. 인자가 잘못됐으면(깨진 JSON, 없는 `--cwd` 폴더 등) 이 메시지보다 그 인자의 오류가 먼저 나오므로, 이 메시지가 보였다면 접속 전에 수행하는 인자 검사를 통과한 것입니다.
- **포트 파일은 있는데 연결이 안 됩니다** — 이전 실행의 파일이 남았거나 다른 인스턴스의 경로를 보고 있을 수 있습니다. 오류에 나온 경로와 `TASTY_HOME`을 확인하고, 해당 파일을 사용하는 Tasty 인스턴스가 종료됐는지 확인하세요. 종료된 인스턴스의 남은 파일일 때만 직접 지우고 다시 시작하세요. 프로세스 이름 검색 결과만으로 파일을 삭제하지 마세요.
- **연결은 되는데 응답이 늦거나 `Error (-32061)` · `Error (-32065)` 같은 줄로 끝납니다** — [CLI 응답 지연과 연결 진단](cli-diagnostics.md)에서 오류 코드별 조치와 `tasty list pressure` 읽는 법을 확인하세요.


- **`tasty: command not found`** — Tasty 가 띄운 터미널 안에서는 PATH 에 자동으로 잡히고, `.deb` · `.rpm` · `.msi` 로 설치했다면 다른 터미널 앱에서도 잡힙니다. 그 밖의 설치 방식은 직접 등록해야 합니다. 설치 방식별 경로는 [설치 위치](../getting-started/install.md#설치-위치).

## 알림이 안 오거나 너무 많을 때

- **OS 알림 센터에 알림이 오지 않습니다** — 현재 Tasty 는 OS 알림 센터로 알림을 보내지 않습니다. 윈도우가 뒤에 있어도 알림은 앱 안의 **알림** <!-- en: Notifications --> 패널, 서피스 테두리, 사이드바 배지로 표시됩니다. 패널은 `Ctrl+Shift+I` 로 엽니다. 앱 안에서도 알림이 보이지 않으면 **설정** > **일반** > **알림** <!-- en: Notifications --> 의 **알림 활성화** <!-- en: Notifications enabled --> 가 켜져 있는지 확인하세요.
- **벨 소리(`\a`)마다 알림이 떠서 시끄럽습니다** — **설정** > **터미널** > **벨 알림 표시** <!-- en: Show bell notification --> 를 끕니다. `config.toml` 에서는 `[general]` 의 `bell_notification = false`. 벨 훅은 그대로 발생합니다.
- **소리가 안 납니다** — **설정** > **일반** > **알림** > **소리** <!-- en: Sound --> 가 기본 꺼짐입니다. 켜도 병합 간격 안에 같은 출처에서 연달아 온 알림은 하나로 합쳐져 소리가 한 번만 납니다.

설정 항목 전체는 [훅 · 알림 · 웹훅](../agents/hooks-notifications.md#설정).

## Claude · Codex 훅이 동작하지 않을 때

**증상** — 자식 에이전트의 완료 알림이 안 옵니다. 에이전트가 응답을 마쳐도 서피스 테두리 · 사이드바 배지가 켜지지 않습니다. 탭을 복원하거나 Tasty 를 재시작해도 같은 세션으로 이어지지 않습니다. `tasty claude reboot` 가 `claude-session-id meta not set`(한국어 설정이면 "claude-session-id 메타데이터 미설정") 으로 실패합니다. `tasty claude children` 이 보여주는 상태가 실제와 다릅니다.

**원인** — 훅이 설치돼 있지 않거나, Tasty 를 업데이트한 뒤 옛 훅 명령이 설정 파일에 그대로 남아 있습니다.

**해결** — 훅을 다시 설치합니다. 여러 번 실행해도 중복되지 않습니다.

```sh
tasty claude install    # ~/.claude/settings.json
tasty codex install     # ~/.codex/config.toml
```

그래도 안 되면 `~/.tasty/hook-failures.log` 와 `tasty plugin logs com.tasty.claude --follow` 를 봅니다. 세부 항목은 [Claude · Codex 와 함께 쓰기](../agents/claude-codex.md#문제-해결).

## 플러그인이 멈췄을 때

- **`tasty plugin list` 에서 enabled 인데 running 이 아닙니다** — 10초 안에 3번 실행에 실패하면 자동으로 정지됩니다. `tasty plugin logs <id>` 로 원인을 본 뒤 `tasty plugin enable <id>` 로 다시 시작합니다.
- **`plugin enable` 직후에는 running 인데 잠시 뒤 running 이 아니게 됩니다** — `plugin enable` 은 플러그인이 Tasty 에 연결하기를 기다리지 않고 바로 돌아옵니다. 그래서 막 켠 플러그인은 연결 전에도 running 으로 보이고, 그 사이 보낸 요청은 연결된 뒤 전달됩니다. 10초 안에 연결하지 못하면 실행 실패로 세어 running 이 아니게 됩니다. 원인은 `tasty plugin logs <id>` 로 봅니다.
- **번들 플러그인이 깨졌습니다** — `tasty plugin upgrade-builtins --force` 로 번들에서 다시 복사합니다. 플러그인 데이터(북마크 · 프로필 등)는 유지됩니다.
- **macOS: 기본 제공 플러그인이 실행되지 않습니다** — 앱에 남은 Gatekeeper 격리 표지(quarantine)가 플러그인 복사본에도 붙어 실행이 막혔을 수 있습니다. Tasty 는 이 표지를 스스로 지우지 않습니다. `tasty plugin logs <id>` 로 원인을 확인하고, 직접 지우려면 터미널에서 `xattr -dr com.apple.quarantine /Applications/Tasty.app ~/.tasty/plugins` 를 실행한 뒤 Tasty 를 다시 시작합니다.

## 버튼이나 단축키를 눌렀는데 작업을 완료하지 못했다는 안내가 뜰 때

레이아웃 변경·분할선 이동·카테고리 초기화·원격 연결 시작 같은 사용자 조작이 실패하면 화면에 실패 안내가 한 번 나타납니다. 분할선 위치를 확정하지 못했다면 이전 위치로 돌아갑니다. 카테고리 초기화 실패는 설정이 바뀌지 않았다는 뜻입니다. 화면의 현재 상태를 확인한 뒤 다시 시도하세요. 계속 실패하면 `~/.tasty/debug.log`의 같은 시각 기록과 함께 문제를 신고하세요. 에이전트 명령의 실패는 화면 토스트 대신 명령 응답이나 로그로 전달합니다.

## 링크나 폴더를 열지 못했다는 알림이 뜰 때

터미널 링크, 시스템 기본 앱으로 여는 파일, 플러그인 윈도우의 홈페이지·설치 폴더는 운영체제의 기본 프로그램에 넘겨 엽니다. 그 프로그램을 실행하지 못하면 알림이 뜹니다.

- **Linux** — `xdg-open` 이 설치돼 있는지, 또는 `BROWSER` 환경 변수가 실행할 수 있는 브라우저를 가리키는지 확인합니다. Tasty 를 실행한 환경의 `PATH` 에서 찾습니다.
- **macOS · Windows** — 해당 주소나 파일 형식에 연결된 기본 앱이 있는지 시스템 설정에서 확인합니다.

알림 없이 아무 일도 일어나지 않으면 기본 프로그램은 실행됐지만 그 프로그램이 열지 못한 경우입니다. 그 프로그램 쪽을 확인합니다.

## 명령으로 파일 선택 팝업을 열 수 없을 때

- **스크립트나 에이전트가 IPC 로 파일 선택 팝업을 열려고 하면 `-32016` 오류가 납니다** — 정상입니다. 파일 선택 팝업은 사용자가 사이드바의 **도구** <!-- en: Tools --> > **파일 열기…** <!-- en: Open File… --> 로 열거나, 플러그인이 엽니다(마크다운의 파일 열기에서 **찾아보기…** <!-- en: Browse… --> 를 누를 때 등). 명령이 팝업을 띄우면 사용자가 입력하던 곳의 포커스를 빼앗고, 고른 경로도 그 명령에게는 돌아가지 않기 때문입니다. 스크립트·에이전트는 파일 경로를 직접 지정하세요.

<a id="내-dev-서버가-몇-번-포트에-떴는지-모를-때"></a>

## 개발 서버의 포트를 찾고 싶을 때

사이드바의 **도구** <!-- en: Tools --> 메뉴에서 **연결 대기 중인 포트…** <!-- en: Listening ports… --> 를 엽니다. Tasty 터미널에서 띄운 프로세스가 열어둔 TCP 포트를 포트 · 프로세스 · 워크스페이스 · 탭과 함께 보여줍니다.

- 기본은 LISTEN 상태만 보입니다. 목록이 비고 "상태 필터에 맞는 포트가 없습니다" 가 떠 있으면 다른 상태의 포트가 있을 수 있습니다 — 필터 행 우측의 **상태** <!-- en: State --> 버튼으로 다른 상태를 켜고 **적용** <!-- en: Apply --> 합니다.
- Tasty 밖 프로세스까지 보려면 **전체 보기** <!-- en: Show all (system-wide) --> 를 켭니다.
- 행을 클릭해 선택하고 **주소 복사** <!-- en: Copy address --> 로 `host:port` 를 클립보드에 넣습니다.
- 별 아이콘으로 즐겨찾기에 넣으면 상단에 항상 보이고, 재시작해도 남습니다 (`~/.tasty/port-favorites.toml`). 다른 윈도우에서 바꾼 즐겨찾기도 바로 보입니다.

## 문제 신고

[GitHub 이슈](https://github.com/zilhak/tasty/issues)에 증상을 알려주세요. 아래 정보를 함께 남기면 원인을 확인하는 데 도움이 됩니다.

- `tasty --version` 출력과 OS · 버전
- 재현 절차
- `~/.tasty/crash-reports/` 의 해당 `crash-*.log` / `hang-*.log`
- 증상 직후의 `~/.tasty/debug.log` (다시 켜면 비워지므로 먼저 복사해 둡니다)

### 부모 에이전트가 자식 결과를 받지 못합니다

자식의 테두리·배지 상태와 부모 결과 수신은 별개입니다. 부모가 Claude Code이면 완료 로그와 Monitor 구독을 확인하세요. [연결·복구 안내](../agents/claude-codex.md)를 따르세요.

### 세마포어 · 배리어를 만들 때 "invalid char" 로 거절됩니다

이름에 대문자나 공백 같은 쓸 수 없는 글자가 들어 있습니다. 메시지가 가리키는 위치는 입력한 이름에서 센 자리입니다(첫 글자가 0). 영문 소문자 · 숫자 · `.` · `_` · `-` 로 바꿔서 다시 만드세요. [동시 실행 제한과 신호](../agents/tasks.md#동시-실행-제한과-신호)
