# tasty-host-plugin Trust Keys

Ed25519 공개키를 빌드에 포함하기 위한 디렉터리다. `build.rs`가 공개키를 `OUT_DIR`로 복사하고,
`bundle_sig.rs`의 `TRUSTED_PUBKEYS`가 그 파일을 컴파일할 때 읽는다.

## 파일

| 파일 | 추적 여부 | 용도 |
|------|-----------|------|
| `dev-pubkey.bin` | 추적하지 않음 | 개발용 개인키에 대응하는 raw 32바이트 공개키 |
| `release-pubkey.bin` | 추적하지 않음 | 선택한 릴리스 개인키에 대응하는 raw 32바이트 공개키 |

두 파일은 헤더 없는 Ed25519 공개키다. 없거나 길이가 32바이트가 아닌 슬롯은 `build.rs`가 all-zero placeholder로 채운다.
release 슬롯이 항상 비어 있어야 하는 것은 아니다. 실제 서명을 검증하려면 해당 개인키에 대응하는
공개키가 빌드에 포함돼야 한다. 두 슬롯이 모두 placeholder이면 release 빌드가 경고한다.
이 대체는 빌드를 계속하게 하지만 해당 슬롯으로 서명을 검증할 수 있다는 뜻은 아니다.

## 키 준비와 재사용

서명 키 선택 순서는 `SIGN_KEY_PATH`, 기존 `~/.tasty-keys/release.pem`, 개발용 `dev.pem`이다.
앞의 두 키를 사용하지 않을 때 `scripts/ensure-sign-key.sh`가 `scripts/gen-dev-key.sh`를 호출한다.
`gen-dev-key.sh`는 기존 개인키를 재사용하고 없을 때만 만든다. 공개키는 그 개인키에서 다시 도출하며,
내용이 같으면 공개키 파일도 다시 쓰지 않는다. 매 빌드마다 새 개인키를 만드는 방식이 아니다.

공개키는 서명할 개인키와 맞도록 Cargo 빌드 전에 준비한다. 모든 빌드에 같은 영구 릴리스 키를
필수로 제공하지는 않지만, 로컬에 만든 개인키는 파일로 남아 이후 빌드에서도 사용될 수 있다.
개인키 보호와 폐기는 빌드 환경의 책임이며 키 내용을 로그에 출력하지 않는다.

## 보호 범위

여기 포함하는 것은 공개키이며 개인키가 아니다. 번들 서명은 매니페스트의 변조를 확인한다.
플러그인 바이너리·번역 파일 전체나 외부 발급자의 장기 신뢰까지 이 서명 하나로 보장하지 않는다.
앱과 플러그인을 독립적으로 배포할 때는 신뢰 루트와 서명 범위를 다시 정해야 한다.

절차는 [플러그인 패키징](../../../docs/dev-guide/plugin-packaging.md#서명),
선택 이유는 [릴리스 결정](../../../docs/adr/0051-release-artifacts-and-versioning.md)을 따른다.
