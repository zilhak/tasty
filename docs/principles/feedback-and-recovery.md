# 결과 피드백과 실패 복구

## 시작 경로에 따른 결과 전달

사용자나 AI 에이전트의 입력으로 시작한 Tasty 작업은 성공과 실패를 명확하게 전달한다.

| 시작 경로 | 결과 전달 |
|---|---|
| 에이전트 호출 | 성공·실패를 식별할 수 있는 문자열 피드백 |
| 사용자 입력 | UI에서 명확한 성공·실패 피드백 |
| 즉각적인 입력에서 시작되지 않은 동작 | 알림 채널 |

접수나 로딩 표시는 성공 확정과 다르다. 작업이 비동기로 이어져도 시작 경로에 따른 최종 결과 전달을 생략하지 않는다. 터미널 안의 모든 프로그램 출력을 분석해 성공·실패를 대신 판정하는 요구는 아니다.

알림은 크리티컬한 실패의 오류, 문제가 있지만 크리티컬하지 않은 실패의 경고, 기능이 의도적으로 알림에 넣는 정보로 구분한다. LNB 진입점·레벨별 미확인 개수·상세 팝업의 요구와 현재 구현 범위는 [알림 기능](../features/notifications/index.md)에 구분한다.

## 알림에 남길 문제

즉각적인 입력에서 시작되지 않은 동작의 오류·경고는 사람이 Tasty를 사용하면서 직접 조치할 수 있을 때만 알림 채널에 남긴다. 설정을 바꾸거나, 파일·권한·네트워크 같은 환경을 고치거나, 다시 시도하거나, 잃은 작업 공간을 다시 구성하는 일이 조치에 해당한다. 알림 본문에는 사용자가 할 수 있는 조치를 적는다.

Tasty 내부 동작의 문제처럼 사용자가 알림을 보고도 할 수 있는 일이 없으면 알림 채널에 남기지 않고 로그에만 남긴다. 이 로그는 개발자가 원인을 추적하는 자료이며, 크래시 보고 같은 진단 피드백에 담길 수 있는 수준으로 보존한다.

이 기준은 알림 채널에만 적용한다. 에이전트 호출의 문자열 피드백과 사용자 입력에 대한 UI 피드백은 조치 가능 여부와 관계없이 성공·실패를 전달한다.

## 배너의 자동 닫힘

배너 안에 사용자가 할 수 있는 동작이 없으면 배너는 자동으로 닫힌다. 사용자가 할 수 있는 동작이 있으면 자동으로 닫지 않고, 사용자가 동작을 고르거나 직접 닫을 때까지 남긴다. 닫기 버튼은 여기서 말하는 동작에 포함하지 않는다.

개발자가 직접 지정한 예외는 이 원칙을 따르지 않을 수 있다. 이 원칙의 예외는 ADR 대신 해당 코드의 주석에 남기며, 개발자의 명확한 지시가 있었다는 사실과 지시 날짜를 함께 적는다.

## 실패 뒤의 처리

실패한 요소 때문에 본래 작업 흐름을 진행할 수 없으면 해당 흐름을 멈춘다. 재시도가 가능하면 재시도하고, 이후 진행에 별다른 영향이 없으면 기록을 남기고 계속한다. 기록을 알림과 로그 중 어디에 남길지는 위 기준을 따른다.

자동 재시도는 원인을 알 수 없거나 시간이 지나면 해소될 가능성이 있어 보이는 경우에 수행한다. 이미 실행됐는지 알 수 없는 결과와 실패 원인을 모르는 상황을 구분하여, 재시도 가능 여부를 판단한다. 횟수·간격·대기 종료 등 구체 기준은 개별 작업에서 정한다.

## 복원 실패

일부 자료를 잃은 경우에는 경고 알림을 남기고 가능한 부분을 복원한다. 이후 터미널 작업은 계속할 수 있어야 한다.

OS 잠금 등으로 복원 데이터를 읽는 것 자체가 불가능하면 오류 알림과 팝업으로 명시적으로 알린다. 팝업은 앱 우측 상단 부근에 표시하고 포커스를 가져가지 않는다. 중앙에서 입력을 가로채는 대신 화면에 표시하여 시선을 끈다.

사용자가 오류 안내를 닫으면 아무것도 복원하지 못한 초기 상태로 시작하여 이후 작업을 할 수 있어야 한다. 초기 상태로 계속한다는 것은 읽지 못한 원본을 삭제하거나 덮어쓴다는 뜻이 아니다.

현재 복원 구조와 구현 범위는 [레이아웃 복원](../features/layout-persistence/index.md)과 [자원 복구](../architecture/resource-recovery.md)에 있다. 복원 작업의 중단과 앱 전체 사용 불가는 구분한다.
