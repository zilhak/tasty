# 응답성과 사용자 설정

## 사용자 응답성

최대한 응답성을 우선한다. 사용자 동작에는 가능한 한 즉시 피드백하고 실제 처리는 그 뒤에 완료되는 방식으로 구성한다. 예를 들어 원격 탭 생성은 클라이언트에 탭과 로딩 상태를 먼저 표시하고 서버 결과로 확정 내용을 동기화한다.

에이전트나 내부 로직은 사용자 경로와 같을 필요가 없다. 불필요한 선행 UI 처리를 생략하고 결과 데이터를 받은 뒤 확정 상태를 적용할 수 있다. 이렇게 즉각적인 응답성을 양보한 에이전트 경로에는 진행 상황을 확인할 수 있는 수단이 반드시 있어야 한다. 예상보다 오래 걸리면 지연 로그 등으로 중간 상태를 알린다. 최종 결과만 나중에 보내는 것으로 대신하지 않는다.

## 부가기능 연결

부가기능은 기본 터미널 사용에 미치는 영향을 최소화한다. 이벤트버스나 [중앙 타이머 허브](../dev-guide/timer-hub.md)를 통해 이벤트 훅·폴링 등으로 동작하며 터미널의 개별 동작에 부가기능 처리를 직접 끼워 넣지 않는다.

특정 터미널 동작을 조건으로 삼아야 한다면 그 동작에 연결된 이벤트 발화 intent를 먼저 만들고 해당 intent의 처리 과정에 연결한다. Intent와 Event의 구별은 [동작 전달](../design/flows/action-dispatch.md)을 따른다. TimerHub는 실행 시점의 키를 전달하고 실제 작업은 외부 처리자가 수행한다.

## 실행 프로그램과 작업 조율

같은 파일을 여러 에이전트가 수정하는 문제는 에이전트 설정 등 실행 주체에서 해결한다. 터미널 안에서 실행되는 프로그램의 동작 문제를 Tasty가 대신 해결하는 것을 기본 책임으로 삼지 않는다.

작업의 자원 독점·과부하도 기본적인 강제 통제 대상으로 삼지 않는다. 유용한 아이디어가 있으면 충돌·독점·과부하를 피할 수 있는 부가기능을 제공할 수 있으며 사용 여부는 선택이다. Tasty 자체 처리의 정확성과 내부 큐·저장 구조를 관리하는 계약과는 구분한다.

## 단축키와 설정

ESC·Enter처럼 당연하게 쓰이는 기본 조작을 제외한 Tasty 자체 동작의 단축키는 설정의 단축키 탭에서 모두 변경할 수 있어야 한다. 특정 키가 포함된 모든 조합을 예외로 삼거나, 터미널 내부 프로그램의 키 설정까지 Tasty가 관리하는 뜻으로 확대하지 않는다.

취향에 따라 선택이 갈리는 값은 사용자 설정으로 제공한다. 성능상 트레이드오프가 있어 선택이 갈린다고 판단하는 값도 설정으로 제공한다. 다만 설정에 따라 성능 선택지 사이를 전환하는 구현이 어려우면 한쪽으로 결정할 수 있다.

커스터마이징을 목적으로 제공하는 기능은 목적에 맞는 설정을 제공한다. 구체 항목과 기본값은 기능별로 정한다. 현재 단축키 문법·저장과 OS 입력 차이는 [키 매핑](../design/policies/key-mapping.md)에 있다.
