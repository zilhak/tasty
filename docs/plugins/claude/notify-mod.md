# Claude completion notification mod

`tasty claude install` installs the existing status hooks and the `tasty-notify` Claude Code function-hooks mod. Re-run install after updating Tasty and start a new Claude process. The mod API was checked against the installed Claude Code 2.1.307 bundled declarations and validator; it is early access, not a guarantee for every older or future CLI. Unsupported CLIs can use the Monitor procedure in [external interaction](../../dev-guide/external-interaction.md#부모-claude-운영-규약--monitor-arm).

## Installation and ownership

The stable directory is `~/.claude/tasty-managed/notify-mod`, next to the existing user settings file. It does not depend on a debug/release instance, plugin installation directory or Tasty data home. The executable embeds the manifest, function-hook modules and state contract; ordinary plugin build/bundle/signing procedures still apply. No additional runtime asset staging is required. The Claude mod manifest has its own version, independent of the Tasty plugin manifest.

Install merges this absolute path into the user settings `env.CLAUDE_CODE_PLUGIN_DIRS` path list (`:` on Unix, `;` on Windows), preserving other values and hooks. It rejects a malformed environment/path list, separator-containing managed path, symlink traversal or an unowned existing target directory. A private ownership marker distinguishes the managed directory. Reinstall compares bytes and rewrites only changed assets/settings; `installed` and `updated` still describe hook events, while `mod_updated` reports a changed mod or path entry. An inherited process-level `CLAUDE_CODE_PLUGIN_DIRS` can override settings; preserve the managed entry there or remove that override yourself. Session profiles and reboot commands do not strip this variable or replace user settings discovery.

Uninstall removes only the exact managed path-list entry, installed asset names and empty managed directories. Other path-list entries, environment keys and hooks survive. Unknown files, including Claude-generated declaration files, are retained with the ownership marker; the directory can therefore remain after uninstall. Installation and removal are ordinary filesystem operations, not an atomic transaction with Claude's live reload. Do not run install/uninstall concurrently with another settings writer. No installer writes to a caller PTY or changes authentication.

## Session watcher

At `session.start`, the mod reads literal `TASTY_SURFACE_ID` and `TASTY_PARENT_HOME` environment keys. Without a numeric surface and an absolute parent home it does not arm. It reads only that namespace's `notify/<surface>.log` and `.log.meta`. A new process starts at the observed EOF, ignoring old notifications; an initially absent file starts at zero when created. Initialization is awaited before the first prompt, so a fast child started by that prompt cannot finish before the cursor is armed. An unreadable/oversized initial snapshot refuses activation rather than establishing a later EOF that silently skips new work.

The watcher uses one owned, non-overlapping 500 ms `$.clock.after` chain, with no platform shell/process dependency. It coalesces complete lines into one prompt per poll, normally up to16KiB, allowing one longer complete line within a1MiB snapshot bound. Larger logs refuse the read until the writer has reduced them; the writer's256KiB cleanup threshold is not a strict file maximum. Offsets count UTF-8 bytes; incomplete lines wait for a newline. A normal successful delivery advances only to the last delivered newline. A refused prompt or transient read keeps that position for retry. It never resubmits a user's original task or writes terminal input.

The namespace and absolute `retention_start + byte position` cursor live in `$.state`, which survives module reload, not in the persistent cross-session store. Claude2.1.307 reruns `session.start` on reload and cancels the old environment's pending timers. The mod also cancels its previous timer on another start and fences retired callbacks. The same process keeps watching across `/clear`, which emits an end but no new start. Final process/session end cancels the timer. A different parent home/surface gets a fresh EOF cursor rather than another namespace's history.

The reader compares metadata around its bounded snapshot and retries a changed retention baseline. It follows the completion-log resume rules for accounted truncation, an observed uncounted shrink, a decreasing host baseline and observed deletion/recreation. It reads from the beginning after those resets. This API offers no shared filesystem lock, inode or host-generation identity: deletion/recreation entirely between polls, uncounted truncate/regrowth past the cursor and writer metadata failures have the existing completion-log uncertainty. Lost retained bytes cannot be reconstructed. Prompt acceptance and cursor commit are also two API calls: normal reload/resume does not replay committed lines, but a crash/reload exactly between acceptance and commit can replay that batch. There is no atomic exactly-once transaction across those calls; do not interpret this as a durable result queue.

`TASTY_CLAUDE_NOTIFY_MOD=<surface-id>` marks a successfully initialized watcher in that Claude process and subsequent Bash children. Match the value to the actual surface before omitting Monitor; an inherited marker alone is insufficient. Outside Tasty, startup clears an inherited marker. Do not also arm Monitor when the mod is receiving: both consumers submit notifications. The marker is not a child result or an acknowledgement that the model completed a turn.

The mod calls `$.prompt.submit` without `asUser`: Claude supplies the plugin origin, and queues a separate turn when the current turn is idle. The visible heading explicitly says that status changes are not task-success evidence. Since this text is also user-visible, the mod ships English, Korean and Japanese headings selected by `TASTY_LOCALE`; its sandbox cannot call Tasty's Rust translator. The existing log lines keep the writer's locale. The API's scheduling/origin contract and local engine tests are separate from a real authenticated model turn and the actual UserPromptSubmit status-hook observation.

## Verification boundary

Local `claude plugin validate`, TypeScript checking, Claude's engine-based `plugin test`, and Rust install/uninstall tests cover the module source, reader and settings/assets invariants. The test runner supplies filesystem/clock/environment and submit stand-ins; it does not establish idle/busy real-model scheduling, hot-reload teardown in a live terminal, actual child completion delivery or UserPromptSubmit status updates. A real authenticated session must establish those acceptance observations before the full notification task is closed. Quota/authentication refusal is not a successful model response; do not change account, key, model or provider to bypass it.

For externally maintained instructions or conductor skills, skip Monitor only when this process's matching marker is present. Keep Monitor and periodic child reconciliation as fallback for unsupported/unloaded mods. Those user-owned files are not modified by the installer.
