# ADR-0052: macOS 권한 프롬프트는 부팅이 아니라 사용자가 요청할 때 띄운다

- **Status**: Accepted
- **Date**: 2026-09-24
- **Tags**: macos, permissions, tcc, boot, settings, discoverability, adr-0012
- **Group**: foundation

## Context

macOS는 보호된 리소스에 실제로 접근하는 순간에만 TCC 프롬프트를 띄운다. PTY로 띄운 자식 프로세스(zsh와 그 안의 AI 에이전트)가 보호 폴더를 건드리면 macOS는 그 접근을 부모 GUI 앱의 것으로 본다. 그래서 프롬프트가 터미널 작업 도중에 떠서 진행이 멈춘다.

이 중단을 없애려고 Tasty는 부팅 직후 워커 스레드에서 대상 경로를 순서대로 읽고 화면 기록을 요청해 프롬프트를 미리 띄웠다. 프롬프트 시점을 부팅으로 몰아 작업 중 중단을 없애는 것이 목적이었고, 그래서 요청 이력도 끄는 설정도 두지 않았다.

실제로는 다른 문제가 생겼다. 앱을 처음 켠 사람에게 이유를 알 수 없는 시스템 프롬프트가 연달아 떴고(홈 폴더 세 개와 마운트된 볼륨 수만큼, 그리고 화면 기록), 그것을 끌 방법이 없었다. 프롬프트를 띄우는 주체가 사용자가 아니라 앱이어서, 무엇을 왜 허용하는지 모르는 채로 결정을 강요받는다. 한 번 거부하면 앱이 다시 물을 수 없고 시스템 설정에서만 되돌릴 수 있으므로, 맥락 없이 누른 거부가 오래 남는다.

## Decision

부팅 직후의 자동 요청을 없앤다. 권한 요청은 설정 > 일반 > 권한 화면에서 [모든 권한 요청하기]를 눌렀을 때만 일어난다(`request_all_permissions`). 요청 순서, 워커 스레드, 하나씩 순차 처리 같은 기존 제약은 그대로 두고, 요청이 진행 중일 때 다시 들어오는 것만 새로 막는다. 요청이 겹치면 프롬프트가 포개져 뜨기 때문이다.

작업 도중 프롬프트로 진행이 멈추는 원래 문제는 부팅 권한 안내가 대신 막는다. 그 안내를 Full Disk Access 전용에서 "확인할 수 있는 권한 중 하나라도 허용되지 않은 경우"로 넓히고, 안내의 버튼이 시스템 설정이 아니라 Tasty의 권한 화면을 열게 한다. 사용자가 권한을 알게 되는 경로를 프롬프트 자체에서 "안내 → 권한 화면 → 사용자가 누르는 요청"으로 옮기는 것이다.

## Consequences

첫 실행이 조용해진다. 프롬프트가 뜨는 시점을 사용자가 정하고, 그 자리에 무엇을 왜 요청하는지 설명이 함께 있다. 요청하기 전에 현재 상태도 화면에서 확인할 수 있다.

대신 권한 화면을 한 번도 열지 않은 사용자에게는 원래 증상이 돌아온다. 에이전트가 작업 도중 프롬프트에 막혀 멈춘다. 이 결정은 그 손해를 감수하고 부팅 안내를 완화책으로 둔다. 안내가 닿지 않는 경우도 하나 남는다. 파일 폴더는 상태를 확인할 방법이 없어 판단에 넣을 수 없으므로, Full Disk Access와 화면 기록을 모두 허용한 사용자는 파일 폴더가 허용되지 않았어도 안내를 받지 못한다.

요청이 UI 상태를 갖게 된 것도 새로 생긴 비용이다. 진행 중 표시와 완료 후 상태 갱신이 필요해졌고, 부팅에서 한 번 부르던 시절에는 없던 재진입 방지와 완료 통지가 따라온다.

## Alternatives Considered

- 부팅 직후 자동 요청을 유지한다. 원래 문제를 가장 확실히 막지만 첫 실행의 프롬프트 폭주와 끌 수 없다는 점이 그대로 남는다. 사용자가 이 형태를 원하지 않는다고 명시적으로 결정했다.
- 첫 실행에만 요청한다. 프롬프트 폭주를 한 번으로 줄이지만 언제 어떤 프롬프트가 뜰지 모른다는 점은 같고, 그 한 번이 하필 앱을 처음 보는 순간이라 맥락이 가장 부족하다. 게다가 첫 실행 여부를 기록해 두면 재설치나 `tccutil reset`, ad-hoc 재빌드로 앱 식별이 바뀌어 TCC가 초기화된 뒤에 요청이 다시 일어나지 않는다.
- 설정에 자동 요청을 끄는 토글을 둔다. 기본값을 어느 쪽으로 하든 한쪽 사용자는 원하지 않는 동작을 겪는다. 토글을 찾으려면 어차피 설정 화면에 와야 하는데, 이미 그 화면에 왔다면 그 자리에서 요청하는 편이 단순하다.
- 기능이 필요할 때 그때그때 요청한다. 화면 기록은 캡처 직전에 요청하는 것이 자연스럽지만, 파일 폴더는 요청하는 주체가 PTY 자식 프로세스라 Tasty가 가로챌 수 없다. 이 방식으로는 원래 증상을 막지 못한다.

## Reconsideration Triggers

macOS가 파일 계열 TCC에 preflight API를 추가하면 다시 검토한다. 그러면 파일 폴더도 안내 판단에 넣을 수 있어 위에 적은 빈틈이 사라지고, 자동 요청 없이도 모든 권한을 안내할 수 있다.

`request_all_permissions`를 부르는 곳이 둘 이상이 되어도 다시 검토한다. 요청 시점이 여러 곳으로 흩어지면 사용자가 한 자리에서 정한다는 이 결정의 전제가 깨진다.

권한 화면을 들르지 않은 사용자가 작업 도중 프롬프트에 자주 막히는지는 사람이 직접 확인해야 한다. `tccutil reset SystemPolicyDownloadsFolder` 등으로 TCC를 초기화한 뒤 Tasty를 띄우고, 권한 화면을 열지 않은 채 에이전트 작업을 시켜 프롬프트가 작업을 멈추는지 본다. 부팅 안내를 닫고도 같은 일이 반복되면 안내가 완화책 역할을 하지 못하는 것이다.
