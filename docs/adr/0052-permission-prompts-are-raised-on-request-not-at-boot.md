# ADR-0052: macOS 권한 프롬프트는 부팅이 아니라 사용자가 요청할 때 띄운다

- **Status**: Accepted
- **Date**: 2026-09-24
- **Tags**: macos, permissions, tcc, boot, settings, discoverability, adr-0012
- **Group**: foundation

## Context

macOS 는 보호 리소스에 **실제로 접근하는 그 순간**에만 TCC 프롬프트를 띄운다. PTY 자식(zsh, 그 안의 AI 에이전트)이 보호 폴더를 건드리면 macOS 가 그 접근의 responsible process 를 부모 GUI 앱으로 귀속시키므로, 프롬프트가 **터미널 작업 도중에** 떠서 자율 진행이 멈춘다. 그 중단을 없애려고 tasty 는 부팅 직후 워커 스레드에서 대상 경로를 순차로 `read_dir` 하고 화면 기록을 요청해 프롬프트를 앞당겼다(`spawn_prewarm`).

그 정책은 문서에 결정으로 못박혀 있었다 — "발화 시점을 부팅 직후로 몰아 작업 중 중단을 없애는 것이 이 기능의 목적", "따라서 상태 플래그도, 끄는 토글도 두지 않는다".

실제로 겪은 것은 다른 쪽이었다. 앱을 처음 켠 사람에게 이유를 알 수 없는 시스템 프롬프트가 **줄줄이** 뜨고(홈 폴더 3 개 + 마운트된 볼륨 수 + 화면 기록), 그것을 끌 방법이 없었다. 프롬프트를 띄우는 주체가 사용자가 아니라 앱이라서, 사용자가 무엇을 왜 허용하는지 모르는 채 결정을 강요받는다. 한 번 거부하면 앱은 다시 물을 수 없고 시스템 설정에서만 되돌릴 수 있으므로, 맥락 없이 눌린 거부가 영구적인 손해가 된다.

## Decision

부팅 직후 자동 발화를 없앤다. 권한 요청은 **설정 > 일반 > 권한** 화면의 [모든 권한 요청하기] 를 눌렀을 때만 일어난다(`request_all_permissions`). 발화 순서·워커 스레드·순차 처리 같은 기존 제약은 그대로 유지하고, 요청 중 재진입만 새로 막는다(원자 교환 — 두 시퀀스가 겹치면 프롬프트가 포개져 뜬다).

원래 문제("작업 도중 프롬프트로 자율 진행이 멈춘다")를 대신 막는 것은 **부팅 권한 안내**다. 그 안내를 FDA 전용에서 "확인 가능한 권한 중 하나라도 미승인" 으로 일반화하고, 안내의 버튼이 시스템 설정이 아니라 **Tasty 의 권한 화면**을 열게 한다. 즉 발견 채널을 "프롬프트 자체" 에서 "안내 → 권한 화면 → 사용자가 누르는 요청" 으로 옮긴다.

## Consequences

- **얻은 것**: 첫 실행이 조용하다. 프롬프트가 뜨는 시점을 사용자가 정하고, 그 자리에 무엇을 왜 요청하는지 설명이 함께 있다. 요청 전에 화면에서 현재 상태를 볼 수 있다.
- **잃은 것**: 권한 화면을 한 번도 열지 않은 사용자에게는 **원래 증상이 돌아온다** — 에이전트가 작업 도중 프롬프트에 막혀 멈춘다. 이 ADR 은 그 트레이드오프를 감수하고, 부팅 안내를 그 완화책으로 둔다. 안내가 닿지 않는 경로가 하나 남는다: 파일 폴더는 상태를 재는 수단이 없어 판정에 못 넣으므로, FDA 와 화면 기록을 모두 허용한 사용자는 파일 폴더가 미승인이어도 안내를 못 받는다.
- **운영 비용 / 유지 부담**: 요청 시퀀스가 UI 상태(진행 중 표시 · 완료 후 상태 갱신)를 갖게 됐다. 부팅 1 회 호출이던 시절에는 없던 축이다 — 재진입 방지와 완료 통지가 그 비용이다.

## Alternatives Considered

- **현행 유지(부팅 직후 자동 발화)** — 원래 문제를 가장 확실히 막지만, 첫 실행의 프롬프트 폭격과 "끌 수 없음" 이 그대로 남는다. 사용자가 명시적으로 이 형태를 원하지 않는다고 결정했다.
- **첫 실행에만 발화** — 폭격을 1 회로 줄이지만 "언제 어떤 프롬프트가 뜰지 모른다" 는 성질은 같고, 그 1 회가 하필 앱을 처음 보는 순간이라 맥락이 가장 없는 때다. 게다가 "첫 실행" 플래그는 TCC 가 초기화된 뒤(재설치 · `tccutil reset` · ad-hoc 재빌드로 앱 identity 변경) 요청이 영영 안 도는 어긋남을 만든다.
- **설정 토글로 자동 발화를 끄게 하기** — 기본값이 무엇이든 한쪽 사용자는 원치 않는 동작을 겪는다. 토글을 찾으려면 어차피 설정 화면에 와야 하는데, 그 화면에 이미 왔다면 그 자리에서 요청하는 편이 축이 하나 적다.
- **필요할 때마다 그 기능이 요청** — 화면 기록은 캡처 직전 요청이 자연스럽지만, 파일 폴더는 요청 주체가 PTY 자식이라 tasty 가 가로챌 수 없다. 이 대안은 원래 증상을 전혀 막지 못한다.

## Reconsideration Triggers

다음 중 하나가 충족되면 본 ADR 을 재검토한다.

**채널이 붙는 것** — 판정 시점에 레포가 읽을 수 있는 사실이다.

- macOS 가 파일 계열 TCC 에 preflight API 를 추가한다. 그러면 파일 폴더를 안내 판정에 넣을 수 있어 위 "안내가 닿지 않는 경로" 가 사라지고, 자동 발화 없이도 사각이 0 이 된다.
- `request_all_permissions` 의 호출처가 둘 이상이 된다. 요청 시점이 다시 여러 곳으로 흩어지면 "사용자가 정하는 한 자리" 라는 이 결정의 전제가 깨진다.

**원리적으로 안 붙는 것** — 사람이 관측해야 한다. 재는 법을 함께 적는다.

- 권한 화면을 안 들른 사용자가 작업 도중 프롬프트에 막히는 일이 실제로 잦다. 재는 법: TCC 를 초기화한 상태(`tccutil reset SystemPolicyDownloadsFolder` 등)로 tasty 를 띄우고 권한 화면을 열지 않은 채 에이전트 작업을 시켜, 프롬프트가 작업을 멈추는지 본다. 부팅 안내를 닫고도 그 일이 반복되면 안내가 완화책 노릇을 못 하는 것이다.
