# ADR-0051: 릴리스는 서명과 고지문을 갖춘 번들로 만들고 내용 변경에 버전을 올린다

- **Status**: Accepted
- **Date**: 2026-09-24
- **Tags**: release, plugins, versioning
- **Group**: rules

## Context

앱과 번들 플러그인은 함께 배포되지만 버전과 서명은 서로 다른 역할을 한다.
버전이 같아도 내용이 달라지면 배포·업그레이드 판단이 모호해진다.
소스 파일이 staged됐다는 사실만으로 내용 변경을 판단하면 포맷 정리에도 버전을 올리게 된다.

## Decision

Tasty 본체의 갱신은 OS 패키지와 릴리스 배포 경로에서 제공한다.
앱 자체가 새 버전을 확인·다운로드·설치하는 기능은 두지 않는다.
이를 코어에 유지하면 플랫폼별 설치·서명 처리와 사용자 알림 등 여러 영역을 관리해야 한다.

번들 플러그인의 산출물에 영향을 주는 내용이 달라지면 패치 버전을 올린다.
대상 경로와 의존성을 비교하고 Rust 파일은 rustfmt로 정규화한다.
주석을 정규식으로 제거하거나 변경 파일 수로 예외를 정하지 않는다.
버전 선언 자체는 내용 변경 증거에서 제외하며 비교는 배포할 범위의 두 끝점에서 한다.

번들 서명에는 빌드 환경의 키를 사용한다. 모든 릴리스가 공유할 영구 개인키를 GitHub Secret으로
필수 제공하도록 하지 않는다. 기본 경로는 로컬 dev 키를 없을 때 만들고 기존 키는 재사용한다.
공개키는 빌드 전에 같은 개인키에서 준비해 앱에 포함한다.
이 방식은 번들과 앱이 한 배포물로 전달되는 모델을 전제로 한다.

고지 파일은 저장소에서 관리하고 모든 배포물에 함께 넣는다. `LICENSES/` 전체를
스테이징하며 최종 산출물에서도 내용이 같은지 확인한다. 실제로 실행하지 못한 플랫폼은
구현 여부와 검증 여부를 나누어 보고한다.

## Consequences

포맷 정리와 제품 내용 변경을 구분하고, 버전은 실제 배포 내용에 맞춰 정할 수 있다.
주석만 바뀌거나 일부 선언 순서만 바뀐 경우에는 보수적으로 버전 증가를 요구할 수 있다.
정규화가 실패하면 원문을 비교하며 필요한 도구나 기준 커밋을 읽지 못하면 측정 실패로 처리한다.

로컬 키를 사용하므로 모든 릴리스에 동일한 발급자 신원을 보장하지 않는다.
키가 매 빌드 새로 생기는 것도 아니다. 기존 키를 재사용하는 기간과 보호 책임은 빌드 환경에 남는다.

## Alternatives Considered

- 앱 안에서 업데이트 설치까지 처리하면 OS 배포 경로와 별도로 관리할 영역이 커진다.
- staged 파일 수나 커밋 type으로 버전 필요성을 판단하면 포맷 변경과 실제 변경을 구분하지 못한다.
- 문자열 공백이나 주석을 정규식으로 지우면 실제 리터럴 변경까지 같다고 볼 수 있다.
- 영구 릴리스 키를 필수로 요구하면 별도 키 배포·회전 운영이 필요하다.

## Reconsideration Triggers

번들 플러그인을 앱과 독립적으로 원격 배포하거나 외부 소비자가 장기 발급자 신뢰를 요구하면
서명키와 신뢰 정책을 다시 정한다. 내용 비교가 실제 산출물 변경을 놓치거나 오검출 비용이
커지면 비교 범위와 정규화 방법을 검토한다.
