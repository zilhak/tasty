# ADR-0275: 최근 목록 캐시는 state.db 수명에 귀속한다

- **Status**: Accepted
- **Date**: 2026-09-15
- **Tags**: storage, recent-files, focus, multi-window

## Context

최근 파일은 인스턴스의 state.db 하나에 저장되지만 AppState를 만들 때마다 별도 캐시를
로드했다. 두 창을 먼저 열고 한 창에서 파일을 기록하면 다른 창의 recent.query는
이전 목록을 반환했다. 이 조회는 대상 창 인자가 없고 종류만 받는 전역 목록이다.
같은 초에 연 파일의 메모리 순서와 DB 저장 실패 때의 메모리 동작도 유지해야 한다.

## Decision

Db가 RecentFiles 캐시를 한 벌 소유하고, load는 그 캐시의 공유 핸들을 반환한다.
각 창의 get은 같은 캐시에서 경로 스냅샷을 얻는다. add는 캐시 갱신과 기존 DB 저장을
캐시 락 안에서 순서대로 수행한다. 공개 IPC 인자와 응답, 종류별 최신순·중복 제거·10개
상한은 유지한다. DB가 없는 독립 테스트의 default 캐시는 다른 인스턴스와 공유하지 않는다.

## Consequences

- **얻은 것**: 창 생성 경로마다 별도 전달 코드를 두지 않아도 기존 창과 새 창이 동일한 목록을 본다.
- **잃은 것**: 조회마다 최대 10개 경로를 복사한다. 빌린 slice를 락 밖에 노출하지 않는다.
- **운영 비용 / 유지 부담**: DB 소유 캐시를 복제할 때는 공유 핸들이어야 한다. DB 저장 실패는 로그로 남고 메모리 결과는 모든 창에 동일하게 유지된다.

## Alternatives Considered

- **매 조회마다 DB 로드** — 초 단위 timestamp가 같은 기록의 즉시 순서를 잃으며, 기존 load는 중복 정리 쓰기도 하므로 읽기 전용 조회와 맞지 않는다.
- **창 생성 시 이전 창 캐시 복제** — 값 복제는 다음 기록부터 다시 갈라진다. 공유 핸들 전달도 창 생성·복원 경로마다 추가 연결이 필요해 DB 수명보다 경계가 넓다.
- **새 window 대상 인자** — 이미 하나인 영속 목록을 창별 공개 계약으로 바꾸므로 기존 의미와 맞지 않는다.

## Reconsideration Triggers

**원리적으로 안 붙는 것**

- 다른 프로세스가 같은 state.db를 수정하는 사용 사례가 필요해지면 공유 범위를 재검토한다. 별도 프로세스 기록 후 기존 인스턴스 조회를 비교해 외부 변경 감지 요구를 정한다.
- 최근 목록 조회의 경로 복사나 기록의 락 대기가 체감 지연으로 보고되면 실제 종류별 목록과 호출 빈도로 지연을 측정한다.
