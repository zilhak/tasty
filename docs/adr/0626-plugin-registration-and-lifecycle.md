# ADR-0626: 플러그인의 소유권과 실행 상태를 따로 관리한다

- **Status**: Accepted
- **Date**: 2026-09-24
- **Tags**: plugins, runtime
- **Group**: plugins

## Context

설치된 플러그인이 어떤 이름과 surface kind를 소유하는지는 실행 여부와 별개다.
실행 중인 프로세스만 보고 라우팅하면 비활성 플러그인의 요청을 모르는 이름으로 오인하거나,
한 요청 때문에 관계없는 플러그인까지 시작하게 된다.

플러그인 연결과 종료를 메인 스레드에서 기다리는 것도 문제였다.
느린 자식 하나 때문에 화면과 다른 IPC가 함께 멈췄다.
반대로 기다림을 전부 없애면 재시작 때 두 프로세스가 같은 포트와 파일을 사용할 수 있다.

## Decision

네임스페이스 소유권은 설치 매니페스트에서 만들고 PluginManager와 IPC가 같은 NamespaceTable을 참조한다.
부팅 때 공유 핸들을 한 번 전달하며 조회 중 호스트 콜백을 실행하지 않는다.
비활성화와 재시작은 소유권을 지우지 않고, 패키지가 없어질 때 제거한다.

번들 설치와 상태 정리는 부팅에 둔다. 실행은 각 기능의 시작 조건을 따른다.
허용된 namespace 호출은 그 소유자와 실제 매칭되는 활성 IPC hook extension만 준비한다.
headless의 kind 지정 생성도 활성 소유자 하나만 시작하고 hello 등록을 기다린다.
없는 이름, 비활성 소유자, 조회 요청을 전체 기동의 이유로 쓰지 않는다.
GUI 부팅과 attach 전체 기동은 각각의 기존 정책을 유지한다.

연결과 단건 종료의 대기는 전용 스레드가 처리한다.
연결 전 요청은 큐에 보관하고 기한은 연결 완료부터 계산한다.
새 프로세스는 옛 프로세스가 회수된 뒤에만 시작한다.
파일 제거·교체와 명시적 enable은 필요한 경우 기존 프로세스 회수를 기다린다.

namespace 응답 만료는 호출자에게 오류로 알린다. 선택적 hook의 시간 초과처럼 성공으로 계속할 수 없다.
반복 무응답은 재시작 사유이며 늦은 namespace 응답은 실패 계수를 지울 수 있다.
이미 끝난 요청의 늦은 응답으로 target·post-hook을 다시 실행하거나 두 번째 결과를 보내지 않는다.

비활성화·제거 때 surface kind는 철회로 표시한다.
열린 surface의 저장과 표시에는 기존 정의를 제공하고 새 생성과 목록에서는 제외한다.
새 hello가 같은 kind를 등록하면 철회를 해제한다.

## Consequences

요청과 관계없는 플러그인의 실행을 줄이고 열린 탭의 저장 정보도 보존한다.
실행 상태는 더 세분된다. 연결 전에도 running:true일 수 있으며 enable 성공이 연결 성공을 뜻하지 않는다.
회수 중에는 running:false와 not-running 오류가 잠깐 보일 수 있다.

headless kind 생성과 attach 전체 기동에는 동기 대기가 남는다.
명시적 파일 교체·enable도 회수 때문에 메인 스레드를 기다리게 할 수 있다.
기한 초과는 결과를 모른다는 뜻이며 플러그인이 이미 수행한 효과를 취소하지 않는다.
철회된 kind의 열린 surface는 남지만 플러그인을 다시 켜기 전까지 응답하지 않을 수 있다.

## Alternatives Considered

- 전체 플러그인을 요청마다 시작하면 무관한 listener와 시작 동작까지 실행된다.
- manifest만으로 kind를 등록하면 실제 hello와 다른 선언을 등록할 수 있다.
- 종료를 기다리지 않고 새 프로세스를 만들면 포트·실행 파일이 충돌한다.
- kind 정의를 삭제하거나 열린 탭을 닫으면 저장 내용 또는 사용자 배치가 손상된다.
- CLI 명령 목록을 IPC 허용 목록으로 쓰면 선언하지 않은 합법적 메서드를 막는다.

## Reconsideration Triggers

첫 kind 생성의 대기, 회수 중 오류, 연결 전 running 표시가 실제 사용을 방해하면 해당 경로를 측정한다.
여러 PluginManager를 한 프로세스에 두거나 완전한 IPC 메서드 목록을 선언하게 되면 조회와 시작 구조를 다시 본다.
정상 namespace 작업이 응답 기한을 넘으면 작업 접수와 결과 통지를 분리할 수 있는지 검토한다.
재시작 실패 뒤에도 남는 kind가 문제라면 자동 철회의 영향부터 확인한다.
