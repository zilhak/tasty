# ADR-0078: 종료 중 IPC 요청은 무시하지 않고 즉시 거절한다

- **Status**: Accepted
- **Date**: 2026-08-23
- **Tags**: shutdown, ipc, cli, error-handling, adr-0077

## Context

[ADR-0077](0077-shutdown-loading-screen.md) 이 종료를 프레임 구동 상태 머신으로
바꾸면서, 종료 가드가 `about_to_wait` 에서 조기 return 해 `process_ipc()` 를
막는다. 그 결과 종료 phase 동안 도착한 IPC 요청은 **아무도 읽지 않고 그대로
버려진다**. ADR-0077 은 이 동작을 "연결은 accept 되지만 응답이 없다" 로 서술했다.

리뷰에서 두 가지가 드러났다.

1. **무응답은 클라이언트 입장에서 hang 과 구분되지 않는다.** 우리 자신의 `tasty`
   CLI 를 포함한 클라이언트는 응답을 기다린다. 이전의 동기 종료 경로는 종료 중
   요청을 구조적으로 처리·응답했으므로, 프레임 구동으로 바꾸면서 **회귀**한
   것이다.
2. **CLI 는 그 상황에서 EOF 를 오독해 스핀했다.** `IpcConnection::send` 의 읽기
   루프가 `read_line` 의 반환값(읽은 바이트 수)을 보지 않고 "빈 줄이면 continue"
   로만 분기해, EOF(영원히 0 반환) 후 코어 하나를 100% 로 태우며 무한 스핀했다
   (커널 블록이 아닌 유저스페이스 스핀이라 겉보기 hang 과 구분도 어렵다). 실측
   재현: `%CPU 99.7`, `STAT RN`, `WCHAN -`.

두 번째는 종료와 무관한 독립 결함이다 — 호스트가 크래시/SIGKILL 로 죽어도 같은
증상이 난다.

## Decision

**종료 중에도 IPC 요청에 답한다 — 처리하지 않되 즉시 거절한다.** 상태 머신이 매
프레임(그리고 `event_loop.exit()` 직전 한 번 더) 큐를 drain 해, 핸들러를 태우지
않고 `-32000 "host is shutting down"` 오류로 회신한다. 상태를 건드리지 않으므로
"정리 중엔 외부 상태 변경이 없다" 는 ADR-0077 의 계약은 그대로다.

이를 위해 종료 가드는 `event_loop.exit()` **이후까지** 유지된다. `finish_shutdown`
은 `App.shutdown` 을 비우지 않고 phase 를 `Exited` 로 옮긴다 — winit 은 `exit()`
즉시 루프를 끊지 않고 콜백을 한 번 더 돌리며, 그 패스에서 가드가 풀려 있으면
**이미 정리가 끝난 상태로** steady-state 파이프라인이 돈다. 재진입 여부 자체가
레이스라 재현은 간헐적이다(Linux/X11 실측 약 50%) — 잡히는 회차가 있다는 것으로
충분하고, 확률이 아니라 가능성이 결함이다.

CLI 측은 `read_line` 이 0 을 반환하면 즉시 "상대가 응답 없이 연결을 닫았다" 로
bail 한다. 읽기 타임아웃은 걸지 않는다 — 프로토콜에 의도적으로 무한 대기하는
호출(`agent task-await --timeout-ms 0`, 사용자 응답을 기다리는 approval 등)이 있어
한 값으로 자르면 정상 동작을 끊는다.

본 ADR 은 ADR-0077 의 "종료 중 IPC 는 응답이 없다" 절을 **개정**한다. 나머지
결정(프레임 구동 상태 머신, 로딩 화면, 창 유무 분기)은 그대로다.

## Consequences

- **얻은 것**: 종료 중 요청이 즉시 명시적 오류로 끝난다. 종료 가드가 프로세스가
  실제로 끝날 때까지 유지되어, 정리 완료 후 파이프라인이 한 패스 더 도는 창이
  사라진다. CLI 는 상대가 죽는 모든 경우(종료·크래시·SIGKILL)에 스핀 대신 즉시
  에러로 끝난다.
- **잃은 것**: 종료가 시작된 뒤의 요청은 성공할 수 없다. 이전 동기 경로에서는 종료
  cascade 중간에 처리될 여지가 있었으나, 그것은 "정리 중 상태를 건드린다" 는 쪽에
  더 가까운 동작이라 되돌릴 대상이 아니다.
- **운영 비용 / 유지 부담**: `reject_pending_ipc` 는 핸들러를 타지 않는 얇은 경로라
  종료 단계가 늘어도 손댈 일이 없다. 다만 `finish_shutdown` 뒤에도 가드가 살아
  있다는 전제를 깨면(예: 어딘가에서 `App.shutdown` 을 비우면) 두 문제가 한꺼번에
  되돌아온다.

## Alternatives Considered

- **A: 종료 중에도 `process_ipc()` 를 계속 돌린다** — 무응답 문제는 사라지지만
  ADR-0077 의 계약("정리 중 외부 상태 변경 없음")을 정면으로 깬다. 이미 close
  cascade 로 정리한 surface 를 다시 만들거나 여는 요청이 그대로 실행된다.
- **B: 그냥 연결을 끊는다(응답 없이 close)** — 클라이언트는 EOF 를 보므로 hang 은
  면하지만 이유를 알 수 없다. 오류 코드/메시지를 주는 편이 진단 가능하다.
- **C: CLI 에 읽기 타임아웃을 건다** — 무한 대기 호출이 프로토콜에 존재해 정상
  동작을 끊는다. 죽은 상대 감지는 EOF 판정으로 충분하다.

## Reconsideration Triggers

다음 중 하나가 충족되면 본 ADR 을 재검토한다.

- 종료 중에도 반드시 성공해야 하는 IPC 요청이 생기면(예: 종료 자체를 취소하는
  메서드) — 지금은 종료가 취소 불가라는 전제 위에 서 있다.
- winit 이 `exit()` 이후 콜백을 돌리지 않는다는 보장을 전 백엔드에서 제공하면 —
  `Exited` phase 를 유지할 이유가 약해진다.
- 프로토콜에서 무한 대기 호출이 사라지면 — CLI 읽기 타임아웃을 방어선으로 다시
  검토할 수 있다.
