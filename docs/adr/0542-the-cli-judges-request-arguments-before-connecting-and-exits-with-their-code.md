# ADR-0542: CLI 는 요청 인자를 연결보다 먼저 판정하고, 그 오류의 종료 코드로 끝난다

- **Status**: Accepted
- **Date**: 2026-09-23
- **Tags**: cli, exit-code, argument-validation, error-message, compatibility, adr-0512

## Context

단발 RPC 명령의 진입점(`crates/tasty-cli/src/run.rs` 의 `run_client_inner`)은 포트 파일을 읽고
연결한 **뒤에** 명령을 요청으로 매핑했다(`command_to_request`). 매핑은 서버 없이 끝나는 검증을
품는다 — 깨진 `--sequence` JSON · 없는 `--cwd` 폴더 등이 실패하면 그 자리에서 원인을 stderr 에
내고 `process::exit` 한다. 그래서 실행 중인 인스턴스가 없으면 그 검증에 닿기 전에
`No running tasty instance found …` 로 끝났고, 사용자는 자기 인자의 잘못을 볼 수 없었다.

순서를 바꾸면 **종료 코드**가 따라 움직인다. 인스턴스가 없을 때 종전에는 인자와 무관하게 늘 1
(인스턴스 없음)이었다. 매핑이 먼저면 그 인자 오류 자리가 부르는 `process::exit` 의 값이 나온다.
구현자의 정적 계수(매핑 트리 `request.rs` + `request/**` 17 파일, `cfg(test)` 제외)로는 exit 자리
38 곳 중 32 곳이 1, 6 곳(`approval` 2 · `telemetry` 4)이 2 다. 종료 코드는 스크립트가 분기하는
외부 값이다.

## Decision

**인자 → 요청 매핑(서버 없이 끝나는 검증)은 연결보다 먼저 하고, 거기서 실패하면 종료 코드는 그
인자 오류 자리의 값이다.** 연결 뒤에는 서버의 값이 있어야 하는 확인(계약 확인 `contract::ensure`)만
남는다.

- 이것은 새 종료 코드를 고른 것이 아니다. 인자 오류 자리들의 값(대부분 1, 일부 2)은 이미 있었고,
  인스턴스가 떠 있을 때는 종전에도 그대로 나갔다. 바뀐 것은 **인스턴스가 없을 때도 그 값이
  드러난다**는 것이다 — "값이 바뀐 것" 이 아니라 "가려져 있던 값이 드러난 것" 이다.
- 인스턴스가 떠 있을 때의 출력 · 종료 코드는 그대로이고, 보내는 요청도 `--ttl` 의 `expires_at`
  하나를 빼면 그대로다 — 그 값은 매핑 시점의 시계(`ttl_to_expires_at`)로 정해지고 매핑이 이제
  연결 앞이라, 기준 시각이 연결 시간만큼 앞당겨진다(아래 Consequences). 그 밖에 달라진 것은 잘못된
  인자가 더는 아무것도 안 보낸 빈 연결을 열지 않는다는 것이다.
- plugin 동적 명령(`try_run_plugin_cli`)은 이미 매핑이 연결 앞이었다 — 이 결정으로 두 경로가
  같은 순서가 된다.

## Consequences

- **얻은 것**: 인자 오류가 인스턴스 유무와 무관하게 같은 원인 · 같은 종료 코드로 끝난다. 사용자는
  Tasty 를 띄우기 전에 자기 인자의 잘못을 고칠 수 있다.
- **잃은 것**: 인스턴스가 없을 때 `approval` · `telemetry` 의 일부 인자 오류가 1 대신 2 로
  끝난다. **영향 범위는 그 조합(인스턴스 없음 + 그 인자 오류)을 종료 코드 1 로 분기하던
  스크립트뿐이다.** 비0 인지로만 보는 스크립트, 인스턴스가 떠 있는 호출은 영향이 없다.
  부수 효과로 `preset save --file -` 는 인스턴스가 없어도 stdin 을 먼저 읽고(파일 경로를 준 정상
  경로는 그대로), `memory … --ttl` 의 `expires_at` 기준 시각이 연결 시간만큼 앞당겨진다.
- **운영 비용 / 유지 부담**: 매핑(`request/`)은 서버 · 포트 파일 · 연결에 닿지 않는 순수 변환으로
  남아야 한다. 매핑 안에서 서버 값을 조회하게 되면 이 순서가 그 자리에서 깨진다.

## Alternatives Considered

- **연결 뒤 검증을 유지한다** — 종료 코드는 인스턴스가 없을 때 늘 1 로 안정되지만, 사용자에게
  원인 대신 "인스턴스가 없다" 를 보여 주는 것이 결함 그 자체다. 게다가 그 1 은 인자에 대한 판정이
  아니라 "판정하지 못했다" 는 값이라, 그 값에 기대는 스크립트는 인스턴스를 띄우는 순간 같은 인자로
  다른 코드를 받는다. 지킬 호환이 인스턴스 유무에 따라 이미 갈라져 있었다. 기각.
- **매핑은 먼저 하되, 인스턴스가 없으면 인자 오류도 1 로 맞춘다** — 종전 값을 흉내 내려고 인자
  오류 자리마다 인스턴스 유무를 물어야 하고, 같은 인자 오류가 인스턴스 유무에 따라 다른 코드를
  내는 상태를 일부러 만든다. 기각.

## Reconsideration Triggers

**채널이 붙는 것** — 판정 시점에 레포가 읽을 수 있는 사실이다.

- 매핑(`request/`)이 서버 값을 조회해야 하는 검증을 갖게 된다(그 검증은 연결 뒤로 가야 하고, 이
  순서를 둘로 나눌지 다시 정한다). 재는 자리: `tests/cli_maps_args_before_connecting.rs`.
- CLI 종료 코드 체계를 한 표로 정하는 결정이 생긴다(인자 오류 1 · 2 의 구분 자체가 다시 열린다).

**원리적으로 안 붙는 것** — 사람이 관측해야 한다. 재는 법을 함께 적는다.

- 인스턴스 없음 + 인자 오류를 종료 코드 1 로 분기하던 외부 스크립트가 깨졌다는 보고가 온다.
  재는 법: 이슈 · 사용자 보고.

## 측정하지 않은 것

- 위 exit 자리 계수(38 곳 · 1:32 · 2:6)는 **구현자의 정적 계수이고, 이 ADR 을 쓰면서 재계수하지
  않았다.** 매핑 트리가 바뀌면 그 값도 바뀐다 — 이 ADR 이 정하는 것은 순서와 "그 자리의 값이
  나간다" 는 규칙이지 그 수가 아니다. 재는 법: 매핑 트리에서 `process::exit` 호출과 그 인자를
  `cfg(test)` 를 빼고 센다.
- 종료 코드 2 가 실제로 나가는 것은 통합 시험이 아니라 정적 계수로만 확인됐다.
