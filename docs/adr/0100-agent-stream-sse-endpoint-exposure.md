# ADR-0100: agent-stream 은 자기 프로세스에서 SSE 서버를 열고, loopback 기본 · 명시 포트 · 광역 bind 시 토큰 필수로 노출을 좁힌다

- **Status**: Accepted
- **Date**: 2026-09-03
- **Tags**: agent-stream, plugin, sse, http, tiny-http, exposure, authentication, backpressure, resume, adr-0046, adr-0048, adr-0093

## Context

[ADR-0093](0093-agent-response-relay-reads-transcript-jsonl.md) 이 정한 수집 파이프라인은 에이전트 세션 transcript 를 정규화해 plugin 메모리 버퍼에 쌓는다. 그 이벤트를 외부 소비자(FE 서버)가 받아갈 채널이 없었다 — `agent_stream.poll` 은 커서 기반 폴링이라 상시 중계에 맞지 않는다.

세 가지가 이미 정해져 있어 선택지를 좁혔다.

1. **인바운드가 이미 소비자 → tasty 방향이다**(웹훅). 소비자가 tasty 에 도달 가능하다는 것이 배치 전제이므로, 아웃바운드도 같은 방향이면 방화벽/NAT 요구가 새로 생기지 않는다.
2. **본체 웹훅 리스너를 재사용할 수 없다.** [ADR-0046](0046-webhook-owner-trust-one-way-ack.md) 의 불변식 2(단방향 ACK)에 의해 `build_ack(status)` 가 실행 결과를 인자로 받지 않는다 — 응답에 내부 데이터가 실릴 코드 경로가 구조적으로 없다. 스트리밍 응답은 그 불변식을 깨야만 가능하고, 그것은 이 작업의 범위가 아니다.
3. **SDK 는 async 를 지원하지 않는다.** 모든 콜백이 동기이고, dispatch 스레드가 막히면 healthcheck(15s ping / 60s 무응답 → 강제 재시작)가 깨진다.

그리고 정책 공백이 하나 있었다. `docs/dev-guide/plugin-sensitive-data.md` 는 민감 데이터의 **저장**만 다루고 **외부 전송**은 다루지 않는데, 이 채널로 나가는 것은 대화 전문(코드·경로·에러 메시지, 경우에 따라 자격증명 문자열)이다.

## Decision

**agent-stream plugin 이 자기 프로세스에서 SSE 서버를 연다**(`GET /events`, `text/event-stream`). HTTP 레이어는 본체 웹훅과 같은 `tiny_http`(blocking, [ADR-0048](0048-webhook-http-tiny-http-blocking.md))이고, accept 스레드 1 개 + 연결당 스레드 1 개로 돈다. 본체 코드는 변경하지 않는다.

노출 정책으로 다섯을 못박는다.

1. **기본 비활성.** 서버는 `agent_stream.serve` 를 명시적으로 부를 때만 뜬다. 그리고 방출 대상은 이미 `watch` 로 등록된 surface 뿐이다 — 켜는 행위와 대상 지정이 각각 명시적이다.
2. **포트는 필수, 자동 폴백 없음.** 본체 웹훅 리스너의 "설정값 only" 정책과 같다. 임의 포트로 조용히 옮겨 뜨면 소비자가 붙을 고정 주소가 없어지고, 재시작마다 주소가 바뀐다. bind 실패는 삼키지 않고 호출자에게 그대로 올린다.
3. **bind 기본값은 loopback, 그보다 넓은 주소는 토큰 없이는 거부한다.** 대화 전문이 나가는 채널이라, "실수로 `0.0.0.0` 에 무인증으로 열림" 조합을 설정 검증 단계에서 구조적으로 막는다. 토큰은 `Authorization: Bearer <t>` 또는 `?token=<t>` 로 제시하고 **상수시간 비교**한다(본체 `src/webhook/auth.rs` 와 같은 규칙). 거부 응답은 상태코드만 있는 빈 바디다.
4. **`thinking` 은 구독 파라미터로만 켠다**(`?thinking=1`). 사고 블록은 응답 텍스트와 민감도가 다르므로 기본은 제외 — 노출을 최소로 시작하고 소비자가 명시적으로 넓힌다.
5. **재개는 `Last-Event-ID` 로 지원하되 버퍼는 수집 버퍼(4096)를 그대로 쓴다.** SSE 의 `id` 는 수집 파이프라인의 전역 단조 증가 `seq` 이고, 그 값이 곧 `poll` 의 `after_seq` 커서다. 별도 재개 버퍼를 두지 않는 이유는 두 버퍼가 서로 다른 상한으로 잘리면 "`poll` 로는 보이는데 SSE 로는 안 보이는" 불일치가 생기기 때문이다. **재개 커서를 주지 않은 구독은 재전송 없이 지금부터** 흘린다. 커서가 버퍼 밖으로 밀려나 재전송이 불가능한 구간이 있으면 재전송에 앞서 **`gap` 이벤트로 그 구간(`from`/`to`)을 먼저 알린다** — 남은 것만 조용히 이어붙이면 소비자는 자기가 무엇을 놓쳤는지도 모르고, 그것은 ADR-0093 의 "침묵하는 누락보다 중복" 과 어긋난다. `gap` 프레임의 `id` 는 소비자가 보낸 커서 그대로라 커서를 전진시키지 않는다.

백압은 구독자별 bounded 큐(256)로 처리한다. 생산자(tail 스레드)는 `try_send` 만 쓰고 **절대 블로킹하지 않는다** — 느린 구독자가 수집 자체를 멈추면 안 되기 때문이다. 가득 차면 버리고 카운터를 올리되, **연속 64 회 버려진 구독은 허브에서 끊는다.** 끊는 것은 허브의 큐 등록뿐이고, 소켓은 진행 중인 write 가 끝나거나 실패할 때 닫힌다 — TCP 송신 버퍼까지 채운 소비자에게는 커널이 그 write 를 포기할 때까지 스레드 1 개가 남을 수 있다. 버리기만 하면 소비자는 "연결은 살아 있는데 구멍 난 스트림" 을 받아 무엇을 놓쳤는지 알 수 없다. SSE 는 끊김이 정상 경로이므로(plugin 강제 재시작만으로도 끊긴다) 끊어서 재연결 + `Last-Event-ID` 재개로 복구를 드러낸다.

끊김이 정상 경로라는 전제 때문에 **`serve` 설정(bind/port/token)은 watch 스냅샷과 함께 영속화하고, 강제 재시작 후 자동으로 다시 연다.** 되살아나지 않으면 watch 는 복구됐는데 붙을 곳이 없어 "재구독으로 복구한다" 는 전제 자체가 무너진다.

## Consequences

- **얻은 것**: 소비자는 폴링 없이 상시 구독을 유지하고, 끊겨도 `Last-Event-ID` 로 이어붙인다. 본체 코드 변경이 0 이며 ADR-0046 의 단방향 불변식도 건드리지 않는다. 노출 범위(무엇이·어디로·누구에게)가 설정 검증과 구독 파라미터 두 지점에 모여 있어 감사 가능하다.
- **잃은 것**: plugin 프로세스가 별도 TCP 포트를 연다 — 호스트 권한 게이트는 host IPC 호출만 막으므로(`plugin-development` §10) 이 포트는 tasty 가 강제할 수 있는 대상이 아니고, 위 정책은 **이 plugin 이 스스로 지키는 규약**이다. 토큰은 평문 공유 비밀이며 스냅샷 파일(`<data_dir>/watches.json`)에 그대로 남는다 — **본체 웹훅 토큰과 같은 신뢰 수준·같은 저장 방식**(설정 파일 평문)이고, unix 에서는 그 파일을 `0600` 으로 만들어 같은 머신의 다른 사용자에게 열리지 않게 한다(Windows 는 파일 ACL 기본값을 따른다). TLS 는 종단하지 않는다(ADR-0048 과 같이 프록시 위임).
- **잃은 것(HTTP 레이어)**: `tiny_http` 는 요청 헤더 누적에 상한이 없고 읽기 타임아웃도 걸지 않는다. 광역 bind 에서는 **연결당 메모리·스레드 상한이 없다** — 헤더를 끝내지 않는 연결 하나가 스레드 하나와 무한정 늘어나는 버퍼를 잡는다. 기본값이 loopback 인 것이 현재의 완화책이고, 광역 노출이 필요하면 **앞단에 리버스 프록시를 두는 것을 권장한다**(상한·타임아웃·TLS 를 거기서 건다).
- **운영 비용 / 유지 부담**: 구독자가 없으면 이벤트 직렬화조차 하지 않아 비용이 0 이다. 구독자당 스레드 1 개 + 큐 256 슬롯. keep-alive 는 15s 유휴마다 주석 한 줄.

## Alternatives Considered

- **A: plugin 이 이벤트마다 소비자에게 POST 로 민다(아웃바운드 push)** — tasty 가 어디 있든 동작한다는 장점이 있으나, 이 프로젝트의 배치 전제(소비자가 이미 tasty 에 도달 가능)에서는 이점이 없다. 대신 순서 보장·재시도·백오프를 직접 다뤄야 하고, 소비자 주소가 죽어 있는 동안의 큐 관리까지 plugin 이 진다. 거부.
- **B: 본체 웹훅 리스너를 확장해 스트리밍 응답을 만든다** — ADR-0046 불변식 2 를 깨야 한다. 인바운드 리스너의 신뢰 모델(응답에 내부 데이터가 실리지 않는다)이 그 불변식으로 성립하므로, 아웃바운드를 위해 그것을 여는 것은 비용이 훨씬 크다. 거부.
- **C: WebSocket** — 양방향이 필요 없다. 인바운드는 이미 웹훅이 담당하므로 SSE 의 단방향이 요구에 정확히 맞고, 재개 시맨틱(`Last-Event-ID`)이 프로토콜에 내장돼 있다. 프레이밍·핸드셰이크 부담만 늘어 거부.
- **D: bind 기본값을 `0.0.0.0` 으로 두고 문서로 경고한다** — 원격 FE 서버 구성이 한 단계 줄지만, 실수 한 번의 결과가 "대화 전문 공개" 다. 넓히는 것을 명시적 행위(토큰 동반)로 만드는 쪽을 택했다.
- **E: 재개를 지원하지 않는다(라이브 전용)** — 구현이 가장 단순하나, 끊김이 정상 경로인 설계에서 재개가 없으면 끊길 때마다 그 구간이 조용히 사라진다. ADR-0093 이 "침묵하는 누락보다 중복" 을 택한 것과 정면으로 어긋나 거부.
- **F: 무인증으로만 두고 접근 제어를 방화벽에 위임한다** — loopback 전용이면 성립하지만, 원격 FE 서버가 요구사항에 있으므로 그 경우를 무방비로 남긴다. 거부.
- **G: 토큰을 영속하지 않고 bind/port 만 남긴다** — 평문 저장을 피하지만, 강제 재시작 후 엔드포인트가 무인증으로 뜨거나(더 나쁨) 아예 못 뜬다. 자동 복구가 이 설계의 전제(위 Decision 마지막 문단)라 거부.
- **H: OS 키링(keyring/Keychain/DPAPI)에 토큰을 넣는다** — 저장 강도는 올라가지만 plugin 이 헤드리스로 도는 환경(SSH·CI·컨테이너)에서 키링이 잠겨 있거나 없어 자동 복구가 불안정해진다. 본체 웹훅 토큰도 같은 이유로 평문 설정에 있어, 이 채널만 다른 저장 모델을 쓰면 운영자가 두 모델을 관리해야 한다. 거부.

## Reconsideration Triggers

다음 중 하나가 충족되면 본 ADR 을 재검토한다.

- **plugin sandbox 가 도입된다**(`docs/dev-guide/plugin-sensitive-data.md` 가 예고). plugin 이 임의 포트를 여는 것 자체를 호스트가 통제하게 되면, "plugin 이 스스로 지키는 규약" 이라는 이 결정의 전제가 바뀐다 — 정책을 호스트 권한 게이트로 옮길지 재검토한다.
- **구독자가 소수(FE 서버 한둘)라는 전제가 깨진다.** 연결당 스레드 모델이 부담이 되는 규모가 되면 ADR-0048 의 재검토 트리거("롱-커넥션 트래픽")와 함께 async 스택을 재평가한다.
- **평문 공유 토큰이 부족해진다**(다중 소비자별 권한 분리, 회수 요구 등) — 토큰 발급/폐기 모델을 재설계한다.
- **이 plugin 이 배포 패키징 대상이 된다**(`bundle = false` 해제). "tasty 를 설치하면 딸려오는 것이 대화 전문을 네트워크로 내보낼 수 있다" 는 의미가 되므로, 기본 비활성만으로 충분한지 다시 본다.
- **`tiny_http` 를 교체하거나 상한을 도입한다.** 헤더 상한·읽기 타임아웃·연결 수 상한이 필요해지면(광역 bind 가 일상 구성이 되거나, 앞단 프록시 없이 노출하는 배치가 나오면) HTTP 레이어 선택을 ADR-0048 과 함께 다시 본다.
- **전송 대상이 transcript 이벤트를 넘어선다**(첨부 파일 내용, 툴 결과 원문 등) — 노출 범위가 이 결정이 전제한 것과 달라진다.
