# ADR-0085: IPC 관측 로그는 무한 보존하지 않는다 — 상한을 한 곳에서 관리하고, audit 은 deny 만 남긴다

- **Status**: Accepted
- **Date**: 2026-08-25
- **Tags**: audit, telemetry, memory-db, retention, observability, cpu

## Context

macOS 보조기에서 release 인스턴스가 CPU 57~101% 를 상시 점유해 추적하다 `memory.db`
비대화를 발견했다. 연속 18시간 실행 시점의 실측이다.

| 항목 | 행 수 | 유입 속도 |
|---|---|---|
| `tasty.audit.*` | 371,936 | 초당 약 14건 |
| `tasty.telemetry.event.*` | 308,603 | 시간당 28,075건 |
| `tasty.telemetry.anomaly.*` | 21,102 | 시간당 약 1,170건 |

파일 271MB, `memory` 테이블 680,850행. 세 로그 모두 IPC 호출량에 정비례한다 —
에이전트 플러그인이 800ms 주기로 생존 확인 + 텍스트 읽기를 쌍으로 호출하는 정상
동작이 유입의 대부분이다(상위 4개 폴링 method 가 audit 의 85%). 유입 자체가 결함이
아니라, **그 정상 호출 하나하나가 영구 레코드를 남긴다**는 쪽이 결함이다. 매 IPC 가
SQLite 트랜잭션 2건을 만들고, 그 커밋이 비대한 WAL 에 대한 체크포인트를 상시 유발해
CPU 로 이어졌다.

세 로그의 보존 상태는 각각 다르게 망가져 있었다.

- **audit**: retention 이 둘인데 서로의 사각을 메우지 못했다. 런타임 경로는 **시간**
  기준 30일이라 18시간 실행에서는 매시간 0건을 지웠고, 실효가 있는 **개수** 기준
  5만 건은 부팅 때만 돌았다. 두 값은 720배 차이가 났고, 30일 보존은 모듈 자신이
  적어둔 실측(일 ~100MB)과도 모순이었다 — 30일이면 3GB 로 `memory.db` 의 1GB
  regular quota 를 애초에 넘는다. 게다가 18시간 동안 **deny 는 0건**이었다. 즉
  356,184건이 전부 allow 였다.
- **telemetry raw event**: TTL 도 런타임 정리도 없고 부팅 시 2만 건 상한만 있었다.
  현재 행 수가 그 상한의 15배였다. 여기에 audit 과 같은 시간 상한(50시간)을 그대로
  복사하면 1,403,750건이 되어 **지금보다 나빠진다**.
- **telemetry anomaly**: TTL 도 없고 부팅 prune 목록에도 없었다. **유일하게 회수
  수단이 전혀 없는 로그**로, 재시작해도 영원히 남았다.

한 가지 사실이 처방을 제약한다. 문서는 "호스트가 주기 rollup task 를 돈다" 고
적었지만 **그런 코드는 없다**(`tasty.telemetry.bucket.*` 0건, `bucket_key` 호출자
0건). 실제 설계는 "raw event 가 유일한 SoT 이고 조회 시점에 즉석 집계" 다. 따라서
raw 를 지우면 그만큼 **조회 가능 기간이 그대로 사라진다.**

## Decision

**관측 로그는 무한 보존 대상이 아니다.** 세 로그의 보존 정책을 한 테이블
(`adapters::ipc::log_retention`)에 모으고, 부팅 경로와 런타임 append 경로가 같은
상수·같은 구현을 부르게 한다. 각 로그는 개수 상한과 시간 상한을 함께 걸되, 유입
속도가 시간 상한을 무의미하게 만드는 로그는 개수 상한만 건다.

| 로그 | 개수 상한 | 시간 상한 |
|---|---|---|
| audit | 50,000 | 50시간 |
| telemetry raw event | 20,000 | 없음 |
| telemetry anomaly | 5,000 | 50시간 |

그 위에 두 가지를 함께 결정한다.

1. **audit 은 deny 만 기록한다.** allow 는 method 와 무관하게 저장하지 않는다.
   폴링 method 제외목록으로 85% 만 거르는 안보다 전면 차단이 단순하고 코드가 적다.
2. **raw event 롤업은 신설하지 않는다.** 문서가 서술한 rollup task 는 존재하지
   않으며, 그 부재를 정식 설계로 인정하고 문서를 코드에 맞춘다. 대신 개수 상한을
   런타임에도 집행해 출혈을 막는다. 그 결과 telemetry 조회 가능 범위는 "최근 2만
   이벤트" 로 고정된다.

## Consequences

- **얻은 것**:
  - `memory.db` 행 수가 유입 속도와 무관하게 상한된다(세 로그 합계 75,000행).
    집행이 최대 1시간에 1회이므로 정상 상태 최대치는 정확히는 "상한 + 1시간치
    유입" 이고, 집행마다 상한으로 되돌아간다. 가장 큰 유입원인 audit allow 는
    아예 생기지 않는다.
  - 매 IPC 의 SQLite 트랜잭션이 2건에서 1건으로 줄어, WAL 체크포인트 압력이 절반이
    된다.
  - anomaly 가 회수 경로를 얻는다. 정책 테이블에 빠진 로그가 있으면 테스트가
    실패하므로 같은 누락이 반복되지 않는다.
  - 상한이 한 곳에 있어 "런타임과 부팅이 다른 값을 쓰는" 재발이 구조적으로 막힌다.
- **잃은 것**:
  - **agent 행동 감사가 무력화된다.** audit 이 명시한 목적 3개 중 하나가 사라진다.
    deny 가 평시 0건이므로 audit 테이블은 사실상 빈 테이블이 되고,
    `plugin.audit_query` 는 평시에 빈 결과만 반환하는 API 가 된다(API 자체는 deny
    조회 용도로 유효하므로 유지한다).
  - **사고 *후에* "이 에이전트가 무엇을 호출했나" 를 되짚을 수단이 없다.** 감사
    로그는 사고 후에 필요해지는데 그때는 남아 있지 않다. 승인된 권한으로 실제 무엇을
    했는지도 여기 포함된다 — 승인 이력 자체(`tasty.approval.*`)는 별도 영속이라
    남지만, 그 권한의 *사용*은 남지 않는다.
  - **telemetry 조회 기간이 데이터 양에 종속된다.** 조용한 인스턴스에서는 2만
    이벤트가 수일치지만, 폴링이 도는 인스턴스에서는 40분치다. "지난주 토큰 사용량"
    같은 질의는 성립하지 않는다.
  - anomaly 는 50시간·5,000건을 넘으면 사라진다 — 읽지 않고 방치하면 없어진다.
- **운영 비용 / 유지 부담**:
  - 새 관측 로그를 추가할 때 정책 테이블에 등록해야 한다(누락은 테스트가 잡는다).
  - 정리는 append 경로에 얹혀 최대 1시간에 1회 돈다. 유입이 전혀 없는 인스턴스는
    다음 부팅 때 정리된다.
  - `MemoryStorage` port 가 prune 2종만큼 넓어졌다.

## Alternatives Considered

- **A: 폴링 method 제외목록으로 allow 를 85% 만 줄인다** — 감사 기능을 보존하면서
  유입을 줄이는 안. 안 고른 이유: 목록을 유지해야 하고(새 폴링 method 가 생기면
  다시 샌다), 남는 15% 도 여전히 초당 2건이다. 전면 차단이 단순하고 코드가 적다는
  이유로 사용자가 전면 차단을 선택했다.
- **B: 주기 rollup task 를 신설하고 raw 는 짧은 TTL 로 자른다** — 문서가 이미
  서술한 설계에 코드를 맞추는 안. 장기 조회를 유지하면서 저장량이 상수로 떨어진다.
  안 고른 이유: 범위가 크다(`timeseries`/`summary`/`top`/`session_summary` 의 집계
  의미를 bucket 기준으로 재정의해야 한다). CPU 문제 해결이 목적이라면 개수 상한만으로
  충분하고, 롤업은 telemetry 를 장기 조회에 실제로 쓰기 시작할 때 필요해진다.
  **폐기가 아니라 분리**다.
- **C: 세 로그에 같은 시간 상한(50시간)을 적용한다** — 정책이 가장 단순하다.
  안 고른 이유: raw event 에는 1,403,750건이 되어 현재보다 4.5배 나빠진다. 유입
  속도가 로그마다 두 자릿수 차이 나므로 같은 시간 상한이 같은 의미를 갖지 않는다.
- **D: 상한 없이 quota 도달 시 거부에 맡긴다** — 안 고른 이유: 1GB 도달 시 memory
  쓰기가 실패하는데, 그 실패가 감사 로그가 아니라 사용자 데이터 쪽에서 터진다.
  관측 로그가 사용자 데이터의 quota 를 잡아먹는 구조 자체가 잘못이다.

## Reconsideration Triggers

다음 중 하나가 충족되면 본 ADR 을 재검토한다.

- **보안 사고가 실제로 발생해 "이 에이전트가 무엇을 호출했나" 가 필요해진다** —
  allow 미기록의 대가가 처음으로 현실화되는 지점이다. 그때는 전면 차단 대신 대안 A
  (폴링 제외목록) 또는 링버퍼 형태의 단기 allow 보존을 재검토한다.
- **telemetry 를 장기 조회에 쓰기 시작한다**(비용 리포트·주간 추세 등) — 개수 상한이
  곧 조회 범위이므로 대안 B(롤업 신설)가 필요해진다.
- **anomaly 에 자동 대응이 붙는다** — 지금은 소비처가 조회 하나뿐이라 보관 가치가
  낮다고 판단했다. 자동 대응이 생기면 보존 요건이 달라진다.
- **폴링 유입이 사라진다**(에이전트 플러그인이 이벤트 구독으로 전환하는 등) —
  전면 차단의 전제였던 유입 규모가 없어지므로 allow 기록을 되살릴 여지가 생긴다.
- **`memory.db` 에 로그 전용 테이블/파일이 분리된다** — 관측 로그가 사용자 데이터의
  quota 를 잡아먹지 않게 되면 상한을 크게 완화할 수 있다.
