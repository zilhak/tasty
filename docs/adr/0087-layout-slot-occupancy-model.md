# ADR-0087: 레이아웃은 창마다 슬롯 파일 하나를 쓰고, 슬롯 점유는 살아있는 engine 에서 파생시킨다

- **Status**: Accepted
- **Date**: 2026-08-25
- **Tags**: layout-persistence, multi-window, slot, occupancy, storage, boot, scrollback, gc

## Context

tasty 는 창 하나가 `CoreState`(engine) 하나를 갖는다 — 워크스페이스 목록·페인 트리·탭·서피스가 전부 창별로 독립이다. 그런데 레이아웃 영속화는 프로세스당 파일 하나(`~/.tasty/layout.json`)를 전제로 만들어져 있었다. 구조는 N 개인데 저장소가 1 개였다.

그 불일치가 두 가지 결함으로 나타났다.

- **창마다 같은 목록이 복제된다.** 새 창을 열면 그 engine 이 같은 파일을 읽어 복원하므로, 두 창이 동일한 워크스페이스 집합을 갖는다. 사용자가 창 A 에서 워크스페이스를 지우고 창 B 에서 살아 있는 사본을 보는 상태가 정상 동작이었다.
- **flush 가 서로를 덮어쓴다.** 저장은 dirty + 500ms 디바운스와 종료 시 일괄 flush 로 도는데, 두 engine 이 같은 경로에 쓰므로 last-writer-wins 다. 창 A 에서 한 작업이 창 B 의 flush 한 번에 사라진다. 종료 시퀀스는 main + parked engine 을 모두 flush 하므로 **정상 종료가 오히려 확실하게 유실을 만들었다.**

이 동작이 의도인지 미구현인지 판별할 근거가 코드에도 문서에도 없었다. `docs/architecture/multi-window.md` 는 창↔engine 관계를 기술하면서 레이아웃 영속화를 아예 언급하지 않았고, 기능 문서는 단일 파일 전제로 쓰여 있었다.

제약이 하나 있다. tasty 는 이미 "점유(occupancy)" 라는 말을 surface/workspace 를 어떤 주체가 잡는다는 뜻으로 쓴다(soft/hard 계층, [ADR-0040](0040-occupancy-soft-hard-tiers-agent-occupant.md)). 레이아웃 슬롯 점유는 **대상도 수명도 다른 축**이다 — 잡는 것이 저장소 슬롯이고, 주체는 사용자나 에이전트가 아니라 engine 이며, 해제 규칙도 별개다. 같은 단어를 쓰되 별개 모델로 구분해 둘 필요가 있었다.

## Decision

**슬롯 = 레이아웃 1 벌 = 파일 1 개다.** 저장 위치는 `~/.tasty/layouts/NN.json` 이고, 파일 하나가 engine 하나의 전체 상태(워크스페이스 목록 · 활성 워크스페이스 · 카테고리)를 담는다. 슬롯 목록과 순서는 파일명의 숫자에서 전부 파생되며 별도 인덱스 파일을 두지 않는다. write 는 `NN.json.tmp` 에 쓴 뒤 rename 하는 원자적 교체다.

**창을 열면 점유되지 않은 가장 낮은 번호의 기존 슬롯을 잡고, 기존 슬롯이 전부 점유돼 있으면 새 번호를 발급한다**(`max(파일 슬롯 ∪ 점유 슬롯) + 1`). 번호 공백은 채우지 않는다 — 파일이 `02`·`03` 뿐이면 답은 `1` 이 아니라 `2` 다. 저장된 레이아웃을 건너뛰고 빈 창을 띄우지 않기 위해서다.

**점유는 살아있는 engine 의 `layout_slot` 에서 파생되는 휘발성 값이다.** 디스크에 기록하지 않고 별도 레지스트리도 두지 않는다. 점유 집합은 그때그때 살아있는 engine 들을 훑어 만든다. engine 이 drop 되면 그 번호는 그 순간 자동으로 free 가 되고, 프로세스가 죽으면 전부 free 로 돌아온다.

**부팅 시 창은 1 개다.** 저장된 슬롯이 몇 개든 첫 창이 가장 낮은 슬롯 하나만 복원하고, 나머지는 창을 더 열 때 순서대로 되살아난다.

창이 닫힐 때 슬롯 파일을 어떻게 할지는 `general.restore_layout` 하나로 갈린다 — 켜져 있으면 디바운스를 무시한 강제 flush 후 **보존**, 꺼져 있으면 슬롯 파일을 **삭제**한다. 마지막 창이 닫혀 engine 이 파킹되는 경우(그리고 macOS 최소화)는 engine 이 살아 있으므로 이 처리를 하지 않는다 — 점유가 유지되고 다시 창을 열면 같은 슬롯을 이어쓴다.

## Consequences

- **얻은 것**:
  - 창 간 덮어쓰기가 구조적으로 사라진다. 각 engine 이 자기 파일에만 쓰므로 flush 순서가 어떻든 남의 상태를 지울 수 없다. 종료 시 일괄 flush 도 창마다 자기 파일로 나뉜다.
  - 창별 독립 세션이 성립한다. 창 A 와 창 B 가 서로 다른 워크스페이스 집합을 갖고, 각자 그대로 재시작을 넘긴다.
  - 슬롯 누수가 원천적으로 없다. 해제가 명시적 호출이 아니라 파생이므로 "해제를 빠뜨렸다" 는 버그가 성립하지 않는다. 크래시가 슬롯을 영구 점유로 남기지도 않는다.
  - 잘린 파일 하나가 다른 슬롯을 오염시키지 않는다(원자적 교체 + 슬롯 격리).
- **잃은 것**:
  - 파일 개수가 창 수만큼 늘어난다. 단일 파일 시절의 "레이아웃은 이 파일 하나" 라는 단순함이 사라졌다.
  - **슬롯 번호라는 새 개념이 사용자에게 노출된다.** 어떤 창이 어떤 번호를 쓰는지는 사용자가 고를 수 없고 배정 규칙에서 결정된다. 창을 여는 순서가 곧 어떤 레이아웃이 뜰지를 정한다.
  - 점유가 휘발성이라 **프로세스 밖에서는 점유를 알 수 없다.** 같은 `TASTY_HOME` 을 공유하는 두 tasty 프로세스는 서로의 슬롯을 모르고 같은 번호를 잡는다 — 이 구성은 지원 대상이 아니다.
- **운영 비용 / 유지 부담**:
  - **scrollback GC 가 전 슬롯 union 이어야 한다는 새 불변식이 생긴다.** 정리는 부팅 1 회, 모든 슬롯의 `scrollback_ref` 합집합 밖에 있는 `.bin` 만 지운다. 슬롯 하나만 보고 정리하면 다른 슬롯이 참조 중인 `.bin` 을 지운다. 나아가 **읽을 수 없는 슬롯이 하나라도 있으면 그 부팅에서는 정리 자체를 건너뛴다** — 참조 목록이 불완전한 상태의 삭제는 사용자 데이터를 잃는 쪽으로 틀리기 때문이다.
  - 슬롯을 새로 잡거나 놓는 경로(창 생성 · 창 닫힘 · 파킹 · 파킹 복귀)가 늘 때마다 점유 파생이 그 경로를 포함하는지 확인해야 한다.
  - 단일 파일 시절 데이터를 위한 1 회 마이그레이션 코드를 유지한다.

## Alternatives Considered

- **A: 단일 파일 안에 레이아웃 배열을 담는다** — 파일 개수가 늘지 않고 "레이아웃은 이 파일" 이라는 단순함이 유지된다. 안 고른 이유: 원인이었던 **flush 경합이 그대로 남는다.** 두 engine 이 같은 파일에 쓰는 이상 배열의 어느 원소를 갱신하든 read-modify-write 가 필요하고, 그 사이에 다른 창이 쓰면 다시 last-writer-wins 다. 이걸 막으려면 파일 잠금이나 프로세스 내 직렬화 계층이 필요해지는데, 파일을 나누면 그 계층 자체가 불필요해진다.
- **B: 점유를 디스크에 기록한다** — 프로세스 밖에서도 점유를 알 수 있고 같은 `TASTY_HOME` 공유 시나리오로 확장할 여지가 생긴다. 안 고른 이유: **크래시가 영구 점유를 남긴다.** 비정상 종료 시 해제 기록을 못 남기므로 다음 부팅이 "이미 점유된" 슬롯을 보고 새 번호를 발급하고, 저장된 레이아웃은 영영 열리지 않는 채 파일만 쌓인다. 이걸 막으려면 stale 판정(PID 생존 확인·TTL)이 필요하고, 그 판정이 틀리면 이번엔 남의 슬롯을 덮어쓴다. 파생값은 이 실패 모드를 아예 갖지 않는다.
- **C: 점유를 별도 레지스트리(프로세스 내 자료구조)로 관리한다** — 조회가 O(1) 이고 파생 비용이 없다. 안 고른 이유: **동기화 누락이 곧 버그가 된다.** engine 이 생기고 사라지는 경로가 여럿(창 생성 · 창 닫힘 · 파킹 · 파킹 복귀 · IPC)이라, 그중 하나에서 레지스트리 갱신을 빠뜨리면 슬롯이 새거나 중복 배정된다. 파생은 그 경로들을 몰라도 항상 맞다. 점유 집합을 만드는 비용은 창 생성 때 한 번 훑는 것이라 무시할 수 있다.
- **D: 부팅 시 저장된 슬롯 수만큼 창을 복원한다** — 세션 재현성이 가장 높다. 안 고른 이유: 부팅 시간과 PTY 수가 슬롯 수에 비례해 늘고, 사용자가 그 시점에 원하지 않는 창까지 강제로 뜬다. 창을 더 여는 것은 사용자의 명시적 행동이므로 그때 복원하면 충분하다 — 슬롯은 남아 있고 순서대로 되살아나므로 재현성을 잃는 게 아니라 **시점을 사용자에게 넘긴 것**이다.

## Reconsideration Triggers

다음 중 하나가 충족되면 본 ADR 을 재검토한다.

- **슬롯 파일이 사용자가 관리해야 할 만큼 쌓인다** — 지금은 배정 규칙이 낮은 번호를 재사용하므로 상시 창 수 근처에서 안정된다. 파일이 계속 늘어난다면 배정 규칙이나 회수 정책(오래된 슬롯의 TTL 등)이 필요해진다.
- **창 위치·크기까지 영속화하라는 요구가 생긴다** — 지금 슬롯은 창의 *내용*만 담고 OS 윈도우 기하는 담지 않는다. 기하가 들어오면 "슬롯 ↔ 창" 의 결합이 지금보다 강해지고, 부팅 시 창 1 개 결정도 함께 흔들린다.
- **여러 tasty 프로세스가 같은 `TASTY_HOME` 을 공유하는 시나리오가 지원 대상이 된다** — 휘발성 점유의 전제(점유를 아는 주체가 프로세스 하나)가 깨진다. 그때는 대안 B 를 stale 판정과 함께 다시 검토한다.
- **레이아웃 저장이 부팅 경로 밖에서도 GC 를 돌려야 할 만큼 커진다** — 지금은 부팅 1 회 union 정리로 충분하다는 전제다. 런타임 정리가 필요해지면 "읽을 수 없는 슬롯이면 전면 스킵" 규칙의 비용도 함께 재검토한다.
