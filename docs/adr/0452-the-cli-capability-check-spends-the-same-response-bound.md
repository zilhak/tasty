# ADR-0452: CLI 의 계약 확인도 같은 응답 대기 상한 안에서 끝난다 — ADR-0366 의 사전 확인 조항 개정

- **Status**: Accepted
- **Date**: 2026-09-21
- **Tags**: ipc, cli, envelope, response-timeout, capability, compatibility, adr-0366, adr-0411

## Context

[ADR-0366](0366-the-cli-bounds-a-single-request-wait-with-a-root-flag.md) 은 루트 플래그
`--response-timeout-ms` 를 단발 요청의 봉투에 싣고, 그 전에 상대가 `ipc.response-timeout` 을
선언했는지 `system.info` 로 묻게 했다. 그리고 "얻은 것" 에 **굳은 핸들러에 걸린 호출이 그 시간 뒤에
결과 불명으로 돌아온다** 를 적었다. "잃은 것" 은 왕복 하나가 는다는 것뿐이었다.

그 확인 요청은 상한 없이 나갔다(`IpcConnection::capabilities` 가 봉투를 비워 보냈고 소켓에는 읽기
기한이 없다). 확인 요청도 호스트 메인 스레드의 큐를 지나므로, 호스트가 굳어 있으면 CLI 는 거기서
기다렸다. 격리 gui 인스턴스에서 메인 스레드를 8 s 세우고 `tasty --response-timeout-ms 300 list
workspaces` 를 부르자 7,719 ms 뒤 정상 결과로 끝났다(2.5 s 정지에서는 2,720 ms). 같은 정지 중에 봉투에
300 을 실은 요청을 직접 보내면 400 ms 에 `-32067` 이 왔다 — 서버는 맞고, CLI 의 확인 단계만 상한
밖이었다. 호스트가 영영 굳으면 CLI 도 영영 기다린다.

## Decision

**요청이 응답 대기 상한을 실었으면 계약 확인도 그 상한 안에 들어간다. 두 요청은 상한 하나를
나눠 쓴다.**

- **나눠 쓴다.** 확인 요청은 확인을 시작하는 순간 남은 상한을 기한으로 받는다 — 소켓 읽기 기한은 그
  남은 시간 그대로, 봉투에는 **밀리초 올림**(아래 "보강")이다. 확인이 끝나면 본 요청의 봉투를 **남은
  시간**(밀리초 내림)으로 줄여 싣는다. 남은 시간이 1 ms 도 안 되면 본 요청은 안 나간다. 그래서 확인과
  본 요청의 대기를 합쳐도 상한을 넘지 않는다(연결·쓰기 시간은 뺀다 — 상한은 **응답 대기**다).
- **확인 요청은 두 겹으로 자른다.**
  - 봉투에 같은 기한을 싣는다 — 그 이름을 아는 서버는 상한에서 확인 요청을 큐에서 물리고
    `-32067` 로 답한다([ADR-0411](0411-a-request-whose-deadline-passed-in-the-queue-is-answered-as-not-run.md)).
    확인 요청이 굳은 호스트의 큐에 남아 나중에 실행되지 않는다.
  - 소켓 읽기 기한을 같은 시간으로 건다 — 봉투를 모르는 **구 서버**는 필드를 조용히 버리고 무한정
    기다리게 하므로(`JsonRpcRequest` 에 `deny_unknown_fields` 가 없다), 거기서도 같은 시간에 끝나려면
    이쪽이 필요하다. 확인 요청은 부수효과가 없어 클라이언트가 먼저 물러나도 안전하다. 확인이
    끝나면 읽기 기한을 원래대로(없음) 돌린다 — 본 요청은 서버가 상한으로 끊는다.
- **답은 본 요청의 "실행 안 됨" 과 같다.** 확인이 제시간에 안 끝나면(읽기 기한 · 서버의 `-32067` ·
  `-32061` 어느 쪽이든) CLI 는 본 요청이 큐에서 만료됐을 때와 **같은 코드·문구**
  (`Error (-32067): the caller's response timeout of <상한> ms passed while the request was still
  queued; it did not run — sending it again is safe`)로 종료 코드 1 이다. 본 요청은 안 나갔으므로
  "실행 안 됨 — 그대로 다시 보내도 된다" 가 참이다. 문구의 상한은 사용자가 준 값이다.
- **상한이 없으면 아무것도 안 바뀐다.** 확인 요청의 봉투도 비어 있고 읽기 기한도 없다.

### 보강 — 확인 요청의 봉투는 올림이다 (같은 lane 의 Gate 4 후속)

처음 구현은 확인 요청의 봉투도 남은 시간의 **내림**으로 실었다(격리 인스턴스 실측: 상한 300 → 봉투 299).
그러면 `--response-timeout-ms 1` 은 확인을 시작하는 순간 남은 시간이 1 ms 에서 몇 µs 모자라 0 이 되고,
0 은 봉투 규약상 "상한 없음" 이라 실을 수 없으므로 **확인 요청조차 보내지 않고** `-32067` 로 끝났다.
이 결정 전에는 상한 1 이 확인(상한 없음) 뒤 본 요청에 1 을 실어 보냈으므로, 서버에 아무것도 안 닿는 것은
호환이 줄어든 것이었다.

그래서 **확인 요청의 봉투만 올림**(1 ms 밑이어도 남은 시간이 있으면 1)으로 싣는다. 합계는 여전히 상한을
넘지 않는다 — 기다림을 끊는 것은 봉투가 아니라 남은 시간 그대로 거는 소켓 읽기 기한이다. 올림이 더하는
것은 새 서버가 확인 요청을 큐에서 물리는 시각이 1 ms 미만 늦어지는 것뿐이다.

**본 요청의 봉투는 내림 그대로다.** 본 요청에는 소켓 기한이 없고 서버가 봉투 값으로 끊으므로, 올리면
합계가 상한을 넘는다. 그래서 상한 1 ms 에서는 확인 요청은 나가지만 그 왕복 뒤 남은 시간이 늘 1 ms
미만이라 **본 요청은 여전히 안 나가고** `-32067`(실행 안 됨)이다 — 시험
`a_one_millisecond_bound_still_sends_the_check` 가 둘 다 고정한다. 상한 2 ms 부터는 확인이 1 ms 안에
끝나면 본 요청이 나간다.

**개정하는 것**: ADR-0366 Decision 의 "못 거는 상대는 거절한다" 조항이 정한 사전 확인에 **시간 상한이
없던 것**. **개정하지 않는 것**: 루트 플래그의 자리와 이름, `0` 을 안 싣는 규약, 선언이 없는 상대에게
보내지 않는 구조화 거절(`sent:false`, 종료 코드 1), 루프·스트림 명령의 거절(종료 코드 2), 만료를 다른
호스트 오류와 같은 모양으로 전달하는 것, 확인이 연결마다 한 번이라는 것.

## Consequences

- **얻은 것**: ADR-0366 이 적은 "굳은 핸들러에 걸린 호출이 그 시간 뒤에 돌아온다" 가 확인 단계까지
  참이 된다. 격리 인스턴스의 같은 재현(8 s 정지 중 상한 300)이 바뀌기 전 CLI 로는 7,592 ms 뒤 정상
  결과(종료 코드 0)였고, 바뀐 CLI 로는 352 ms(프로세스 기동 포함) 뒤 `-32067` · 종료 코드 1 이었다.
  답하지 않는 가짜 구 서버에는 바뀌기 전 CLI 가 5 s 안에 안 끝났고(끊었다), 바뀐 CLI 는 347 ms 였다.
- **얻은 것**: 구 서버(봉투 상한을 모르는 서버)가 굳어 있어도 CLI 는 상한 뒤에 돌아온다. 전에는
  확인 단계에서 무한정 기다렸다.
- **잃은 것 / 호환**: 본 요청의 봉투에 실리는 값이 플래그 값보다 조금 작다(확인에 쓴 시간만큼 —
  건강한 호스트에서는 1 ms 안팎). 서버 로그나 봉투를 기록하는 도구가 그 값을 플래그 값과 비교하면
  어긋난다.
- **잃은 것**: 확인 요청의 봉투에 상한이 실린다. 구 서버는 그것을 버리므로 동작이 같다.
- **잃은 것 / 호환**: 상한 1 ms 의 본 요청은 늘 안 나간다(`-32067`). 이 결정 전에는 서버가 1 ms 안에 꺼내면
  성공할 수 있었다. 확인 요청은 나간다(위 보강).
- **운영 비용**: 확인 요청이 클라이언트 읽기 기한으로 끝난 연결은 늦은 답이 소켓에 남을 수 있어
  다시 쓰지 않는다 — CLI 는 그 자리에서 종료하므로 해당 없다. 같은 연결을 이어 쓰는 새 호출자는 이
  오류(`CapabilityProbeExpired`) 뒤 연결을 버려야 한다.

## Alternatives Considered

- **A: 두 요청이 각자 상한 전체를 쓴다** — 본 요청의 봉투 값이 플래그 값 그대로 남는다. 안 골랐다.
  굳은 호스트에서 최악이 상한의 두 배가 되어, "그 시간 뒤에 돌아온다" 가 다시 거짓이 된다.
- **B: 봉투에만 싣고 소켓 기한은 안 건다** — 연결의 "읽기 기한 없음" 규약을 안 건드린다. 안 골랐다.
  구 서버는 봉투를 버리므로 거기서는 지금과 똑같이 무한정 기다린다. 구 서버에서 지금보다 나빠지지는
  않지만 나아지지도 않는다.
- **C: 소켓 기한만 걸고 봉투에는 안 싣는다** — 확인 요청의 줄이 지금과 같다. 안 골랐다. 새 서버에서
  확인 요청이 굳은 큐에 남아 호스트가 풀린 뒤 실행된다 — 부수효과는 없지만 CLI 마다 한 건씩 적체를
  남기고, 입장 장부의 바이트를 쥔다.
- **D: 확인을 건너뛰고 상한을 그대로 싣는다** — 왕복이 준다. 안 골랐다. ADR-0366 이 거절한 결함(구
  서버가 상한을 조용히 버린다)이 돌아온다.
- **E: 확인 만료를 `-32061` 이나 별도 문구로 낸다** — 안 골랐다. 본 요청은 안 나갔으므로 결과 불명이
  아니고, 별도 문구는 호출자에게 새 갈래를 가르게 한다. 같은 사실(실행 안 됨)에는 같은 답을 쓴다.

## Reconsideration Triggers

**채널이 붙는 것**

- 확인 요청이 상한 없이 기다리기 시작하면 `tasty-cli` `contract.rs` 의 시험
  `a_bound_covers_the_capability_check_when_the_host_does_not_answer` 가 5 s 뒤 빨개진다(답하지 않는
  가짜 호스트 — 구 서버와 굳은 호스트를 함께 대신한다).
- 본 요청이 남은 시간이 아니라 플래그 값을 싣기 시작하면 같은 파일의
  `the_request_carries_what_is_left_after_the_check` 가 빨개진다.
- 확인 요청의 봉투가 다시 내림이 되면(상한 1 ms 에서 확인 요청이 안 나가면) 같은 파일의
  `a_one_millisecond_bound_still_sends_the_check` 가 빨개진다.
- 확인 뒤 읽기 기한이 연결에 남으면 같은 파일의 `the_check_leaves_no_read_timeout_on_the_connection`
  이 빨개진다.

**원리적으로 안 붙는 것**

- 봉투 값이 플래그 값과 다르다는 이유로 도구가 깨진 보고. 재는 법: 서버 쪽 요청 기록의
  `response_timeout_ms` 와 호출자의 플래그 값을 대조한다.
- 확인 왕복이 상한의 큰 몫을 먹는다는 보고(확인 뒤 남은 시간이 너무 적어 본 요청이 늘 `-32067` 로
  끝난다). 재는 법: 같은 호스트에서 `tasty list info` 의 벽시계와 쓰는 상한을 견준다.
