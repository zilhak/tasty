# ADR-0118: 캡처는 읽기라 행동 대상 집합을 넓히지 않는다 — 명시한 `window_id` 는 모달까지 찍고, 자동 선택은 main 창 하나로 유지한다

- **Status**: Accepted
- **Date**: 2026-09-04
- **Tags**: screenshot, ipc, window, modal, focus, identity-principle-1, identity-principle-3, local-only, ai-verification

## Context

`ui.screenshot`(CLI `tasty screenshot`)은 `window_id` 를 명시해도 **main 창만** 대상으로
받았다. 설정 · 플러그인 · 종료 확인 모달과 preset 창처럼 별도 winit 창으로 뜨는 UI 를
지정하면 `Target window is not a main view` 로 거절했고, 그쪽 렌더 경로에는
`pending_screenshot` readback 지점 자체가 없었다.

그래서 자동 시각 검증이 main 창에 갇혔다. 모달을 `debug.settings.open` 으로 띄울 수는
있어도 그 결과를 IPC 로 캡처할 수 없어 디자인 정합 확인이 사람 눈에 의존했다. X11
화면 캡처는 GPU 창에서 검게 나오므로 대안이 되지 못한다.

이걸 풀려면 먼저 **무엇이 실제로 문제인가**를 정해야 했다. "에이전트가 사용자가 보고
있는 창을 찍을 수 있다" 는 것이 불가침 원칙 1 에 걸리는가? 원칙 1 의 금지 대상은
에이전트 행동의 부수효과가 **사용자 상태**(포커스 / 닫은 항목 히스토리 / 선택 · 스크롤 ·
커서)에 닿는 것이고, 읽기는 그 문언에 직접 걸리지 않는다. 그러나 "문언에 안 걸린다" 만으로
넓히면 다음 사람이 같은 논리로 다른 것도 넓힌다. 경계를 명시적으로 정해야 했다.

관련해서 이미 코드에 박혀 있던 불변식이 하나 있다. `window.close` 는 대상을 main 창으로
좁히면서 그 이유를 "**modal/preset 은 사용자 조작 영역이라 IPC close 대상이 아님**" 이라
적고, 그 범위를 `window.list` 가 노출하는 범위와 같다고 못박았다. 즉 이 API 계열에는
**"`window.list` 범위 = 에이전트 행동 대상 범위"** 라는 불변식이 있었다.

## Decision

캡처의 경계를 **창의 종류가 아니라 다른 두 축**으로 긋는다.

**1. 캡처는 읽기이지 행동이 아니다 — 행동 대상 집합을 넓히지 않는다.**
`window_id` 를 명시하면 모달 · preset 을 포함한 모든 창을 찍을 수 있다. 그러나
`window.list` 와 `window.close` 는 종전대로 main 창만 다룬다. 위의
"list 범위 = 행동 대상 범위" 불변식은 그대로 유지되고, 모달은 에이전트가 *조작할 수 있는
것들* 의 목록에 들어오지 않는다.

이것이 원칙 1 을 어기지 않는 이유는 두 가지다. 첫째, 캡처는 이미 그려진 프레임의
swapchain readback + 리페인트 요청이고 리페인트는 멱등이라 포커스 · 히스토리 · 선택 ·
스크롤 · 커서 중 무엇도 바꾸지 않는다. 둘째, `ui.screenshot` 은 `local_only`(plugin
미노출)라 호출자는 이미 사용자 권한으로 `config.toml`(설정 창이 그리는 내용 전부)과
PTY 를 읽을 수 있다 — 모달 캡처를 막아도 새로 감춰지는 정보는 없고 자동 검증만 잃는다.
**경계는 창의 종류가 아니라 호출자의 신뢰 수준**이며, 그 신뢰 수준은 `local_only` 로
이미 그어져 있다.

**2. 넓어지는 것은 명시 지정뿐이다 — 자동 선택은 넓히지 않는다.**
`window_id` 를 생략했을 때의 대상 선택은 종전대로 **main 창이 정확히 하나일 때만**
성립하고, 모달로 폴백하지 않으며 포커스를 보지 않는다(원칙 3). 자동 선택이 "사용자가
지금 무엇을 열어두었는가" 에 의존하기 시작하면 같은 명령이 실행할 때마다 다른 것을
찍는다. main 창이 하나도 없을 때의 에러 문구도 "Multiple windows open" 에서
"No main window open" 으로 갈라 무엇이 문제인지 말하게 한다.

**모달 ID 의 발견은 OS 창 목록에 맡긴다.** `window.list` 를 넓히지 않았으므로 모달 id 는
tasty 가 알려주지 않는다. X11 에서는 winit `WindowId` 가 X11 window id 그 자체라
`xdotool` 등이 돌려주는 값을 그대로 넘길 수 있다(창 이름으로 골라야 한다 — 입력 전용
더미 창까지 나온다). 이 발견 경로를 가진 호출자는 이미 그 X 디스플레이 전체를 캡처하고
키를 주입할 수 있으므로, 여기서 새로 열리는 능력은 없다.

`debug.fullscreen.*` 의 `pick_debug_window` 는 명시한 id 도 **main 창만** 받는 채로 둔다.
무대를 여닫는 것은 읽기가 아니라 행동이므로 위 1 번이 적용되지 않는다.

## Consequences

- **얻은 것**: 설정 · 플러그인 창 등 별도 창으로 뜨는 UI 의 디자인 정합을 자동으로
  확인할 수 있다(실제로 설정 창의 언어 콤보를 캡처해 검증했다). 경계가 "창의 종류" 가
  아니라 "읽기냐 행동이냐 / 명시냐 자동이냐" 로 서술되어, 다음에 비슷한 요구가 왔을 때
  판단 기준이 남는다.
- **잃은 것**: 대상 후보가 넓어진 만큼, 자동 선택이 모달을 집지 않는다는 것을 코드가
  스스로 지켜야 한다. 그 자리를 순수 함수(`resolve_screenshot_window`)로 뽑고 단위
  테스트로 고정했다 — 실제 경로는 `App` 과 GPU 상태를 요구해 감쌀 수 없다.
- **운영 비용 / 유지 부담**: 모달 창이 타는 렌더 경로(`finish_egui_frame`)에도 present
  직전 readback 지점이 생겼다. 새 창 종류를 추가하면 그 경로가 이 함수를 지나는지
  확인해야 한다 — 지나지 않으면 그 창에 대한 캡처 요청이 큐에 남아 영구 대기한다.
- **플랫폼 편차**: 모달 id 의 발견이 OS 창 목록에 의존하므로, winit `WindowId` 와 OS
  창 식별자의 대응이 X11 만큼 곧지 않은 플랫폼에서는 이 기능을 실제로 쓰기 어렵다.
  아래 셋째 재검토 트리거가 그 지점이다.

## Alternatives Considered

- **`window.list` 에 모달을 넣고 `kind` 필드를 붙인다** — 모달 id 를 OS 창 목록 없이
  얻을 수 있어 모든 플랫폼에서 균일하게 동작한다. 그러나 "list 범위 = 행동 대상 범위"
  불변식이 깨진다. 그 불변식이 사라지면 `window.close` 를 비롯한 **모든 소비자가 각자
  다시 필터해야** 하고, 한 곳이 빠뜨리는 순간 에이전트가 사용자의 설정 창을 닫는다.
  표면을 넓히는 것이 아니라 필터 의무를 소비자 전체에 전가하는 거래라 기각했다.
- **모달 캡처를 아예 막는다(현행 유지)** — 표면이 가장 좁다. 그러나 막아서 감춰지는
  정보가 없다(호출자가 이미 `config.toml` 을 읽는다). 얻는 것 없이 자동 시각 검증만
  잃는 거래다.
- **자동 선택도 모달로 폴백시킨다** — "창이 하나뿐인데 왜 에러냐" 는 불편이 사라진다.
  그러나 같은 명령의 결과가 사용자가 무엇을 열어두었는지에 따라 달라진다. 원칙 3 이
  금지하는 바로 그 형태이고, 자동 검증의 재현성도 함께 잃는다.
- **`window_kind` 파라미터를 새로 받는다**(`--window-kind settings`) — id 발견이 필요
  없어 플랫폼 편차가 사라진다. 그러나 release 메서드의 파라미터 계약을 넓히는 일이고,
  "설정 창이 열려 있는가" 를 응답으로 알려주게 되어 오히려 사용자 상태를 더 직접적으로
  노출한다. 셋째 재검토 트리거가 발동하면 이 안을 먼저 다시 본다.

## Reconsideration Triggers

다음 중 하나가 충족되면 본 ADR 을 재검토한다.

- **`ui.screenshot` 이 plugin-callable 로 바뀐다** — 위 1 번의 근거가 "호출자가 이미
  사용자 권한을 가진다" 이므로, plugin(더 낮은 신뢰 수준)에 열리는 순간 그 전제가
  무너진다. 그때는 창 종류가 다시 경계가 될 수 있다.
- **`window.list` 에 모달을 넣자는 요구가 생긴다** — 그때 다시 검토할 것은 목록의
  확장 자체가 아니라 "list 범위 = 행동 대상 범위" 불변식을 유지할 다른 방법이 있는가다
  (예: 행동 대상 전용 목록을 따로 두는 것).
- **macOS / Windows / Wayland 에서 모달 시각 검증이 필요해진다** — 지금은 모달 id 발견이
  X11 의 `WindowId` == X11 window id 대응에 기대고 있다. 그 대응이 없는 플랫폼에서
  이 기능이 실제로 필요해지면, 위 `window_kind` 안이나 debug 전용 열거를 검토한다.
