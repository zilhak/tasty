# ADR-0007: IPC는 제한된 시간만 실행하고 완료 결과를 돌려준다

- **Status**: Accepted
- **Date**: 2026-09-24
- **Tags**: ipc, scheduling, timeout
- **Group**: foundation

## Context

큐를 모두 비울 때까지 IPC를 처리하면 무거운 요청이 타이머와 화면 갱신을 밀어낸다.
한 번에 처리할 명령 수만 제한해도 한 명령의 비용에 따라 지연이 커진다.
호출자가 대기를 포기한 요청이 나중에 실행되는 문제도 별도로 다뤄야 한다.

## Decision

GUI와 헤드리스는 공용 회차 규칙으로 명령 수와 시간 예산 중 먼저 닿는 지점에서 멈춘다.
한 건씩 꺼내 처리하고 첫 명령은 항상 진행한다. 나머지는 원래 큐에 남긴다.
FIFO는 실행 시작 순서를 정하며 비동기 완료 순서까지 보장하지 않는다.
종료 시 남은 요청을 거절하는 drain에는 정상 회차 제한을 적용하지 않는다.

GUI는 IPC wake가 연속 회차를 열지 않도록 about_to_wait에 차례를 넘긴다.
헤드리스는 대기 wake를 하나로 합친다. 두 빌드 모두 남은 요청을 다시 처리할 wake를 명시적으로 만든다.
그 wake가 다른 이벤트의 진행을 막지 않도록 GUI 면제 횟수와 헤드리스 채널 순서를 지킨다.

응답 대기 기한은 호출자가 정한다. 없거나 0이면 무한 대기를 유지한다.
큐에서 만료된 요청은 lifecycle 상태의 비교·교환으로 실행을 막고 미실행으로 답한다.
시작 뒤의 만료는 결과 불명이며 실행 중 작업을 취소하지 않는다.
내부 주입도 기본적으로 같은 기한을 쓰되, 재발생하지 않는 훅 사건의 단계는 포기 뒤에도 실행한다.

CLI의 단발 요청은 루트 응답 대기 옵션을 사용할 수 있고 capability 확인도 같은 예산을 쓴다.
loop·stream·로컬 처리에는 정의되지 않은 옵션을 조용히 무시하지 않고 거절한다.
실패 가능한 release winit 작업은 예약 성공 대신 완료 채널로 실제 결과를 요청자에게 돌려준다.

## Consequences

지속 IPC 부하에서도 다른 이벤트가 진행할 기회를 얻고 큐의 만료 요청이 뒤늦게 실행되지 않는다.
호출자는 미실행과 결과 불명을 구분할 수 있다.

이미 시작된 동기 handler는 선점하지 못한다. 16ms 예산은 한 handler의 실행시간까지 늘어날 수 있다.
호출자별로 처리 기회를 균등하게 나누지는 않는다. 여러 연결을 연 호출자가 더 많은 요청을 처리할 수 있다.
CLI 예산은 응답 대기용이며 연결·쓰기·프로세스 기동까지 포함한 총 실행시간 한도는 아니다.

## Alternatives Considered

- 먼저 전부 꺼내 별도 버퍼에서 실행하면 남은 요청이 큐 사용량과 대기 계측에서 사라진다.
- 호출자별 라운드로빈은 인증 전 큐 분류와 별도 상태가 필요해 현재 도입하지 않는다.
- 모든 요청에 기본 timeout을 걸면 사람 승인을 기다리는 의도적 무한 대기를 자른다.
- winit 작업 완료를 같은 메인 스레드에서 막고 기다리면 교착한다.
- 모든 훅 단계에 기한을 걸면 이미 ACK한 사건이나 완료 통지가 사라질 수 있다.

## Reconsideration Triggers

시간 중단률·타이머 간격·화면 갱신과 실제 처리량을 함께 측정해 예산을 재검토한다.
macOS·Windows의 메뉴·resize 중 IPC 지연과 winit 이벤트 처리 변경도 확인한다.

새 내부 요청 생성 경로는 포기 뒤 실행이 필요한지 명시적으로 선택한다.
새 실패 가능 예약 작업은 완료 응답을 연결하고,
시작 전/후 timeout 경합과 회차마다 한 건만 처리하는 재개 시나리오를 검증한다.
