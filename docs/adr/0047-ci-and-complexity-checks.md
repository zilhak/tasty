# ADR-0047: CI는 실제 병합 결과를 검사하고 복잡도 증가를 제한한다

- **Status**: Accepted
- **Date**: 2026-09-24
- **Tags**: ci, complexity, quality
- **Group**: rules

## Context

검사 스크립트가 있어도 실제 개발 흐름에서 실행되지 않으면 회귀를 막지 못한다.
또한 기존의 큰 함수와 파일을 모두 즉시 실패시키면 검사를 도입하기 어렵다.
검사 범위, 실행 조건, 예외의 의미가 함께 정해져야 한다.

## Decision

함수의 인지 복잡도는 clippy의 `cognitive_complexity`를 `deny`로 검사한다.
파일 크기는 tokei로 제품 코드의 SLOC를 계산한다.
현재 임계값은 설정과 스크립트에서 관리하고 [복잡도 가이드](../dev-guide/complexity-gate.md)에 설명한다.
기존 초과분은 위치별 사유와 함께 예외로 관리하며, 분해가 끝나면 예외를 제거한다.
전체 임계값을 올려 새 위반까지 허용하지 않는다.

실제 통합 방식인 main push에서 검사가 실행되도록 한다.
PR이나 수동 실행만 지원하는 검사는 main 직접 push를 보호한다고 표현하지 않는다.
CI의 명령, 빌드 조합, 트리거, 실패 차단 여부는 [CI 가이드](../dev-guide/ci-gates.md)에서 관리한다.

검사 성공, 규칙 위반, 측정 실패를 구분한다.
외부 도구 오류나 빈 결과를 위반 없음으로 처리하지 않는다.

예외 파일의 제품 SLOC 총합도 별도 예산으로 검사한다. 총합이 줄면 예산도 낮추고,
증가 허용 폭은 파일 임계값에서 가져온다. 예산 한 줄의 증가는 리뷰에서 드러나야 한다.
임계 1000 자체를 품질 공식에서 도출한 값이라고 주장하지 않는다.

## Consequences

기존 부채를 한 번에 모두 고치지 않아도 새 복잡도 증가를 제한할 수 있다.
예외는 좋은 설계라는 인증이 아니며, 특히 검사 미실행 기간에 생긴 초과분은 정리할 부채다.
리팩터링 때 사유와 필요성을 다시 확인한다.

인지 복잡도는 코드 품질 전체를 대표하지 않는다. 도구의 계산 방식과 매크로 처리에도 한계가 있다.
파일 크기 검사는 컴파일과 별도로 tokei와 관련 스크립트를 실행하는 비용이 든다.

## Alternatives Considered

- 외부 도구로 여러 복잡도 지표와 함수별 baseline을 관리하면 식별·버전·파싱 비용이 늘어난다.
- 관측만 하고 실패시키지 않으면 회귀를 차단하지 못한다.
- 기존 위반까지 모두 즉시 실패시키면 초기 상태에서 검사를 사용할 수 없다.
- 한 검사를 위해 저장소의 전체 통합 방식을 PR 중심으로 바꾸는 것은 범위를 벗어난다.

## Reconsideration Triggers

예외가 지속적으로 늘거나 도구 버전 변경으로 오탐이 급증하면 지표와 임계값을 다시 검토한다.
기존 검사로 드러나지 않는 복잡도가 실제 유지보수 문제를 반복해서 만들면 별도 지표를 검토한다.
