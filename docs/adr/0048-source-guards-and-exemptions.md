# ADR-0048: 소스 검사는 공용 분석기를 쓰고 검사 범위와 예외를 함께 확인한다

- **Status**: Accepted
- **Date**: 2026-09-24
- **Tags**: guards, testing, source-analysis
- **Group**: rules

## Context

정적 검사는 조건식이 맞아도 필요한 파일을 읽지 않으면 위반을 놓친다.
개별 파일 목록은 새 파일이 생길 때 빠지기 쉽고, 최소 파일 수만으로는 일부 누락을 찾기 어렵다.
주석과 문자열을 실제 코드로 세는 검사도 잘못된 실패를 만들 수 있다.

## Decision

소스 검사는 검사 대상과 판정 조건을 따로 검증한다.
스캔 범위는 가능한 한 디렉터리로 정하고 제외할 파일은 이유가 있는 예외로 관리한다.
파일 목록을 완전히 확인해야 할 때는 이름 집합을 비교한다.
최소 개수는 경로 오류나 빈 순회를 찾는 용도로만 사용한다.

검사 범위와 예외의 종류를 구분한다. 제품 의존 방향을 보는 계층 검사에서는
테스트 전용 파일을 별도 목록으로 둘 수 있다. 그 파일이 실제로 `cfg(test)`로만
선언됐는지와 예외 대상 참조가 남아 있는지를 함께 검사한다.
제품에 포함되지 않는 테스트 픽스처 때문에 통합 테스트로 옮길 수 없는 경우도 명시한다.

같은 문법·제품 포함 여부를 판단하는 검사는 공용 분석기를 사용한다.
문자열과 주석에 있는 예시를 실제 호출로 세지 않도록 처리한다.
분석기가 지원하지 않는 형태와 검사 대상에서 제외한 범위를 문서에 밝힌다.

파일만 읽는 문서 가드는 외부 의존성 없는 `tasty-doc-guards`로 분리한다.
제품 전체를 빌드하지 않고 문서 변경에도 실행할 수 있도록 비용을 낮춘다.
소스 텍스트 판독이 제품 상수와 같은지는 제품을 링크하는 별도 검사로 대조한다.

## Consequences

파일을 추가할 때 스캔 목록을 별도로 갱신하는 부담을 줄이고 누락을 발견할 수 있다.
반면 검사 범위를 넓히면 기존 위반도 드러나므로 실제 비용을 확인하고 정리해야 한다.

집합이 같아도 두 집합이 함께 비면 통과할 수 있다. 이 경우 최소 개수 확인도 필요하다.
가드가 두 빌드 조합에서 실행된다는 것만으로 검사 파일 집합까지 같다고 판단하지 않는다.

## Alternatives Considered

- 파일 목록을 손으로 유지하고 갱신을 부탁하는 방법은 실제 누락을 발견하지 못한다.
- 모든 가드가 저장소 전체를 검사하면 관련 없는 계층을 예외로 관리하는 비용이 커진다.
- 검사 파일 수만 고정하면 같은 수의 파일 교체를 놓친다.
- 테스트 전용 예외를 기존 제품 부채 목록에 넣으면 없애야 할 부채와 정상 범위가 섞인다.

## Reconsideration Triggers

스캔 범위 확대가 큰 오검출 비용을 만들거나 공용 분석기가 실제 컴파일과 다르게 분류하면
범위와 분석 방식을 다시 검토한다. 테스트 픽스처를 제품 밖 공용 크레이트로 옮길 수 있게 되면
계층 검사 예외도 다시 확인한다.
