# ADR-0129: 확률적 테스트 실패(flake)의 부류별 표준 처방

- **Status**: Proposed
- **Date**: 2026-09-04
- **Tags**: testing, flaky-tests, ci, concurrency, test-isolation

## Context

`cargo test` 는 한 테스트 바이너리 안의 테스트를 기본으로 병렬 실행한다. 그래서 여러
테스트가 **공유하는 무언가**를 각자 변형하면 실행 순서에 따라 확률적으로 실패한다. 이
저장소는 또한 여러 git worktree 에서 테스트를 동시에 돌리므로, **프로세스 밖에서 유일한
자원**(포트·파일경로)을 놓았다 다시 잡는 테스트는 다른 완주와 경합한다.

증상은 하나다: **자동 CI 채널에 상주하는 확률적 red.** 문제의 테스트들은 전부
`--lib --bins` 소속이라 `crossplatform-check` 의 check-windows 와 check-headless **양쪽
자동 채널**에서 돈다(채널 정본은 [ci-gates](../dev-guide/ci-gates.md)). 자동 채널에
확률적 red 가 상주하면 이후 작업이 진짜 회귀를 "또 그 flake" 로 넘기게 된다 — 실제로 한
라운드에 세 작업 트랙이 같은 테스트들을 서로 모르고 각자 만나 각자 판별했다.

부류는 셋이다. 경합 대상이 다르고, 그래서 처방이 다르다.

- **형태 A — 프로세스 내 전역 공유 상태.** `static` 전역(`RwLock`/`Mutex`/`OnceLock`),
  프로세스 환경변수(`std::env::set_var`), 프로세스 현재 디렉토리(`set_current_dir`) 처럼
  **한 프로세스 안에서 하나뿐인 것**을 여러 테스트가 reset/set 한다.
- **형태 B — 프로세스 밖 OS 자원.** 포트·파일경로·소켓처럼 **프로세스 밖에서 유일한
  것**을 테스트가 잡았다 놓았다 다시 잡거나, 고정 이름을 여러 프로세스가 공유한다.
- **형태 C — 부하 의존 타임아웃.** 공유 상태 경합이 아니라 러너가 바쁘면 고정 타임아웃을
  못 지키는 것. 원인 축이 달라 본 ADR 의 범위 밖이며 별도로 추적한다.

### 자연실험 — 같은 레포 안에서 이미 대조된 결과

이 저장소에는 형태 A 의 표준 처방을 정당화하는 **자연실험**이 이미 있다.

- `src/core/surface_registry/webview_kind.rs` 의 `WEBVIEW_KINDS` 와
- `crates/tasty-themes/src/plugin_defaults.rs` 의 `USER_DEFINED_KINDS` 는

**정확히 같은 타입**(`RwLock<Option<HashSet<String>>>`)이고, 둘 다 두 테스트가
`reset` 헬퍼로 전역을 비운 뒤 등록·조회한다. 유일하게 다른 변수는 **테스트 직렬화
`Mutex` 의 유무**다: `plugin_defaults` 는 `reset()` 이 `static TEST_LOCK: Mutex<()>` 를
잡아 반환하고 두 테스트가 그 가드를 함수 끝까지 유지한다. `webview_kind` 는 그 락이
없다. 그리고 `webview_kind` 만 확률적으로 실패한다. 같은 shape 가 한쪽은 터지고 한쪽은
안 터지는 이유가 그 락 하나로 좁혀진다.

이 대조가 성립하려면 `plugin_defaults` 가 안 터지는 이유가 **정말로 그 락**이어야 한다
— 락 밖에 그 전역을 만지는 다른 경로가 있으면 대조가 무너진다. 감사 결과 그 전역
(`PLUGIN_DEFAULTS`/`USER_DEFINED_KINDS`)을 만지는 프로덕션 함수는
`add_plugin_surface_default`/`record_user_defined_surface_kinds`/`apply_plugin_defaults_to`
셋이고, 같은 테스트 바이너리(`tasty-themes` lib) 안에서 이들을 타는 테스트는
`plugin_defaults` 모듈의 두 개뿐이다(둘 다 락 안). 같은 크레이트의 `state.rs` 테스트는
`resolve()` 만 부르는데 `resolve` 는 그 전역을 만지지 않는다(ctx 값만 읽는다). 따라서
락 적용범위에 빈틈이 없고 대조는 유효하다.

### 락은 "잡는 쪽끼리만" 막는다 — 형태 A 의 하위형태

직렬화 `Mutex` 가 있다고 안전한 것이 아니다. 락은 **그 락을 잡는 코드끼리만** 줄
세운다. 어떤 테스트가 락을 안 잡고 같은 자원을 만지면 — 특히 그 자원을 읽는 **프로덕션
경로**를 간접 호출하면 — 락은 아무것도 막지 못한다. 관측된 형태:
`crates/tasty-host-plugin` 의 env-var 락(`HOME_ENV_LOCK`)은 그 가드를 지나는 소수의
테스트끼리만 `HOME` 을 직렬화하는데, 같은 바이너리의 다른 테스트가 프로덕션
`tasty_home()` 경로로 `HOME` 을 읽으면 가드가 `HOME` 을 바꿔 둔 창 안에서 남의 홈을
읽을 수 있다. 결함은 "락 부재" 가 아니라 **락 적용범위**이고, 검색으로도 "직렬화 장치
없음" 패턴으로도 안 잡힌다.

## Decision

flake 를 위 부류로 판정하고 부류별 표준 처방을 적용한다.

**형태 A (프로세스 내 전역 공유 상태) — 모듈 전용 `static TEST_LOCK: Mutex<()>` 로
직렬화한다.** reset+mutate+assert 시퀀스를 하나의 임계구역으로 묶어, `reset` 헬퍼가
락 가드를 반환하고 각 테스트가 그것을 함수 끝까지 유지한다. 이것은 이미 이 저장소가
네 곳(`plugin_defaults` · `method_meta` 의 `PLUGIN_PREFIXES` · `webhook/registry` 의
`STATE` · env-var 락들)에서 쓰는 in-repo 패턴이며, 외부 크레이트(`serial_test`) 의존이
필요 없다.

- **하위형태(락 적용범위 gap)**: 그 자원을 락 밖에서 만지는 경로(특히 프로덕션 read 를
  간접 호출하는 다른 테스트)가 있으면, 처방은 **락을 넓히는 것이 아니라 자원 자체를
  테스트-로컬로 만드는 것**이다 — 전역/env 대신 값을 인자로 주입하거나, 그 자원을 읽는
  코드가 테스트마다 자기 인스턴스를 쓰게 한다. 락으로 못 덮는 read 경로가 남는 한
  락 확대는 끝나지 않는다.

**형태 B (프로세스 밖 OS 자원) — 하위형태별로 다르다.**

- **정방향(놓은 자원을 다시 잡음)**: 자원을 **놓지 않는다.** 포트를 고르는 헬퍼는
  리스너를 드롭하지 않고 잡은 채 넘기고, 테스트는 그 리스너가 살아 있음을 검증한다 —
  drop→rebind 창 자체가 사라진다. 프로덕션 시그니처가 "번호만" 을 요구해 리스너를 잡을
  수 없으면, 이미 이 저장소에 있는 lease+retry 선례(`tests/webhook_common` 의
  `PortLease` + 재시도)를 적용한다.
- **역방향(자원이 없어야 함, 예: 연결 거부 기대)**: 놓지-않기가 성립하지 않는다(닫힌
  포트가 필요하니까). 검증 대상이 실제 OS 소켓 동작이 아니라 **에러 변환 로직**이면
  실제 포트 없이 그 매핑만 검증하도록 바꾼다. 그럴 수 없으면 재시도 또는 단정 약화를
  쓰고 그 이유를 남긴다.
- **고정 경로/이름 공유**: 고정 이름 대신 **프로세스-유일 이름**(tempfile 크레이트,
  pid+nonce 접미사)을 쓴다.

**형태 C 는 본 ADR 에서 고치지 않는다.** 원인 축(여유 부족 vs 경합)이 다르다. 별도로
추적한다.

### 적용 채널별 우선순위

고쳐야 할 진짜 경합/TOCTOU 는 전부 `--lib --bins` 소속이라 양 자동 채널에 상주한다 —
main push 마다 두 자동 잡에서 도니 "상시 red" 이고 최우선이다. `tests/*.rs` 통합 테스트
소속(예: 고정경로 scrollback, webhook 하네스)은 **컴파일 축만 자동이고 실행 축은
수동**이다: check-windows/check-headless 의 `clippy --workspace --all-targets` 와
check-macos 의 `cargo check --workspace` 가 이들을 컴파일하므로 컴파일을 깨는 변경은
자동으로 잡히지만, **flake(실행 시의 확률적 실패)는 컴파일 축에 걸리지 않는다.** 그
실행 축(전체 스위트 = 수동 트리거 잡)은 수동을 넘어 사실상 휴면이다 — 잡 이력 조회
범위에서 마지막 실제 실행이 약 3개월 전이고 이후 회차는 조건상 skip 되어, 성공 기록이
남아 있지 않다. 따라서 이 소속의 flake 는 우선순위가 낮고, 이미 완화된 것은 방침 적용
여부만 기록한다.

## Consequences

- **얻은 것**: 자동 채널의 상시 red 가 사라져, 이후 작업이 진짜 회귀를 flake 로 넘기지
  않는다. 부류 판정 기준과 처방이 하나로 서서, 같은 부류의 새 flake 를 매번 다시
  진단하지 않는다.
- **잃은 것**: 형태 A 의 직렬화 락은 그 전역을 만지는 테스트들이 병렬로 못 돈다 —
  다만 대상이 소수라 전체 병렬도에 대한 영향은 무시 가능하다(아래 측정).
- **운영 비용**: 새 테스트가 같은 형태를 다시 들이지 않게 소스 스캔 가드로 강제한다
  (아래 "적용 강제").

## Alternatives Considered

- **`--test-threads=1` 로 전량 직렬화** — 쉬운 답이지만 기각한다. 이 방침이 실제
  적용되는 채널은 `--lib --bins`(check-windows·check-headless)이므로 비용도 그 채널에서
  매긴다. 문제 테스트만 `TEST_LOCK` 하면 나머지 병렬도는 그대로인데, 전역 직렬화는 그
  채널의 전체 실행을 직렬로 만든다. 실측(`cargo test --workspace --lib --bins --locked`,
  같은 커밋, warm compile 후 각 1회): 기본 스레드 **73s** vs `--test-threads=1` **89s**
  (+16s, **+22%**). 둘 다 test result 52줄·0 failed 로 동일 모수다. 다만 두 회차의 러너
  부하가 달랐다 — 기본 회차 loadavg ~7.4–7.7, 직렬 회차 7.68→4.81(측정 중 하락). 직렬
  회차가 더 한가한 구간을 일부 탔는데도 더 느렸으므로 **+22% 는 페널티의 하한**이다(부하가
  통제되지 않아 정확한 배수는 단정하지 않는다). "배증" 은 근거 없는 과장이었고 실측은
  +22% 하한이지만, 방향은 명확하다: 전역 직렬화는 이 채널을 유의하게 느리게 한다. 반면
  대상 flake 는 소수라 그것만 `TEST_LOCK` 하면 이 페널티 없이 경합을 없앤다.
- **`serial_test` 크레이트 도입** — 기각. 이미 in-repo `TEST_LOCK: Mutex<()>` 패턴이
  네 곳에서 동작하며, 외부 의존을 늘릴 이득이 없다.
- **형태 A 를 전역 제거로 근본 해결**(전역을 registry 값으로 이동) — 대상에 따라
  호출부가 매 프레임 조회하는 곳(`sync_webviews`)까지 바꿔야 해 범위가 크다. 직렬화가
  경합을 실제로 없애므로 근본 재설계는 별도 결정으로 미룬다.

## Reconsideration Triggers

- 형태 A 직렬화 후에도 같은 부류의 새 flake 가 자동 채널에서 관측되면 — 락 적용범위
  gap 을 의심하고 자원 테스트-로컬화로 전환한다.
- `hook_handler` 의 전역 레지스트리에 clear-all 류 헬퍼가 추가되면 — 현재는 unique-id
  스코프로 간섭이 없지만 destructive reset 이 생기는 순간 형태 A 진짜 경합이 된다.
- `--lib --bins` 직렬화 비용이 측정상 유의하게 커지면(위 측정 대비) — 대상 테스트를
  줄이거나 전역 제거를 재고한다.

## 적용 강제 (가드)

새 테스트가 같은 형태를 다시 들이는 것을 소스 스캔 가드로 막는다. 가드는 판정을 순수
함수로 뽑고, 면제마다 그것을 겨냥한 변이와 의도된 false negative 를 유닛 테스트로
고정하며, `crates/*/src/` 또는 루트 `src/` 의 `#[cfg(test)] mod` 로 두어 양 자동 채널
(check-windows·check-headless)에서 실행되게 한다. 상세는
[test-isolation](../dev-guide/test-isolation.md).

**배치만으로 "양 자동 채널"은 성립하지 않는다 — 이름으로 확인한다(양방향).** `#[cfg(test)]
mod` 에 둔 사실은 가드가 두 채널 모두에서 돈다는 보장이 아니다. 가드가 `#[cfg(feature =
"gui")]` 아래 있으면 check-headless(`--no-default-features`)의 컴파일 단계에서 통째로
사라져 그 잡에서 **부재**가 되고, 부재는 실패할 수 없으므로 잡은 초록인 채 가드가 한 번도
돌지 않는다. 반대로 `#[cfg(not(feature = "gui"))]` 아래 있으면 check-windows(기본
`--lib --bins`)가 못 본다 — **함정은 대칭이다.** 따라서 가드가 실제로 두 채널에서 도는지는
잡 초록이 아니라 두 조합 각각의 실행 목록에 그 가드 **이름**이 뜨는지로 판정한다:

```
cargo test --workspace --lib --bins --locked -- --list | grep <가드 이름>
cargo test --workspace --lib --bins --no-default-features --locked -- --list | grep <가드 이름>
```

둘 다에서 이름이 나와야 자동 채널이 둘이다. 첫째에만 나오면 `not(gui)` 쪽에 걸려
check-headless 가, 둘째에만 나오면 `gui` 쪽에 걸려 check-windows 가 그 가드를 영영 못 본다.
가드 배치를 보고할 때는 이 두 조합 실측과 cfg 의존 여부를 함께 적는다 — 배치 위치만으로는
채널 수가 나오지 않는다.

이 부재는 드문 구석 사례가 아니다: 두 조합 `--list` 이름 차집합 전수 측정에서 기본 조합에만
있고 헤드리스에 없는 테스트가 949 건(기본 목록의 약 5 분의 1), 반대로 헤드리스에만 있는 것이
4 건이다. 이 949/4 는 이름 dedup 여부와 무관하다 — 동명 타깃은 공통 집합에만 앉아 차집합을
건드리지 않는다(항등식을 인용할 때만 원시/dedup 기준을 밝히면 된다).

**사정거리는 가드가 무엇을 보는가로 갈린다.** 컴파일된 심볼을 참조하는 가드는 심볼이 cfg 로
사라지면 판정 자체가 사라진다 — 949 의 실제 사정거리가 여기다. 반면 디스크의 텍스트를 읽는
소스 스캔 가드는 스캔 대상 파일이 cfg 와 무관하게 디스크에 있어 **애초에 면역**이다. 단
스캔 루트를 런타임 `read_dir`/`read_to_string` + `CARGO_MANIFEST_DIR` 로 얻을 때만 그렇다:
`include_str!` 나 cfg 게이트된 상수에서 스캔 경로를 얻으면 경로가 같이 갈려 면역이 깨진다.

**이름은 존재를 보이고, 스캔 모집단 앵커는 "같은 것을 본다"에 다가간다 — 강도가 셋이다.**
이름이 양 조합에 뜨는 것은 가드가 존재함만 보인다. 스캔 모집단이 cfg 로 갈리지 않았음을
못박는 앵커는 강도가 셋이다:

- **스캔 파일 하한**(`files.len() >= FLOOR`): 스캔 루트가 통째로 깨진 사고만 잡는다. 하한
  위로 부분 누락되면 못 잡는다.
- **정확한 허용 건수**(특정 파일의 위반 수 == N): 그 파일들을 양쪽에서 같은 수로 본다는
  것까지. 위반 0 건인 파일이 누락되면 offender 목록이 안 움직여 신호가 없고, 같은 수로
  상쇄되는 교체도 못 잡는다.
- **스캔 모집단 집합 동등**(`BTreeSet` 스냅샷 비교): 추가·삭제를 양방향으로 잡아 모집단이
  실제로 같음을 못박는다.

하한 < 건수 고정 < 집합 동등. **본 ADR 이 새로 두는 스캔 가드는 집합 동등으로 못박는다** —
하한과 건수 고정은 부분 누락을 놓치므로 cfg 불변성의 증거로는 약하다.

`shadow_policy_guard` 는 텍스트 스캔 면역의 실례다: 스캔 루트가 `CARGO_MANIFEST_DIR/../..`
런타임 `read_dir` 이고 이름이 두 조합 모두 10 건 뜬다(실측). 다만 그 모집단 앵커는 하한
(`SCAN_FILE_FLOOR`)과 정확 건수(`allowed_total == 1`)까지라 위 계층에서 집합 동등 아래에
있다 — cfg 배제 파일을 읽는다는 실례로 인용하되 스캔 집합 전체의 동등 증거로는 쓰지 않는다.

**등급 주의.** "소스 스캔이 cfg 로 배제된 파일에 닿는다"는 측정된 사실이다(허용 건수 앵커의
양 조합 통과). 그러나 "cfg 게이트 안쪽에 진짜 위반을 심어 헤드리스 조합이 그것을 잡는다"는
아직 재현된 적 없는 **합성**이다 — 기전은 같아도 관측이 아니다. 가드의 cfg 안전성을 보고할
때 이 둘을 뭉뚱그리지 않는다.
