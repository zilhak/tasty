# ADR-0046: 검증 결과에는 검사 범위와 실패 원인을 구분할 근거를 남긴다

- **Status**: Accepted
- **Date**: 2026-09-24
- **Tags**: testing, verification, diagnostics
- **Group**: rules

## Context

테스트가 통과해도 잘못된 바이너리를 실행했거나 검사할 대상을 읽지 않았다면 근거가 되지 않는다.
실패 역시 코드 결함, 실행 환경, 준비되지 않은 의존성을 구분해야 수정할 대상을 알 수 있다.
특히 벽시계 시간 하나로 동시성이나 이벤트 발생을 판단하면 머신 부하가 결과에 섞인다.

## Decision

검증은 무엇을 검사했는지와 의도한 결함을 실제로 검출하는지를 함께 확인한다.
정상 실행, 의도적으로 결함을 넣은 실행, 복구 뒤 정상 실행을 구분해서 기록한다.

변경 여부는 가능한 한 값이나 이벤트로 검사한다.
두 작업의 동시성은 시작·종료 순서로, 실행하지 않아야 할 명령은 실제 호출 여부나
구별되는 오류 값으로 확인한다. 시간이 제품 요구사항일 때만 지연 상한을 단언한다.

지연 검사의 대조군은 같은 자원을 사용하면서 검사 대상 코드 경로는 지나지 않아야 한다.
자원 부하에는 반응하고 대상 코드의 지연에는 반응하지 않는지 각각 확인한다.
평소 변동이 너무 크거나 필요한 자원을 측정하지 못하면 원인을 판정할 수 없다고 보고한다.
CPU 대조군으로 디스크나 IPC 지연까지 설명하지 않는다.

실패 메시지에는 원인을 구분하는 관측값과 다음 진단에 필요한 전제를 넣는다.
PTY 종료 실패라면 자식 생존 여부, 종료 감지 진행 상태, 출력 꼬리를 함께 남긴다.
PTY에 되비친 입력은 자식이 실행됐다는 증거로 쓰지 않는다.

## Consequences

실패 보고를 받은 사람이 같은 원인을 다시 조사하는 일을 줄일 수 있다.
다만 대조군과 진단 코드도 잘못될 수 있으므로 그것들이 구분할 수 있는 범위를 명시해야 한다.

이벤트 대기의 타임아웃은 영원히 기다리는 일을 막기 위한 것이다.
정상 완료 시간과 상한 사이에 실제 표본이 없이 상한만 늘리면 원인을 해결하지 못한다.
로그인 셸과 초기 입력 전달을 검사하는 테스트를 단순 종료 프로그램으로 바꾸면
검사 범위가 줄어든다는 점도 함께 판단해야 한다.

## Alternatives Considered

- 실패할 때마다 재시도하면 간헐 결함의 빈도와 근거가 사라질 수 있다.
- 전역 부하 수치만으로 테스트를 건너뛰면 어떤 자원이 부족한지 구분하지 못한다.
- 진단 한계를 문서에만 적고 단언을 유지하면 판정 불가능한 값으로 빌드를 실패시킬 수 있다.
- 시간 비교를 없앨 수 있는 검증에 대조군을 추가하면 복잡성만 늘어난다.

## Reconsideration Triggers

대조군이 제품 코드 변경에 영향을 받거나 필요한 부하에 반응하지 않으면 사용을 중단하고 다시 선정한다.
제품이 진행 카운터 등 직접 관측값을 제공하면 시간에 의존한 검증을 바꾼다.
