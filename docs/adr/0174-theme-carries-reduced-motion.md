# ADR-0174: 접근성 "모션 감소" 는 `Theme` 이 실어 나르고, 위젯의 기본값이 그것을 읽는다

- **Status**: Accepted
- **Date**: 2026-09-05
- **Tags**: accessibility, theme, motion, widgets, defaults

## Context

설정에는 `accessibility.reduced_motion` 이 있고, 설정 창에 실제로 켤 수 있는 스위치가
있으며, 그 설명은 "활성 시 모든 UI 페이드/슬라이드 애니메이션을 즉시 끝낸다" 라고
약속한다.

그런데 이 값이 위젯에 닿는 방식이 **호출부가 인자로 넘기는 것** 하나뿐이었다.
`Spinner` 는 `reduced_motion(bool)` 빌더를, `status_dot` 은 함수 인자를 갖고 있었고,
그리는 쪽은 그것을 받으면 정지 fallback 으로 갈 준비가 되어 있었다. 문제는 넘기는
쪽이다 — 레포 전체에서 `Spinner` 를 만드는 자리가 17 곳인데 `.reduced_motion(` 호출은
**0 이었다.** 기능은 구현돼 있고 문서도 있고 설정도 있는데, 설정을 켜도 스피너는
계속 돌았다. 값을 넘기는 것이 각 자리의 기억에 달려 있으면, 자리가 늘어날수록 잊는
자리가 늘어난다.

같은 형태가 이미 한 번 사고를 냈다. 전역 `Theme` 설치 함수가 `ui_zoom` 을 인자로
받는 형태였고, 그것을 빠뜨린 install 이 전역 `Theme` 을 배율 1.0 으로 되돌려 다른
윈도우의 UI 가 줄어들었다. 그 사유가 지금도 호출부 주석에 남아 있다. 즉 이건 한
위젯의 실수가 아니라 **"설정값을 인자로 나르는" 형태 자체의 실패 양식**이다.

egui 에는 `prefers-reduced-motion` 매체 질의가 없다(0.31 기준 확인). 그래서 이
판정은 어차피 tasty 가 직접 해야 한다.

## Decision

`Theme` 에 `reduced_motion: bool` 필드를 싣고, **모션을 쓰는 위젯의 기본 동작이 그
값을 읽는다.** 위젯 빌더/인자는 남기되 그 의미를 "설정을 무시하는 override" 로
바꾼다.

`Theme` 인 이유는 그리는 코드가 `Theme` 없이는 그릴 수 없기 때문이다 — 색·치수를
받으려면 이미 `&Theme` 을 들고 있으므로, 새 위젯이 생겨도 이 값에 접근하지 못하는
경우가 없고 "넘기는 것을 잊는" 자리가 원리적으로 생기지 않는다.

값을 채우는 자리는 `Settings::theme_runtime()` 하나로 모은다. 이 함수는 설정에서
오는 런타임 값(`ui_zoom`, `reduced_motion`)을 `ThemeRuntime` 한 덩이로 내고, 전역
`Theme` 설치 경로 4 곳이 전부 그 덩이를 그대로 넘긴다. 값이 하나 더 늘어도 호출부
모양은 안 변한다.

override 를 남기는 근거는 실제 사용처가 있기 때문이다 — 갤러리 specimen 은 실행 중인
설정과 무관하게 회전본과 정지본을 **나란히** 보여야 한다. 제품 화면에는 override 를
쓸 자리가 없다(현재 0 곳).

## Consequences

- **얻은 것**: 설정이 실제로 동작한다. 스피너 17 자리가 한 줄도 안 고치고 설정을
  따르게 됐고, switch-overlay 페이드와 모달 흔들기도 같은 값을 읽는다. 새로 추가되는
  모션 위젯은 아무것도 안 해도 기본이 옳다.
- **얻은 것**: `ui_zoom` 을 빠뜨려 배율이 리셋되던 실패 양식이 같이 닫혔다 — 이제
  install 호출부가 값을 하나씩 고르지 않는다.
- **잃은 것**: `Theme` 이 색·치수가 아닌 값을 하나 갖는다. `Theme` 의 정의가 "디자인
  토큰 묶음" 에서 "그리는 데 필요한 것 묶음" 으로 조금 넓어졌다.
- **운영 비용 / 유지 부담**: `Theme::with_colors*` 로 직접 만든 인스턴스는 이 값을
  `false` 로 갖는다(테스트 · 갤러리 · plugin 프로세스). host 의 전역 설치 경로만 설정을
  싣는다. plugin 프로세스는 `ThemeWire` 에 이 값이 없어 아직 설정을 모른다 — 현재
  plugin 이 그리는 스피너가 0 이라 잠재 구멍이고, 닫으려면 wire 필드 1 개와 plugin 쪽
  재구성 지점들을 함께 고쳐야 한다.

## Alternatives Considered

- **A: 호출부 5(실측 17) 곳에 `.reduced_motion(...)` 을 붙인다** — 지금 도는 스피너는
  멈추지만 함정을 그대로 재생산한다. 열여덟 번째 자리가 또 잊는다. 이번에 발견된 것이
  바로 그 형태의 결과물이다.
- **B: 붙이는 것을 강제하는 가드(테스트)를 만든다** — 두 번째 판정을 만드는 것이다.
  첫 번째 판정(기본값)이 구조적으로 옳으면 가드가 필요 없다. 가드는 기본값을 옳게
  만들 수 없을 때의 차선이다.
- **C: 전역 함수(`reduced_motion()`)를 위젯이 직접 읽는다** — `Theme` 을 안 건드려도
  되지만, 위젯 크레이트가 설정 크레이트에 의존하게 되거나 또 하나의 전역이 생긴다.
  이미 `Theme` 이 전역으로 배달되고 있으므로 운반 수단을 늘릴 이유가 없다.
- **D: OS 의 `prefers-reduced-motion` 을 읽어 설정을 대체한다** — 대체가 아니라 입력
  하나가 느는 것이다. OS 값을 읽게 되더라도 그것은 `Settings::theme_runtime()` 이
  합성할 입력이지, 이 결정의 형태를 바꾸지 않는다. 그래서 이 ADR 과 독립이고, 지금은
  안 읽는다.

## Reconsideration Triggers

- `Theme` 이 실어야 하는 "색·치수가 아닌 값" 이 셋 이상으로 늘어난다 — 그때는 별도
  운반체(예: `Theme` 옆의 런타임 컨텍스트)를 분리할 값이 생긴다.
- plugin 프로세스가 모션을 쓰는 위젯을 그리기 시작한다 — 위 "운영 비용" 의 잠재
  구멍이 실재가 되므로 `ThemeWire` 확장을 결정해야 한다.
- override 사용처가 갤러리 밖으로 늘어난다 — 제품 화면이 설정을 무시해야 하는
  사유가 생겼다는 뜻이므로, override 의 의미를 다시 정의해야 한다.
- egui 가 `prefers-reduced-motion` 을 1 급으로 노출한다.
