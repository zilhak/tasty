# ADR-0158: plugin CLI 이름과 호스트 명령의 충돌은 등록 시점에서만 판정한다

- **Status**: Accepted
- **Date**: 2026-09-05
- **Tags**: plugin, cli, manifest, guards, layering, adr-0140, adr-0105

## Context

plugin 은 매니페스트 `[[contributes.cli]]` 로 top-level 명령 이름을 선언한다. 그 이름이
호스트 명령과 겹치면 무슨 일이 일어나는지가 **두 자리**에 적혀 있었다.

- `crates/tasty-plugin-manifest` 의 `is_reserved_cli_name` — 손으로 적은 이름 목록.
  걸리면 매니페스트 자체가 거절되어 **plugin 이 뜨지 않는다.**
- `crates/tasty-cli` 의 `dynamic.rs` 모듈 주석 — *"정적 우선, plugin 이 호스트 명령을
  가릴 수 없다."* 등록 쪽에는 대조하는 코드가 없었고, 이 문장은 **파싱 순서**의 성질을
  등록의 성질처럼 적은 것이었다.

### 실측한 것

2026-09-05, Linux. 서로 다르게 쓴 매처 둘이 같은 수를 냈다.

| 무엇 | 수 |
|------|----|
| 호스트 top-level CLI 명령 | 36 |
| `is_reserved_cli_name` 손목록 | 18 |
| 호스트 명령인데 목록에 없는 이름 | 22 |
| 목록에 있는데 명령이 없는 이름 | 4 |

그 22 중 하나(`terminal`)를 선언한 최소 매니페스트를 실제로 설치해 두 프로필에서 돌렸다.

| 프로필 | 관측 |
|--------|------|
| release | 패닉 없음. `tasty terminal --help` 는 호스트 명령이 받는다. plugin 쪽 명령은 **도달 불가**, 경고도 에러도 없음 |
| debug | `tasty --help` 와 **모든 plugin 명령**이 `Command tasty: command name 'terminal' is duplicated` 로 패닉 |

즉 손목록의 22 개 구멍은 release 에서는 조용한 죽은 등록이고 debug 에서는 **CLI 전체를
못 쓰게 만드는 결함**이었다. plugin 하나의 이름 하나가 다른 모든 plugin 의 CLI 까지
같이 죽였다.

### 왜 손목록이 늙을 수밖에 없는가

`tasty-plugin-manifest` 는 `tasty-cli` **아래** 크레이트다(`tasty-cli` 가 매니페스트를
읽는다). 그래서 매니페스트 검증 시점에 실제 clap 명령 집합을 볼 방법이 없다 — 그
자리에 놓을 수 있는 것은 손목록뿐이고, 손목록은 호스트 명령이 늘 때 따라 늘지 않는다.
실제로 18/36 에서 멈춰 있었다.

## Decision

**충돌 판정은 등록 시점 한 자리에만 둔다.**

- `tasty-cli` 의 `build_augmented_cli` 가 clap 명령 트리에서 **이름과 모든 alias 를
  그때그때 도출**해, 겹치는 plugin CLI 이름을 등록하지 않고 경고한다.
- `is_reserved_cli_name` 과 그것을 부르던 매니페스트 검증 분기를 **삭제한다.**
  매니페스트는 이제 호스트 명령 이름을 이유로 거절하지 않는다.

목록을 18 에서 36 으로 늘리는 선택지는 택하지 않았다. 그것은 두 번째 진실의 원천을
키우는 일이고, 다음에 호스트 명령이 하나 늘면 같은 자리에서 같은 방식으로 다시 늙는다.

## Consequences

- **서드파티가 잃는 기능이 0 이다.** plugin CLI 매칭은 정적 파싱이 `InvalidSubcommand`
  로 실패했을 때만 진입한다(`src/boot/cli_routing.rs`). 정적이 아는 이름은 애초에 그
  경로에 닿은 적이 없으므로, 등록을 막는 대상은 **release 에서 이미 도달 불가였던
  이름뿐**이다.
- 기존 18 개 이름의 취급이 **거절 → 경고 후 그 이름만 skip** 으로 바뀐다. 지금까지는
  이름 하나 때문에 plugin 전체가 뜨지 못했는데, 이제 plugin 은 뜨고 그 CLI 이름만
  못 쓴다 — 저자에게 더 관대한 방향이다.
- 매니페스트 검증만 보는 소비자(`tasty plugin doctor` 등)는 이 충돌을 더 이상 설치
  시점에 알려주지 않는다. 대신 그 plugin 이 설치된 동안 CLI 호출마다 stderr 에 경고가
  뜬다. 판정이 늦어지는 대신 **완전해졌다** — 36 개 전부와 alias 까지 본다.
- 회귀는 손목록에 우연히 들어 있던 몇 개가 아니라 **실제 명령 집합 전체**를 하나씩
  흉내 내 보고, clap 이 debug 에서 패닉하던 그 경로(`Command::debug_assert`)를 직접
  밟는다. 명령이 늘면 그 명령도 자동으로 대상이 된다.

## Alternatives considered

- **손목록을 36 으로 채운다** — 그 순간은 맞지만 갱신 의무가 남는 자리를 그대로 둔다.
  이 ADR 이 고치려는 것이 바로 그 자리다.
- **손목록을 남기고 `⊇ 실제 명령 집합` 가드를 붙인다** — 목록을 `pub` 으로 열어야
  가드가 볼 수 있다. 없애려는 것을 유지하려고 API 표면을 넓히는 셈이라 택하지 않았다.
- **release 에서도 에러로 만든다** — 지금까지 조용히 무시되던 등록이 갑자기 실패가
  된다. 도달 불가였던 것을 막는 데 그치는 이번 결정과 달리 관측되는 동작이 바뀐다.

## 재검토 조건

- 매니페스트 검증 시점에 실제 명령 집합을 얻을 방법이 생기면(예: 명령 집합을 두
  크레이트 아래의 데이터로 내리면) 판정을 다시 앞으로 당길 수 있다.
- 22 개 중 어느 이름이든 release 에서 **실제로 동작하던** 것이 발견되면 그것은 이
  결정의 전제("도달 불가였던 것만 막는다")를 깨므로 별도 결정이 필요하다.
