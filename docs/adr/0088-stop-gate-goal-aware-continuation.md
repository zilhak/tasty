# ADR-0088: Stop-훅 게이트는 세션 goal 을 근거로만 자율 계속-진행을 지시한다

- **Status**: Accepted
- **Date**: 2026-08-30
- **Tags**: claude-plugin, stop-hook, gate, memory, goal, i18n, autonomy

## Context

host 기본 게이트(`continue-checklist`) 본문의 3번 항목은 이렇게 적혀 있었다.

```
3. 후속 작업이 남아 있는가? 남아 있다면 무엇인지 밝혀라. 없다면 없다고 명시적으로 밝혀라.
```

이것은 **공시(disclosure) 요구**지 **완료 요구**가 아니다. 에이전트가 "후속 작업 A, B 가
남았습니다" 라고 서술하는 순간 3번은 충족되고, 본문 마지막의 "세 가지 모두 충족됐다면
센티넬을 포함해라" 조건이 성립해 센티넬을 출력하고 정상 종료한다. 판정 코드는 센티넬
유무만 보므로(`checklist.rs` 의 `decide`) 게이트는 "정말 끝났는가" 를 판정할 수단이 없고
그 판단을 통째로 본문 문구에 위임하고 있다. **현재 동작은 문구대로의 정확한 결과이며
코드 버그가 아니다.**

구조적으로 3번은 게이트를 약화한다. 1·2번은 재작업을 유도하는데 3번만 "남은 걸 말하면
끝내도 된다" 는 합법적 조기 탈출구를 준다 — 쉬운 절반만 하고 나머지를 "후속" 으로
선언하는 것이 1번(요청 충족)을 우회하는 정당한 경로가 된다.

한편 [ADR-0083](0083-stop-gate-named-registry.md) 이 게이트를 (본문·센티넬·상한) 3요소를
이름으로 등록하는 프리미티브로 일반화해 두었다. 그래서 이 문제의 해결책은 host 기본
게이트 하나만 고치는 것으로 끝날 수 없다 — 등록 게이트도 같은 능력을 쓸 수 있어야 하고,
동시에 등록 게이트 저자의 본문에 예고 없이 남의 문장이 붙어서도 안 된다.

## Decision

게이트가 **세션에 설정된 goal 이 있을 때만** 자율 계속-진행을 지시한다. goal 은
surface 스코프 memory 오버레이(`tasty memory goal`, `memory.goal_get`)에서 온다.

- **판정 근거는 훅이 직접 읽는다.** 본문에 "goal 을 조회해라" 라고 적어 모델에게 맡기지
  않는다. 게이트의 존재 이유가 "모델의 자기판단을 믿지 않는 것" 인데 그 판단을 다시
  모델에게 돌려주는 셈이 되고, 조회를 건너뛰어도 아무도 모른다. 훅이 읽어 `reason` 에
  넣으면 모델이 반드시 보고, 모델 쪽 tool call 은 0 이며, goal 유무 분기를 훅이
  결정적으로 처리할 수 있다.
- **주입 경로는 본문의 `{{goal}}` placeholder — opt-in 규약이다.** 본문에 토큰이 있을
  때만 훅이 그 자리를 치환한다. goal 있음 → goal 절(`claude.checklist.goal_clause`)로
  치환, goal 없음 → 토큰이 있던 줄째 제거(나머지는 바이트 단위로 그대로), 토큰 미포함
  본문 → 완전 무변화.
- **goal 부재 시 기존 동작을 유지한다. 3번 항목 문구 자체는 손대지 않는다.** goal 이
  없다는 것은 사용자가 자율 진행 범위를 선언하지 않았다는 뜻이므로, 계속-진행을 지시할
  근거가 없다.
- **계속-진행 대상은 "사용자 판단이 불필요하고 스스로 진행 가능한 것" 으로 좁힌다.**
  판단이 필요한 항목은 멈추므로 자기제한적이고, 우선순위 결정권을 에이전트가 가로채지
  않는다.
- **조회 실패는 goal 부재와 동일하게 취급한다.** 호스트 IPC 오류·surface id 부재 등
  어떤 실패도 에러로 올리지 않는다 — 이 모듈의 "불확실하면 통과/무시" 방침 그대로다.
  goal 조회 하나 때문에 세션이 종료 불가가 되면 안 된다.

### 왜 goal 이 발산을 막는가

"후속 작업이 있으면 무조건 계속하라" 로 바꾸는 안은 성립하지 않는다. 모델은 후속
작업(테스트 추가·리팩터링·문서·인접 개선)을 무한히 생성할 수 있어 판정이 발산하고, 매 턴
라운드 상한 백스톱에 도달해 게이트가 "N턴 강제 연장기" 로 변질된다. 이는 ADR-0083 이
등록 본문에 대해 `BodyMissingSentinel` 로 차단하려던 변질 모드와 같은 종착지다(센티넬이
있어도 도달 불가능하면 없는 것과 같다). 또한 요청 범위 밖 작업을 에이전트가 스스로
실행하게 되어 사용자의 우선순위 결정권을 침해한다.

goal 은 사용자가 선언한 **유한한 문장**이라 충족 판정이 수렴하고, 동시에 범위 경계
역할을 해서 goal 밖 후속 작업은 계속-진행 사유가 되지 않는다.

### 권한과 쓰기 주체

goal 은 CLI(`_host`)가 쓰고 plugin 은 **읽기만** 한다. regular memory 영역의 read 는
caller 무관 전체를 보므로 `memory.read` 권한이면 충분하고, plugin 이 `_host` 소유 entry 를
쓰려 하면 어차피 `OwnedByOther` 로 거부된다 — 쓰기 경로를 만들지 않는 것이 설계이자
집행이다.

### surface id 전달

훅 명령 문자열은 바꾸지 않는다. `checklist_hook_args` 에 `surface`(u32, optional) 인자를
선언해 두면 CLI 층이 미지정 시 `TASTY_SURFACE_ID` env 로 채운다. 따라서 `--surface` 가
없던 시절 설치된 훅 명령도 그대로 goal 을 읽는다 — ADR-0083 이 `--gate` 에서 지킨
하위호환 성질과 같다. 훅 명령이 애초에 `TASTY_SURFACE_ID` 가드 안에서만 실행되므로 env 가
빈 경우는 발화하지 않는다.

## Consequences

- **얻은 것**: 3번 항목의 조기 탈출구가 goal 이 있는 세션에서 닫힌다. 게이트가
  "무엇을 향해 계속할 것인가" 라는 유한한 기준을 갖게 되어, 계속-진행 지시가 발산하지
  않는다. placeholder 규약 덕에 등록 게이트도 같은 능력을 opt-in 으로 쓴다.
- **잃은 것**: goal 을 설정하지 않은 세션에서는 아무것도 달라지지 않는다 — 이 ADR 의
  효과를 보려면 사용자가 goal 을 선언하는 절차가 하나 늘어난다. 계속-진행 여부의
  판정 자체는 여전히 모델이 한다(훅은 goal 텍스트를 제시할 뿐 충족 여부를 계산하지
  않는다).
- **운영 비용 / 유지 부담**: 본문 lang 문자열에 토큰과 goal 절 두 축이 생겨, 번역자가
  어느 로케일에서든 `{{goal}}` 토큰이나 goal 절의 `{}` 자리를 떨어뜨리면 그 로케일만
  조용히 goal 을 못 받는다(에러도 경고도 없다). 그래서 센티넬 크로스체크와 나란히
  로케일별 컴파일 타임 테스트로 두 불변식을 강제한다. block 확정 + 토큰 포함일 때만
  IPC 를 하므로 호출 빈도는 늘지 않지만, 게이트 판정 경로가 memory 시스템에 의존하게
  되는 것 자체가 새 결합이다.

## Alternatives Considered

- **A — 3번 항목 문구를 "후속 작업이 있으면 계속하라" 로 바꾼다**: 변경 표면이 가장
  작지만 판정이 발산한다(위 "왜 goal 이 발산을 막는가"). 매 턴 라운드 상한까지 도달해
  게이트가 강제 연장기가 되고, 요청 범위 밖 작업을 에이전트가 스스로 실행한다.
- **B — 본문에 "`tasty memory goal get` 으로 확인하라" 라고 적는다**: 코드 변경이 거의
  없지만 핵심 판정 근거 획득을 모델의 성실성에 맡긴다. 조회를 건너뛰어도 게이트는 그
  사실을 알 수 없고, goal 부재 분기도 모델이 알아서 처리해야 한다.
- **C — host 가 작성한 goal 절을 모든 본문 뒤에 무조건 append 한다**: placeholder 없이
  구현이 단순해지지만, 등록 게이트 저자의 본문에 예고 없이 남의 문장이 붙는다. 반대로
  host 기본 본문에만 하드코딩하면 등록 게이트가 goal 을 영영 못 쓴다 — 게이트를
  프리미티브로 일반화한 ADR-0083 과 어긋난다.
- **D — goal 을 workspace 스코프로 둔다**: 부모 Claude 와 spawn 된 자식들이 goal 을
  공유하게 되어, 자식이 자기 subtask 를 끝냈는데도 부모의 goal 미충족을 이유로 계속
  돈다. goal 은 세션 단위 개념이라 surface 스코프가 맞다(상속도 넣지 않는다).

## Reconsideration Triggers

다음 중 하나가 충족되면 본 ADR 을 재검토한다.

- goal 절을 받은 세션이 실제로 라운드 상한까지 도달하는 빈도가 유의미해질 때 — goal 이
  범위 경계로 기능하지 못한다는 신호이므로, 계속-진행 조건(사용자 판단 불필요 + 자율
  진행 가능)을 다시 좁혀야 한다.
- 게이트 본문이 goal 외의 런타임 값을 더 필요로 할 때 — placeholder 가 하나 더 생기는
  시점에서 토큰별 특수 처리 대신 일반적인 치환 컨텍스트를 도입할지 다시 본다.
- goal 소비자가 이 게이트 밖으로 늘어날 때 — 지금은 "훅이 읽어 본문에 주입" 하나뿐이라
  goal 의 표면이 좁게 유지되고 있다.
