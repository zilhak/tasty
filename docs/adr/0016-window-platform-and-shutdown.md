# ADR-0016: 창의 OS 통합과 종료 처리를 앱 수명에 맞춘다

- **Status**: Accepted
- **Date**: 2026-09-24
- **Tags**: window, platform, shutdown
- **Group**: terminal

## Context

Tasty는 세 OS에서 창을 직접 구성하면서도 각 OS의 창 조작과 백그라운드 복귀 방법을 존중해야 한다. 창을 닫는 과정 때문에 이벤트 루프가 멈추거나 작업이 사라져서는 안 된다.

## Decision

타이틀바는 Tasty가 그리는 CSD를 사용한다. macOS는 투명 타이틀바와 fullsize content view로 콘텐츠 공간을 확보하면서 네이티브 신호등 버튼을 유지한다. Windows와 Linux는 네이티브 데코레이션을 끄고 캡션 버튼을 그린다.

시스템 트레이는 가능한 환경에서 제공하고, 등록할 수 없는 환경에서는 태스크바·도크 동작으로 복귀할 수 있게 한다. 트레이 부재만으로 앱 실행을 실패시키지 않는다.

surface를 닫는 GUI 루프에서는 자식이나 observer worker의 종료를 기다리지 않는다. Unix는 직접 SIGHUP을 보내고 별도 reap 스레드가 유예 후 SIGKILL과 wait를 처리한다. 자동 해제한 observer worker는 뒤에서 회수하되 명시적 observe_stop은 sink 종료를 보장하기 위해 join한다.

보이는 창이 있는 앱 종료는 프레임마다 진행하는 ShutdownPhase 상태 머신으로 처리한다. 대기 중에는 모든 창에 부팅과 같은 로딩 화면을 표시한다. 즉시 진행 가능한 단계는 같은 프레임에서 처리하고 최소 표시 시간을 넣지 않는다. 그릴 창이 없으면 동기 종료 경로를 사용한다.

종료 중 새 IPC는 실행하지 않고 `-32000 "host is shutting down"`으로 거절한다. event_loop.exit 이후에도 Exited 상태를 유지해 일반 이벤트 처리가 다시 시작되지 않게 한다. CLI는 응답 없는 EOF를 즉시 오류로 처리하되, 정상 무한 대기 API가 있으므로 공통 읽기 시간 제한을 두지 않는다.

메인 이벤트 루프가 멈춘 경우 별도 watchdog이 콜백과 acquire/submit/present 단계를 기록한다. 5초 이상 반환하지 않은 콜백은 보고하고 같은 정지가 이어지면 30초마다 로그를 갱신한다. hang 파일은 사건당 하나를 남긴다. watchdog은 프로세스를 종료하거나 렌더링을 복구하지 않는다. 사용자 선택을 기다리는 native 모달은 without_stall_watch로 제외하고 복귀 시 시간을 다시 잰다.

창·GPU·engine 생성 실패는 기존 세션을 종료하지 않고 요청 실패로 처리한다. 첫 창이나 GPU가 없어 안내를 그릴 수 없으면 로그에 진단을 남기고 exit(1)한다. 창과 GPU가 준비된 뒤 engine 생성에 실패하면 실패 화면을 유지하고 사용자가 종료할 때 exit(1)한다. 예상 밖 GPU 내부 오류는 crash 진단 대상이다.

사용자가 요청한 새 창·설정·plugin 모달 생성 실패는 남아 있는 main 창에 맞는 안내를 표시한다. 에이전트 요청의 실패는 IPC 오류로 요청자에게만 반환한다. 종료 확인 모달을 만들 수 없으면 사용자의 종료 요청을 수행하고 확인 생략 사실을 로그와 가능한 안내로 남긴다.

## Consequences

OS별 창 장식과 리사이즈 처리를 유지해야 한다. macOS 네이티브 버튼은 접근성·전체화면·디밍을 OS가 처리한다. Linux 트레이는 GTK/AppIndicator 계열 런타임과 이벤트 처리가 필요하다.

닫기 함수가 반환한 시점에 자식과 observer의 정리가 끝났다고 보장하지 않는다. 이미 채널이 수락한 observer 항목은 worker가 끝까지 기록하며 종료 단계와 router Drop에서 worker를 회수한다. 파일 삭제는 측정상 주된 지연이 아니므로 동기로 둔다. Unix PID를 얻지 못하면 종료를 기다리는 방식으로 처리한다. Windows의 TerminateProcess 경로와 ConPTY 해제는 별도로 유지한다.

종료 화면은 이벤트 루프가 끝난 뒤 Drop 비용을 가리지 못한다. 번들 plugin의 정상 종료가 빨라진 이후에는 이 비용이 더 큰 비중을 차지하지만, 응답하지 않는 plugin의 종료 대기에는 여전히 화면이 필요하다. 이 변화에 대한 화면 정책 재검토는 미결이다.

watchdog은 멈춤의 위치를 남기지만 응답성을 되돌려주지 못한다. 파일은 최초 탐지 시점의 시간이므로 전체 정지 시간을 알려주지 않는다. 재보고 로그는 host 재시작 때 초기화되며 CLI 실행은 로그를 지우지 않는다. 절전·디버거 정지는 오탐을 만들 수 있고 중첩 콜백은 탐지를 놓칠 수 있다.

종료 확인을 생략하는 예외가 있지만 생성 실패 때문에 사용자가 앱을 종료할 수 없는 상태는 피한다. 로그는 stderr와 파일 양쪽에 남긴다. observer worker 생성 실패는 요청 오류로 전달하고, agent runner 생성 실패는 로그와 running:false로 드러낸다. 별도 plugin 프로세스의 스레드 생성 실패는 host 전체 작업을 잃지 않으므로 기존 panic·감지 복구 구조를 유지한다.

## Alternatives Considered

- 네이티브 타이틀바만 사용하면 제품 테마와 상단 공간 구성을 통제하기 어렵다.
- macOS 버튼까지 직접 그리면 기본 클릭·접근성·전체화면 동작을 다시 구현해야 한다.
- 탭은 pane에 속하므로 곧바로 window 타이틀바에 합치면 다중 pane 구조와 맞지 않는다.
- Linux 트레이를 전면 포기하면 지원하는 데스크톱 환경에서도 기능을 잃는다. 반대로 모든 환경에서 필수로 요구하면 트레이 없는 환경을 사용할 수 없다.

- Terminal 전체 Drop을 다른 스레드로 옮기면 닫기 뒤 재생성과 공유 상태 정리 순서가 흐려진다. 병목인 종료 대기만 옮긴다.
- worker join을 완전히 제거하면 프로세스 종료 때 마지막 출력이 유실될 수 있다. 전용 join 스레드를 추가하기보다 완료 여부를 조회하고 종료 때 회수한다.
- 연관 자원의 종료 처리 전체는 메인 스레드 소유 상태 때문에 그대로 다른 스레드로 옮길 수 없다. 동기 대기를 유지한 채 화면만 그리면 스피너도 멈춘다. 별도 종료 창은 종료 중 새 창과 포커스 부작용을 만든다.
- 종료 중 일반 IPC를 실행하면 정리한 surface가 다시 만들어질 수 있다. 무응답으로 끊기보다 명시적인 종료 오류를 반환한다.

렌더 스레드 분리는 egui 프레임 준비와 window 호출까지 포함하는 큰 변경이며 macOS에서는 메인 스레드와 다시 동기화된다. GPU submit/present를 취소할 API가 없는 상태에서 호출 스레드만 버리면 누수가 남는다. watchdog의 자동 종료는 오탐 한 번으로 모든 PTY 작업을 잃게 한다.

모든 실패를 modal이나 toast로 표시하면 에이전트 요청이 사용자의 화면에 영향을 준다. 모든 실패를 panic으로 만들면 셸 경로 오타만으로 기존 PTY 세션을 잃는다. 종료 확인 모달 실패까지 취소하면 사용자가 강제 종료밖에 할 수 없게 된다.

## Reconsideration Triggers

winit이 Windows hit test나 Wayland CSD를 더 잘 지원하면 직접 처리 범위를 줄인다. 제품이 탭을 창 상단에 통합하기로 하거나 플랫폼별 유지 비용이 커지면 CSD 구성을 검토한다. 트레이 라이브러리의 OS별 한계와 지원 환경의 유지 비용이 커져도 구현 범위를 다시 판단한다.

Windows ConPTY 해제, reap 스레드 생성, 파일·DB 삭제가 닫기의 주요 비용으로 관측되면 해당 처리만 다시 검토한다. portable-pty의 Unix 종료 방식이 바뀌면 직접 SIGHUP 경로도 대조한다. observer에 자체 버퍼나 네트워크 sink가 추가되면 flush 완료 조건을 정한다. 종료 취소 API나 논블로킹으로 만들 수 없는 단계가 생기거나, winit이 exit 뒤 콜백을 하지 않는다고 보장하면 상태 머신을 재검토한다. 무한 대기 API를 없애면 CLI 타임아웃도 다시 고려할 수 있다.

실제 GPU 멈춤이 반복되거나 GPU API에 취소·시간 제한이 추가되면 복구 구조를 재검토한다. SurfaceError::Timeout 반복, 절전 오탐 누적, hang 파일 쓰기 실패는 각각 재시도·시간 보정·기록 방법을 검토할 조건이다.

설정·plugin 창의 에이전트 release API를 열면 요청 출처를 전달하도록 바꾼다. 확인 생략으로 작업 유실이 생기면 기존 창 안의 확인창 등 다른 방법을 검토한다. 창이나 GPU가 전혀 없어 로그만 남는 실패가 런처 사용자에게 문제가 되면 OS별 기본 안내창을 검토한다.
