# ADR-0565: ADR 인덱스의 행은 ADR 헤더에서 생성하고, 그룹은 ADR 헤더가 선언한다

- **Status**: Accepted
- **Date**: 2026-09-23
- **Tags**: adr-conventions, documentation, code-generation, guards, parallel-lanes, merge, adr-0138, adr-0239, adr-0508
- **Group**: docs-adr

## Context

`docs/adr/index.md` 는 두 층이 한 파일에 섞여 있었다. 그룹 목록과 그룹 머리말(결정 사슬 · 운영 문서)은
사람이 쓰는 산문이고, 그룹마다의 표 행(번호 · 제목 · Status · Date · Tags)은 ADR 헤더의 복사본이다.
행은 손으로 복사됐고 `crates/tasty-doc-guards/tests/adr_index_parity.rs` 가 열마다 "행이 헤더와 같은
값을 싣는가" 를 물었다.

여러 lane 이 병렬로 ADR 을 더하면 각자 같은 그룹 표의 끝에 행을 붙인다. 그래서 rebase 마다 인덱스가
충돌하고, 사람이 그 충돌을 손으로 풀면서 행이 빠지거나 다른 그룹으로 옮겨지거나 머리말이 두 벌로
남았다. 실측(2026-09-23, 이 결정을 적용하기 직전의 main 트리):

- 한 그룹(파일 핸들러 · 파일 피커)의 머리말이 두 벌로 남아 있었고, 그중 한 벌은 존재하지 않는
  `0613` 을 불렀다(같은 문장이 `0520` 으로 한 번 더 적혀 있었다).
- 네 그룹에서 행이 번호순이 아니었다(0536 · 0516 · 0504 · 0521 이 끝에 덧붙어 있었다).
- 행의 표기 관례가 행마다 갈렸다 — 제목에 강조 마커를 남긴 행 3, `Superseded by ADR-0247` 처럼
  접두를 남긴 행 1, 본문 `(부분)` 을 버린 행 1(같은 형태의 0040 은 싣는다).

기존 가드는 뒤의 둘을 정규화로 관용했고, 앞의 둘(머리말 · 순서)은 보지 않았다. 행은 헤더에서
파생 가능한 값인데 사람이 병합하고 있었다.

## Decision

1. **행은 생성물이다.** 그룹 절마다 `<!-- adr-rows:begin <slug> -->` · `<!-- adr-rows:end <slug> -->`
   마커를 두고, 그 사이(표 머리글 포함)는 `tasty_doc_guards::adr_index` 가 ADR 헤더에서 만든다. 마커
   밖(인덱스 머리 목록 · 그룹 목록 · 그룹 머리말)은 사람이 쓰고 생성기가 안 건드린다. 그래서 마커 밖에는
   표 줄을 두지 않는다 — 머리말은 ADR 을 산문 속 번호로 부른다. 파생 규칙은
   제목에서 강조 마커 `**` 제거와 공백 접기, Status 에서 링크 벗기기 · `Superseded by ADR-` 의 `ADR-`
   떼기 · 괄호 밖 첫 ` — ` 앞에서 자르기, Date · Tags 는 그대로, 행 순서는 번호순이다.
2. **그룹은 ADR 헤더가 선언한다.** 모든 ADR 은 헤더에 `- **Group**: <slug>` 한 줄을 갖고, slug 는
   인덱스의 마커가 정의한다. 그룹을 고르는 **판단**은 여전히 사람의 것이다(template 의 "인덱스에 행을
   추가할 때"). 바뀌는 것은 그 판단을 적는 자리다 — 공유 파일이 아니라 ADR 자신이라 병합에서 잃을 수
   없다.
3. **생성기는 `tasty-doc-guards` 에 둔다** — 라이브러리 모듈 `adr_index` 와 그것을 부르는 bin
   `adr-index`(`--write` · `--check`). 가드도 같은 모듈을 부른다. 셸이나 다른 언어로 사본을 만들지
   않는다. 둘은 같은 모듈을 부르되 **묻는 것이 다르다**.
   - **생성기는 자기 출력이 완전한가**를 본다 — 모든 ADR 이 생성 구역 안에 정확히 한 행을 갖는가.
     아니면 `--check` · `--write` 둘 다 rc 1 이다. `Group` 이 없거나 인덱스에 없는 slug 를 가리키는
     ADR 은 행 없이 빠지는데, 그래도 파일은 생성 결과와 **같다**. 그래서 "생성 결과와 같은가" 만
     rc 로 내면 ADR 이 인덱스에서 빠진 상태가 rc 0 으로 지나가고, 수동 절차의 완료 기준이 그
     rc 이므로 사람이 그 상태를 `git add` 한다. 절차에 가드 실행을 한 단계 덧붙이는 대신 판정을
     도구에 둔다 — 수동 절차에 더한 단계는 건너뛰어진다.
   - **가드는 그룹 배치와 결정 사슬**을 본다 — 왜 빠졌는가(그룹이 없다 · 인덱스에 없는 그룹이다 ·
     그룹이 둘이다), 빈 그룹이 있는가, 대체된 ADR 이 대체한 ADR 과 같은 그룹인가, 사슬이 양 끝에
     적혔는가. 완전성은 생성 결과의 행을 세면 답이 나오지만, 이 물음들은 ADR 헤더와 ADR 끼리의
     관계를 읽어야 나온다 — 빈 그룹과 같은 그룹 조건은 모든 ADR 이 정확히 한 행을 가진 인덱스에서도
     깨진다.
4. **가드의 물음을 바꾼다.** `adr_index_parity.rs` 는 열 단위 대조를 그만두고 다음을 묻는다.
   - 번호가 식별자로 성립하는가(번호 유일 · 본문 제목 번호 = 파일명 번호) — 그대로 둔다.
   - 생성 구역이 생성 결과와 글자 단위로 같은가 — 손으로 고친 행, 다시 안 만든 행이 여기서 걸린다.
   - 그룹 배치: 모든 ADR 이 정확히 한 그룹에 있고, 그 그룹이 인덱스에 실재하고, 인덱스의 모든 그룹에
     ADR 이 있는가.
   - 결정 사슬이 양 끝에 적혔는가: `Superseded by S` 면 S 가 실재하고 이 ADR 을 부르며 같은 그룹이다.
     `개정 대상` ↔ `부분 개정`(또는 `부분 개정 후 철회`), `통합 대상` ↔ `중복 조항 통합` 이 짝으로 있다.
   - 머리말(마커 밖)이 부르는 네 자리 번호가 실재하는가.
   - 머리말에 git 충돌 표지가 안 남았는가 — 생성기는 머리말을 안 건드리므로 병합 뒤 생성기만 돌리고
     머리말을 안 합친 상태가 여기서 걸린다.
   - 행이 생성 구역에만 있는가: 마커 밖의 표 줄이 0 이고, 마커 안의 행 수가 ADR 수와 같은가. 생성기는
     마커 밖을 안 건드리므로 머리말에 끼우거나 `adr-rows:end` 아래에 덧붙인 행은 "생성 결과와 같은가" 에
     안 걸린다. 손으로 쓴 행 시절의 가드가 "한 번호가 두 행이면 실패" 로 잡던 형태가 이것이다.

적용하면서 드러난 기존 결함은 같은 변경에서 고쳤다 — 위 Context 의 머리말 두 벌을 한 벌로 합쳤고,
사슬이 한쪽에만 적힌 세 자리의 빠진 쪽 References 줄을 더했다(0413 · 0465 의 `개정 대상`). 네 번째
후보(0152)는 불릿 없이 적은 같은 줄이라 판독을 넓혔고, 다섯 번째(0266)는 `부분 개정 후 철회` 라는
정당한 변형이라 짝으로 인정했다.

## Consequences

- **얻은 것**: 생성 구역의 충돌은 푸는 법이 하나다 — 어느 쪽 내용이 남았든 생성기를 다시 돌리면
  ADR 파일에서 같은 행이 나온다. 행 누락 · 그룹 오배치가 병합으로 생기지 않는다. 그룹 배치와 사슬 규칙이 처음으로
  판정기를 가진다(이전에는 template 의 문장뿐이었다).
- **남는 것**: 머리말은 여전히 사람이 병합한다. 생성 구역에만 해당하는 "어느 쪽이든" 을 파일에
  적용해 인덱스를 파일째 한쪽으로 받으면(`git checkout --ours` 등), git 이 이미 자동 병합한 상대 쪽
  머리말 줄이 버려지고 생성기는 그것을 되살리지 못한다 — 산문이라 파생 원천이 없다. 그 유실은
  판정으로 안 잡힌다. 그래서 절차는 충돌 표지를 둔 채 생성기를 돌리고 머리말의 충돌만 사람이
  합치는 것이고, 머리말에 충돌 표지가 남은 상태는 가드가 잡는다(`docs/dev-guide/adr-index.md`).
- **잃은 것**: ADR 헤더에 줄이 하나 는다(모든 ADR 396 개에 한 번씩 더했다). 그룹 slug 가 두 자리
  (마커 · 헤더)에 적히므로 slug 를 바꾸면 그 그룹의 모든 ADR 을 함께 고쳐야 한다 — 그룹 **이름**
  (`## ` 제목)은 slug 와 독립이라 자유롭게 고친다.
- **운영 비용 / 유지 부담**: ADR 을 더하거나 헤더를 고치면 생성기를 한 번 돌린다. 안 돌리면 가드가
  처방(명령)과 함께 빨개진다. `Group` 을 빠뜨렸으면 생성기 자신이 rc 1 로 그 ADR 을 찍는다. 절차는 `docs/dev-guide/adr-index.md`.

## Alternatives Considered

- **A. 그룹 소속을 인덱스 안의 번호 목록으로 둔다**(마커가 `adr-rows:begin <slug> 0002 0008 …` 처럼
  구성원을 나열) — 헤더를 안 건드리지만, 여러 lane 이 같은 목록 줄을 고치므로 병합 충돌과 누락이 그대로
  남는다. 이 결정이 풀려는 문제가 그 자리다.
- **B. 그룹 소속을 ADR 디렉토리의 별도 매핑 파일(TOML 류)로 둔다** — A 와 같은 이유로 기각. 공유 파일이
  하나 더 생길 뿐이다.
- **C. 헤더에 그룹 이름(제목 문자열)을 적는다** — slug 대신 사람이 읽는 이름을 쓰면 헤더만 보고도
  그룹이 읽히지만, 제목을 다듬을 때마다 구성원 전부를 고쳐야 한다. 제목은 편집 대상이고 slug 는
  식별자라 갈랐다.
- **D. 생성기를 `scripts/` 의 셸 · 파이썬으로 둔다** — 가드가 같은 규칙을 러스트로 다시 쓰게 되어 답이
  둘이 된다. 이 크레이트는 의존 0 이라 bin 하나를 더해도 CI 비용이 안 는다(ADR-0138).
- **E. 행을 생성하지 않고 기존 열 대조 가드를 유지한다** — 값이 같은지는 잡지만 누락 · 오배치 · 순서는
  병합하는 사람이 계속 손으로 막아야 하고, 실측으로 막지 못했다.
- **F. 인덱스에서 표를 없애고 그룹 머리말만 남긴다** — 번호 · 제목 · 상태를 한눈에 보는 카탈로그가
  사라진다. 표가 필요 없어서가 아니라 손으로 쓰는 것이 문제였다.

## Reconsideration Triggers

**채널이 붙는 것**

- 인덱스에서 `adr-rows:begin` 마커가 사라지면(표를 다시 손으로 쓰기로 했거나 인덱스 구조를 바꿨다면)
  이 결정은 무효다. `adr_index_parity.rs` 의 `every_adr_sits_in_exactly_one_known_group` 이 "마커를 하나도
  못 읽었다" 로 빨개진다.
- `crates/tasty-doc-guards/Cargo.toml` 의 `[dependencies]` 가 비지 않게 되면(ADR-0138 이 뒤집히면) 대안 D 의
  기각 근거 중 비용 논거가 약해진다. 레포가 읽을 수 있는 사실이지만 그것을 재는 시험은 이 결정을 쓰는
  시점에 찾지 못했다 — `crates/tasty-doc-guards/src/lib.rs` 모듈 주석이 부르는 이름의 시험이 레포에 없다
  (`git grep -n 'fn the_crate_has_no_dependencies' -- '*.rs'` 가 0 줄 — 범위를 안 좁히면 이 문장 자신이
  1 줄로 잡힌다). 채널 없음.

**원리적으로 안 붙는 것**

- 그룹 slug 변경이 잦아 구성원 일괄 수정이 부담이 되면 대안 C 의 반대편(헤더에 식별자 대신 다른
  간접층)을 다시 본다. 재는 법: `git log -p -- docs/adr/index.md` 에서 `adr-rows:begin` 줄의 slug 가
  바뀐 커밋 수를 센다.
- 생성 구역의 병합 충돌 자체가 부담으로 보고되면 `.gitattributes` 의 병합 드라이버로 인덱스 충돌을
  자동 해소하는 것을 검토한다. 재는 법: lane 착지 보고에서 인덱스 충돌 해소 횟수를 센다.
