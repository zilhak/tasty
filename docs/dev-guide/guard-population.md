# 소스 검사의 대상과 예외 관리

소스 검사의 대상 파일, 최소 개수, 제외 목록을 관리하는 방법을 정리한다.
선택 이유는 [소스 검사와 예외 관리](../adr/0048-source-guards-and-exemptions.md)에 있다.

## 검사 범위와 예외를 정하는 순서

먼저 검사할 디렉터리와 파일 종류를 정한다. 새 파일이 기본으로 포함되도록 디렉터리를 순회하고,
일부 파일을 빼야 하면 명시적인 예외와 이유를 둔다. 파일 수 하한은 대규모 누락만 잡는다.
전체 범위가 같은지 확인하려면 빠진 경로와 추가된 경로를 집합으로 비교한다.
둘 다 빈 집합이 될 수 있으면 빈 순회를 거부하는 검사도 둔다.

최소 개수, 정확한 개수, 집합 비교 중 무엇을 택했는지와 그 검사가 놓치는 경우를 함께 적는다.
같은 사실을 검사하는 두 가드가 있으면 검사 루트도 비교한다.
`git ls-files`와 순회 결과를 비교하는 검사는 Git 의존성을 갖는다는 점을 명시한다.
수동 관리 스냅샷을 추가해서 새 파일 등록을 다시 사람에게 맡기지 않는다.

계층 검사에서 테스트 전용 파일을 제외할 때는 다음을 확인한다.

- 부모의 `#[cfg(test)] mod ...;` 선언이 실제로 해당 파일을 가리킨다.
- 파일에 예외가 필요한 참조가 아직 남아 있다.
- 제품 허용 경로, 기존 부채, 테스트 전용 목록이 서로 겹치지 않는다.
- 통합 테스트로 옮길 수 없다면 필요한 픽스처가 `cfg(test)` 전용인지 확인한다.

현재 계층 검사는 일부 정규 선언 형식만 인식한다. 동등한 cfg 표현이라도 인식하지 못하면
통과시키지 않는다. 루트 lib 타깃이 있다는 것과 테스트 전용 심볼을 외부에서 링크할 수 있다는
것은 다르다. 예외가 필요한 이유가 사라지면 목록도 정리한다.

<a id="모수가-걷기에서-오지-않을-때"></a>

## 고정 목록을 검사할 때

디렉터리 순회는 시작점이 잘못되면 빈 결과를 낼 수 있다.
`const` 배열이나 `include_str!`로 관리한 고정 목록은 새 소스가 생겨도 자동으로 늘지 않는다.
목록의 크기에 하한을 두는 것만으로는 새 대상이 빠졌는지 확인할 수 없다.
목록을 비웠을 때도 통과하는지 확인해 빈 검사까지 허용하는지 살핀다.

<a id="처방--목록을-소스에서-뽑아-동적으로-바꾼다"></a>

## 소스에서 목록을 읽어 대조한다

소스와 동기화해야 하는 목록은 소스에서 대상 집합을 추출해 양방향으로 비교한다.
소스에만 있는 대상과 목록에만 남은 대상을 모두 잡아야 한다.
추출은 새 파일을 포함하도록 디렉터리에서 시작한다.

동결된 스냅샷과 일부 대상만 대조하는 검사라면 집합 동등 대신 의도한 정확한 개수를 쓸 수 있다.
대상 집합의 검사는 목록을 만드는 곳에 두어 모든 소비자에게 적용한다.
순회 결과와 목록이 동시에 빌 수 있다면 집합 비교 외에 빈 결과를 거부하는 하한도 둔다.

## 소스 추출기의 범위

`t(`를 찾을 때는 insert·expect의 끝부분까지 찾지 않도록 식별자 경계를 검사한다.
주석과 문자열 속 예시를 코드로 세지 않는다. 실제로 포함해야 할 입력과 제외해야 할 입력을
합성 픽스처로 확인하고, 추출기의 픽스처가 제품 입력에 포함되지 않도록 시작점을 정한다.

### match 팔과 함수 정의

match 팔을 표와 대조할 때는 `tasty_doc_guards::match_arms`를 사용한다.
`source_text::mask_non_code_aligned`로 바이트 위치를 유지한 채 주석·문자열·문자 리터럴을
가리고, 구조는 가린 사본에서, 이름은 원문에서 읽는다. 줄 시작이나 쉼표만으로 나누면
리터럴 속 구분자, `"a" | "b"`, guard가 있는 팔, 중첩 match를 잘못 읽을 수 있다.

지원하지 않는 구조는 Err로 반환한다. 그러나 팔의 패턴을 리터럴 이름으로 읽을 수 없는
경우의 처리는 소비자마다 다르다. 창 라우터 호출자·합산 목록·권한 토큰 판독과
non_literal_arms는 이를 제한한다. 액션 검사·라우터 표·번들 namespace·단축키·
routing_key_method_scope의 dispatch_arms는 읽지 못한 팔을 건너뛰는 경우가 있다.
공용 구조 분석기의 오류 처리를 모든 소비자의 검출 보장으로 확대하지 않는다.

함수 정의를 찾는 범위도 구분한다.

| 구현 | 범위와 제약 |
|---|---|
| 공용 match_arms의 fn_bodies | 같은 이름의 정의를 모두 반환. 소비자가 전부 검사하거나 정확히 하나를 요구함 |
| src/source_guards의 fn_body | 첫 정의만 반환. cfg로 나뉜 같은 이름의 뒤 정의를 놓칠 수 있음 |
| routing_key_method_scope의 fn_index | 사설 fn_bodies 결과를 모듈·이름으로 등록하며 첫 정의만 유지 |
| 직접 find로 정의를 찾는 소비자 | 첫 일치 뒤만 읽을 수 있으므로 개별 확인 필요 |

fn_index의 호출자는 `git grep -n 'fn_index(' -- src`에서 찾고 그 결과를 사용하는 함수까지
따라간다. helper 이름이 같아도 공용 구현과 같다고 가정하지 않는다.
첫 정의에 알려진 위반을 넣었을 때와 cfg 뒤 정의에만 넣었을 때를 비교하면 이 누락을
확인할 수 있다. 직접 find를 쓰는 모든 소비자를 변이로 확인했다는 뜻은 아니다.

이 분석기는 렉서와 구분자 구조를 사용하며 완전한 Rust 문법 파서는 아니다.
의존성 없는 가드 크레이트에서 쓰는 이유와 세부 한계는 match_arms 모듈 설명을 따른다.
고정된 블록 하나를 확인하는 검사나 이미 가린 소스를 받는 소비자까지 같은 API로 바꾸지는 않는다.

### 임시 조사에도 같은 소스 구분을 쓴다

일회성 조사에서도 주석·문자열 속 언급을 실제 코드로 세지 않는다.

```bash
dir=$(bash scripts/masked-tree.sh)
rg '<패턴>' "$dir"
rm -rf "$dir"
```

사유 주석을 읽어야 하면 `--keep-comments` 사본을 별도로 쓴다.
주석을 지운 사본으로 사유 유무를 판단하거나 주석을 남긴 사본으로 코드 수를 세지 않는다.
기록에는 입력 트리와 측정 방법을 남긴다. 이 수동 절차 자체를 모든 임시 스크립트에 강제하는
자동 검사가 있는 것은 아니다.

### 빈 입력과 알려진 위반으로 검증한다

소스에 is_empty 단정이 있다는 사실만으로 빈 수집을 막는다고 판단하지 않는다.
실제로 검사 입력을 비웠을 때 실패하는지 확인한다. 고정 배열·include_str 목록은
배열이나 픽스처를 비워야 한다. 순회 시작점만 바꾸는 변이는 고정 목록에 영향을 주지 않는다.

<a id="하한에는-판별식이-붙어야-한다"></a>

## 최소 개수 미달의 원인을 구분한다

파일 수가 하한보다 작아지면 실제 대상이 줄었는지, 수집이 잘못됐는지 먼저 구분한다.
실패 메시지에는 해당 검사에서 이를 확인할 경로나 명령, 확인 없이 하한을 낮추지 말라는
안내, 정상적인 감소를 확인했을 때 값을 갱신하는 방법을 적는다.
구분할 방법이 없다면 그 한계도 적는다. 모든 검사에 같은 추상적인 문장을 복제하지 않는다.

<a id="하한의-실측값에는-출처가-둘이다--섞으면-조용히-죽는다"></a>

### 저장소 측정값과 픽스처 크기를 구분한다

순회 시작점이 저장소라면 저장소 측정값을, 임시 디렉터리라면 합성 픽스처의 크기를 쓴다.
픽스처의 작은 하한을 저장소 공용 값으로 치환하면 그 테스트의 검증 의미가 달라진다.

### 최소 개수의 근거를 관리한다

`Floor`의 측정값과 측정 시점은 사실이고, 최소 개수와 여유의 이유는 해당 가드의 판단이다.
여러 가드가 같은 대상을 세면 측정값은 `floored_walk::populations::Population` 하나를
참조한다. 여기에는 측정 트리(`counted_on`)와 세는 방법(`how`)도 남긴다.
최소 개수까지 하나로 합치지는 않는다. 검사마다 허용할 정상 변동이 다를 수 있다.
임시 디렉터리의 합성 픽스처는 저장소 측정값을 참조하지 않고 자기 크기를 사용한다.

미추적 캐시 디렉터리까지 걷는 검사는 같은 커밋에서도 머신마다 결과가 다르다.
이 경우 추적 트리에서 재현할 수 있는 하한을 기록하고 실제 순회값과 다르다는 이유를 적는다.
검사 목적이 캐시 확인인데 재현성을 위해 캐시를 대상에서 빼지는 않는다.

여유는 '넉넉하게' 같은 형용사 대신 정상 변경 한 번의 단위와 허용 횟수로 설명한다.
예를 들어 플러그인 하나의 언어 파일 수와 몇 개 플러그인의 삭제를 견딜지로 정한다.
과거 변동은 근거로 쓰되 짧은 기간의 최대 변동만으로 자동 계산하지 않는다.
단위를 정할 수 없으면 이유를 명시한다. 기준을 갱신할 때 설명도 여전히 맞는지 확인한다.

<a id="공용-모수는-푸시할-트리에서-다시-센다"></a>

### 공용 측정값은 푸시할 트리에서 다시 센다

`Floor::validate` 는 `min <= measured`, 날짜 형식, 근거 문자열을 검사한다.
실제 트리와의 정합은 `scripts/check-population-freshness.sh --rev <commit>` 이 별도로
검사한다. pre-push B.10 은 Git 이 건넨 로컬 tip 을 이 스크립트에 넘겨 `SRC_RS`,
`ROOT_TEST_TARGETS`, `CRATE_TEST_TARGETS`, `DOCS_MD` 네 공용 모수를 대조한다.
인라인 리터럴과 소비자의 `why_this_gap` 산문은 이 검사의 대상이 아니다.

파일이 추가되거나 이동하면 해당 `Population` 의 `measured`, `measured_on`, `counted_on` 을
같은 트리를 기준으로 갱신한다. 소비자의 하한은 그대로 두고, 그 하한에서 파생한 여유와
깊이 분포도 다시 센다. `SRC_RS` 의 경우 `layering` 의 깊이별 개수·총량 여유와
`modal_state_has_one_writer` 의 감소 허용 폭이 그 사본이다. `layering` 의 깊이는
레포 상대 경로를 `/` 로 나눈 조각 수다. 파일 총수가 늘어도 얕은 파일 수는 그대로일 수 있다.

<a id="낡은-값과-안-잰-값을-가르는-판별식"></a>

### 측정 기록과 현재 값을 대조한다

기록한 값과 현재 값이 다르면 `counted_on` 등으로 기록 당시 트리를 확인하고 다시 센다.
당시 값이 맞았다면 갱신하고, 당시에도 틀렸다면 기록을 정정한다.
값이 틀렸다는 사실만으로 실제 측정하지 않았다고 단정하지 않는다.
어느 경우든 하한과 여유의 이유가 새 값에도 맞는지 함께 확인한다.
`Floor::validate`는 `min <= measured`만 검사하므로 실제 개수를 증명하지 않는다.

값 X를 양쪽에서 확인하려면 임시로 `min`과 `measured`를 모두 X로 두고 통과하는지,
둘을 X+1로 두면 해당 하한 검사에서 실패하는지 확인한다.
이는 각각 실제 개수가 X 이상, X+1 미만이라는 뜻이며 정수 개수라면 둘을 합쳐 X다.
`min`만 올려 선언 검증에서 먼저 실패한 결과는 순회 검증으로 쓰지 않는다.
변이 뒤 백업을 복구할 때는 `touch` 등으로 변경 시각도 갱신해 Cargo가 변이 바이너리를
재사용하지 않도록 하고 원래 검사가 통과하는지 확인한다.

### 수가 줄었을 때

실제 입력 감소인지 수집 누락인지 확인한 뒤 하한을 갱신한다. 이름이 바뀌거나 파일이
다른 패키지로 옮겨졌다면 더 넓은 시작점에서 다시 찾는다. 검사마다 시작점이 여럿이면
각 시작점에 하한을 둔다. 총합은 한쪽 누락을 다른 쪽 증가로 가릴 수 있고,
최솟값 하나는 원래 크기가 다른 디렉터리에 같은 기준을 적용하게 된다.

### 정상 결과가 0인 검사

위반이 없는 입력에서 위반 수 0은 정상이다. 대신 입력 파일·항목을 실제로 읽었는지와
알려진 위반을 잡는지를 따로 확인한다. 단일 파일도 줄 수보다 필요한 구조를 읽었는지가
중요하다. 파일이 존재하지만 내용이 비었거나 파서가 일부를 놓쳐도 정상처럼 보일 수 있다.
하한과 합성 반례는 서로를 대신하지 않는다.

자연어를 검사할 때는 부재·자동 실행·조합 한정 표현이 어느 문장에 붙는지 구분한다.
표의 한 행, 목록 항목, 문단을 섞어 면제하지 않는다. 긍정 주장과 부재 표지가 함께 있으면
표지 하나만으로 제외하지 않는다. 검색 도구의 정규식 문법도 알려진 입력으로 확인한다.
특정 머신의 grep 구현 차이를 모든 환경의 일반 규칙으로 쓰지 않는다.

### 저장소 밖 파일과 캐시

가드가 로컬 임시 파일이나 캐시를 읽으면 같은 커밋에서도 결과가 달라질 수 있다.
별도 작업 트리에서 실제 파일·점 디렉터리·다른 이름의 빌드 캐시를 만들어 결과를 비교한다.
심볼릭 링크만 둔 경우와 실제 디렉터리는 순회 결과가 다를 수 있다.
`.github`는 추적 자산이므로 점으로 시작한다는 이유만으로 제외하지 않는다.

확인할 결과는 위반 수뿐 아니라 읽은 경로와 내용이다. 파일을 열었다는 로그만으로 내용까지
검사했다고 단정하지 않는다. 캐시 판정을 위해 CACHEDIR.TAG만 열었을 수도 있다.
경로에서 제외했는지, 내용을 읽기 전에 제외했는지, 내용을 검사했지만 위반이 없었는지를 나눈다.
캐시에서 빠진 합성 위반을 근거로 본문 분석기가 위반을 놓쳤다고 보고하지 않는다.

### 추적 파일과 실제 디렉터리 순회의 차이

`git ls-files`를 사용하는 게이트는 미추적 파일을 읽지 않는다. 파일시스템을 직접 순회하는
가드는 설정된 제외 조건에 따라 미추적 파일도 읽는다. staged diff 기반 훅은 또 다른 입력을
검사한다. 같은 파일을 추가해도 검사별 개수 변화가 다른 이유를 먼저 확인한다.

| 입력 | 확인할 차이 |
|---|---|
| 추적한 새 소스 | 실제 검사 범위·소스 개수·하한·예외에 미치는 영향 |
| 미추적 소스 | Git 기반 검사에서 제외되고 실제 순회에 포함되는지 |
| 빌드 캐시 | 표식으로 제외되는지, 표식 확인과 본문 읽기가 구분되는지 |
| 로컬 작업 디렉터리 | 일반 디렉터리와 링크의 처리, 점 디렉터리 예외 |

비교할 때는 같은 검사 바이너리와 입력 상태를 쓰고, 합성 파일을 제거한 뒤 원래 결과로
돌아오는지도 확인한다. 하나의 성공 결과를 모든 순회·게이트가 같은 범위를 본다는 증거로 쓰지 않는다.

## 검사에서 제외하는 기준

### 캐시와 외부 자산 제외

빌드 캐시는 `is_build_cache_dir`가 `CACHEDIR.TAG`의 서명까지 확인해 제외한다.
`target`이라는 이름만으로는 다른 `CARGO_TARGET_DIR`에 만든 산출물을 찾을 수 없다.
표식이 없는 도구의 산출물에는 별도 이름 규칙이 필요할 수 있다.
Git 추적 여부만으로 외부 자산과 직접 작성한 자산을 구분하지 않는다.

vendored 번들은 파일별로 열거하고 목록에 없는 새 번들과 사라진 항목을 양쪽으로 확인한다.
`assets` 전체를 제외하면 직접 작성한 desktop 파일이나 NOTICE까지 검사에서 빠진다.
가드별 제외 목록은 검사 목적이 다를 수 있으므로 이름이 비슷하다는 이유만으로 합치지 않는다.
공유할 것은 캐시 판정 함수이며 모든 목록의 내용이 아니다.

`.gitignore`도 이름에 의존하고, `cargo metadata`는 현재 설정된 빌드 디렉터리만 알려준다.
이전에 다른 이름으로 만든 캐시까지 찾으려면 디렉터리의 표식을 확인해야 한다.
Cargo의 표식은 실제 빌드 때 생기므로 metadata 조회만으로 캐시 검증을 대신하지 않는다.

<a id="아홉-번째-가드가-이-판정을-안-쓰는-것은-못-막는다"></a>

### 공용 함수 사용 여부는 별도로 확인한다

공용 함수를 만들었다는 사실만으로 모든 가드가 사용한다고 보장할 수 없다.
소스의 함수 이름이나 `read_dir` 문자열만으로 재귀 여부와 순회 시작점을 추측하지 않는다.
순회 가드를 추가하거나 시작점을 저장소 루트로 넓힐 때는 별도의 작업 트리에서 다른
이름의 빌드 디렉터리를 만든 뒤 결과와 시간을 비교한다. 이 확인은 수동 절차다.
병렬 검사와 충돌할 수 있으므로 일반 가드가 실행 중인 트리에 캐시를 만들지는 않는다.

<a id="면제가-실제로-무엇을-덮는가--차집합으로-잰다"></a>

## 예외가 허용하는 대상을 확인한다

여러 예외 목록이 같은 대상을 덮을 수 있다. 먼저 목록 전체를 비워 검사하고,
그다음 항목을 하나씩 빼서 해당 예외만이 허용하는 대상을 확인한다.
여러 테스트 타깃의 실패를 모으려면 `--no-fail-fast`를 쓴다.
실패 로그에서 항목 이름만 검색하면 다른 목록의 출력과 섞일 수 있으므로 근거로 쓰지 않는다.

### 예외를 지우기 전에

예외를 빼도 통과한다면 그 이유를 읽는다. 경로·패턴 ID의 존재를 검사하는 것과
예외의 필요성·허용 범위를 판단하는 것은 별개의 작업이다.

### 차집합이 0 이어도 지우지 않는다

현재 위반을 임시로 허용한 항목은 위반이 사라지면 삭제한다.
검사 범위 자체를 정한 정책 예외는 지금 해당 코드가 없어도 필요할 수 있다.
예외를 빼도 검사가 통과한다는 사실만으로 둘을 구분할 수 없다.

### 이것을 가드로 만들지 않는다

모든 예외가 현재 위반을 하나 이상 허용해야 한다고 검사하지 않는다.
그 검사는 필요한 정책 예외까지 삭제하도록 요구한다.
대신 파일·디렉터리·패턴 ID가 실제 존재하는지는 검사할 수 있다.

<a id="면제가-가리키는-것이-실재하는가--참조-무결성"></a>

## 예외의 참조가 유효한지 확인한다

파일 이동이나 이름 변경 뒤 예외 목록에 옛 이름이 남지 않도록 참조를 확인한다.

<a id="초록의-뜻"></a>

### 참조 검사가 보장하는 범위

참조 검사가 통과했다는 것은 대상이 존재한다는 뜻이다. 예외가 필요한지, 경로 접두사가
너무 넓은지, 해당 코드가 여전히 위반하는지까지 보장하지 않는다.

<a id="겹마다-가리키는-것의-갈래가-다르다--하나의-검사로-안-덮는다"></a>

### 참조 종류에 맞는 검사를 사용한다

파일·디렉터리·패턴 키는 존재를 검사한다. `PENDING_FIX_*`나 `TEST_ONLY_FILES`처럼
대상이 아직 위반하는지를 직접 검사하는 목록에는 그 검사를 사용한다.
`Ctrl`, `Alt` 같은 규칙 단어 목록은 현재 코드에 등장하지 않아도 유효하므로
파일 존재 검사나 문자열 등장 횟수로 삭제 여부를 판단하지 않는다.

`(경로, 패턴 ID)`나 `(키, 언어 코드 목록, 사유)` 항목은 각 구성요소를 따로 검사한다.
경로에는 `tasty_doc_guards::missing_referents()`를 사용하며, 후행 슬래시로 디렉터리를
구분해 디렉터리 자리에 파일이 있는 경우도 잡는다.

<a id="회귀는-합성으로-건다"></a>

### 합성 입력으로 회귀를 검사한다

실제로 잘못된 저장소 항목에 기대지 말고 존재하는 항목과 존재하지 않는 항목을 픽스처로
검증한다. 가드 소스 자체도 검색 대상이면 없는 이름을 조각으로 조립해 자기 소스가
우연히 검색을 통과시키지 않도록 한다.

<a id="마크다운-링크는-문서-자신의-자리에서-푼다"></a>

### 마크다운 링크는 해당 문서 위치에서 해석한다

상대 링크는 저장소 루트가 아닌 해당 문서의 디렉터리에서 해석한다.
`cited_coordinates_exist.rs`는 스킴이 있는 URL, `mailto:`, 같은 문서 앵커,
루트 절대 경로를 이 검사에서 제외한다. 인라인 코드의 링크 문법 예시도 제거한다.

<a id="판정에서-빠지는-것은-형식-단위로-선언한다"></a>

### 검사하지 않는 파일 형식을 명시한다

인용 검사는 Markdown 본문과 소스 주석을 읽는다. 주석 문법을 지원하지 않는 형식은
제외 이유를 선언하고, 선언하지 않은 형식이 빠지면 실패한다.
파일별 예외로 만들면 같은 형식의 파일이 추가될 때마다 불필요한 등록이 생기므로
`every_gathered_but_unjudged_file_declares_its_format`은 형식별로 관리한다.
해당 형식의 마지막 파일이 사라졌다고 선언까지 제거하도록 강제하지는 않는다.

<a id="빈-면제-겹은-지우지-않는다"></a>

### 빈 예외 목록도 유지 이유를 확인한다

목록 전체가 비어 있는 것과 목록의 한 항목 안에 패턴이 없는 것은 다르다.
빈 목록에는 앞으로 등록할 형식이나 이행 완료 사실을 남길 수 있다.
`layering::BASELINE_FILES`처럼 새 항목을 추가하면 안 되는 목록도 있다.
각 목록의 주석을 읽고 유지 이유를 판단한다.

## 직접 디렉터리를 순회하는 검사

직접 read_dir 호출을 발견했다고 모두 공용 저장소 순회로 바꾸지 않는다.
제품 실행 중 사용자 디렉터리를 읽는 코드, 임시 픽스처를 읽는 시험, 저장소를 검사하는 가드,
공용 순회 구현 자체를 구분한다. 런타임 디렉터리는 비어 있어도 정상일 수 있다.
저장소 가드의 빈 수집은 검사를 하지 않은 결과일 수 있다. 한 단계의 명부 열거와 재귀 순회도 다르다.

호출 수와 함수를 포함한 파일 수는 같은 단위가 아니다. 래칫을 정할 때 어떤 단위를 세는지
명시한다. 함수 이름이나 문자열만으로 시작점·재귀 여부를 추측한 조사는 추상화된 호출을
놓칠 수 있으므로 정확한 전수 분류로 보고하지 않는다.

`scripts/check-shared-walk-ratchet.sh`는 tests/*.rs와 crates/*/tests/*.rs의 직접 호출 위치를
센다. 제품 코드나 src 안의 인라인 테스트 순회를 모두 검사하는 도구는 아니다.
줄어도 실패하므로 실제 개선인지 검사 범위 밖으로 이동했는지 확인한 뒤 상한을 낮춘다.
검사기가 없으면 원문으로 대신 세지 않고 rc 2로 측정을 거부한다.
현재 상한과 근거는 스크립트에 두고 문서에 개수를 복제하지 않는다.

### 문장으로 적은 예외

CI 자동 실행 여부를 검사하는 문서 가드는 표의 한 행, 산문의 한 문단, 연속된 주석 블록을
하나의 설명으로 읽는다. 같은 설명에서 자동 실행과 실행 부재를 모호하게 함께 주장하면
면제를 인정하지 않는다. 서로 다른 검사에 관한 설명이면 문장을 나눠 대상을 명시한다.
잡 이름을 인용한 것 자체는 자동 실행 주장과 다르다.

CI 문서의 `tests/*.rs`도 검사 대상 전체를 가리키는 표현이다.
이때 루트 패키지의 통합 타깃과 다른 크레이트의 같은 이름 타깃을 구분한다.
파일명 없이 쓴 일반 표현까지 현재 추출기가 모두 이해한다고 주장하지 않는다.
조합을 한정한 문구도 다른 이유로 낡을 수 있으므로 리터럴 표지 면제의 한계를 확인한다.

### 타입을 근거로 관리하는 락 목록

프레임·레코드를 쓰는 스트림 락은 poison 복구 뒤 이어 쓰면 메시지 경계를 손상시킬 수 있다.
복구 금지 이름 목록은 `TcpStream`, `HandleStream`, `HandleClient`를 보호하는 선언과 대조한다.
새 이름의 락도 빠지지 않아야 한다. 줄이 일부 잘려도 허용되는 로그 파일이나 값 자료구조는
같은 규칙으로 금지하지 않는다. 실제 오류 처리 정책은 [오류 처리](error-handling.md)를 따른다.
현재 텍스트 검사는 타입 별칭과 이름 없는 선언을 모두 추적하지 못한다.
이런 형태를 추가하면 사용 지점과 오류 전파를 직접 확인한다.

### 공용 분석기의 역할

| 확인할 내용 | 공용 구현 |
|---|---|
| cfg가 특정 조건을 함의하는지와 적용 줄 범위 | `cfg_predicate` |
| 인라인 테스트 모듈과 자식 모듈 선언 | `src/source_guards/test_gate` |
| 파일 전체가 제품 코드에 포함되는지 | `shipping_scope::test_only_files` |

`shipping_scope`는 선언 관계와 Cargo 테스트 타깃을 다룬다.
같은 판단을 다른 가드에서 다시 만들지 않고 검사 범위만 각각 지정한다.
공용 구현을 사용할 수 없는 의존 경계에서는 사본이라는 사실, 함께 갱신할 조건,
상호 참조를 적는다. 이름이 같다는 이유만으로 함수를 합치지 않는다.
같은 입력 집합으로 결과를 비교해 의도한 범위 차이와 구현 차이를 구분한다.
공유할 것은 공통 판단이며 가드마다 다른 제외 조건은 소비자에 남긴다.
