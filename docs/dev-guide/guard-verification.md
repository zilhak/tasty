# 가드 검증

가드가 검사할 파일을 읽는지는 [검사 대상 관리](guard-population.md)에서 확인한다.
이 문서는 그 가드가 의도한 결함을 실제로 검출하는지 확인하는 방법을 설명한다.

## 가드가 실제 결함을 잡는지 확인하기

정상 입력과 의도적으로 잘못 만든 입력에 서로 다른 결과를 내는지 확인한다.
먼저 변경이 실제 적용됐는지 diff로 확인하고, 실행 명령에 해당 테스트 타깃이 포함됐는지 본다.
`--lib`만 실행하면 `tasty-doc-guards/tests/`의 통합 검사는 실행되지 않는다.
복구 뒤에는 원본 해시를 대조하고 같은 검사를 다시 실행한다. 복구로 파일을 비우거나
mtime을 되돌려 이전 바이너리를 재사용하지 않도록 주의한다.

변경을 넣었는데 통과했다면 다음 순서로 확인한다.

1. 변경한 파일이나 입력이 검사 범위 안에 있는가.
2. 다른 규칙이 먼저 거부하거나 제외하지 않았는가. 실패 이유가 바꾼 내용을 가리키는가.
3. 픽스처에서 정상 구현과 잘못된 구현이 서로 다른 결과를 만들 수 있는가.
4. 기존 예외나 다른 단언이 같은 변경을 먼저 잡아 검사 효과를 가리지 않는가.
5. 주입한 키나 요청이 현재 설정의 실제 바인딩과 연결돼 있는가.

예를 들어 빈 맵에서는 일부 항목만 남기는 코드와 모두 지우는 코드의 결과가 같다.
작은 파일 목록은 우연히 정렬돼 정렬 누락을 드러내지 못할 수 있다.
`!output.contains(x)`만 확인하면 출력 전체가 비어도 통과한다.
같은 출력에 정상 데이터가 도착했다는 양성 단언을 함께 둔다.
입력 주입과 출력 수집이 살아 있는지도 앞뒤에서 확인한다.

검사가 무엇을 찾았는지 일시적으로 목록을 출력해 본다.
패턴 문자열을 담은 가드 자신을 실제 사용처로 세고 있지 않은지 확인한다.
주석뿐 아니라 문자열도 공용 분석기로 가린다. 자기 파일 제외가 필요하면 고정 파일명보다
`file!()` 등 이동을 따라가는 식별을 사용한다.
같은 수집기의 결과끼리만 비교하면 둘 다 비었을 때 통과하므로 독립된 입력과도 대조한다.

구조를 지키는 검사라면 값은 그대로 둔 채 구현 경로만 바꾸는 경우도 확인한다.
함수 호출을 같은 값의 리터럴로 바꿔도 실패해야 호출 관계를 검사한다고 말할 수 있다.
반대로 타입이나 기존 검사가 이미 같은 문제를 더 강하게 막으면 중복 검사를 추가하지 않는다.
순수 계산의 정확한 예상값 비교에 환경 대조군을 불필요하게 붙이지 않는다.

### 실패 메시지를 따라도 보호가 남아야 한다

최소 개수 미달은 실제 삭제와 수집기 고장 양쪽에서 발생한다.
메시지에는 둘을 구분할 확인 방법, 근거 없이 숫자만 낮추지 말라는 안내,
실제 삭제가 확인됐을 때 합법적으로 기준을 갱신하는 방법을 함께 적는다.
원인이 아직 구분되지 않았는데 탐색 고장이라고 단정하지 않는다.

목록을 지우라는 안내를 따르면 깨진 순회까지 통과하는 경우가 있다.
실패 안내대로 최소한만 고친 뒤 원래 결함이 여전히 검출되는지 확인한다.
안내가 무한 재빌드나 영구 실패로 이어지면 원인 구분과 복구 절차부터 고친다.
공유할 수 있는 판정 규칙을 공유해 원인이 두 개 생기는 구조 자체를 없애는 편이 낫다.

### 측정과 로그의 함정

- `grep -c`는 일치가 없어도 0을 출력한다. 뒤에 `|| echo 0`을 붙이면 0이 두 번 나온다.
- 종료 코드를 읽기 전에 파이프로 `head` 같은 명령을 붙이지 않는다.
- 테스트 통과 출력은 기본 libtest가 숨긴다. 값을 남기려면 `--show-output` 등 로그 경로도 확인한다.
- 실제 stdout FD에 직접 쓰면 병렬 테스트 결과 줄과 섞일 수 있다. 캡처를 우회하지 않는다.
- 하나의 패닉 뒤 `PoisonError`가 이어졌다면 실패 수를 독립 결함 수로 세지 않는다.
- 파일 이동을 삭제로 오인하지 않도록 이전 위치와 새 위치를 함께 비교한다.
- 공유 하네스 변경의 영향은 모듈 수가 아니라 그 모듈을 포함한 테스트 바이너리 수로 본다.

측정값에는 커밋, 빌드 조합, 실행 환경과 확인하지 못한 범위를 남긴다.
컴파일·실행·원하는 결함 검출은 서로 다른 확인 결과다.

## 규칙을 무엇이 지키는지 설명하기

규칙 하나에 여러 조건이 있으면 각각을 따로 확인한다.
예를 들어 debug 전용 파일 배치는 자동 검사할 수 있어도, 기능이 사용자 입력 재현인지
판단하는 일은 리뷰가 필요할 수 있다. 다음 상태를 쉬운 말로 구분한다.

| 상태 | 필요한 설명 |
|---|---|
| 타입·가시성이 금지 | 어떤 타입이나 접근 제한이 막는가 |
| 자동 검사 존재 | 어느 조건을 검사하며 실제로 실행되는가 |
| 검사 코드는 있지만 자동 실행하지 않음 | ignore, 빌드 조합, 트리거 중 무엇 때문인가 |
| 아직 검사가 없음 | 조사한 범위와 구현할 수 있는 방법 |
| 현재 입력으로 자동 구분할 수 없음 | 두 경우를 구분할 관측값이 왜 없는가 |
| 만들 수 있지만 정확한 동작이나 문서를 해침 | 오검출과 가장 쉬운 수정이 무엇을 훼손하는가 |

이름 검색으로 못 찾았다는 것은 검사 부재의 증명이 아니다. 구현과 실행 경로도 확인한다.
현재 테스트가 통과하는지는 별도의 실행 결과이며 위 상태표에 섞지 않는다.
검사를 추가하기 위해서만 새 명부를 만들면 그 명부의 누락을 다시 검사해야 한다.
가능하면 실제 런타임 등록처, 공개 타입, 디렉터리 목록처럼 이미 쓰이는 자료를 기준으로 삼는다.
그 자료를 거치지 않아도 같은 결함이 발생하는 경로가 있는지도 확인한다.

규칙을 타입이나 가시성으로 표현할 수 있으면 컴파일 단계에서 막고 중복 텍스트 검사를 줄인다.
호출이 의미상 정당한지까지 컴파일러가 판단한다고 주장하지 않는다.
가드 때문에 사용자 가이드의 자연스러운 표현을 내부 식별자로 바꾸는 수정은 피한다.
검사에 맞는 문장을 만들기보다 검사가 판단할 수 있는 범위를 좁혀야 한다.

### 목록 항목과 검사 효과

검사기의 패턴 목록은 각 항목을 독립된 리터럴 픽스처로 확인한다.
검사할 상수에서 픽스처를 만들면 같은 오타를 양쪽이 공유해 통과한다.
픽스처 하나에는 확인할 패턴을 하나만 넣어 다른 패턴이 대신 검출하지 않도록 한다.
실제 판정 함수를 호출하며, 실패 메시지는 빠진 항목을 이름으로 지목한다.

변이는 검사 강도를 약하게 만드는 방향으로 정한다. 검출 대상 삭제, 허용 대상 추가,
제외 범위 확대는 서로 다른 방향이다. 무조건 목록 첫 항목을 지워 얻은 통과를 결함으로
세지 않는다. 그 항목의 실제 사용이 없거나 다른 검사가 먼저 잡았는지도 구분한다.

가드의 존재와 효과를 따로 보고한다. 의도한 위반을 해당 위치에서 검출했는지,
일부만 검사하는지, 관련 없는 실패만 만드는지를 확인한다.
실패 메시지에 형제 검사와 비교하라는 문장이 있어도 그 비교를 실행한 것은 아니다.
여러 루트 중 하나가 빠질 수 있으면 전체 하한만 두지 말고 루트별 결과도 확인한다.
한계를 적을 때에는 그 때문에 확인하지 못하는 동작까지 명시한다.

### 개수가 줄었을 때

테스트·메서드·등록 항목 수의 감소를 바로 손실로 판단하지 않는다.
이전 위치와 새 위치를 함께 포함해 이동 여부를 확인하고, 합쳐진 항목과 삭제된 항목을
이름과 검증 내용으로 대조한다. 합친 테스트가 이전 조건을 모두 확인하는지도 읽는다.
대상이 없어져 검증이 필요 없어졌다면 그 이유를 남긴다.
비교에 사용한 경로 범위와 커밋을 함께 기록한다.

### 거절한 이유를 검사한다

셸 검사의 `0/1/2`는 성공·위반·판정 불가를 구분한다. 어느 조건이 거절했는지까지
구분하지는 못하므로 회귀 검사는 종료 코드와 그 조건만의 메시지 조각을 함께 확인한다.
문장 전체를 고정해 표현 개선을 막지 않는다. 메시지 조각이 다른 거절이나 일반 출력에도
나오는지 확인하고, 해당 게이트를 호출하는 테스트에서 나온 증거만 사용한다.
거절 메시지 검사의 잔여 상한은 증가와 감소 양쪽을 검사하며, 감소하면 상한도 낮춘다.
현재 수집기가 지원하는 거절 형식 밖까지 검사한다고 보고하지 않는다.

## 새 검사가 필요한지 판단하기

기존 검사나 타입이 같은 결함을 이미 막는지 먼저 찾는다.
새 실패 메시지가 요구할 수정이 실제로 문제를 해결하는지도 확인한다.
단순히 숫자를 맞추거나 정상 문서를 기계 표현으로 바꾸게 만드는 검사는 추가하지 않는다.
그다음 실제 검사 대상과 위반 조건을 정한다.

검사를 만들지 않을 때는 구체적인 이유와 다시 검토할 조건을 남긴다.

| 이유 | 다시 검토할 때 |
|---|---|
| 기존 검사가 같은 문제를 처리함 | 그 검사가 없어지거나 범위가 달라짐 |
| 실패 후 올바른 수정 방법을 정할 수 없음 | 문제와 정상 상태를 구분할 기준이 생김 |
| 현재 검사할 대상이 없음 | 대상이 실제로 생김 |
| 필요한 사실이 검사 입력에 없음 | 입력이나 관측 방법이 생김 |
| 규격 검토·측정이 먼저 필요함 | 그 선행 작업이 완료됨 |
| 무엇을 위반으로 볼지 아직 미정 | 정책이 결정됨 |

대상이 적다는 이유만으로 검사를 금지하지 않는다. 적은 범위만 보장한다고 명확히 쓰면 된다.
대상이 정상 사례인지 위반 사례인지도 구분한다. 가드가 읽지 않는 문서가 늘어났다는 것만으로
새 결함이 늘어난 것은 아니다. 모든 문서 숫자에 자동 검사를 요구하지 않는다.
담당자가 정해지지 않아 작업하지 못한 사정은 검사가 불필요하다는 설계 근거가 아니다.
병합 트리에서만 드러나는 문제는 검사 입력을 새로 만들기 전에 병합 결과에서 기존 검사를 실행한다.

일반 산문이 가리키는 의미 전체를 자동 검사한다고 주장하지 않는다.
인용 경로의 존재나 이름 붙인 테스트의 실행 경로는 확인할 수 있지만,
그 테스트가 문장의 주장 자체를 검증하는지는 실제로 깨뜨려 확인해야 한다.
문장 옆에 변이 기록이 존재한다는 검사로 현재 검출력을 대신하지 않는다.

### 한 번만 일어나야 하는 효과

같은 ID를 재전송하거나 소비자를 한 번 더 실행해 두 번째에는 효과가 없음을 확인한다.
첫 번째에는 효과가 있었고 다른 ID까지 지우지 않았다는 것도 함께 확인한다.
목록 상한에 따른 퇴출 때문에 ID가 사라져 검사가 통과하지 않도록 입력 크기를 정한다.
재시작이 상태를 비워야 하면 새 프로세스에서 다음 판정도 실행한다.

once 훅은 한 호출에 맞는 사건이 여러 개여도 첫 사건에서 한 번만 실행되고,
지속 훅은 사건마다 실행되는지 확인한다. 이런 동작은 문법 패턴 명부보다 행동 테스트로 지킨다.
`remove`나 `take`의 반환값에 효과가 묶여 있는 구조와 별도 제거 줄에 의존하는 구조를 구분한다.
반복해도 같은 결과인 멱등 동작에 '정확히 한 번'을 일률적으로 요구하지 않는다.

## 판정 대상과 분석기의 한계

변이 실행이 컴파일 오류로 끝났다면 테스트가 검출한 것으로 보고하지 않는다.
테스트 결과 줄과 실행한 타깃을 확인한다. 합성 파일도 해당 빌드의 모듈로 선언돼 있어야 한다.
복구 뒤 `cp -p`로 옛 mtime을 되살렸다면 `touch`하고 다시 컴파일되는지 확인한다.
테스트 이름과 개수만 같다는 것은 새 소스로 만든 실행 파일이라는 증거가 아니다.

번역 키를 그대로 돌려주는 스텁에서는 키 문자열 포함 여부만으로 번역문을 검사할 수 없다.
실제 번역 함수의 결과와 비교한다. 라우팅 키도 메서드에 따라 타입이 다르면
키 이름 하나 대신 메서드와 키의 쌍을 검사한다.

소스 분석기를 쓸 때는 재수출, 같은 이름의 함수, 메서드 호출과 자유 함수,
여러 줄 리터럴, 공백을 제거하며 합쳐진 토큰을 확인한다.
첫 후보의 실패로 전체 탐색을 끝내지 않는지도 본다.
독립된 방법과 결과 집합을 비교하되, 두 방법이 같다고 완전성이 증명됐다고 쓰지는 않는다.

리팩터링으로 표를 나누었다면 새로 어긋날 수 있는 관계를 나열하고 타입·생성 과정·테스트가
각각 무엇을 막는지 확인한다. 타입이 이미 막는 관계에 같은 텍스트 검사를 덧붙이지 않는다.

지표를 줄이기 전에 값이 가장 작아지는 상태가 원하는 상태인지 묻는다.
예를 들어 길이 타입의 `.value()` 호출을 전혀 세지 못하는 무타입 코드는 좋은 결과가 아니다.
허용된 외부 API 경계에 변환이 모였는지를 확인한다.
같은 기본값을 가진 상수와 디자인 토큰은 기본 배율에서 구분되지 않으므로
둘 이상의 배율에서 동작을 확인한다.
위젯 크기를 호출자가 별도 상수로 보정한다면 원본 값 변경에 함께 따라가는지 본다.

## 문서를 읽는 검사

Markdown 절은 다음 헤딩뿐 아니라 파일 끝에서도 끝날 수 있다.
같은 정보가 헤딩·본문·불릿에 나타날 수 있고, 코드펜스 안의 규격 예시는 실제 선언이 아니다.
영문·한글 제목, 숫자·낱말 표기도 함께 확인한다.
처리한 문서 수와 후보 목록을 비교해 제외한 이유를 확인한다.
소스에서 예시가 잘 보인다는 이유만으로 렌더 결과도 완전하다고 가정하지 않는다.

준비 부족과 제품 결함이 같은 메시지로 나오면 실제 실패 위치에 구분 진단을 붙인다.
자세한 예는 [자체 검증](self-verification.md#준비-부족과-제품-결함을-구분한다)을 따른다.
