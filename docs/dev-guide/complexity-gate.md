# 복잡도 검사

큰 함수와 파일의 증가를 제한하고 기존 예외를 줄인다.
선택의 이유는 [CI와 복잡도 검사 결정](../adr/0047-ci-and-complexity-checks.md)에 있다.

## 무엇을·도구·임계값

| 검사 | 도구 | 기준 | 예외 또는 기준값 |
|---|---|---|---|
| 함수 인지 복잡도 | clippy `cognitive_complexity` deny | 20 | 함수의 allow와 구체적 사유 |
| 파일 제품 SLOC | tokei와 `check-file-size.sh` | 1000 | `.complexity-file-allowlist` |
| 예외 파일 총합 | `check-frozen-sum-ratchet.sh` | 예산부터 예산+파일 임계값까지 | `frozen-sum-budget` |
| doc 주석 계측 편향 | 같은 tokei의 두 측정 | 기록된 편향과 같음 | `doc-comment-bias` |

설정값은 `clippy.toml`과 검사 스크립트가 관리한다.
예외 개수는 본문에 복제하지 않고 실제 목록을 확인한다.
인지 복잡도는 모든 코드 복잡도를 대표하지 않으며 도구 버전과 매크로 처리에 영향을 받는다.

## 예외 컨벤션

### 함수 (cognitive)

`#[allow(clippy::cognitive_complexity)]`에는 `complexity-exempt:` 주석으로
왜 분해가 부적절한지 구체적으로 적는다. 빈 사유나 나중에 고치겠다는 말만으로 허용하지 않는다.
클로저의 lint는 감싸는 함수의 lint 범위도 확인한다.
리팩터링으로 임계 이하가 되면 allow를 제거한다.

### 파일 (SLOC)

큰 파일은 먼저 분할을 검토한다. 예외가 필요하면 저장소 상대 경로와 이유를 남긴다.
검사 미실행 기간에 생긴 기존 부채 목록은 새 위반을 추가하는 장소가 아니다.
예외가 필요 없어지면 항목과 총합 예산을 함께 줄인다.

테스트 코드와 생성 코드는 이유가 다르다.
테스트는 제품 빌드에 들어가지 않으며, 생성 코드는 제품에 들어가도 사람이 직접 유지하지 않는다.
패키지 루트의 Cargo `tests/`와 `src/` 안에서 이름만 tests인 모듈도 구분한다.
생성 파일은 `DO NOT EDIT` 등 실제 표지를 확인한다. 이름을 바꾸는 것만으로 면제받지 않는다.

`sloc_gate_skip_proxy`는 스크립트의 이름 패턴을 선언 기반 분류와 대조한다.
테스트 전용 파일은 전체를 빈 줄로 측정하므로 부채 목록에 등록할 이유가 없다.
별도 가드가 raw 줄 수를 tokei SLOC 대신 사용하지 않는다. 문자열을 지운 줄 수 역시
제품 SLOC의 안전한 상한이 아니다.

## 로컬 재현

```bash
cargo build -p tasty-doc-guards --bin strip-cfg-test
cargo clippy --workspace --all-targets
bash scripts/check-file-size.sh
bash scripts/check-frozen-sum-ratchet.sh
```

파일 검사는 tokei, Python, 준비된 `strip-cfg-test`가 필요하다.
필요하면 `TASTY_STRIP_CFG_TEST_BIN`으로 바이너리 경로를 지정한다.
0은 측정 성공·위반 없음, 1은 측정한 규칙 위반, 2는 도구·입력·파싱 등의 측정 실패다.
빈 Rust 보고를 성공으로 처리하지 않는다.

## baseline 갱신

함수나 파일이 임계 이하가 되면 해당 예외를 제거한다.
새 예외에는 구체적인 이유를 남기고 임계값 자체를 회피 목적으로 올리지 않는다.
임계값 변경은 근거와 영향 범위를 검토한 별도 선택이어야 한다.

## CI 배선

실행 이벤트와 빌드 조합은 [CI 가이드](ci-gates.md)를 따른다.
파일 크기와 예외 총합은 함께 실행한다. 한 검사의 통과가 다른 검사를 대신하지 않는다.

## 임계값과 예외 예산을 바꿀 때

파일 SLOC 1000은 코드 품질에서 수학적으로 도출한 값이 아니다.
과거 이력에서 인접 임계값별 분해 요구 건수를 비교했을 때, 상향해도 요구 건수가 줄지 않는
구간의 가장 낮은 값이어서 유지했다. 분포의 상위 몇 퍼센트라는 설명만으로 정당화하지 않는다.
과거와 현재를 비교할 때는 양쪽 소스를 같은 검사기로 측정해야 한다.

예외 파일에는 경로만 있으므로 개별 파일 성장은 파일 크기 검사만으로 막을 수 없다.
`check-frozen-sum-ratchet.sh`는 예외 파일의 제품 SLOC 총합을 검사한다.
`frozen-sum-budget`은 지금까지 줄인 총합을 기준으로 두며, 허용 여유는 파일 임계값에서 읽는다.
총합이 예산과 여유의 합을 넘으면 실패하고, 예산보다 줄어도 예산을 낮추도록 실패한다.
개별 파일 상한 대신 총합 한 줄을 택한 이유는 예산을 늘린 변경을 리뷰에서 쉽게 찾기 위해서다.
전체 코드 대비 비율은 저장소와 예외 파일이 함께 자라면 변하지 않아 사용하지 않는다.

실패한 커밋이 누적 증가의 주된 원인이라고 단정하지 않는다. 파일별 이전 변경을 확인한다.
예외 경로를 추가·삭제하면 총합도 바뀌므로 같은 변경에서 예산을 조정하고 목록 변경 사유를 남긴다.
테스트를 제외하는 등 측정 방법이 바뀐 결과를 제품 코드 감소로 보고하지 않는다.

다음 상황은 자동 검사와 별도로 검토한다.

- 예외 파일 중 임계값의 두 배를 넘는 파일이 5개 이상이면 개별 상한 도입을 검토한다.
- 12개월 동안 리팩터링으로 제거한 예외가 없으면 예외 정리 방식을 다시 정한다.
- 12개월에 세 번 이상 목록 변경 없이 예산만 올렸다면 총합 방식의 우회 여부를 검토한다.
- 예산을 낮추라는 실패가 12개월에 30회를 넘으면 실제 관리 비용을 비교한다.
- 새 측정 기간에 1000과 1250의 분해 요구 건수 차이가 3 이상이면 임계값 유지 근거를 다시 본다.

이 항목들은 자동 알림이 있다는 뜻이 아니다. 목록 변경 이력과 CI 실패 로그로 확인한다.

총합 검사는 한 파일 증가와 다른 파일 감소가 상쇄되면 개별 성장을 발견하지 못한다.
파일마다 같은 허용 여유를 주면 전체 허용량이 파일 수만큼 커지고, 총 허용량을 같게 줄이면
작은 변경마다 예산 갱신이 필요해진다. 그래서 총합을 유지한다. 상쇄된 성장이 실제 문제를
만들거나 예외 목록이 크게 늘면 개별 상한과 총합의 비용을 같은 기간으로 다시 비교한다.

## 계측용 사본과 측정값 보정

`strip-cfg-test`는 인라인 테스트와 테스트 전용 파일을 빈 줄로 바꾼다.
줄 번호는 유지한다. 파일 전체가 테스트 전용인지는 파일명이 아닌 선언 경로로 판단한다.
여러 선언 중 하나라도 제품 코드에서 도달할 수 있으면 제품 파일로 남긴다.
두 SLOC 스크립트는 같은 `SCAN_DIRS`, 임계값, 전처리 플래그를 사용한다.
공유 설정을 읽지 못하면 기본값으로 진행하지 않고 측정 실패로 끝낸다.

SLOC 측정에만 `--neutralize-char-literal-quotes`를 사용한다.
tokei가 문자 리터럴의 따옴표를 문자열 시작으로 오독하지 않도록 측정 사본을 바꾸는 옵션이다.
플러그인 내용 비교에는 사용하지 않는다. 다른 문자를 같은 것으로 바꾸면 실제 변경을 놓친다.
보조 바이너리는 호출 전에 빌드하며 검사 스크립트가 cargo를 중첩 호출하지 않는다.

총합 검사는 doc 주석을 포함한 사본과 doc 주석 줄을 뺀 사본을 같은 tokei로 측정한다.
그 차이는 `doc-comment-bias`로 고정하고, 편향이 변하면 예산도 측정값 변화에 맞춰 보정한다.
예를 들어 누락 편향이 Δ만큼 커져 측정 총합이 Δ만큼 작아지면 예산도 Δ만큼 낮춘다.
예산을 현재 총합에 바로 맞추면 같은 변경에 포함된 실제 코드 증가까지 허용할 수 있다.
최소 재현의 결과가 달라지면 도구의 계산 방식부터 확인하고 예산을 고친다.

총합이 줄었다면 코드 감소, 예외 목록 삭제, 검사 누락, 계측기 오류 교정을 구분한다.
오류 교정을 이유로 예산을 낮추려면 다음 두 근거를 남긴다.

1. 손으로 올바른 줄 수를 셀 수 있는 최소 재현과 회귀 검사.
2. 감소한 파일 전체의 전후 값. 해당 오독 형태가 없는 파일까지 감소하지 않았는지 확인.

제품 코드 증가와 테스트 증가를 따로 넣어 보는 검사만으로 특정 문법의 누락까지 배제할 수는 없다.
이전 측정값은 자동 보관되지 않으므로 변경 전에 저장하거나 이전 Git 트리를 다시 측정한다.
