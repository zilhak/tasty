# 가드 파일을 **옮길 때** 무엇이 깨지는가

검사 대상과 조건이 같아도 가드 파일을 옮기면 저장소 루트, 빌드 조합, 실행 타깃이 달라질 수 있다. 이동 전후에 인용 경로와 실제 실행 목록을 확인한다.

검사 대상을 정하는 방법은 [guard-population](guard-population.md), 결함 검출력을 확인하는 방법은 [guard-verification](guard-verification.md)을 따른다. 이 문서는 파일 이동 때문에 달라지는 조건을 설명한다. 루트 통합 테스트를 별도 문서 검사 크레이트로 옮기는 경우도 아래 항목을 함께 확인한다.

<a id="두-방향으로-깨지는데-채널은-한쪽에만-있다"></a>

## 이동으로 바뀌는 검사 조건

파일을 옮기면 기존 경로 인용이 깨질 뿐 아니라 새 디렉터리의 검사 대상에 들어갈 수 있다.
새 위치에서 읽는 가드의 필터와 하한까지 확인한다. 다음 항목 이름은 survey-guard-move가
출력하는 분류와 대응한다.

## 축 일곱

### M-a — 새 뿌리가 그것을 세기 시작한다

새 경로를 순회하는 가드가 파일을 검사 대상으로 받아들이는지 확인한다.
공용 순회 함수를 쓴다는 사실만으로 모든 소비자의 제외 조건이 같은 것은 아니다.
경로 이름을 찾는 조사 결과는 후보이며 실제 조건식을 읽어야 한다.

### M-b — 세기 시작하는데 그 내용이 위반의 모양이다

파서 시험에 들어 있는 금지 구문·코드포인트·옛 경로 예시가 새 검사에서 실제 위반으로
읽힐 수 있다. 실제 코드인지 합성 입력인지 구분하고, 시험의 의미를 유지한다.
정상 예시를 삭제하거나 가드의 범위를 넓게 제외해 통과시키지 않는다.

### M-c — 뿌리를 얻는 **표현식**이 위치 의존이다

패키지가 바뀌면 CARGO_MANIFEST_DIR의 기준도 바뀐다. 저장소 루트가 필요한 가드는
repo_root와 대표 파일 확인을 사용한다. 잘못된 경로에서 빈 결과가 나와도 통과하지 않게 한다.

### M-d — 파일이 자기 **채널에 대한 주장**을 담고 있다

새 패키지의 자동 실행 범위를 확인하고 해당 파일과 관련 문서의 설명을 갱신한다.
GUI/headless, 컴파일/실행, 수동/자동을 구분한다. 다른 파일에 적힌 설명도 검색한다.

### M-e — 뿌리 **목록**이 같아도 뿌리별 **하한**이 있다

파일 이동은 총수를 유지해도 출발 디렉터리의 개수를 줄인다.
전체 합뿐 아니라 각 디렉터리의 하한을 확인하고, 정상 이동인지 확인한 뒤 근거를 갱신한다.

### (가) — 옛 경로를 가리키는 인용

옛 경로를 전수 검색하고 실제 인용을 갱신한다. 경로 문법을 시험하는 합성 문자열은
존재하는 파일을 가리키는 인용과 다르므로 의미를 확인한 뒤 유지한다.

### (가′) — 이동 **뒤에** 생긴 인용

다른 작업이 옛 경로를 사용한 문서를 추가했다면 두 작업을 합친 뒤에야 링크가 깨진다.
rebase나 병합 직후 다음 검사를 실행한다.

```bash
cargo test -p tasty-doc-guards --locked --test cited_coordinates_exist
```

## 이동 전에 재는 법

`scripts/survey-guard-move.sh` 가 위 항목을 조사하고, 축마다 **찾은 것과 찾은
명령**을 함께 찍는다.

```bash
bash scripts/survey-guard-move.sh <옮길-파일> <목적지-경로>
```

**이 도구는 위반을 판정하지 않는다.** 정상 조사 종료는 0, 조사할 수 없는 경우는 2다. 이름이 `check-` 가 아닌 것도 그래서다 — 이 레포에서 `check-*.sh` 는 전부 판정하고
훅과 CI 가 그것으로 커밋을 막는데, 위 축들에는 정당한 예외가 실제로 있다(M-b 만 해도
세 갈래 중 둘은 처방이 "아무것도 하지 않는다" 이다). 이를 모두 위반으로 처리하면 정당한 예외도 실패하게 된다.

한계도 그 도구의 주석에 적혀 있다. M-a 와 M-d 는 **후보만** 내고, M-b 는 절반만 기계적이다
(코드포인트는 셀 수 있지만 "이 내용이 저 가드에게 위반인가" 는 가드마다 다르다).
그리고 **(가′) 는 원리적으로 못 잰다** — 이 도구는 이동 전에 도는데 그 축은 이동 뒤에
생긴 글이다. 억지로 넣는 대신 그 자리에 rebase 뒤 돌릴 명령을 찍는다.

## 이동 뒤에 돌릴 것 — **양쪽 패키지**를 돌린다

```bash
cargo test --locked -p tasty-doc-guards --no-fail-fast
cargo test --locked -p tasty --lib --no-fail-fast
```

`-p <크레이트>` 는 **루트 패키지의 통합 타깃을 안 돌리고, 그 반대도 마찬가지다.** 이동은
두 패키지를 건드리므로 한쪽만 돌리면 절반이 미측정이다.

★ 여기에 이동 고유의 함정이 하나 더 있고, **두 형태가 갈린다.**

| 어떻게 부르는가 | 무슨 일이 나는가 |
|---|---|
| 옛 패키지에 **이름을 주고** 부른다 (`-p tasty --test <옮긴 이름>`) | 그런 타깃이 없어 명시적으로 실패한다 |
| `--test` 를 **안 붙이고** 패키지만 돌린다 | 그 타깃이 **조용히 빠진다** |
| 루트 패키지를 `--bins` 로 좁힌다 (`-p tasty --bins`) | 루트의 단위시험은 전부 lib 타깃에 살아서 **`test result: ok. 0 passed` 가 찍힌다**. 좁히려면 `--lib` 다 |

위험한 것은 뒤엣것이다. 실패하지 않고, 로그에 그 타깃의 `test result:` 줄이 **아예 없을
뿐**이다. 누락된 실행을 성공으로 오해할 수 있다 — 그래서 판정은 rc 가 아니라 **`test result:`
줄의 존재와 내용**으로 한다. 이동한 타깃은 새 패키지 이름으로 부른다.

`--no-fail-fast` 를 빼면 앞 타깃이 실패하면 뒤 타깃들이 안 돌고, 그 결과는 실패가
아니라 **미측정**이 된다. 이동은 여러 타깃을 동시에 건드리므로 이 플래그가 특히 중요하다.

### 인라인 가드와 다른 패키지도 확인한다

가드는 tests 디렉터리뿐 아니라 각 크레이트의 `#[cfg(test)]` 모듈에도 있다.
옮긴 경로를 읽는 호출자와 확장자·디렉터리를 순회하는 소비자를 함께 찾는다.
실제 소유 패키지는 Cargo.toml과 cargo metadata로 확인한다. 파일 이름만으로 패키지를
짐작하지 않는다. 루트 유닛 가드는 `--lib`가 필요하며 `--bin`만으로 실행되지 않는다.

이동 중인 다른 작업자는 현재 트리에서 타깃 소유 패키지를 다시 확인한다.
예전 `-p` 명령이 성공해도 해당 타깃이 다른 패키지로 옮겨졌다면 검사한 결과가 아니다.
`-- --list`와 실행 로그로 의도한 시험 이름·개수가 있는지 확인한다.

문자열 인용의 역색인은 후보를 찾는 도구다. 디렉터리 순회, 런타임 경로 구성, 공용 하네스
의존성을 모두 찾지는 못한다. 서로 다른 입력을 우연히 같은 결과로 판정하는 경우도 있으므로
목적지 경로를 실제로 읽는지 확인한다. 자세한 영향 조사는 [CI 가이드](ci-gates.md)를 따른다.

## 왜 하한을 낮추면 안 되는가

루트 `tests/` 는 **설계상 계속 줄어드는 중**이다. 그러니 그 뿌리에 걸린 하한은 이동마다
한 번씩 낮춰야 하고, **매번 낮춰야 하는 상수는 래칫이 아니라 세금이다.** 세금은 낼 때마다
느슨해진다.

처방은 둘로 갈린다.

- **하한이 두 검사 대상 집합의 관계를 재는 것이면 부등식으로 바꾼다.** 예: "넓힌 뿌리 목록이 좁은
  것보다 넓다" 는 절대 수가 아니라 두 순회의 비교로 물을 수 있고, 그러면 이동이 몇 번
  나든 상수를 안 만진다. 비교는 **양쪽을 독립으로 걷는다** — 넓은 쪽에서 빼서 좁은 쪽을
  구하면 부등식이 자기참조가 되어 두 목록이 같아진 고장을 못 잡는다.
- **그럴 수 없으면 여유를 한 번에 크게 준다.** 매 이동마다 조금씩 낮추는 대신, 그 뿌리가
  줄어드는 뿌리라는 사실을 주석에 적고 여유를 한 번에 준다. 그리고 **왜 이 뿌리만 여유가
  다른지**를 그 자리에 적는다 — 안 적으면 다음 사람이 그 값을 다른 뿌리들과 같은 규칙으로
  읽는다.

## 자동 채널

위 명령들이 CI·훅 중 어디서 실제로 도는지는 [`ci-gates.md`](ci-gates.md) 가 정본이다.
여기에 다시 적으면 두 곳이 어긋난다.

한 가지만 이 문서의 주제라 적어 둔다 — pre-commit 훅은 **새로 추가된 파일**을 보고 그것을
처음 보는 타깃을 제안한다(`.githooks/pre-commit` 의 `check_new_file_judges`). 그것이 바로
M-a 를 커밋 시점에 짚는 자리다. 경고일 뿐 커밋을 막지 않으므로, **그 줄이 나오면 제안된
명령을 실제로 돌린다.**

## 문서 검사를 옮길 위치

제품 크레이트를 링크하지 않고 파일을 읽는 문서 검사는 `tasty-doc-guards`에 둔다.
이 크레이트는 외부 의존성을 추가하지 않고 유지하며, 문서만 바뀐 push에도 실행한다.
본체 빌드 비용 때문에 문서 경로를 CI에서 제외하는 문제가 반복되지 않도록 하기 위해서다.

제품 상수가 필요하면 소스 텍스트 판독과 링크한 실제 값의 교차 검사를 분리할 수 있다.
텍스트 판독은 알 수 없는 형태와 빈 결과를 거부한다. 실제 타입을 링크해야 하는 검사는
해당 패키지에 두고 문서 변경에도 실행되는 경로가 있는지 확인한다.
이미 별도 워크플로가 이름으로 실행하는 타깃은 이동 전에 그 호출도 확인한다.

이동 뒤 저장소 루트는 공용 `repo_root()`로 찾고 표지 파일을 확인한다.
`Cargo.toml` 하나만 확인하면 가드 크레이트 디렉터리를 저장소 루트로 오인할 수 있다.
검사 실행 경로는 파일 이름보다 성질로 확인한다. 경로 필터가 없고, 자동 이벤트에서 실행되며,
패키지 전체를 필요한 범위로 검사하는지를 본다. 크레이트를 workspace에서 빼면
`cargo test --workspace`의 검증도 사라진다.

## 파일이나 도구를 추가한 뒤 확인할 것

Cargo가 새 타깃을 찾아 컴파일했다는 것과 출력이나 등록 내용을 검사했다는 것은 다르다.
새 바이너리의 출력, 크레이트 등록·라이선스, 플러그인 매니페스트 검증 중 무엇이 필요한지
확인하고 실제 검사 타깃을 실행한다. 파일이나 함수를 옮겼을 때도 cfg 때문에 실행 범위에서
빠지지 않았는지 테스트 목록을 확인한다.

검사 코드가 없으면 필요한 검사를 추가한다. 코드가 있는데 실행되지 않았다면 다음을 나눈다.

- 앞 단계 실패나 취소로 이번 실행에서만 건너뛰었는가.
- `#[ignore]`, 빌드 조합, 수동 전용 트리거 때문에 자동으로는 실행되지 않는가.

후자에는 같은 검사를 하나 더 만들기보다 기존 실행 경로부터 고친다.
소스 갱신 뒤에는 `cargo build -p tasty-doc-guards --bins`로 보조 도구를 다시 준비한다.

새 파일 종류별 검사 안내는 `.githooks/pre-commit`의 W.2 목록에서 관리한다.
문서에 같은 목록을 복제하지 않는다. 이 안내는 staged 추가 파일만 보는 경고이며,
수정·이동과 모든 관련 검사를 망라하지 않는다. 미분류 파일도 표시한다.
확장자와 shebang만으로 종류가 완전히 정해진다고 가정하지 않는다.
source 전용 셸에는 shebang이 없을 수 있다.
