# HTTP transport bridge

The `tasty-ipc` HTTP leaf defines an opt-in Control-frame family separate from file HTML transfer. It does not enable or advertise a remote HTTP viewer. The leaf is publicly exported for shared host/client integration. Export alone does not activate dispatch or advertise capabilities; those require working server and native routes.

`HttpRequest` and `HttpReply` preserve the six-field transfer identity, source generation and server-issued response serial. Only encoded chunks cross this wire. Complete carries both encoded and decoded byte lengths and SHA256 identities. Clients assemble and verify the encoded body, decode under a separate bounded worker quota, verify the decoded identity and scan before exposing a body to native rendering. Native must receive the same immutable encoded representation with matching status and end-to-end headers.

Both directions validate the complete serialized frame before enqueue. Header order, duplicate names and non-UTF8 value bytes are retained. Metadata, header counts/bytes, methods, chunk windows, decoded base64 and portable lengths are bounded. HTTP DTOs deliberately omit Debug implementations for request URLs, headers and payloads. Failure reasons must be sanitized by their producer; validation bounds their size and rejects control characters.

CommandRejected identifies a rejected command with CommandKind and an optional supplied response identity. It does not end an existing accepted response. Failure is reserved for an attempt that actually ended; its exact identity cannot later complete or be reused.

HttpReply::retained_bytes is a nonconsuming, allocation-free query for dynamic capacities, independent of validation or frame serialization. Head includes URL capacity, all allocated header-vector slots (including spare slots), and initialized header name/value capacities. Chunk includes base64 string capacity; Failure and CommandRejected include reason capacity. Other variants retain no dynamic bytes. Arithmetic saturates; fixed queue slots, wire payload/framing and encoded document consent are accounted separately.

The HTTP and HTTPS capabilities additionally require the existing HTML transfer capability. Existing file wire messages and old-peer behavior remain unchanged. The server descriptor must not advertise an executor merely because these types compile. Native parsing, TLS exceptions, cache retirement and browser consent are separate integration obligations.

## Server ownership and flow

`remote::html_http_server::Server` receives an already constructed finite HTTP Backend and the same injected resource limits. Construct network/TLS clients on a setup worker. Server admission, commands and polling perform no network I/O, runtime construction or waiting joins.

The engine captures its actual registration, SSH grant, source Weak and generation before calling `admit(Capture)`. Capture contains the authoritative entry identity and reported URL plus the document's fixed client cross-origin policy. Retain that actual authority alongside the returned opaque OwnerToken. Pass that token and a current-authority predicate on every `handle` and `poll`; matching client numbers cannot manufacture this local token. A failed predicate retires the owner and drops queued core events. `retire` also handles disconnect, source replacement and fresh Reload. The caller remains responsible for invalidating frames already handed to its connection and fencing native publication by full identity.

GUI and headless consume one ordered inbound File/Http Control queue. A peer must declare transfer and HTTP support before its validated HTTP commands enter this queue; actual host admission additionally requires the viewer capability and HTTPS capability for secure destinations. The server descriptor still does not advertise HTTP/HTTPS support. The engine's HttpHost dispatches admitted commands to the finite executor and polls through the existing HTML collector. It captures the specific surface's ready workspace grant, membership, registration, source Weak and generation; matching a client that owns some other workspace is insufficient.

StreamHub::admit_html_request owns the registration-scoped request and transfer high-watermarks and compares the captured binding under the same sink lock. File and HTTP admission share this allocator. New Begin claims both counters only after source, policy, upload and document/request-capacity checks and existing-document duplicate classification. A rejected claim advances neither counter and cannot retire an accepted document. Registration replacement resets the new cursor without allowing the old binding to reset it back. Upload, commit, credit and lifecycle commands allocate no identity. An HTTP document's first Begin must name its captured source and reported URL; later requests remain subject to the core origin policy.

The engine lazily starts a bounded setup worker for admitted HTTP work. This worker constructs the platform-normal TLS client and an injected two-thread Tokio runtime; construction, blocking decode termination and runtime destruction never run on the engine loop. At most eight setup/runtime owners remain live, including retired workers until actual termination. Finished setup threads are joined only after is_finished. Network and decode workers are bounded at eight, document owners at eight, request/tombstone slots at256 per document, and individual retained/upload/encoded/decoded capacities by the existing64MiB connection resource limit. These resource limits do not grant browser consent: the100000-byte Allow threshold and2000000-byte aggregate Continue accounting remain independent client obligations. Network waits have30-second connect/read/active-network limits; user consent and credit waits do not consume that active-network time. Backend event enqueue wakes the actual engine callback. A pending initial Begin owns its shared ID while setup completes; no upload window is sent before actual server admission.

Begin reserves one bounded request/tombstone slot and checks the declared upload size before assembly. Poll grants a single exact-offset upload window. Commit freezes a complete upload, verifies its length and SHA, then calls the existing Document.open once. Duplicate admission uses the executor-equivalent normalized method, fragment-free URL, upload identity and ordered cleaned headers. Keep this admission signature aligned with the finite backend's header cleaner and fingerprint; differential component tests compare the public executor's pending/retired duplicate decisions. A failed or cancelled ID cannot be used for another POST.

Each running request retains only its core one-slot event channel. Poll returns at most one validated Control frame and keeps no additional encoded output queue. Reserve MAX_FRAME_LEN plus FRAME_HEADER_LEN in the connection's existing byte budget before polling; charge the actual payload plus framing after return. If that reservation is unavailable, poll leaves the event in the bounded core channel. The integrating host schedules polling through its existing pump/timer while work is pending; the bridge does not create a thread or event loop. Send errors retire that connection's captured owners. Synchronous command errors use rejection_reply(&request, &error), never failure_reply, through that same bounded connection queue and only under current captured authority. Keep the bounded command available for this correlation when passing an owned command to handle. Stale ownership does not authorize publication to a replacement owner.

Commit errors before consuming the upload leave that attempt pending. Once Commit consumes it, a SHA mismatch or core open error also queues exactly one terminal Failure in the existing request slot for normal poll. The host's CommandRejected may arrive before that terminal result. Duplicate Commit or Begin rejection cannot overwrite the queued failure. Unadmitted Begin rejection has no admitted operation and needs no additional terminal event. No extra outbox, runtime, retry or POST is created.

## Connection sender accounting

StreamHub::reserve_frame captures the actual registration and an injected connection wire-byte limit before executor polling. Its non-cloneable reservation accounts for MAX_FRAME_LEN plus FRAME_HEADER_LEN alongside all queued/live frames and other reservations. Publish with push_reserved, which reconciles to actual payload length plus framing and rejects a replaced registration. Existing traffic keeps its frame-count admission policy and contributes to the reservation counter.

The production socket writer uses recv_held_timeout and holds the byte lease through write success or failure. An incompatible stream handshake flushes its single queued negative Control ACK on the connection thread before starting any asynchronous writer or unregistering the sink. That flush retains the same held lease and live-registration/document checks; cleanup then removes the sink and bulk binding without dispatching attach. It never permits already-unregistered queues to publish. Every held frame carries a weak registration identity; reserved frames may additionally capture the unique PublicationFence retained by their actual document/grant owner. The writer checks those identities before writing, so a replacement owner cannot authorize an old queued frame. Reserved HTTP frames also carry a current-authority callback. Grant readiness, membership, disconnect and source generation invalidate queued publication synchronously, before the next engine collector pass. The engine drops the document fence when it retires that owner; a socket write already started cannot be retracted by this check. Dropped reservations and failed queues release their charges; legacy raw-frame convenience methods release at dequeue.

The engine HTTP collector reserves before polling and uses this actual sender/writer path. Native HTTP response delivery and client consent remain separate, unactivated boundaries. The wire-byte counter is separate from decoded/retained memory capacity and encoded document consent accounting. HTTP/HTTPS capabilities remain unadvertised.

## Response lifecycle

Credit names the full ResponseId, exact offset and one outstanding window. Known large responses require their own Allow. Unknown responses stop at encoded byte100001; a positive EOF probe at exactly100000 may produce completion without an Allow question. Client aggregate reservations and Continue remain independent of response Allow. The server's transferred_bytes counter records actual encoded chunks only, including short-window reconciliation; it never counts reuse as network traffic. Core payload quotas remain independent resource bounds.

Clients branch on CommandRejected before terminal handling and ignore unknown or stale full identities. Its optional response correlates the rejected Credit, Reuse or Release, not an inferred current accepted response. Keep the admitted POST, body, native waiter and accepted credit/aggregate reservations; a rejected duplicate Credit cannot release the original window. A subsequent model-authorized valid Credit can continue the same response. Do not replay, resubmit or retry automatically. A rejected first Begin may resolve its local waiter only if no existing active or complete same-ID attempt exists. Normal Chunk/Complete, terminal Failure/Cancelled, explicit cancel/Stop/close or a new user Reload resolves the lifecycle. Failure ends only the exact current failed attempt and releases provisional bytes/reservations once, retaining the tombstone and prohibiting later completion or reuse.

Complete leaves the immutable response retained in the core. Reuse emits the identical Head and both Complete identities without Chunk or network traffic; the client must already retain verified bodies. Release records the core tombstone. Stop cancels pending uploads and operations, blocks new requests and preserves successfully completed retention. Close retires the whole owner. Retirement cancels without waiting on the engine: completed operation outputs are dropped immediately, while running operations are joined asynchronously on the injected runtime. The core task retains its worker permit until actual network/decode termination. The owner of the injected runtime must complete asynchronous retirement before shutting that runtime down.

Component tests cover real finite Backend requests through a loopback HTTP fixture, upload windows and commit SHA, full identities, duplicate normalization, encoded gzip identities, exact size thresholds, cancellation and stale authority with a real completion already queued, and bounded admission. Actual engine integration tests exercise ordered Control dispatch, binary POST, asynchronous wake, credit rejection, reuse and queued authority invalidation against a loopback fixture. They do not establish negotiated native routes, native certificate challenge behavior, client aggregate consent or browser rendering. Those require the integrating host's reachable GUI/headless/native checks before capability advertisement.

## Client representation verification

The client html_http_body worker accepts a completed encoded allocation, its full response head, the original Begin method/upload identity and both Complete identities. It checks encoded length/SHA, performs cancellable identity/gzip/deflate decoding, checks decoded length/SHA and scans those exact decoded bytes. Concatenated gzip members are included. Script detection keeps its existing prefix bound while the fingerprint covers the entire decoded response. No provisional response is produced.

VerifiedBody retains the original encoded allocation and status/byte-valued headers for native delivery, plus the decoded scan allocation. Its shared BodyBudget charges retained header and body capacities; identity encoding shares one allocation. Compressed output reserves the advertised decoded length before allocating and cannot grow beyond that length or the injected decode limit. The body owner retains those leases through native writes and reuse. Pending assembly, bounded worker slots, frame queues and scan scratch have separate owners. A native resubmission must match the full ResponseId, method and upload identity; verification never performs network traffic or retries.

This verifier is a client component boundary. Current-owner publication, actual native response/proxy, script continuation and selected cache/TLS barriers still require integration. HTTP/HTTPS capabilities remain inactive; this component alone does not establish App scan/render equality or a single upstream POST.

## Client receive model

ClientDocument in tasty-remote::html_http_client owns one captured document/source and ConnectionEpoch. ClientLimits inject finite request, upload, encoded, decoded and verifier-job caps; PendingBudget shares provisional capacity across documents independently of BodyBudget and encoded consent. Closing one document does not retire the shared connection. The host allocates both counters through the common file/HTTP allocator and sends the Begin returned by admit immediately, before allocating the next Begin. The model emits no automatic Begin retry or POST replay.

Each next_command advances local state and returns one Upload, Commit or Credit. The caller must serialize and enqueue it once through its bounded sender; encode or enqueue failure calls send_failed. UploadReady grants one exact-offset bounded window. The immutable upload hash and length are checked at admission, and Commit is returned once after the last authorized Upload is handed to the ordered sender. The server sends no trailing UploadReady. Empty uploads still require their initial UploadReady. Full transfer/source/response identity fences incoming replies, while local attempt ownership fences verification results. CommandRejected preserves accepted POST/body/credit reservations. Failure is strictly terminal and tombstones the attempt.

Encoded consent reserves every possible credited byte against received plus outstanding windows before sending. Allow grants only one oversized response; Continue removes only the document cumulative pause. A known exact EOF uses a one-byte non-body probe with zero possible-body reservation. Unknown EOF probes reserve one possible byte and cannot admit byte100001 without Allow. A late known-size notice never revokes an accepted Allow or Credit. Decline immediately ends Receiving but retains in-flight reservations until exact late chunks or terminal events settle; accepted late bytes count once and their body is discarded.

Complete creates a finite VerifyJob only after head/offset/length checks. The host moves jobs into its existing bounded worker pool, runs them off the engine loop, then polls verification. The job invokes html_http_body::verify, with provisional leases and its worker slot retained until actual termination; cancellation and dropped jobs resolve their mailbox. The host still revalidates actual source/grant/native generation before publishing verified. No runtime, thread, network call or waiting join is created by the model.

Reuse requires the exact retained VerifiedBody, response, method and upload identity. Only identical Head then Complete finishes the handshake, returning the same Arc without Chunk, credit, redecoding or new network accounting. Release disables future reuse while native-held Arcs remain valid. Stop resolves unfinished presentation and preserves completed verified bodies; Close cancels document-owned work. Fresh Reload constructs a new model and identity. Script continuation retains the same verified object.

The attach reader parses validated HTTP replies into a distinct MirrorEvent::Http on the same ordered outbox as file replies and terminal/structural events. The outbox charges actual retained reply capacities; overflow reports desynchronization and clears both file and HTTP document owners. Unknown or malformed HTTP replies are not treated as file responses.

HtmlSession owns at most eight captured HTTP documents. Each CapturedDocument binds its ConnectionEpoch and a caller-supplied current source/grant/native-generation predicate before and after model access. Replacement, role removal, desynchronization and table destruction retire native-held clones; a rejected older registration preserves the accepted owner. A poisoned model is retired without recovering partially mutated state. Routing preserves full model identities and distinguishes CommandRejected from terminal Failure. No file/network I/O, decode/scan, native calls or waiting joins may run under the model mutex.

CapturedDocument::admit_and_send validates the sender’s actual ConnectionEpoch, advances admission and enqueues the Begin before another shared ID is allocated. Its command pump advances Upload, Commit and Credit once under the same model access, uses the existing bounded ConnectionSender and stops after32 commands per document/pass, waking the owner if the batch is full. The actual attach synchronization pass drives these pumps only while the connection is live and HTTP was negotiated. Encoding/enqueue failure ends the attempt without retry. Queued HTTP commands retain a weak captured-document guard checked again by the actual TCP writer; legacy frame epoch/disconnect/Detach handling and byte leases remain intact. A wire frame already being written is not retractable. The typed HttpAction adapter applies response Allow, document Continue, Decline, Stop, exact Reuse and Release under that same model/sender fence. Invalid or stale actions do not enqueue; these actions carry no JavaScript permission or new Begin. Retirement may mint one model-authorized Close for the exact entry/source before local revocation. This bounded terminal cleanup alone remains connection-scoped after native-document retirement; it cannot carry Begin/Upload/Commit/Credit, and server full-identity/source checks still apply. Desync and role removal use this cleanup before dropping their table entries.

This routing does not yet construct the document from a live native surface, dispatch verification jobs or connect the body factory/native listener. HTTP/HTTPS capability advertisement remains inactive. Portable model and ordered-outbox tests do not establish native rendering or upstream POST counts.

## Native HTTP byte boundary

The exported html_http_native codec reads one finite native HTTP request after endpoint authentication and destination admission. Destination binds the scheme, canonical host and effective port; both Host and absolute request targets must match it. It preserves methods, binary uploads and ordered byte-valued headers, handles finite Content-Length or chunked uploads and local100-continue, and reserves a known upload’s complete native capacity before publishing that interim response. For unknown chunked uploads with Expect, it first reserves an initial window bounded by CHUNK_BYTES and the upload limit; subsequent chunk growth reserves replacement capacity while retaining the old lease, before reading that chunk. A non-Expect chunked upload keeps incremental admission. It refuses ambiguous framing, CONNECT and WebSocket upgrades. Request trailers are explicitly unsupported. It performs no DNS, socket connect, upstream request or direct-network fallback. The endpoint must bound accepted connections before authentication and close every rejected, retired or completed connection.

NativeBudget charges provisional native header/body capacities separately from model PendingBudget, verified BodyBudget and encoded consent. Keep the NativeRequest owner alive while its upload and metadata remain in use. Chunked buffer replacement reserves the new allocation while the old allocation is still charged. Read/write I/O deadlines do not run while the host waits for size consent, script consent or verified-body delivery.

write_response accepts an existing VerifiedBody plus the exact expected response identity, method and upload identity. It validates framing before publishing the status line, preserves status, duplicate end-to-end header values and original encoded bytes, and retains the verified owner through actual writes. A guarded I/O adapter rechecks generation before each underlying read/write/flush/shutdown poll, including partial writes and Pending repolls. Already accepted bytes cannot be retracted. It cannot create a Begin, resubmit a POST, change origin, inject file CSP or grant a certificate exception. These exported byte boundaries still require the actual authenticated listener, native context and App session connections; their asynchronous byte tests do not establish browser or App execution. HTTP/HTTPS capabilities remain inactive.


## Linux private native profile lifecycle

The Linux `http_context::profile` component prepares one unpredictable private disk-backed native store per connection. It does not create a runtime or worker. On an existing bounded worker, the host prepares an explicit absolute namespace with safe ancestry, current-UID ownership and mode0700, then calls `PreparedProfile::create(parent, max_roots)`. Missing, symlinked, foreign, writable ancestry (apart from root-owned sticky temporary ancestors) or unsupported safe filesystem operations fail without a fallback or changes to shared ancestors. Root/data/cache directories are explicitly0700 and the exact ownership record is0600 even under a restrictive umask. The finite root cap counts unclassified entries; a nonblocking namespace lock reports contention as Capacity. Capacity and filesystem errors reach the existing session error presentation.

Native construction consumes PreparedProfile into NativeProfileLease, retains clones through managers, views, probes and callbacks, and uses both supplied data/cache paths on the same non-ephemeral manager with persistent credential storage disabled. These moves, getters and both Drop paths perform no filesystem I/O. A cancelled unpublished preparation can return to its worker for `discard_unpublished`; a published lease cannot invoke that deletion. Selected cache and service-worker clearing keeps the same manager and excludes cookies, localStorage and IndexedDB. Native construction, worker dispatch and actual session ownership require the integrating host's separate validation.

A bounded worker may call `reclaim_dead(parent, max_entries)` later. Valid ownership includes exact path bytes, UID, root/namespace device and inode, PID/start and boot identity. Live owners and mismatched or inaccessible observations are retained; no age or weak-object-finalization rule authorizes deletion. A dead owner additionally requires a complete bounded read-only same-UID process FD/maps/cwd/root/exe audit with no current consumer. Denial, unsupported observation or exhausted bounds retains uncertainty. The audit is an observation of current consumers, not a public WebKit teardown acknowledgement. The component requires Linux openat2 no-follow/no-mount traversal and safe no-follow permission operations; it fails closed if unsupported. Reclamation revalidates the anchored tree, never follows symlinks, and reports inspected/removed/live/uncertain/failed counts plus a scan-limit flag. A deletion error retains or attempts to restore the exact ownership record and reports recovery failures without overwriting replacement records. Disk-backed private data can survive crashes and uncertain cleanup; this is no secure-erasure guarantee.

Component tests bind the actual module through an isolated harness while the shared declaration is being integrated. They exercise real private filesystem paths, normal-exit owned child identity, live retention and actual FD/mmap consumers. A positive public dead-owner removal requires complete process visibility: permission-denied environments establish conservative retention, not deletion success. Whole-App service-worker retirement and negotiated native activation remain separate acceptance obligations.

The preparation job and native receipt are separate owners. The caller schedules ProfileWork on an existing bounded worker; it creates no runtime or product thread itself. Only that worker prepares the fixed native-http-profiles namespace leaf below the explicit app data home, validates ancestry, runs the bounded sweep and creates the connection profile. It never changes shared ancestor permissions or falls back to another home. A freshly created namespace receives explicit0700 permissions before opening, including under restrictive umask; existing unsafe directories fail without chmod.

The native Preparation receipt polls memory only. Before claim, cancellation, receipt Drop or a finite claim deadline returns unpublished ownership to the same worker for discard; failure logs the exact owned root and preserves its record. Currentness is checked before filesystem preparation, after the sweep and before native claim. Work dropped before execution resolves its receipt as Worker; cancellation before execution performs no namespace I/O. A successfully claimed PreparedProfile belongs to the native caller, which must recheck connection ownership before constructing its DataStore; published roots keep the conservative lease rules above. Mutex poisoning retains uncertain ownership and reports failure without recovering partially changed state. The claim deadline is capped at30seconds after readiness; it is unrelated to user consent or native network waits.

These storage/preparation modules have source-bound worker/filesystem fixtures; the shared native factory and actual App scheduling still require integration. Test workers are bounded owned fixture threads, with a separately spawned normal-exit child for process-local umask. Neither a private filesystem fixture nor an empty native lease proves GTK manager destruction or public dead-owner reclamation. A configured app home with writable ancestry is refused; build/fontconfig XDG caches under a development target are not a substitute for a safely owned private browsing namespace.

## Linux native context component

The Linux http_context::linux component consumes the actual worker-prepared profile in DataStore::new. It refuses non-UTF-8 native paths before constructing GTK objects, creates one non-ephemeral WebsiteDataManager with both private paths, and disables persistent credential storage. The manager, contexts, views, asynchronous clear callbacks and TLS probes retain filesystem-free native leases. Those leases do not certify native subprocess teardown or authorize deletion.

DataStore::prepare(ContextConfig, done) is initial-view preparation, not a Reload primitive. It asynchronously clears memory/disk HTTP cache, service-worker registrations and DOM Cache on the same manager before exposing a new PreparedView. It excludes cookies, localStorage and IndexedDB. A live view or pending clear returns Busy. Close, cancellation, stale currentness and clear failure settle the callback once; late callbacks do not publish a view. PreparedView::webview borrows the exact GTK widget; close and Drop retire it on its owning native thread. The caller must retain the owner for the widget's useful lifetime.

ContextConfig supplies one authenticated loopback SOCKS endpoint, a currentness predicate and an exact host/effective-port to expected leaf SHA-256 map. There is no bypass list or direct fallback. HTTPS navigation holds the original native decision while a script-disabled probe obtains the native TLS failure. Only exactly UNKNOWN_CA with the admitted authority and exact DER hash can authorize the original decision. This preserves its native method and upload instead of reconstructing a request. Close/staleness/timeout cancels held decisions and deferred continuations. Pending plus deferred decisions are bounded at8, as are per-view admitted authorities. The manager retains a finite64-entry certificate allowance history across views: already allowed or concurrently reserved leaves are refused, successful reservations persist, failed probes release their reservation, and capacity fails closed. The endpoint must use a genuinely fresh key and DER for each new document/authority; a new WebContext alone does not reset native certificate exceptions.

Script Allow must retain the same PreparedView, original native method/upload context and exact verified response. It neither calls prepare nor creates another document or upstream POST. Fresh-view WebViewSessionState restoration is unsuitable for POST Reload: native controls retained the upload but lost the SameSite=Lax request cookie, while a same-view selected-clear/native continuation retained it. Copying cookies or headers is not a substitute.

The compatible lifetime extension needed by the integrating host is a retained-view clear barrier, separate from initial prepare. The same caller-owned PreparedView must survive while the host revokes the old document's body/endpoint/probe callbacks, awaits endpoint/socket joins, clears the selected data types, rechecks the replacement authority and installs its fresh endpoint/leaf map, then releases exactly one original native continuation. The barrier must not navigate, restore a session into a fresh view, grant JavaScript, copy cookies, infer replay identity from a URL or send another upstream POST. This extension is not exposed by the current component API; callers must not use initial prepare as an equivalent. Endpoint retirement, immutable response ownership and native view lifetime have separate fences.

The component remains outside the shared WebView factory until integration. Source-linked GTK fixtures use real profile preparation and an isolated display, local authenticated endpoint and controlled destination listeners. These checks concern this native adapter, not App scheduling, body publication, capability negotiation, script consent or foreign platform acceptance. Public HTTP/HTTPS activation remains gated on that integration.
## Metadata and native-view fences

HtmlMirror::http_source captures only an admitted HTTP metadata response on the current file/metadata request identity. It retains the exact source generation and logical document prefix, a canonical fragment-free network URL and the original address including query/fragment. Credentials, invalid URLs, zero source generations and file sources cannot produce an HTTP source. Non-file metadata ends the file receive attempt; its later file Failure is ignored while the separately negotiated HTTP source remains available. This does not authorize a native route, allocate an HTTP protocol ID, read a client file or publish a body.

The logical source fence uses the captured ConnectionEpoch and an atomic lifetime, so a model/endpoint callback checks it without reentering the mirror mutex. Begin, user Reload, disconnect, changed metadata and mirror Drop revoke captured sources synchronously. A native view has a separate monotonic atomic nonce: a replacement retires old callbacks, and the last old-view Drop cannot revoke or resurrect its replacement. Retiring/recreating a widget preserves the logical body source; user Reload retires that source and requires a new document/model with reset accounting. An integrating factory still captures the actual registered surface/plugin role and negotiated HTTP/HTTPS support, and generates a fresh certificate map for each new native document/context. These source/model fences alone do not establish an App native view or capability activation.

## Native request and verified-response bridge

HttpBridge accepts quota-owned NativeRequest Arcs and lazily constructs CapturedDocument on its first engine drive. Native setup/submit allocates no protocol ID. A non-entry first request is rejected before allocation; each admitted request obtains the next shared file/HTTP identity and immediately calls admit_and_send before another ID. The caller registers document() in the actual HtmlSession table before draining the next reply batch; registration failure closes that exact owner before accepting UploadReady or sending Commit. This library bridge does not install a surface or advertise native capabilities.

At most8 native waiters are retained, including ready NativeResponse owners through actual encoded writes. Dropping a pending future signals only its exact slot and wakes the engine to apply the existing Decline/Cancel transition; no runtime/thread/network call is created by Drop. Ready responses retain their original NativeRequest and immutable VerifiedBody. CommandRejected leaves accepted work/window ownership intact; terminal Failure, decline and retirement resolve the matching waiter. Worker dispatch uses existing VerifyJob, outside bridge/model locks, with finite unstarted retry slots. Pending-work handoff rechecks currentness under the queue lock, so close cannot be followed by late rejected-job reinsertion; rejected jobs drop outside that lock. VerifyJob::request_id is a read-only captured Begin identity for dropping cancelled unstarted pool work; it grants no publication authority. Worker/result/native capacity remains owned until actual run or Drop.

No body is returned until encoded and decoded Complete identities and scan are verified, and full response/method/upload/logical URL match. Reuse requires the retained exact ResponseId and matching native request; identical Head/Complete returns the same Arc without Begin, Chunk, decode, new encoded consent or upstream replay. A mismatched reuse fails without falling back to submit. Allow and cumulative Continue remain separate model actions; Decline ends Receiving immediately. Native consent waits have no added network timeout. Future Wakers are registered before checking readiness and invoked/dropped outside state locks, so a reentrant close cannot publish a late verified body.

Close mints the exact model-authorized terminal cleanup before revoking its local model predicate. User Reload must close the bridge before revoking the logical metadata source; it then creates a new model with reset accounting. Native view replacement can instead keep that logical bridge/body and use an explicit one-use native replay permit owned by the integrating script gate. The bridge carries no JavaScript settings/permissions and cannot infer replay by URL. Actual App allocator/table registration, source/view fences, native policy and runtime scheduling remain the integrating host's responsibilities; component queue/verifier tests do not establish an App renderer or an upstream POST count.
