# Multi-agent collaboration (Agent collaboration)

- **Status**: Implemented
- **Actor**: AI agent (several sharing one instance)
- **ADR**: [ADR-0073](../../adr/0073-task-graph-view-unblock.md) (starting the task-graph views — two surfaces: host builtin surface + workspace popup). The earlier deferral, [ADR-0066](../../adr/0066-task-graph-view-deferred.md), is superseded by ADR-0073.
- **Code**: `agent.*` handlers (`src/adapters/ipc/handler/agent.rs`), persistence in `tasty-memory`
- **Screens**: both show the same data ([ADR-0073](../../adr/0073-task-graph-view-unblock.md)) — the [DAG graph surface](screens/dag-graph-surface.md) (`tasty new tab --type dag_graph`) is a resident observer that occupies one tab; the [DAG list popup](screens/dag-list-popup.md) (tools menu · `KeybindingSettings.toggle_dag_list`) is a workspace-scoped window for picking one from the list, glancing at it and closing. The IPC/CLI observation methods (`agent.task_list`/`task_graph`/`task_get`/`dag_list`/`dag_get`) remain valid as before.
- **Method list**: [reference/api](../../reference/api.md#에이전트-협업-agent)

## Purpose

Six collaboration primitives for several AI agents sharing one tasty instance. All are granted by the single `agent` (AgentManage) permission — one `agent.*` namespace with a `<verb>_<modifier>` pattern. Persistence uses `tasty.agent.*` memory keys (task/barrier/semaphore/lease are `workspace:<id>` scoped, rate-limit is `global`).

## Internals

### `*_await` — differs per method

`barrier_await` is not blocking; it **answers with the current state immediately** (a poll, alias of `barrier_state`) — the caller repeats the call until it reaches a terminal state.

`task_await` is **genuinely blocking** (built on `TaskWakerHub`, handled on a worker thread). With `timeout_ms` omitted it waits up to a default of 10 minutes (600,000 ms, a provisional value — to be retuned once real usage accumulates); if the task has not reached terminal by then it returns `{"outcome":"timed_out"}`. Passing `timeout_ms: 0` explicitly bypasses the default and waits forever. **Local callers only** (`local_only`) — symmetric with `approval.await`: the plugin SDK processes requests serially on a single worker thread, so a plugin blocked in `task_await` cannot service any of its own host→plugin requests (receiving the response to its own call goes through a separate path, so it is not a self-deadlock, but if that task calls back into the plugin the dispatch timeout (5 s) fails otherwise-normal work). A plugin instead declares a completion strategy (`[[contributes.completion_strategy]]`) so the runner waits on its behalf, or polls `task_get`.

### The 6 primitives

- **Task DAG** — dependency graph + state machine. Cycles are rejected at create time; on a state change the transitive downstream is re-evaluated automatically. 8 states (`waiting/ready/running/succeeded/failed/cancelled/skipped/unknown`). 4 commands (`run/custom` (with optional `poll` polling) `/reduce/wait_barrier`). `run` is a bare subprocess without a Surface; it captures stdout/stderr up to the last 64 KiB each (tail) and puts them in `TaskResult.output` (`{"pid","stdout":{"text","truncated","dropped_bytes"},"stderr":{...}}`) on success or in the error message on failure (no tty — use `pty.*` if you need one). 3 OnFailure kinds (`abort` (default, downstream skip cascade) / `continue_downstream` / `fallback{task}`) — **which task you set it on differs per kind**: `abort`/`continue_downstream` must be set on the depending (downstream) task itself so that it takes part in that downstream's readiness evaluation. `fallback` is the opposite: it must be set on the task that may fail (upstream), because the moment that task transitions to `Failed` it inspects its own `on_failure` and promotes the fallback. Setting `fallback` on the downstream side has no effect on the `Skipped` transition caused by a dependency failure, and that task stays in `waiting` forever (without a warning). The target named by `fallback{task}` (a reference to an existing task) is **dormant** until its main transitions to `Failed` — even with an empty `depends_on` it does not become `ready` right away; it is promoted only at the moment the main becomes `Failed`. If the main ends as `Succeeded`/`Cancelled`/`Skipped` and can never become `Failed` again, that fallback does not linger in `waiting` but is closed out automatically as `skipped`. `fallback{inline}` skips the dormant state entirely, since the task itself is created dynamically only when the main transitions to `Failed`. **Creation-order TOCTOU protection (`reserved_for_fallback`)**: `fallback{task}` has an ordering constraint — the referenced task must exist before the referrer. Between the two calls "create the fallback task" → "create the main task (referencing that fallback)", the runner could tick and dispatch that fallback (at that point nobody referenced it yet, so it was legitimately `ready`), defeating the dormant correction and running it regardless of the main's success or failure. Passing `reserved_for_fallback: true` to `task_create` (CLI `--reserved-for-fallback`) pins that task in `waiting` — it never passes through `ready` even when all of its `depends_on` have finished. The later `task_create` call that creates a main referencing it as `fallback{task}` lifts the reservation and hands it over to the normal dormant judgement. However long the gap between the two calls (however many times the runner ticks), it is safe. If you reserve and never create a referencing main, that task stays in `waiting` forever (an opt-in contract — clean up with `task_delete` and recreate). Creating without `reserved_for_fallback` (the old way) gives no such protection, so the two calls must follow each other closely. `custom` completion supports push (an external hook reporting) as well as poll (repeated calls) — e.g. `host/command-completed` (based on OSC 133 shell integration: a hook reports shell command completion and the exit code decides success/failure). Strategy registry and wiring details: [dev-guide/agent-runner](../../dev-guide/agent-runner.md#완료-판정-전략-레지스트리-srccompletion_strategy); `run` capture details: [dev-guide/agent-runner](../../dev-guide/agent-runner.md#run-출력-캡처).
  - **Reference validation scope**: `task_create` validates at creation time not only `depends_on` but also the existence of the task ids named by `OnFailure::Fallback{task}` and `TaskCommand::Reduce.inputs` (`crates/tasty-agent/src/task/store.rs`) — a missing one is rejected with `-32602`. `Fallback{inline}` is not validated, since its target legitimately does not exist at creation time (it is created dynamically on the failure transition). This validation only blocks **new creations** — dangling references persisted before the validation was introduced are not migrated and remain as they are (a task using such a reference observably stays in `waiting` forever; a dangling fallback also leaves a `tracing::warn!` on the failure transition).
  - **Data flow between nodes (`${task.<id>.output<pointer>}`)**: `depends_on` only orders execution, so to pass an upstream task's result as the **input** of a downstream task you use this placeholder — right before dispatch, the value is extracted from the upstream's `result.output` with an RFC 6901 JSON Pointer and injected into `Custom.params` (the whole JSON tree) / `Run.command` arguments / `Run.cwd`. Omitting the pointer (`${task.t-a.output}`) gives the whole output. Its main use is passing values unknown at `task_create` time and settled only at runtime, such as the child surface id from `claude.spawn`; it is what lets `spawn` → `tell` to that child be expressed as one DAG. **Types are preserved** — if a string value is exactly one placeholder and nothing else, it is replaced wholesale by the extracted JSON value, so a number stays a number (passing `as_u64` checks such as `require_surface_id`). Only when mixed with other text is it string interpolation. The referenced task **must be declared in `depends_on` (∪ `Reduce.inputs`)**, otherwise `task_create` rejects with `-32602` — without the declaration it would be a race, dispatching before the upstream finishes. Resolution failures (referenced task missing / no `result` / pointer miss) and syntax errors surface as failures, not a silent `null`. Details: [dev-guide/agent-runner §passing upstream task output as parameters](../../dev-guide/agent-runner.md#선행-task-출력을-파라미터로-넘기기--tasktidoutputpointer).
  - **`Reduce.inputs` is an implicit dependency** — merged with `depends_on` it takes part in graph edges and cycle detection. Its readiness semantics differ from `depends_on`, though: a reducer (especially `all`) deliberately collects failed inputs too, so one failed input does not push this task to `skipped` — it stays `waiting` only until every input has *settled* (success or failure) and then proceeds to `ready`.
  - **Observation (`task_get`/`task_graph`)**: the CLI text rendering of `task_get` shows `command` (kind summary) / `depends_on` / `on_failure` / `metadata` together — audit questions such as "is this task really gated on that fallback/dependency task" can be answered from the CLI alone, without parsing raw JSON or bypassing into the memory store. `task_graph`'s `nodes` carry `command_kind`/`on_failure_kind`, and `edges` are tagged with three `kind`s: `depends_on` / `fallback` (`OnFailure::Fallback.task`) / `reduce` (`Reduce.inputs`) — a direct visualisation of the three reference kinds the "reference validation scope" above covers. **But `fallback` is only a reference relation, not subject to cycle detection**: cycle detection (`detect_cycles()`/`TaskGraph::dfs_cycle`) walks only `depends_on`/`Reduce.inputs` and ignores `OnFailure::Fallback.task` — a cycle of mutual fallback references such as `A`→(`fallback:F`), `F`→(`fallback:A`) is stored as-is once it passes creation-time existence validation; it is observable through `task_graph` but not automatically blocked with `-32602`. The `dot` format draws `depends_on` as solid lines, `fallback` as orange dashed lines and `reduce` as blue dashed lines.
  - **DAG groups (`dag_list`/`dag_get`)**: Tasty's persistence model has no DAG record — a task belongs only to a workspace, and `task_list`/`task_graph` handle that workspace as a whole. Running several unrelated graphs in one workspace (conductor-style use) is normal, so instead of treating "workspace = DAG" the DAG is **derived**: ① if `task.metadata.dag` is a string, that value is the group key (**explicit**) — tasks with the same key are grouped into one DAG regardless of connectivity. ② The rest are **weakly connected components** (**derived**) — edges are the same 4 kinds `task_graph` draws (`depends_on` ∪ `Fallback.task` ∪ `Reduce.inputs` ∪ the `metadata.fallback_of` back-reference), treated as undirected. Attaching `metadata.dag_name` gives the display name (otherwise explicit key > root task name). `metadata` is used because adding a new field to `Task` would drop every already-persisted task to "no DAG" and make existing graphs vanish from the list — derivation folds existing tasks in automatically with no migration (the same convention as the extension points `semaphore`/`lease`/`fallback_of` already use).
    - DAG ids are explicit `d:<metadata.dag value>` / derived `c:<root task id>` (the minimum `(created_at, id)` within the group). The same task set yields the same id on every call (the screen holds its selection by id and recomputes on every poll, so determinism is the contract). The full identity is `(workspace_id, id)` — explicit keys are chosen by users, so two workspaces may use the same value.
    - Each element of a `dag_list` response: `id`/`workspace_id`/`name`/`source` (`explicit`|`derived`)/`task_count`/`state_counts` (8 kinds)/`rollup_state`/`created_at`/`updated_at`/`root_task_ids`/`has_cycle`, plus `task_ids` only when `include_tasks:true`. `rollup_state` is decided in the order `running` > `failed` > all terminal (`succeeded`/`skipped`) > `ready` > `waiting`.
    - **Enumeration scope**: with `workspace_id` omitted, every *currently live* workspace is walked (focus-independent — does not depend on the active workspace). Orphan tasks left in deleted workspaces do not appear, and the response states that fact with `scope: "live_workspaces"` — orphan cleanup is the responsibility of the automatic GC at boot.
    - `dag_get` produces `nodes`/`edges` (or `--format dot`) **identical** to `task_graph` for just that DAG's subset — the rendering rules are shared, so the two surfaces never diverge.
  - **Delete (`task_delete`) / bulk delete (`task_purge`)**: deleting a task that is referenced (`depends_on` ∪ `Fallback.task` ∪ `Reduce.inputs`) is refused by default and the referrer list is returned in `error.data.referenced_by` (`-32010`) — to prevent `create()` failures from dangling references (`UnknownDependency`) and downstream tasks stuck in `waiting` forever. `cascade:true` deletes all transitive referrers as well; `force:true` bypasses only the reference check (dangling references become the caller's responsibility). The only state that forbids deletion is `running` (`-32011`) — `waiting`/`ready`/terminal states are always allowed regardless of `cascade`/`force`. The constraint is just `running` rather than narrowed to terminal-only because an abandoned `waiting` task (e.g. a `Reduce` whose inputs never finish) could never be deleted under a terminal-only rule, and it would hold its inputs by reference so they too would never become GC candidates. `task_purge` selects candidates by a state-name list (`states`) and elapsed time (`older_than_ms`), but automatically preserves tasks referenced from outside the candidate set (`retained`) — `dry_run:true` shows the plan without deleting. When deletion actually happens, the `tasty.agent.handle.<id>`/`tasty.agent.run_result.<id>` side keys are cleaned up too.
- **Barrier** — a gate that closes once N signals have arrived. On `timeout_ms` elapsing it **lazily transitions** to `timed_out` (no separate thread — stamped on signal/state/list calls).
- **Semaphore** — N permits held concurrently. Re-acquire by the same holder is idempotent (retry-safe); a permit is recovered only by that holder's release. **Also used as a concurrency limit**: tasks tagged with `task.metadata.semaphore = { name }` run `Running` only up to that semaphore's permit count, and the excess waits in `Ready` automatically — `task-create --concurrency-limit <name>` does this tagging for you. Procedure and live examples: [dev-guide/agent-runner §concurrency limit](../../dev-guide/agent-runner.md#동시성-제한-concurrency-limit).
- **Lease** — a cooperative (advisory) resource-occupancy marker + TTL. Not an OS lock (violation-detection level). Mode `fail` (`-32009` on conflict) / `block` (`acquired:false`). Expiry is lazily evicted on list/acquire. **Pool mode** (`task.metadata.lease.candidates`): declare an array of candidates instead of a single `resource` and the task is assigned one of the N; the dispatched task receives the actual assigned resource through `command` (Run.cwd/Custom.params — `${lease.resource}` placeholder substitution). With `elastic` (explicit opt-in; the default is fixed, rotating only within the candidates) a new candidate `overflow_prefix+N` is synthesised atomically when exhausted (`-32012` when the pool is exhausted). Details and live examples: [dev-guide/agent-runner §resource pool assignment](../../dev-guide/agent-runner.md#자원-풀-배정-lease-pool--candidateselastic).
- **Reducer** — combines N task results into a single value. 5 strategies: `first_success`/`all`/`merge_json`/`concat_text`/`custom` (host shell, result-array JSON on stdin). Either one-shot `agent.task_reduce` or a DAG node (`TaskCommand::Reduce`, in which case `inputs` is an implicit dependency — see the Task DAG item above).
- **Rate-limit** — a (agent, metric) token bucket (refill rate `limit/per_ms`, ceiling `burst`). `global` scope. Distinct from the cumulative-threshold [telemetry cap](../telemetry/index.md) (this one is a *rate per time*). Provides CRUD + `try_consume`, and the IPC dispatcher middleware (`should_rate_limit`) evaluates every call automatically.

## Child agents as DAG nodes

**Launching a Claude / Codex child and waiting for it to finish** can be expressed as a single Task DAG node. There is no dedicated command kind — a `custom` node calling the plugin's spawn method is enough. The core only IPC-dispatches → polls, without knowing which agent it is.

```sh
tasty agent task-create --workspace-id 1 --name spawn-worker \
  --command '{"kind":"custom","ipc_method":"claude.spawn",
              "params":{"surface_id":560,"workspace":"wt-11",
                        "cwd":"/home/me/work/wt-11","prompt":"Fix the tests in this directory"}}'
```

**The point is not to pass `poll`.** Both plugins declare `[[contributes.completion_strategy]]` in their manifests and name their own `spawn`/`tell` methods in `default_for_methods`, so the runner picks that strategy up automatically at dispatch time and transitions into polling mode. Without the strategy (= that plugin is disabled) a `custom` node becomes `Succeeded` as soon as dispatch succeeds, and does not wait while the child runs.

`params.surface_id` is the **parent** surface the child hangs off. The `child_surface_id` from the spawn response travels via `map_from_response` into the poll call's parameters.

The two plugins' strategy values differ, so do not copy one to the other:

| | claude | codex |
|---|---|---|
| dispatch methods | `claude.spawn` · `claude.tell` | `codex.spawn` · `codex.tell` |
| poll method | `claude.state` | `codex.state` |
| `map_from_response` (spawn) | `child_surface_id` → `surface_id` | `child_surface_id` → `surface` |
| `map_from_response` (tell) | `surface_id` → `surface_id` | `surface_id` → `surface` |
| `terminal_states` (success) | `idle`, `needs_input` | `idle` |
| `failure_states` (failure) | `exited` | `exited` |

The poll parameter keys differ because each plugin's state handler requires a different name (`surface_id` vs `surface`); codex's list lacks `needs_input` because codex has no hook event that raises that state, so it would never actually be observed — it was left out to avoid a false contract. spawn and tell also differ in their source key: the spawn response carries `child_surface_id` (the newly created child), the tell response carries `surface_id` (an already existing target).

### Following up with instructions (`tell`)

`tell` also has a default strategy (`tell-wait`), so the node stays `running` **until the child finishes that instruction**. Unlike a spawn node, `surface_id` here is the **child** surface:

```sh
tasty agent task-create --workspace-id 1 --name tell-worker \
  --command '{"kind":"custom","ipc_method":"claude.tell",
              "params":{"surface_id":561,"message":"Re-run the tests you just fixed"}}'
```

The host `terminal.tell` clears the target child's `idle` (and `needs_input`) flags right after the body is injected successfully — otherwise the first polling tick would read the previous turn's state and complete the node before the child has even started answering. `terminal.broadcast` does the same.

### Failure judgement

If the child dies (`exited` — process death or surface disappearance) the node is **`failed`**. Both plugins classify `exited` under `failure_states`, so `on_failure` (`abort` / `continue_downstream` / `fallback`) works on child-agent nodes as well — with the default `abort`, downstream cascades to `skipped`. The failure message carries the state value together with a summary of the poll response.

claude's `needs_input` (waiting for human approval) stays on the **success** side. It is a state that finishes once a person approves, not a permanent failure, and this keeps the contract in which both plugins' spawn/tell completion notifications already treat it the same as `idle`. If you want approval-waiting to count as failure, give that node an inline `poll` and specify `failure_states` yourself.

Passing an earlier node's output into a later node's parameters (e.g. handing the surface id of the child created by spawn to the following tell node) is covered by "data flow between nodes (`${task.<id>.output<pointer>}`)" above.

Strategy registry and dispatch wiring details: [dev-guide/agent-runner](../../dev-guide/agent-runner.md#hostexecutor-매핑).

## Interface

- **AI agent / CLI**: `tasty agent {task-create,task-list,...,dag-list,dag-get,barrier-*,semaphore-*,lease-*,task-reduce,rate-limit-*}`. `--command`/`--metadata` take inline JSON or `@path`. Full table → [reference/api](../../reference/api.md#에이전트-협업-agent).
- **State filters are comma-separated multi-values** — `task-list --state` (singular) and `task-purge --states` (plural) differ only in flag name and share the same parsing: `--state waiting,ready,running` matches several states with OR, and a single value works as before. This is the basic pattern of completion detection that answers "are there unfinished tasks left" in one query. Examples → [dev-guide/agent-runner §CLI examples](../../dev-guide/agent-runner.md#cli-예).

## Restart behaviour

Tasks are persisted (`Scope::Workspace`) but the runner thread is in-memory — after a host restart **the runner does not come back on automatically.** Instead:

- **A single cleanup pass at boot** — for every live workspace: reclaim stale semaphore/lease holders + close out previously `Running` tasks as `Failed("host restart")` + reload persisted `DispatchHandle`s (live `ShellProcess`/`PolledDispatch`/`BarrierPoll`/unexpired `AwaitExternal` are restored, dead ones are closed out). The runner thread is still off, so actually polling a restored handle needs a manual (or plugin) `agent.task_run --action start`.
- **Automatic GC runs in the same boot cleanup path** — tasks abandoned for longer than a provisional threshold (7 days), regardless of state, are swept using the same reference-safe logic as `task_purge` (`plan_sweep`/`apply_sweep_plan`). Memory's own TTL (`PutOpts.expires_at`) is not used — TTL expiry bypasses reference-integrity and state checks and would reintroduce dangling references. Details: [dev-guide/agent-runner](../../dev-guide/agent-runner.md#자동-gc).
- **The stopped state is visible through queries** — `task_list`/`task_graph` responses carry `runner: { running, crashed, ready_count, running_count }`. Even with the runner off, `ready_count`/`running_count` are the store's real values, so "there is work but nobody is running it" is evident from this response alone. `task_get` attaches `awaiting_external: { wait_key, deadline_ms }` to a task waiting for an external signal via `AwaitExternal`, distinguishing it from "just running".
- **`hook_task_waits` (the hook_id → task_id map of the push completion strategy) is not persisted** — after a restart that task can no longer be woken by the hook. Instead the `AwaitExternal` handle itself carries `deadline_ms` (handles are persisted), so the reload on the next restart independently judges expiry and closes it out.
- `agent.task_run` is callable by plugins too (`AgentManage`) — since there is no auto-start, a plugin must be able to revive its own workspace's runner.

Details: [dev-guide/agent-runner](../../dev-guide/agent-runner.md#재시작-계약).

## Error codes

`-32004` (not found) · `-32008` (already terminal) · `-32009` (lease conflict) · `-32010` (task is referenced — `task_delete` refused by default, referrer list in `error.data.referenced_by`) · `-32011` (task is `running` — cannot delete, `cancel` first) · `-32012` (lease pool exhausted — all fixed candidates held, or the elastic `max_candidates` ceiling reached, mode `fail`) · `-32602` (cycle / missing dep (`depends_on`/`Fallback.task`/`Reduce.inputs`) / invalid strategy / a `${task.<id>.output…}` reference pointing outside `depends_on` or with broken syntax, etc.) · `-32603` (internal).
