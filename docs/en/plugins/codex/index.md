- **Status**: Implemented (bundled plugin)
- **Actors**: AI agent / local user (`tasty codex` CLI · IPC)
- **Distribution / integration**: bundled · cli + ipc_namespace + multi-agent — [plugin concepts](../../concepts/plugins.md)
- **Code**: `crates/tasty-plugin-codex/`
- **Permissions**: `terminal.spawn` etc. (manifest `permissions`)
- **Screens**: none — a CLI/IPC orchestration plugin (headless).
- **Flow**: the multi-agent orchestration diagram, isomorphic to claude's (spawn · tell · wait · hook · state machine) — [Figma · Flows & IA](https://www.figma.com/design/ct3uPefwY2uk6i1i9wYpkU/Untitled?node-id=33-915).

## Purpose

An integration that **runs and orchestrates the Codex CLI inside tasty**. Isomorphic to the [claude](../claude/index.md) plugin, and mainly used to have Codex cross-check code or judgements you have written.

## Internal behaviour

- **cli `codex`** (`tasty codex …`) — subcommands: `launch` · `spawn` (a child, in a pane split) · `children` / `parent` · `tell` (send a message, newlines preserved, auto-submitted) · `notify-caller` (internal, below) · `broadcast` · `kill` / `respawn` · `reboot` (restart resuming the same session, below) · `hook` (stop / prompt-submit / session-start). `install` / `uninstall` (install the Tasty hooks into the Codex CLI config).
- **ipc_namespace `codex`** — the IPC surface of the above.
- **event_subscribe** `surface.closed` — instance state cleanup.
- **Hook commands are installed in per-OS shell syntax** — Codex runs hook commands under PowerShell on Windows and POSIX sh elsewhere, so `install` emits `if ($env:TASTY_SURFACE_ID) { $input | tasty codex hook … }` (PS) on Windows and `if [ -n "$TASTY_SURFACE_ID" ]; then tasty codex hook … --surface $TASTY_SURFACE_ID || true; fi` (POSIX) elsewhere. On the POSIX side the guard and failure handling are separate — the outer `if` handles environments outside tasty (`$TASTY_SURFACE_ID` unset) with a silent exit 0, and the inner `|| true` handles only hook-command failure (keeping exit 0 so the codex turn is never blocked). The failure itself is recorded in `<tasty_home>/hook-failures.log` ([ADR-0075](../../adr/0075-agent-hook-delivery-failure-record.md)). **Because the command string changed, existing users must re-run `tasty codex install`** — re-running removes the old entries by marker (`tasty codex hook`) and inserts the new ones, so nothing is duplicated. codex invalidates trust when a hook command's hash changes, but tasty launches every codex instance with `--dangerously-bypass-hook-trust`, so actual firing is unaffected (only the trust shown in the `install` response may change to `needs_review`). The hook reads `session_id` from the JSON payload Codex passes on stdin and records it in surface meta (`codex-session-id`, `restore.command`) — `reboot` and session restore consume that meta. Only the three below are installed (fewer than [claude](../claude/index.md)'s six — Codex has no hook events corresponding to `Notification` / `SessionEnd`):

  | Codex config table key | tasty hook token | trust state key |
  |---|---|---|
  | `Stop` | `stop` | `stop` |
  | `UserPromptSubmit` | `prompt-submit` | `user_prompt_submit` |
  | `SessionStart` | `session-start` | `session_start` |

  They are planted in the `[hooks]` section of `~/.codex/config.toml` (not `settings.json` — that is not Codex's hook dispatch path). Codex does not fire a new hook entry until it is *trusted* — `--dangerously-bypass-hook-trust` (below) bypasses that approval step.
- **`spawn` / `tell` never wait synchronously** — they return immediately, and a notification is injected into the caller surface every time the target goes idle and, finally, when it exits. Internally, once (one-shot) hooks are registered on two events — `codex-idle` (fired via `surface.fire_hook` by the `stop` hook) and `process-exit` (host built-in) — and whichever fires first runs `notify-caller`, which sends the notification and then cleans up its sibling hook (independent of registration order — at fire time it finds siblings with the **same command** via `hook.list` (filtered to the target surface) and `hook.unset`s them. No shared state, so overlapping spawn/tell registrations on the same surface never clobber each other's siblings and leave zombies). After cleanup, `notify-caller` checks with `surface.locate` whether the target is still alive (= this fire was not process-exit) and, if so, re-registers both hooks (self re-arming) — even if codex-idle repeats many times (e.g. wait then resume), notifications keep coming until exit. There is no `needs_input` notification — the Codex CLI has no event corresponding to Claude Code's `Notification` hook, so it is structurally unreachable. **A sandbox-initialisation-failure hint is appended to completion notifications automatically** — right before `notify-caller` assembles the notification it looks at the target surface's recent screen output (`surface.screen_text`, the last 800 lines) and, if `RTM_NEWADDR` (the failure signature from the sandbox policy flag item below) is visible, adds a phrase like "looks like sandbox initialisation failed — try again with `--full-auto`" to the notification body (best-effort — on lookup failure or no match the notification is unchanged).
- **`--dangerously-bypass-hook-trust` on every codex launch command** — `spawn` / `launch` / `reboot` add this flag whenever they start codex, so the hooks tasty planted always fire without the user approving them manually via `/hooks` (a legitimate use since tasty plants its own hooks). `install` still reports the trust state in its guidance (for the case of running `codex` directly by hand), but it has no effect on hook behaviour for instances launched by spawn/reboot.
- **Approval / sandbox policy flags** (shared by `launch` / `spawn` / `respawn` / `reboot`) — `--approval <untrusted|on-request|never>` (codex `-a`), `--sandbox <read-only|workspace-write|danger-full-access>` (codex `-s`), `--full-auto` (codex `--dangerously-bypass-approvals-and-sandbox`; rejected with invalid_params if combined with `--approval` / `--sandbox`) are passed straight through to the launch command. Precedence is **per-call flag > global setting (Settings › Plugin › Codex "Default approval policy" / "Default sandbox mode", storage keys `default_approval_policy` / `default_sandbox_mode`) > hard-coded default**. **`approval` resolves to `never` unconditionally when there is neither a per-call flag nor a global setting (or the global setting is `inherit`)** — the completion hook does not fire while waiting for approval (there is no `needs_input` notification), so if nobody answers it hangs forever; the old behaviour of "when nothing is set, codex's own interactive default" no longer exists. If interactive approval is genuinely needed, pass `--approval untrusted` / `on-request` explicitly. **`sandbox`, unlike approval, does not cause a hang by itself, so as before no flag is added when unset and codex's own default is used** — but in execution environments that do not support nested sandboxes (bubblewrap), specifying `--sandbox read-only` / `workspace-write` can fail with something like `RTM_NEWADDR: Operation not permitted`, so in such environments `--full-auto` (bypassing the sandbox entirely) must be chosen explicitly.
- **`reboot`** (`tasty codex reboot [--surface <id>] [--delay <secs>] [--prompt <extra text>] [--approval <value>] [--sandbox <value>] [--full-auto]`) — terminates the Codex in a surface and **restarts it resuming the same session** (isomorphic to [claude reboot](../claude/index.md)). Behaviour: immediate response → after the delay (default 5 s) Ctrl+C ×4 → confirm the foreground has left → send `codex resume --dangerously-bypass-hook-trust [policy flags] -c check_for_update_on_startup=false <session_id>` (preventing the update prompt from hijacking the launch) → confirm it is back → submit the restart guidance prompt with screen verification, retries, and a separate Enter. Policy flags are resolved by the same approval/sandbox rules above. The safety guards are the same as claude's (no send and abort on foreground mismatch, duplicate reboot refused). **Call it as the last action of the turn.** Codex has no SessionEnd hook, so the session meta is not cleared on exit; the next session-start overwrites it.
- **Spawn child-count warning** — after a successful `spawn`, the parent's current child count is re-queried and, if it exceeds the Settings › Plugin › Codex "Spawn child warning threshold" (default 6), a `warning` field is carried in the response (a soft warning; spawn itself is not blocked). If there are reuse candidates, it lists their indices and suggests `respawn` instead of spawning anew, split into two lists with different evidence: **`idle`** means the child itself reported completion via hook, whereas **confirmed `stale`** (`confidence: confirmed` = the foreground returned to the shell) means no report arrived but host observation caught the agent process ending (hook loss — the scenario [ADR-0072](../../adr/0072-child-state-hook-observation-fusion.md) targets). Saying "already finished its work" for the latter would read as if the child reported it when it never did, so the wording is kept separate. The three phrases live in the plugin's `lang/{en,ko,ja}.toml` under `codex.spawn_warning.{total,idle,stale}` and follow the active language (`general.language`) — the plugin process cannot access the host i18n catalogue, so it loads its own `lang/` with the SDK `Translator` ([i18n](../../dev-guide/i18n.md) "Plugin namespace").

  `stale` with `confidence: heuristic` is **not counted** — observationally indistinguishable from SIGSTOP, long reasoning, or a silent command, so calling those respawn candidates too would recommend restarting a child that is working (the same judgement by which [api-conventions](../../dev-guide/api-conventions.md) excludes `stale` from the default terminal-state set). The judgement axis itself is in "judgement response fields" of [child-terminal](../../features/child-terminal/index.md).

## Interface

- **AI agent / user**: `tasty codex launch|spawn|tell|broadcast|kill|respawn|children|parent|hook|install …`.
- Typical flow: `spawn --prompt "…"` → (optional) `tell` → wait for the completion notification (auto-injected into the caller surface) → check the output.

## Non-goals

- Codex's own features — an external CLI. This plugin does *launch, placement, and relationship management*.
- Terminal / PTY internals — host.

## Acceptance Criteria

- [ ] Given the plugin is enabled When `tasty codex spawn --prompt "…"` Then a child Codex is created in a pane split and the CLI returns immediately.
- [ ] Given a child When `tasty codex tell <msg>` Then the message is sent and submitted with newlines preserved and the CLI returns immediately.
- [ ] Given a completion wait registered by `spawn` / `tell` When the target reaches idle or exited Then a notification is injected into the caller surface and the sibling hook is cleaned up. If it was not exited (= idle), the sibling hooks are re-registered so later state transitions keep notifying.
