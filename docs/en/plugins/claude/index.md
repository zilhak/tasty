# Claude Code (`com.tasty.claude`)

- **Status**: Implemented (bundled plugin)
- **Actors**: AI agent / local user (`tasty claude` CLI · IPC)
- **Distribution / integration**: bundled · cli + ipc_namespace + multi-agent — [plugin concepts](../../concepts/plugins.md)
- **Code**: `crates/tasty-plugin-claude/`
- **Permissions**: `terminal.spawn` etc. (manifest `permissions`) · `memory.read` (the Stop-hook gate reads the firing surface's goal — read-only)
- **Screens**: none — an orchestration plugin that drives terminal surfaces over CLI/IPC (headless).
- **Flow**: the multi-agent orchestration diagram (spawn · tell · wait · hook · state machine) — [Figma · Flows & IA](https://www.figma.com/design/ct3uPefwY2uk6i1i9wYpkU/Untitled?node-id=33-915).

> **As an example**: the **maximal integration reference** (~3.5k lines) — cli + ipc namespace + multi-agent + **hooks** + event_subscribe + external install. The model for splitting state/handlers/install/hook/error_scan modules → [plugin-development](../../dev-guide/plugin-development.md#cli--ipc-namespace).

## Purpose

An integration that **runs and orchestrates the Claude Code CLI inside tasty**. It starts a Claude instance in a new workspace/pane and spawns and controls multiple instances in a parent-child relationship (multi-agent).

## Internal behaviour

- **cli `claude`** (`tasty claude …`) — subcommands: `launch` (run in a new workspace) · `spawn` (a child instance, in a pane split) · `children`/`parent` (relationship queries) · `tell`/`broadcast` (send messages) · `kill`/`respawn` · `reboot` (restart resuming the same session, below) · `child-profile` (attach a persistent profile to a child, below) · `hook` (Claude Code hook integration, the "Claude Code hook integration" section below) · `checklist-hook` (the `Stop` hook dedicated to the `continue-checklist` session profile, the "continue-checklist session profile" section below) · `checklist-enable`/`checklist-disable`/`checklist-status` (turn a per-gate marker file on/off and query it — `continue-checklist` when `--gate` is omitted, same section) · `notify-done` (internal: deliver the notification to the caller on a spawn/tell state transition + clean up and re-arm the sibling hooks, below) · `profile-register`/`profile-unregister`/`profile-list`/`profile-show`/`profile-current` (the Claude session profile registry, the "Claude session profile registry" section below).
- `spawn`/`tell` **return immediately without blocking**. Every time the target (a child or the tell target surface) reaches idle/needs_input, and finally when it reaches exited, a completion message is automatically injected into the caller surface (the surface that invoked spawn/tell) — implemented by registering three once (one-shot) surface hooks, `claude-idle`/`needs-input`/`process-exit`; when one fires, `notify-done` sends the notification, cleans up the remaining sibling hooks, and, if the target surface is still alive (= this fire was not process-exit, checked with `surface.locate`), re-registers all three hooks (self re-arming). Thanks to this, a transient state transition such as needs-input (a follow-up question) does not lose the notification at the real completion afterwards — it is "a notification per state transition while the child lives", not "one notification per spawn/tell".
- **ipc_namespace `claude`** — the IPC surface of the above.
- **event_subscribe** `surface.closed` — receives surface termination to clean up instance state.
- The actual Claude process runs inside a terminal surface (`terminal.spawn`); the plugin manages its lifecycle and relationships.
- **`reboot`** (`tasty claude reboot [--surface <id>] [--delay <secs>] [--prompt <extra text>] [--profile-file <path> | --profile <name[,name2,...]>] [--clear-profile]`) — terminates the Claude in a surface and **restarts it on the same session**. Claude cannot turn its own TUI off and on, so an agent invokes this command on its own surface (to pick up settings/hook/version changes). Behaviour: return an immediate response → after `--delay` (default 5 s) Ctrl+C ×4 (0.5 s apart) → confirm the foreground process has left Claude, then send `claude -r <session_id>` to the shell (with `--settings "<path>"` appended if a profile resolves; the session id is captured from the surface meta `claude-session-id` at request time) → confirm Claude is back, then submit the restart guidance prompt via `terminal.tell` (screen verification, retries, and a separate Enter for deterministic submission). Safety guards: if the foreground is still Claude, no text is sent and it aborts; if Claude does not return after resume, the guidance is not sent (avoiding shell pollution); a duplicate reboot on the same surface is refused. **Call it as the last action of the turn** — the turn in progress after the delay is cut off.
  - **When reboot fails because the `claude-session-id` meta is empty**: the `no active claude session on surface {id} (claude-session-id meta not set …)` error can occur even with hooks installed — the cause is that the session-start hook failed to plant this meta. There are at least three places it can fail silently: ① the registered command in `install.rs` is `[ -n "$TASTY_SURFACE_ID" ] && tasty claude hook … || true`, so with `TASTY_SURFACE_ID` unset the tasty binary itself never runs (cannot log), ② the session-start branch of `apply_hook` in `hook.rs` skips recording the meta when the stdin JSON has no `session_id` (logged with `tracing::warn!`, check `tasty plugin logs com.tasty.claude --follow` or `~/.tasty/plugins-logs/com.tasty.claude.log`), ③ `read_stdin_json` in `dynamic.rs` returns `None` on TTY/parse failure (the hook is a CLI process, so tracing goes **only to stderr** — not to the shared log file, [ADR-0092](../../adr/0092-file-log-host-process-only.md). The delivery failure itself is recorded in `$TASTY_HOME/hook-failures.log`). Manual recovery: `tasty surface-meta set --key claude-session-id --value <session id>`.
- **`child-profile`** (`tasty claude child-profile [--surface <parent>] --child <index> [--delay <secs>] [--prompt <extra text>] [--profile-file <path> | --profile <name[,name2,...]>] [--clear-profile]`) — **a parent attaches a persistent session profile to a child**. It resolves `--child <index>` (the index shown by `claude children`) to the child's surface id via `terminal.children` and then runs **exactly the same path** as `reboot` above for that surface (profile validation → attach to surface meta → Ctrl+C sequence → `claude -r <sid> --settings "<path>"` → guidance prompt). It is a reuse of the reboot entry point rather than a separate attach mechanism, so the attached state is **inherited by the child's later argument-less `reboot`**. The duplicate guard uses the same set as reboot — if `reboot` and this command overlap on the same child, the later one is refused as "already in progress".
  - **Difference from `reboot` 1 — the turn is not cut off.** `reboot`'s "call it as the last action of the turn" warning is a constraint for **when the caller itself is restarted**. This command restarts only the child, so **the parent's turn is not cut off** — keep working after calling it.
  - **Difference from `reboot` 2 — a completion notification is armed.** As with `spawn`/`tell`, the `claude-idle`/`needs-input`/`process-exit` notification hooks are auto-registered toward the caller surface (the same self re-arming cycle as the spawn/tell item above). When the child finishes restarting and reaches idle, the parent is notified. `reboot` arms no notification (the target is itself, so nobody is there to receive it).
  - **`--child` is required.** Attaching to oneself belongs to `reboot --profile`, so the entry points do not overlap. A nonexistent index is an immediate error listing the available indices, and **no child is killed** — profile argument validation (mutual exclusion · unregistered names · JSON parsing) also completes entirely **before** the Ctrl+C sequence starts.
  - **Difference from `--profile` on `spawn`/`respawn`/`launch`**: those carry `--settings` on that **one** launch command only and do not touch meta — the profile drops off as soon as the child `reboot`s. Use this command when persistent attachment is needed.

- **Claude session profile** (term definition: [ubiquitous-language.md](../../concepts/ubiquitous-language.md)) — Claude Code reads hooks only once at process start, so the only way to add hooks to a live session is one of the four launch paths `reboot`/`spawn`/`respawn`/`launch`. There are two ways to attach a profile and they are **mutually exclusive** (giving both is an immediate error):
  - `--profile-file <path>` (`path_kind = "file"`, the CLI normalises to an absolute path relative to the caller's cwd, **repeated specification refused** — "Why the CLI refuses repeats" below) — uses the file path as-is.
  - `--profile <name[,name2,...]>` — attaches by a profile name registered in the "Claude session profile registry" below, or by a **gate name** registered in the "Stop-hook gate registry" (the two registries share a namespace). Giving two or more names comma-separated uses the single file the registry produces by merging.

  Either way, the launch command ends up with `--settings "<path>"` appended — Claude Code's `--settings` **merges with, rather than replaces**, the existing hooks in `~/.claude/settings.json`, so tasty's built-in hooks (via `claude hook`) keep firing. Only `reboot` (and `child-profile`, which takes the same path targeting a child) records the attached state in surface meta so that **the next argument-less reboot inherits it as the default** — attaching by path records `claude-session-profile` (the path as-is), attaching by name records `claude-session-profile-names` (the name string), and the two metas are managed mutually exclusively (writing one clears the other). The name meta is **re-resolved from the registry at every inheritance** — the path is not cached, so if `profile-register` updated the content in between, the next reboot reflects the latest content. Both metas are synchronously re-validated at every reboot (file existence + JSON parsing; if an inherited profile is broken, the kill sequence is not started and an error is returned). `--clear-profile` removes both. `spawn`/`respawn`/`launch` apply the profile only to that one launch command and do not touch meta (repeated restarts are a concept of the `reboot` family only) — if a child launched that way needs persistent attachment, use `child-profile`.
  - **Profiles survive restores** — "How profiles survive restores" below.
  - **Why the CLI refuses repeats**: Claude Code's `--settings`, when given repeatedly, **keeps only the last value and silently drops the earlier ones** (measured). Accidentally giving the tasty CLI argument itself (`--profile-file`) twice could fall into the same trap, so the manifest `CliArg.reject_repeat = true` (`crates/tasty-cli/src/dynamic.rs`) registers it with clap as `ArgAction::Append` and rejects a second value with an error instead of silently discarding it.

### How profiles survive restores

App restart (layout restore) and closed-tab restore (Ctrl+Shift+T) **cannot carry surface meta** — a restore issues a new surface id that does not collide with the stale one and immediately purges the meta of non-live surfaces. So if the attached state lived only in meta, a restored Claude would come up with just `claude -r <id>` and the profile hooks would not fire.

The plugin solves this with an **attachment record keyed by session id** (the host is not involved — the `restore.command` contract of [layout-persistence](../../features/layout-persistence/index.md) stays agent-agnostic).

- **Record location**: `TASTY_PLUGIN_DATA_DIR/profiles/attachments/<session_id>.json`. Content is `{"kind": "names"|"path", "value": …}` — **what was attached by name is recorded as names** (re-resolved on restore). The data dir is separate from the install directory, so it survives `upgrade-builtins`/reinstalls ([plugin-development](../../dev-guide/plugin-development.md) §6 "data dir lifetime contract").
- **Write**: `reboot` updates it at the same point it updates surface meta when attaching/detaching a profile (`--clear-profile` removes the two meta keys and the record together).
- **Recovery**: the `session-start` hook looks at the profile meta first and, if empty (= a session that came through a restore), revives the meta from the record. It then **re-resolves the names every time** (reflecting the latest registry content) and writes `restore.command` as `claude -r <id> --settings "<path>"`. The session id is preserved across `claude -r <id>`, so it can serve as the record key — if that premise breaks (Claude Code issuing a new id on resume), only the profile silently drops off, so the post-restart session-survival check stays in the release checklist.
- **Re-stamp**: once a profile is settled, the record is rewritten at every session-start. `reboot`'s Ctrl+C fires `SessionEnd`, which deletes the record just written (the cleanup itself is correct behaviour), and the following session-start immediately recovers it from the profile meta — without this re-stamp every reboot would lose the record permanently.
- **Failure is a silent downgrade**: if the attached name was `profile-unregister`ed/`gate-unregister`ed in the meantime or the path is broken, only a warn log is left and the restore proceeds **without the profile**. In the same situation `reboot` errors and does not even start the sequence (a launch that fails on a broken profile leaves the foreground abandoned), but session-start has nobody to return an error to, and failing here would break session restore itself.
- **Lifetime**: the global `session-end` does not delete the record immediately but only **marks it ended** (`ended_at`), and a sweep reclaims it after a 24-hour grace. The reason for not deleting immediately is the measured closed-tab restore path — closing a tab kills the PTY and fires `SessionEnd`, and the host is still alive so the hook arrives normally. Deleting the record here would leave the immediately following Ctrl+Shift+T restore with no basis to revive the profile meta (the process itself comes up with `--settings` thanks to `restore.command`, but `profile-current` and argument-less reboot inheritance break). Records are keyed by session id, so even alive during the grace, no other session can read them — the only path by which the same id reappears is `claude -r` (= restore). Leftovers from hooks that never ran at all (forced termination etc.) are handled by a 90-day TTL, and records of live sessions keep getting younger through re-stamps, so there is practically no room for false positives. Only `--clear-profile` deletes immediately without grace, because the user explicitly detached it.
- **Gates take the same path**: profiles and gates share the name plane, so what was attached by gate name is restored the same way. If the same name was re-registered profile↔gate, the next restore resolves to the **new definition** (a consequence of not caching the path).
- **Out of scope**: layout presets are structural templates, not session restores, so they do not store `restore_command` — applying a preset attaches no profile. `spawn`/`launch`/`respawn --profile` create no attachment record (repeated restarts are a `reboot`-only concept).

### Claude session profile registry

Instead of hand-crafting a profile file every time and memorising paths, a layer where you **register it under a name** and attach it with `--profile <name>` above. It mirrors the shape of `src/hook_handler/registry.rs` (patch semantics · `<owner>/<short>` id) without sharing types — this plugin is the only consumer, so no new host registry is created and it lives inside the plugin (`crates/tasty-plugin-claude/src/profile.rs`).

- **Register**: `tasty claude profile-register <name> --file <path>` — reads `<path>` (a JSON object) and stores a **copy** at `TASTY_PLUGIN_DATA_DIR/profiles/registered/<name>.json` (if the original is later moved or deleted the registry is unaffected). An already-registered name has its content overwritten. Names are lowercase/digits/`-`, max 32 chars.
- **Unregister**: `tasty claude profile-unregister <name>`.
- **List**: `tasty claude profile-list` — shows **everything attachable by name**: registered profiles (`user/<name>`, no `description`) · registered gates (`user/<name>`, a `description` saying it is a gate) · the host default gate (`host/continue-checklist`). Added to these are the eight built-in hooks that are always globally installed (`host/<token>`, not attachable — listing `install.rs::MANAGED_HOOKS` from the "Claude Code hook integration" section as-is, without duplicating definitions). `profile-list` and `gate-list` both showing gates is intentional duplication — the former is the "things attachable" view, the latter the "gate definition" (body · sentinel · limit · on/off) view.
- **Show**: `tasty claude profile-show <name>` — the original JSON as-is for a registered profile; for a gate, the **generated Stop-hook fragment** that triggers that gate. `owner` reflects the actual source (`user` for registered profiles/gates, `host` for the default gate). `tasty claude profile-current [--surface <id>]` — shows what is currently attached to that surface (name or path) together with the built-in hook list ("what profile/gate is on this session right now").
- **Name resolution order (when attaching)**: the order for **attaching** with `--profile <name>` — ① `profiles/registered/<name>.json` → ② a registered gate → ③ the host default gate → ④ a built-in hook token yields an "not attachable" error → ⑤ otherwise an unregistered error. ① and ② are mutually excluded at registration time (the name-collision refusal in "Stop-hook gate registry" below) but the order is fixed defensively. `profile-show` above does not use this path, so ④ does not apply — giving a built-in hook token yields an unregistered error (`no registered profile named 'user/stop'`), not "not attachable".
- **Combination merge** (`crates/tasty-plugin-claude/src/profile_merge.rs`) — `--settings` has only one slot (measured above), so with two or more names each registered file is folded in order into one JSON, materialised at `TASTY_PLUGIN_DATA_DIR/profiles/generated/<sorted-names>.json` (a separate subdirectory from the registered originals — so a regenerated artefact never overwrites an original). It is rebuilt at every attach, always reflecting the latest registered content. Rules per key kind:

  | Key kind | Example | Rule |
  |---|---|---|
  | Hook event arrays | `hooks.Stop` | union (duplicate command strings removed) — effectively concat, both fire |
  | Object maps | `env`, `enabledPlugins` | recursive per-key merge. Leaf conflicts follow the scalar rule |
  | Allow/deny lists | `permissions.allow`/`deny` | union, then **an invariant is enforced**: entries in `deny` are removed from `allow` — deny always wins regardless of profile order (tests: `profile_merge::tests::deny_beats_allow_*`) |
  | Scalars (most) | `theme`, `effortLevel` | on differing values, log a warning and last-wins with the later profile's value |
  | Scalars (security-sensitive) | `permissions.defaultMode` | on differing values, **refuse** (error) — blocking a permission mode silently weakening through combination takes priority over last-wins |

- **Storage** — all under `TASTY_PLUGIN_DATA_DIR` (`~/.tasty/plugin-data/com.tasty.claude/`). The host creates this directory in advance, so it is writable without the `fs.write` permission. In an abnormal start where the host did not inject this env (`data_dir = None`), both registration and attachment are refused with an explicit error — `~/.claude/` or a new path is never used silently.
- IPC: `claude.profile_register`/`claude.profile_unregister`/`claude.profile_list`/`claude.profile_show`/`claude.profile_current` — 1:1 with the CLI subcommands (principle 2, agent operability).
- If, at spawn, the parent's live child count exceeds the configured threshold, a `warning` field is carried in the response — adjust the threshold under Settings › Plugin › Claude Code. Reuse candidates are split into two lists with different evidence: **`idle`** (the child itself reported completion via hook) and **confirmed `stale`** (`confidence: confirmed` — no report, but the foreground returned to the shell so the agent process ending was observed, i.e. hook loss). `stale` with `confidence: heuristic` is not counted because it is indistinguishable from SIGSTOP or long reasoning — see "judgement response fields" in [child-terminal](../../features/child-terminal/index.md) for the judgement axis.
- **No approval policy flags (unverified)** — the [codex](../codex/index.md) plugin can set a child's approval/sandbox policy with `--approval`/`--sandbox`/`--full-auto` (the fix for approval prompts freezing a child permanently in non-interactive automation), but this plugin's `build_launch_command` (`crates/tasty-plugin-claude/src/handlers.rs`) has no corresponding flags. Claude Code uses a `settings.json` (`permissions`)/`--permission-mode` based permission model rather than codex-style launch-time CLI flags, so the structure differs, but whether a child launched with `spawn`/`launch`/`respawn` freezes permanently at an approval prompt, isomorphic to codex, when `permissions.defaultMode` requires approval has not yet been reproduced or verified. If it reproduces, policy flags isomorphic to codex's need exposing.

### Stop-hook gate registry

A layer that **registers gates by name** — gates that block session termination and inject a checklist. A gate has three parts — a **body** (the instruction injected as `reason` when blocked), a **sentinel** (the string by which the model declares completion), and a **round limit** (the backstop). It mirrors the shape of the session profile registry above (`profile.rs`) without sharing types (`crates/tasty-plugin-claude/src/gate.rs`). Decision background: [ADR-0083](../../adr/0083-stop-gate-named-registry.md).

- **Register**: `tasty claude gate-register <name> --body-file <path> [--sentinel <string>] [--rounds <n>]` — stores the body file as a **copy** (the gate stays alive if the original is moved or deleted). An already-registered name has both definition and body overwritten. Name rules are the same as profiles (lowercase/digits/`-`, max 32 chars).
- **Unregister**: `tasty claude gate-unregister <name>` — deletes **both** the definition and the body copy (a leftover body becomes an orphan that makes the next registration look like it silently overwrote an old body). The gate's **runtime state** (the marker + rounds under `checklist/gates/<name>/`) is deleted too — left behind, re-registering the same name would resurrect the old enabled state and round counter, so a "deleted and recreated" gate would inherit its predecessor's state. This cleanup failing does not fail the unregistration itself (warning log only — disappearing from the registry is the main goal, and leftover state is never resolved anyway).
- **List**: `tasty claude gate-list` — registered gates (`user/<name>`) and the host default gate (`host/continue-checklist`) together, each with its effective `sentinel`/`round_limit`, the limit's source (`round_limit_source`: `gate` = the definition set it directly / `settings` = unset, so it falls back to the plugin setting), and the **marker on/off** (`enabled`) — this is the place to see per-gate on/off at once (`checklist-status` answers one gate at a time). If the user registered a gate with the same name as the host default, that name appears **only as the user entry** — if the same name showed as two lines, the list alone could not tell which is effective.
- **Attach**: `tasty claude launch|spawn|respawn|reboot --profile <gate name>` — gate names share the plane with profile names, so they attach with `--profile` directly. What attaching creates is a single `Stop` hook pointing at that gate:

  ```
  if [ -n "$TASTY_SURFACE_ID" ]; then tasty claude checklist-hook --gate <name> || true; fi
  ```

  The gate's three parts (body · sentinel · limit) are not carried in this command — the hook re-reads the registry via `--gate` when it fires, so re-registering a gate to fix its body is reflected at the next fire **without re-attaching**. The command string is built in one place only, `install.rs::tasty_guarded_command` (structurally preventing the shape from diverging across two paths). The gate name goes straight into a shell command, and that is safe because the short-name rule (lowercase/digits/`-`) rules out shell metacharacters — loosening the name rule requires touching quoting/escaping as well.
- **Combination**: attaching two gates like `--profile gate-a,gate-b`, or mixing a gate and a profile like `--profile mygate,myprofile`, **registers a Stop hook for each** per the `hooks` concat rule of `profile_merge` (which is why round state and markers are per gate).
- **Show**: `tasty claude gate-show <name>` — the definition (sentinel · limit) together with the body text. Without a user registration it falls back to the host default gate, and `owner` then reflects the actual source (`host`).

**Validation at registration**

- **The body must contain the gate's effective sentinel.** Refused otherwise — without the sentinel in the body the model never learns how to declare completion, always reaches the round limit, and the gate degenerates into a "force N more turns" device. For the host default body the same invariant is enforced by per-locale compile-time tests (user bodies cannot have compile-time tests, so it moved to runtime validation at registration).
- **Empty sentinel refused** — an empty string matches every message (`str::contains("")` is always true), so the gate would pass on the first round.
- **`--rounds` is 1 or more.**
- **Collision with a same-named session profile is refused** — registering a gate makes it attachable under that name just like a profile, so the two registries **share a namespace**. If the same name existed on both sides one would silently shadow the other, so registration refuses **in both directions** (`gate-register` refuses a same-named registered profile, `profile-register` a same-named gate).
- In an abnormal start without `data_dir`, register/unregister are explicit errors. **Queries (list/show) return only the host default gate** — queries do not require storage.

**Storage** — under `TASTY_PLUGIN_DATA_DIR`, with the same "user originals vs tasty-generated" separation as the profile registry:

| Path | Content |
|---|---|
| `gates/registered/<name>.json` | the gate definition — `sentinel` (if unset at registration, the default sentinel is materialised: the effective value must be readable from the definition alone) · `round_limit` (absent as a key if unset) |
| `gates/bodies/<name>.md` | a copy of the body original |

**The host default gate is code, not a file** — `continue-checklist` is not materialised in the data directory and exists only as a lookup function (body = the `claude.checklist.body` translation key, sentinel = the default sentinel, limit = unset → settings fallback). Materialising it would leave no path to revive it if the user deleted it (the same shape as `install.rs::MANAGED_HOOKS`). A user registration under the same name wins.

- IPC: `claude.gate_register`/`claude.gate_unregister`/`claude.gate_list`/`claude.gate_show` — 1:1 with the CLI subcommands (principle 2). No GUI exposure.

### Stop-hook gate judgement

The layer that enforces registered gates at actual `Stop` hook fires (`crates/tasty-plugin-claude/src/checklist.rs`). The judgement itself is the same four-way branch (the continue-checklist section below), fetching the three parts (body · sentinel · limit) **per gate**.

- **Which gate comes as a command argument** — `tasty claude checklist-hook --gate <name>`. The Stop payload (`session_id`/`prompt_id`/`stop_hook_active`/`last_assistant_message`) carries nothing that identifies the gate, so baking it into the hook command string at attach time is the only path. `--gate` is optional with default `continue-checklist`, so hook commands already installed without `--gate` keep working as the host default gate.
- **Round state path**: `TASTY_PLUGIN_DATA_DIR/checklist/gates/<gate>/rounds/<session_id>.json`. The key is (gate × session) **because two or more gates can be attached at once** — under the `--profile a,b` merge rule the `hooks` array is concat, so both gates' Stop hooks are registered and each fires. Without distinguishing gates the two would read and write one counter and eat each other's rounds (the same reason the session axis was introduced, lifted one axis up).
- **Round limit precedence**: gate definition (`--rounds`) **>** Settings (gate default round limit) **>** 3. The general principle that an explicit setting beats the global default — if a gate registered with `--rounds 5` were silently overridden by the Settings value, the registration argument would be meaningless. **This fallback does not distinguish gate origin (host default / user registered)** — a gate that sets no limit falls to the Settings value either way, and `gate-list`'s `round_limit_source` then says `settings`. The Settings item's storage key name (`continue_checklist_round_limit`) looks specific to the host default gate, but **its meaning was redefined as the default shared by all gates** (the user-visible label says "the default when a gate does not set its own value"; the key itself was kept to avoid losing tuned values). Interpreting it narrowly per the key name and dropping user gates straight to 3 would leave **no means to adjust the default limit of user gates** short of specifying `--rounds` on every gate, so that is not done. The host default gate also sets no limit and takes the same fallback, so **existing behaviour is preserved as-is**.
- **The `{{goal}}` placeholder in the body (opt-in)**: if the body contains the `{{goal}}` token, the hook emits as `reason` the result of replacing it with **the firing surface's goal clause**. The hook reads the goal directly with `memory.goal_get` — writing "look up the goal" in the body and leaving it to the model would make acquisition of the gate's core judgement evidence depend on the model's diligence, contradicting the gate's raison d'être (not trusting the model's self-judgement). Three-way: goal present → the goal clause in the token's place (`claude.checklist.goal_clause`, with the goal text inserted) · no goal → the **whole line** containing the token is removed (the rest of the body untouched = byte-identical to before the token was introduced) · **body without the token → completely unchanged** (backwards compatibility for registered gates — nobody else's sentence gets appended to an author's body unannounced). The goal lookup IPC happens **only when a block is confirmed and that body contains the token**, so passing fires and token-less gates never make an IPC call. If the lookup fails (host IPC error, missing surface id, etc.) it is treated the same as no goal — this module's "when uncertain, pass/ignore" policy as-is. The surface id comes as the `surface` (u32, optional) argument of `checklist_hook_args`; the CLI layer fills it from the `TASTY_SURFACE_ID` env when unspecified, so **hook command strings already installed without `--surface` keep working** (the same property of backwards compatibility `--gate` maintained). Decision rationale: [ADR-0088](../../adr/0088-stop-gate-goal-aware-continuation.md).
- **Body resolution**: a registered gate's body is **read from the file at every fire** — a body updated by re-registration must be reflected without restarting the session (the same intent as checking the marker at every fire). Only the host default gate's body keeps using the lang string cache resolved once at start.
- **Unregistered gates pass silently** — a session whose registration was deleted while the hook command remains is a normal state. Erroring here would make that session impossible to end, so this module's existing "when uncertain, pass" policy applies as-is. No state file is created and no Settings lookup IPC is made either.
- **SessionEnd cleanup iterates all gates** — the global `session-end` hook is always installed via `MANAGED_HOOKS` and fires regardless of gates, so the call site cannot know the gate. It therefore deletes all of `checklist/gates/*/rounds/<session_id>.json` (other sessions' files untouched).
- **Legacy path** — the pre-gate-axis `checklist/rounds/<session_id>.json` is neither read nor written. Round state is volatile data that disappears with the session lifetime, so it is not migrated, but so that files left by old versions do not remain as orphans, **session-end cleanup deletes this path too**.

**When several Stop hooks block at once (measured)** — the feel of attaching two gates to one session hinges on this, so it was reproduced directly in Claude Code (two independent hooks registered on `Stop`, each blocking with a different `reason`):

- Both hooks **fire on every `Stop` fire** (fire counts match in lockstep).
- **Both `reason`s are delivered to the model** — when each hook instructed a different token to be put in the final answer, both tokens appeared in the answer. It is not a one-hook-wins scheme.
- **If any one blocks, the turn continues** — with two hooks of different limits (1 / 3), even after the one reaching its limit first turned to pass (`{}`), the session continued because of the one still blocking, and it ended on the fire **where both passed**.
- From the second fire on, both hooks receive `stop_hook_active=true` (the plugin uses this value only as a sanity check, not for judgement).

### continue-checklist session profile

**One host default instance on top of the gate primitive** — not a feature special-cased by proper name, but the gate the gate registry above embeds as host-sourced (`host/continue-checklist`), whose attach path is exactly the same as a registered gate's. Attaching with `--profile continue-checklist` (a profile the user registered under the same name takes precedence) plants `tasty claude checklist-hook --gate continue-checklist` as a `Stop` hook — it is not part of the global `install` (the eight in the "Claude Code hook integration" section above) and fires only in sessions it is attached to. The description below is based on this default instance's values (body · sentinel · limit fallback); registered gates write their own values in the same slots.

- **Behaviour**: at every `Stop` hook fire, read the stdin JSON (`session_id`/`prompt_id`/`stop_hook_active`/`last_assistant_message`) and decide four ways: ① if it differs from the stored `prompt_id` (or there is no stored state), treat as round 0 ② if `last_assistant_message` contains **this gate's** sentinel (host default `[[TASTY-CHECKLIST-DONE]]`), pass ③ if the round count reached the limit, pass (backstop) ④ otherwise return `{"decision":"block","reason":"<checklist body>"}` and round +1. The `reason` body is the string `t("claude.checklist.body")` (lang file, three languages) resolved in the active locale, consisting of three general items (re-examine whether the result met the request / whether code/config changes were actually verified / state whether follow-up work remains) · a `{{goal}}` placeholder paragraph · the sentinel-inclusion instruction. Item 3 is a **disclosure requirement**, not a completion requirement, so merely stating "remaining work A, B exists" satisfies it — the goal clause after it gives the follow-up instruction "judge the disclosed remaining work against the goal, and for what needs no user judgement and can proceed on its own, do not stop here but proceed" (the wording of item 3 itself is unchanged). **If no goal is set, that paragraph disappears entirely and the previous behaviour applies** — the absence of a goal means the user has not declared a scope of autonomous progress, so there is no basis to instruct continue-proceeding. The goal is set with `tasty memory goal set "<sentence>" --surface <id>` ([memory](../../design/systems/memory.md)).
- **Why the round-limit backstop is needed**: Claude Code itself has no host-side safety net against infinitely repeated `Stop` hook blocks (measured — even when the model recognised it was stuck in a loop it could not escape). The limit is exposed as the gate default round limit item under Settings › Plugin › Claude Code (default 3) — a gate specifying its own `--rounds` wins.
- **Round state storage**: `TASTY_PLUGIN_DATA_DIR/checklist/gates/continue-checklist/rounds/<session_id>.json` — keyed by (gate × session) (the "Stop-hook gate judgement" section above). When that session's `SessionEnd` hook arrives (one of the eight in the "Claude Code hook integration" section below, always fired regardless of this profile), the state file is cleaned up.
- **Marker file gate (per gate)**: `TASTY_PLUGIN_DATA_DIR/checklist/gates/<gate>/enabled.marker` — its existence turns that gate's triggering on and off. Profile attachment (= hook registration) is fixed at Claude Code process start, but the marker is re-checked for file existence at every hook fire, so it toggles immediately without a restart. This is also why the marker is per gate — with several gates attached and one marker, the immediate toggle becomes all-or-nothing and the point of separating gates disappears on the toggle axis only. It sits under the same `gates/<gate>/` as the round state, so one gate's runtime state gathers in one directory.
  - The `checklist-enable [--gate <name>]` / `checklist-disable [--gate <name>]` / `checklist-status [--gate <name>]` CLI (and corresponding IPC) are the controlled entry points that create, delete and query the marker — no need to manipulate it with raw `touch`/`rm`. **Omitting `--gate` means `continue-checklist`**, so argument-less invocations from before the gate axis work as-is, and the `checklist-status` response is the same `{ "enabled": bool }` as before.
  - **enable/disable refuse unregistered gate names** (preventing marker directories made by typos from piling up as ghost state invisible even in `gate-list`). Conversely, **the query (`checklist-status`) and trigger (hook) paths are lenient** — status answers `enabled: false` + `registered: false`, and the hook passes silently (erroring in a session whose registration was deleted but whose hook command remains would make that session impossible to end).
  - **One-time legacy marker migration**: if a marker exists at the pre-gate-axis path (`checklist/enabled.marker`), it is moved to `gates/continue-checklist/enabled.marker` and the original deleted. It runs on whichever entry point is hit (enable/disable/status/hook), so even an instance that never calls a command and only runs hooks gets migrated. Unlike round state, the marker is a setting the user explicitly turned on, so silently turning off across an upgrade would look like a regression.
- **Safe-pass principle**: every uncertain condition — marker absent, `session_id`/`prompt_id` missing, stdin parse failure — passes silently without blocking; not trapping the session in an undecidable state takes priority.
- IPC: `claude.checklist_hook` — a parameter schema separate from `hook_args` (`checklist_hook_args`). The Stop payload fields are all auto-filled from stdin, and only `gate`, absent from stdin, comes as a command argument (default `continue-checklist`). `stop_hook_active` is declared as `string`, not `bool` — `CliArgType::Bool` cannot express absence (`extract_value` always returns `Some(false)`), so combined with a `stdin_field` mapping the stdin value would never be reflected (the handler compares the `"true"`/`"false"` strings directly). `claude.checklist_enable`/`claude.checklist_disable`/`claude.checklist_status` — `checklist_gate_args` (`--gate`, optional, default `continue-checklist`); create/delete/query that gate's marker file. The status response is `{ "enabled": bool, "registered": bool }` — `enabled` as before, and `registered` (whether a gate of that name actually exists — `true` for the host default gate too) is the field that lets a typo be recognised since the query does not refuse it. In an abnormal start without `data_dir`, enable/disable refuse with an explicit error (the same policy as decision 3 in profile.rs), and status falls back safely to `enabled: false`, the same as `marker_present` (not an error — a query must always be answerable).

### Claude Code hook integration

`tasty claude install` plants the eight events below in `hooks` of `~/.claude/settings.json`. All events use a command string of the same shape:

```
if [ -n "$TASTY_SURFACE_ID" ]; then tasty claude hook <token> || true; fi
```

**The guard and failure handling are separate.** The outer `if` handles "environments using Claude Code outside tasty" (`$TASTY_SURFACE_ID` unset) with an **explicit successful exit**, making no noise. The inner `|| true` is responsible only for the failure of `tasty claude hook` itself — keeping exit 0 so as not to block the agent's turn, but **not discarding the fact of failure**: one line is recorded in `<tasty_home>/hook-failures.log` ([ADR-0075](../../adr/0075-agent-hook-delivery-failure-record.md)). The old shape (`[ -n … ] && … || true`) swallowed both cases with one operator, so a lost state push vanished without a trace.

The command string is generated in exactly one place, `install.rs::tasty_guarded_command` — the session profile's (`continue-checklist`) hook command uses the same function (previously the same shape was hard-coded separately in `profile.rs`, which caused an accident of fixing only one side).

> **Existing users need to re-run `tasty claude install`.** The command string is already recorded in the user's `settings.json`, so updating the plugin leaves the old string as-is. Re-running finds existing entries whose marker (`tasty claude hook <token>`) matches and **updates them in place**, so entries are not duplicated.

Per-event variable data such as `session_id`/`message`/`notification_type` arrives as **stdin JSON**, not command arguments — the manifest `hook` cli entry declares `stdin_json = true`, and the `--session`/`--message`/`--notification-type` flags are each auto-filled from the stdin JSON via `stdin_field` (Claude Code gives a JSON payload on stdin when running a hook). Only one POSIX shell syntax is emitted — there is no Windows PowerShell branch like [codex](../codex/index.md).

| Claude Code event | matcher | tasty hook token | `terminal.set_state` | `surface.fire_hook` | surface meta | `surface.completion` kind |
|---|---|---|---|---|---|---|
| `Stop` / `SubagentStop` | `""` (all) | `stop` / `subagent-stop` | `idle` | `claude-idle` | — | `completion` |
| `SessionEnd` | `""` (all) | `session-end` | `idle` | `claude-idle` | `claude-session-id`·`restore.command` **unset** (the two profile meta keys are not touched. The profile **attachment record** is only marked ended and reclaimed after the grace — "How profiles survive restores" above) | `completion` |
| `Notification` | `""` (all) | `notification` | `needs_input` (skipped if `notification_type` is `idle_prompt` — a no-input-wait false positive with no actual question) | `needs-input` (same condition) | — | `needs_input` (same condition) |
| `UserPromptSubmit` | `""` (all) | `prompt-submit` | `active` | — | — | — |
| `SessionStart` | `""` (all) | `session-start` | `active` | — | `claude-session-id` = session ID, `restore.command` = `claude -r <id>` **set** (skipped if the stdin JSON has no `session_id`). If a profile is attached it is written as `claude -r <id> --settings "<path>"`, and if the profile meta was lost through a restore it is **recovered** from the attachment record ("How profiles survive restores" above) | — |
| `PreToolUse` | `AskUserQuestion` | `pre-tool-use` | `needs_input` | `needs-input` | — | `needs_input` |
| `PostToolUse` | `AskUserQuestion` | `post-tool-use` | `active` | — | — | — |

`surface.completion` is called with `{ surface_id, kind }` (`HostCall::SurfaceCompletion`,
`hook.rs`), and `kind` carries the table's value as-is — the host's `AttentionStore` displays
`NeedsInput` at higher priority than `Completion` (yellow surface border, and the same priority for the tab
title and workspace badge, see [surface-highlight](../../features/surface-highlight/index.md)).

`UserPromptSubmit` is essential for clearing the `idle=true` residue left by the previous `Stop` hook when a child receives its second and later prompts — without it there is a state bug that misreports an actually active child as idle. Only `PreToolUse`/`PostToolUse` are registered narrowed to matcher `AskUserQuestion`, firing only on that tool call (the other six take the whole event with matcher `""`) — measurement (running real Claude Code and dumping the hook stdin payload) showed that answering `AskUserQuestion` does not raise `UserPromptSubmit` (the question/answer is a tool interaction within the same prompt turn and is not counted as a new prompt), so the existing `UserPromptSubmit` (→active) alone cannot catch the moment needs_input clears in this case. `PreToolUse` fires **before** the question UI appears (including `tool_input.questions`) and turns needs_input on, and `PostToolUse` returns it to active as its pair immediately on answer (observed `duration_ms: 0`) — `needs_input` now comes from two paths, `Notification` and `PreToolUse`.

These eight are all the hooks install plants — it does not hook the whole of `PreToolUse`/`PostToolUse` without a matcher, nor other Claude Code events such as `PreCompact`. The `install_preserves_other_hooks` test in `install.rs` verifies that a user-added `PreToolUse` entry (with a different matcher) is kept intact, separate from tasty's `AskUserQuestion`-matcher entry.

install identifies its own entries by the marker substring (`tasty claude hook <token>`) and behaves idempotently — an existing entry whose marker matches only has its command string overwritten with the latest form (preventing a regression where a wrong command planted by an old version lingers), and other entries the user added are untouched. For events with a matcher such as `PreToolUse`/`PostToolUse`, a marker match alone does not guarantee the matcher value, so install updates the matcher to the canonical value (`AskUserQuestion`) too.

The surface hook events this plugin fires are the four `claude-idle`/`needs-input`/`claude-error`/`claude-error-stalled`, declared via the manifest `contributes.hook_events` — the host validates `hook.set` registrations against the (built-in ∪ active plugin declarations) set ([hooks](../../features/hooks/index.md)), so with this plugin disabled, hook registrations under those four keys are refused too. **Not all four come from the eight installed hooks above** — `claude-idle` comes from `apply_hook` above (Stop/SubagentStop/SessionEnd) and `needs-input` from two paths, `Notification` (excluding idle_prompt) and `PreToolUse` (matcher `AskUserQuestion`), but `claude-error`/`claude-error-stalled` are a separate producer unrelated to this hook mechanism: `error_scan.rs` pattern-matches surface output text and, on a match, fires directly with `surface.fire_hook` (the stall judgement is the section below). Claude Code's eight hooks have no event corresponding to "the API call failed", and in particular when a request hangs without a response the turn never ends, so `Stop` **structurally does not fire** — the error string printed to the PTY is the only signal available then. `claude-idle`/`needs-input` are consumed by [surface-highlight](../../features/surface-highlight/index.md) (Stop hook → highlight) and [telemetry](../../features/telemetry/index.md) (`wall_time_ms` from `session-start`→`stop`, `input_tokens` from `notification`), and the meta set/unset of `SessionStart`/`SessionEnd` is consumed by the `restore.command` restore of [layout-persistence](../../features/layout-persistence/index.md).

### PTY error scan (`claude-error`) scope

`error_scan.rs` polls at an 800 ms period, reading `surface.read_since_mark` (strip-ansi) per tracked surface, matches known network/API error patterns (`API Error` / `Output blocked by content filtering policy` / `overloaded_error` / `rate_limit_error` / `Internal Server Error` / `network error` / `Bad Request`), and on a match fires `claude-error` on that surface. The same text caught again in consecutive polls does not fire (dedupe), and a new-turn start signal (`prompt-submit`/`session-start`/`active`) releases the dedupe.

The tracked set is **all top-level surfaces made by `claude launch` and all child surfaces made by `claude spawn`/`claude respawn`**. Children nobody is watching on screen are precisely the ones that need detection most, so children are not excluded.

Cleanup (untracking) rides the same polling period without a separate subscription, but **the liveness criterion differs by registration path**:

| Target | Registration | Liveness judgement |
|------|------|-----------|
| top-level (`launch`) | not in the child registry | surface existence via `surface.locate` |
| child (`spawn`/`respawn`) | host child registry | **parent-child relationship** existence via `terminal.parent` |

Children are judged by relationship because [`terminal.release`](../../features/child-terminal/index.md) releases only the relationship and soft occupancy without closing the surface — judging by surface existence alone, it would be polled forever after release and keep firing `claude-error` at a user terminal that is no longer a child. The host runs `reconcile_child_terminals()` before the relationship query, so this one query also sweeps the case where a surface survived a failed kill/close. `claude kill` immediately `disable`s using the `killed_surface_id` of the success response, removing even the up-to-800 ms residual fire window. If the query itself fails (IPC error) it is not concluded "dead" and tracking is kept — there is no re-activation path, so a false cleanup is riskier than a false keep.

**The mark is a shared resource, so there is a detection blind spot.** The scanner's `surface.read_since_mark` does not advance the mark (`Terminal::read_since_mark` takes `&self`), so it does not consume the agent's `tasty read since-mark` result, but conversely when the agent moves the mark forward with `tasty set mark`, the window the scanner sees moves with it. Errors that passed before that vanish from the scanner's view. This coupling is accepted — a scanner-only mark would duplicate the mark resource and blur the meaning of the agent's `set mark`.

### Stall notification (`claude-error-stalled` → parent completion log)

`claude-error` itself **does not notify the parent.** The patterns include transient errors Claude Code retries automatically, such as `overloaded_error`/`rate_limit_error`, so notifying as-is would flood a session that retries often. Instead the scanner separates "retrying" from "stuck", fires **`claude-error-stalled`** separately, and the parent notification subscribes only to that.

The criterion is **simultaneous** satisfaction of two conditions (`error_scan.rs`):

| Condition | Why |
|---|---|
| After the error match, PTY output **has not changed at all for 30 s or more** | While retrying, attempt counts and backoff countdowns keep drawing, so output flows. When hung without a response, output stops completely. The comparison is a **fingerprint of the whole text**, not the dedupe snippet (first 200 chars) — output appended later leaves the first 200 chars unchanged, so by snippet a retry would be misjudged as a stall |
| `terminal.state` is still **`active`** | If `idle`/`needs_input`/`exited`, the turn already ended and the completion-notification trio (`claude-idle`/`needs-input`/`process-exit`) already told the parent about that event — preventing two notifications for the same event |

Noise cap: once per static interval (released when output resumes), and at least five minutes apart per surface. A new-turn signal (`prompt-submit`/`session-start`/`active`) resets the static-interval measurement along with the dedupe but keeps the cooldown (it is the frequency cap for errors repeating across turns, meaningless if released at turn boundaries).

**The state axis is untouched.** This path does not call `terminal.set_state`, so the `state` of `claude children` does not change — an error can recover through retries, so promoting it to a state would be a false positive, and derived state is the output-only contract of observation fusion ([ADR-0072](../../adr/0072-child-state-hook-observation-fusion.md)).

The wiring (`handlers.rs`) has a **lifetime separate** from the completion-notification trio:

- `register_notify_hooks` registers, along with the trio (once), one `claude-error-stalled` as a **persistent hook** (`once: false`). Its command string differs — `tasty claude notify-error --caller-surface … --target-surface …` — so it is not caught by the sibling group's `cleanup_sibling_hooks` (exact command match).
- Being persistent, **no re-arming is needed** — it does not entangle with the trio's fire→cleanup→re-arm cycle. The fire frequency cap lives on the sending side (the cooldown above).
- Registration is idempotent: it is called several times — after spawn, on tell, and at sibling re-arming — so an existing hook with the same command is removed first and a new one added.
- The `notify-error` handler reads `surface.screen_text` right before assembling the notification and appends the matched error line as a hint (the same way as codex `notify-caller`). The notification goes out as the same single line in `<parent_home>/notify/<caller_surface>.log` as completion notifications ([child-completion-notify-log](../../dev-guide/external-interaction/child-completion-notify-log.md)).

- Claude Code's own features — an external CLI. This plugin does *launch, placement, and relationship management*.

## Acceptance Criteria

- [ ] Given the plugin is enabled When `tasty claude launch` Then Claude runs in a new workspace.
- [ ] Given a parent instance When `tasty claude spawn` Then a child instance is created in a pane split and appears in `children`.
- [ ] Given a child When after `tasty claude spawn` (or `tell`) the child reaches idle/needs_input/exited Then a completion notification is injected into the caller surface and the sibling hooks are cleaned up together. If the child reached a non-exited state (idle/needs_input), the sibling hooks are re-registered so later state transitions keep notifying.
- [ ] Given a hook entry the user added directly to `~/.claude/settings.json` When `tasty claude install` runs Then the six tasty hook entries are added/updated and the user's entry is preserved as-is.
- [ ] Given a valid profile JSON When `tasty claude reboot --profile-file <path>` Then in the restarted Claude the profile hooks and tasty's built-in hooks fire together, and rebooting again without arguments inherits the profile. After `--clear-profile`, a reboot no longer fires the profile hooks. A nonexistent path/broken JSON returns an error immediately without starting the kill sequence.
- [ ] Given two registered profiles (each with a `SessionStart` hook leaving a different marker) When both names are attached together comma-separated in `--profile` and spawned Then **both** fire (the merge does not collapse to last-wins). Attaching a profile containing `permissions.deny` makes that tool disappear from that child (removed from the toolset, not a denial prompt), and attaching a `deny` profile together with a profile that `allow`s that tool still leaves the tool absent (deny beats allow). Giving `--profile-file` and `--profile` together is an immediate error.
- [ ] Given a session attached with `--profile continue-checklist` + the marker file present When Claude tries to end a response without the sentinel Then it is blocked and the checklist body is injected, and responding with the sentinel or reaching the round limit ends normally. A session without the profile attached is entirely unaffected by this behaviour. Two sessions with the same profile attached running concurrently do not mix their round counters.
- [ ] Given no marker file When `tasty claude checklist-enable` Then the marker file of the `continue-checklist` gate is created and `checklist-status` reports `enabled: true`. When `tasty claude checklist-disable` Then the marker file is deleted and `checklist-status` reports `enabled: false` — calling `checklist-disable` again with the marker already absent returns `enabled: false` without an error (idempotent).
- [ ] Given two registered gates (`gate-a`/`gate-b`) When `checklist-enable --gate gate-a` Then `checklist-status --gate gate-a` is `enabled: true`, `--gate gate-b` is `enabled: false`, and `gate-list` shows both states together. In that session only the `gate-a` hook blocks and the `gate-b` hook passes silently. Calling `checklist-enable --gate nope` with an unregistered name is an error and no marker directory is created, while `checklist-status --gate nope` returns `enabled: false, registered: false` without an error.
- [ ] Given a gate turned on with accumulated rounds When `gate-unregister <name>` then `gate-register` again under the same name Then `checklist-status` is `enabled: false` and the round counter starts from 1 again (the previous instance's state is not inherited).
- [ ] Given an instance with a marker only at the pre-gate-axis path (`checklist/enabled.marker`) When any entry point (`checklist-status` or a hook fire) Then the marker is moved to `gates/continue-checklist/enabled.marker`, the legacy file disappears, and the enabled state is preserved as-is.
- [ ] Given a gate registered with `gate-register mygate --sentinel '[[MY-DONE]]' --rounds 2` and turned on with `checklist-enable --gate mygate` When `spawn --profile mygate` Then `checklist-hook --gate mygate` is hooked as that child's `Stop` hook, and trying to end a turn without the sentinel injects **mygate's body** (not the host default checklist body) and blocks. Answering with `[[MY-DONE]]` passes, and continuing without it passes by backstop at **mygate's limit of 2**. Rounds accumulate in `checklist/gates/mygate/rounds/<session>.json` and are cleaned up when that session ends.
- [ ] Given a registered gate `mygate` and a child with it attached via `reboot --profile mygate` (the only launch path that records the name meta is `reboot`, so a child launched with `spawn` has `attached_names` `null` even with the hook attached) When `profile-list` / `profile-show mygate` / `profile-current --surface <child>` Then the list shows `user/mygate` (attachable, gate description) together with `host/continue-checklist`, show returns owner `user` and the generated Stop hook JSON, and current's `attached_names` contains `mygate`.
- [ ] Given two gates When attached with `--profile mygate,continue-checklist` Then the `hooks.Stop` of `generated/<sorted-names>.json` has 2 entries, pointing at `--gate mygate` / `--gate continue-checklist` respectively.
