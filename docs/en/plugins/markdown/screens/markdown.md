# Markdown surface screen

- **Parent plan**: [../index.md](../index.md)
- **Visual source**: a sanitised HTML document generated by the plugin — rendered by the host native OS WebView. The markdown surface design in `design-system/` (if any), to be vendored.

The markdown render surface that opens inside a [work area](../../../features/work-area/screens/work-area.md) tile. The plugin puts an HTML document built with `pulldown-cmark`+`ammonia` onto the host's native OS WebView overlay (WebKitGTK/WKWebView/WebView2) to render it (webview, [ADR-0065](../../../adr/0065-markdown-webview-render-channel.md)) — the host does not touch the document's pixels.

## Trigger

Opening a markdown file or creating/converting to a `markdown` surface.

## UI element inventory

- **Rendered markdown body** — headings/paragraphs/lists/code blocks/links etc. Every heading receives a GitHub-compatible
  auto-slug `id` (the "Heading id + table of contents (TOC)" section below).
- **Address bar** — an `<input>`+`<button>` embedded in the document itself (not a host egui widget).
- **Table of contents (TOC)** — with one or more headings, a collapsible `<nav>` is inserted right below the address bar,
  above the body (embedded in the document itself, not a host egui widget). Not rendered without headings.
- **Search bar** — embedded in the document itself (not a host egui widget), hidden by default. Appears at the top right
  on `Ctrl+F`/`Cmd+F` while the document has focus (the "Find in page" section below).
- The tab display name is the file name.

## Visuals per state

- No file / load failure etc. are shown as a `.tasty-state` div inside the document.

## Mermaid diagrams

Fenced code blocks whose language is `mermaid` (` ```mermaid `) survive as `code.language-mermaid` and are rendered
by [mermaid.js](https://github.com/mermaid-js/mermaid) (MIT, vendored offline —
`crates/tasty-plugin-markdown/assets/mermaid.min.js` + `NOTICE.md`). If the document has no mermaid
block at all, this script is not inserted at all (it is a multi-MB bundle, so inlining it into every document that
does not need it is avoided). The theme maps to mermaid's built-in `default`/`dark` palette according to `Theme.is_light`,
and since a theme switch regenerates the whole document (`reload_all_webviews`), it is reflected automatically
without separate runtime re-theming logic. A diagram with broken syntax leaves only that block as the original code text
and does not affect rendering of the remaining content.

## Math (LaTeX) rendering

Inline `$...$`/block `$$...$$` math is parsed, when `pulldown-cmark`'s `Options::ENABLE_MATH`
(`parser_options()`) is on, into `<span class="math math-inline">`/`<span
class="math math-display">` respectively (the original LaTeX source as HTML-escaped text) — **this shape is
the library's default behaviour as-is** (unlike GFM alerts/footnotes, no separate AST event rewrite on the Rust side
was needed). The actual math rendering is done, as the same class of work as mermaid (a client-side JS
library, conditionally inserted trusted script), by
[KaTeX](https://katex.org) (MIT, vendored offline —
`crates/tasty-plugin-markdown/assets/katex.min.{js,css}` + `assets/fonts/KaTeX_*.woff2` +
`NOTICE.md`). If the document has no math span at all, this script (JS+CSS+fonts, about
1 MB combined) is not inserted at all — the same conditional-insertion saving pattern as mermaid/highlight.js.

- **How the sanitizer was extended**: ammonia does not support a whitelist at the class *value* level (only per tag/attribute)
  — the choice was to allow the `span` tag + the whole `class` attribute (`div`+`class` is already opened the same way in this
  crate — `.tasty-state`/`.tasty-state-error` etc.). The alternative of assembling only math events afterwards as separate
  trusted HTML bypassing the sanitizer was considered too, but a `class` value by itself cannot run a script or open a URL, so
  even if a user imitates `<span class="math math-inline">hand-written LaTeX</span>` in raw HTML the result is only "their own
  content rendered by KaTeX", and because pulldown-cmark's default behaviour can pass through as-is with no custom event rewrite
  code needed at all, this approach was chosen.
- **Fonts included offline — data URIs**: every other vendored asset of this plugin (mermaid.js/highlight.js,
  and the rendered document itself) is completely self-contained inside the single HTML string handed to the host WebView
  — there is no "plugin assets directory" on disk that a relative font URL could reference at runtime
  (`include_str!`/`include_bytes!` bake into the binary and nothing is written back to disk). The document's only `<base href>`
  already belongs to the user's markdown file directory, so re-pointing it would break the user's relative-path images/links.
  So `render.rs::katex_css_with_embedded_fonts` replaces each `@font-face` `src:` in `katex.min.css` (originally a three-format
  relative-path list `woff2`/`woff`/`ttf`) with a single `data:font/woff2;base64,...` entry of the base64-encoded vendored
  `woff2` bytes (string replacement — no regex dependency needed, the 20 font basenames are fixed at compile time). The
  `woff`/`ttf` siblings were not vendored — the engines this webview embeds (WebKitGTK/WKWebView/WebView2) are all evergreen,
  so no legacy-browser fallback is needed.
- **Measured binary size**: the vendored original assets are KaTeX JS 272 KB + CSS 24.7 KB + 20 woff2 fonts totalling about
  254 KB (base64 encoding is computed once at render time at runtime — `OnceLock` memoised; the binary itself holds only the
  raw font bytes). Directly comparing the release binary size against the commit right before (without KaTeX):
  **9.69 MB → 10.26 MB (+576 KB)**.
- **Security**: `throwOnError: false` (on parse failure, render the original TeX in the error colour instead of throwing —
  no crash or blank screen; the span's original escaped text before failure is also untouched, so the worst case is still
  "the original text as-is") and `trust: false` (blocking arbitrary URL/markup insertion through LaTeX macros such as
  `\includegraphics`/`\href`/`\url`, a line of defence separate from `sanitize_html`'s whitelist) are set **explicitly**
  (`katex.render(tex, el, {throwOnError:false, trust:false, displayMode})`) — not relying on KaTeX's own defaults.
- **Text extraction**: the original LaTeX is recovered with `el.textContent` (not `innerHTML`) — the DOM automatically
  converts the HTML entities `escape_html` encoded back to the original characters, so the exact string the author typed
  between `$...$` is obtained (the same rationale as the code block copy button's use of `code.textContent`).
- **Block/inline distinction**: `displayMode` is decided by `el.classList.contains('math-display')`.
  The centring and margins of block math are already handled by KaTeX's own CSS (`.katex-display`), so this plugin
  adds no CSS of its own.
- **Theme coupling**: the vendored `katex.min.css` hard-codes no colours (only `color:currentColor` exists, verified directly)
  — math simply inherits `body`'s `color:var(--md-fg)`, so on dark/light switching it follows the body text colour
  automatically with no separate runtime re-theming logic (the whole document being regenerated on theme change is the same
  as for every other element).
- **Duplicate-render prevention**: the `data-tasty-math-rendered` attribute prevents `katex.render` running twice on the
  same span (the same idempotency convention as the code block copy button/image failure UI) — a reload always builds the
  whole document afresh so it is not structurally necessary, but it was added defensively.

**Verified on real hardware (this repo's dev machine, Linux/WebKitGTK, libwebkit2gtk-4.1)**: actual `render_document()` output
containing one inline formula (`$E=mc^2$`), one block formula (`$$\sum_{i=1}^n i$$`), and one deliberately broken formula
(`$\frac{1}$` — the second argument of `\frac` missing) was loaded with `WebKit2.WebView.load_html` and the DOM inspected
directly — the two valid formulas rendered as real KaTeX MathML structure (`<math xmlns="http://www.w3.org/1998/Math/MathML">...`),
the block formula was wrapped in `.katex-display`, and the broken formula was replaced by a `.katex-error` element without a
crash or blank screen, with its text matching the original TeX source (`\frac{1}`) exactly. macOS/Windows cannot run on this
machine — only confirmed by code review that KaTeX itself uses only standard browser APIs (not verified on hardware; KaTeX is a
pure JS library with no per-platform branches, so the risk from engine differences was judged low).

## Code block syntax highlighting

Fenced code blocks (` ```rust ` etc.) are rendered keeping the `code.language-<lang>` class whose language token
`sanitize_fence_lang` normalised to `[A-Za-z0-9_+-]`, and the actual token highlighting is done **client-side** by
[highlight.js](https://highlightjs.org) (BSD-3-Clause, vendored offline —
`crates/tasty-plugin-markdown/assets/highlight.min.js` + `NOTICE.md`, the "common" bundle
containing 36 languages). Client-side was chosen over server-side (syntect etc.) because the tag/attribute whitelist of
`sanitize_html` (`render.rs`) need not be touched, and the "conditional script insertion into the trusted wrapper" pattern
mermaid already proved can be reused as-is.

- **Conditional insertion**: if the document has no fenced code block at all, the highlight.js script itself is not
  inserted (the same saving pattern as mermaid — `render_document`).
- **Language mapping**: where the language identifiers highlight.js recognises overlap with the normalised result of
  `sanitize_fence_lang` (e.g. `rust`/`javascript`/`typescript`/`python`/`json`/`bash`/`yaml`/`markdown`,
  and `toml` — registered in highlight.js only as an alias of the `ini` grammar), they pass through with no separate
  mapping table. The initialisation script extracts `<lang>` from each code block's `language-<lang>` class and first checks
  support with `hljs.getLanguage(lang)`; unsupported languages (or code blocks with no language at all) quietly remain
  unhighlighted without error — a "language" highlight.js does not know, such as `mermaid`, is naturally skipped by this
  path too.
- **XSS safety**: highlight.js's `highlightElement` only reads the element's plain-text content and rewrites `innerHTML`
  with its own escaped `<span class="hljs-*">` markup; it does not reinterpret existing markup. A literal `<script>` text
  inside a code block is already HTML-escaped by `sanitize_html`, so after highlighting it stays inert text.
- **Theme coupling**: highlight.js's own built-in themes (github.css etc.) are not vendored — instead the `hljs-*` token
  classes are painted directly by CSS rules (`render.rs::hljs_css`, always included in `theme_css`) mapping them to the
  Catppuccin-style `Theme` hue fields this plugin already uses (`mauve`/`blue`/`green`/`peach`/`teal`/`lavender`/`red` etc.).
  highlight.js knows nothing about colours and only classifies tokens, so unlike mermaid there is no need to bake
  light/dark into the script — on a theme switch the whole document is regenerated and `theme_css` is simply recomputed.
  Following the theme the user chose (mocha/latte/custom) was preferred over a vendored fixed palette (GitHub colours etc.).

## Code block copy button

A copy button revealed on hover is attached to each `#tasty-md-body pre > code` (body code blocks only — the load-error
detail `.tasty-state-detail` is a separate `<pre>` outside `#tasty-md-body` and is not a target)
(`render.rs::copy_button_script`). If the document has no `<pre><code` at all (most non-code documents)
this script itself is not inserted — the same conditional-insertion saving pattern as mermaid/highlight.js.
Code blocks without a language label (fenced without language/indented blocks — `<pre><code>` with no `class` at all)
are included as targets too.

- **Coordinating execution order with mermaid/highlight.js**: `mermaid.run()` is asynchronous (the promise is not awaited,
  see the `mermaid_script` docs), so script insertion order alone (`nav_script` → `highlight_script` →
  `mermaid_script` → this script, `render_document`) cannot guarantee that mermaid's DOM replacement has finished at
  inspection time. So, without relying on order, the attach loop checks
  `code.classList.contains('language-mermaid')` directly and skips — mermaid blocks get no button
  (rather than copying the original markdown, no button at all was chosen: the code after replacement by a diagram looks
  different from the original anyway, making "copy" ambiguous). highlight.js, conversely, has no ordering problem —
  `highlightElement` only wraps existing characters in `<span class="hljs-*">` and never changes them (the actual vendored
  bundle was loaded in the WebKitGTK engine and `textContent` before/after highlighting compared directly — see "Verified
  on real hardware" below), so reading `code.textContent` at click time always yields the original code text regardless
  of whether highlighting has completed.
- **Clipboard**: `navigator.clipboard.writeText()` first; on failure (no implementation or a rejected promise) it falls
  back to an off-screen `<textarea>` + `document.execCommand('copy')`.
- **Accessibility/touch**: the button is keyboard-focusable via `tabindex="0"`+`aria-label` (`markdown.copy.label`),
  hidden by default at `opacity:0` and appearing on `pre:hover`/`:focus-visible`. Touch environments without hover
  show it always via `@media (hover:none)`.
- **Feedback**: on copy success/failure the button text changes to `markdown.copy.copied`/`markdown.copy.failed`
  and a `data-state` attribute is added (CSS colour change, see the "Design token mapping" section), reverting to the
  original label after 1.5 s.
- **Duplicate-attach prevention**: `reload_webview` (`main.rs`) calls `render_document` again on every reload and
  replaces the whole document (not a partial DOM patch) — so there is no structural path for listeners to accumulate per
  reload. The attach loop also defensively skips a `<pre>` that already has a button via `pre.querySelector('.tasty-copy-btn')`.

**Verified on real hardware (this repo's dev machine, Linux/WebKitGTK, the same libwebkit2gtk-4.1 engine the `webkit2gtk`
crate wraps)**: the document `render_document` actually produced (including a fenced rust code block) was loaded as-is with
`WebKit2.WebView.load_html`, and after the actually vendored highlight.js finished running, `code.textContent` was read and
matched the original source exactly (no alteration from highlighting; `hljs-*` span attachment confirmed); a copy-button click
was dispatched, `navigator.clipboard.writeText()` succeeded (`data-state` transitioned to `copied`), and the original code text
landing intact in the system clipboard was confirmed directly by GTK clipboard readback — on this backend the primary path
succeeded outright, so the `execCommand('copy')` fallback was not actually exercised. macOS (WKWebView)/Windows (WebView2)
cannot run on this machine, so **only the presence of a standard async Clipboard API implementation was confirmed by code
review** (not verified on hardware).

## Frontmatter hiding

YAML (`---\n...\n---`) or TOML (`+++\n...\n+++`) frontmatter at the very top of the document (first line) is
the metadata block commonly attached by Jekyll/Hugo/Obsidian/Zettlr etc. With `pulldown-cmark`'s
`ENABLE_YAML_STYLE_METADATA_BLOCKS`/`ENABLE_PLUSES_DELIMITED_METADATA_BLOCKS` options it is recognised at parse time as a
`Tag::MetadataBlock` event, and the HTML writer always treats this block as non-writing, so it disappears completely from
the rendered body — no separate metadata display panel is provided (a choice to avoid adding parsing dependencies, i18n
and broken-YAML fallback handling costs). This rule applies **only at the very beginning of the document**, per the
CommonMark frontmatter extension spec — a `---` mid-document renders as `<hr>` as before.

## Smart punctuation

`pulldown-cmark`'s `ENABLE_SMART_PUNCTUATION` option is always on (no settings toggle). Straight quotes
`"`/`'` → curly quotes, `--`/`---` → en/em dashes, `...` → ellipsis are substituted automatically. A choice aligned with
the default of most document viewers such as Obsidian; that it is not fully identical to GitHub's raw rendering is an
accepted trade-off. Inline code (`` `--` ``), text inside fenced code blocks, and backslash-escaped punctuation
(`\"`, `\-\-`) are unaffected by this substitution and remain verbatim.

## Callouts (GFM alerts + Obsidian extended types)

`> [!note]`-style blockquote tags — the five GFM alerts and the Obsidian-style extensions (extra types · folding · custom
titles) — are handled by one unified path, `render.rs::rewrite_callout_events`/`rewrite_callout_buffer` — the two syntaxes
are not split into different functions. `pulldown-cmark`'s `Options::ENABLE_GFM` is a parser option applied once to the
whole document, so it cannot be split as "only the GFM five on, only the Obsidian extension off", hence this design (the
unified function replaced its predecessor, the GFM-only `rewrite_alert_blockquote_event`).

### Supported types

- **The five GFM types** (existing behaviour kept as-is): `note`/`tip`/`important`/`warning`/`caution`.
- **Ten Obsidian extended types** (settled per the official docs [obsidian.md/help/callouts](https://obsidian.md/help/callouts)
  — only types not overlapping the GFM five): `abstract`/`info`/`todo`/`success`/`question`/
  `failure`/`danger`/`bug`/`example`/`quote`.
- **Aliases per the Obsidian docs** (only non-conflicting ones, `render.rs::CALLOUT_ALIASES`): `summary`/`tldr`→
  abstract, `hint`→tip, `check`/`done`→success, `help`/`faq`→question, `fail`/`missing`→failure,
  `error`→danger, `cite`→quote.
- **Deliberately excluded aliases**: the Obsidian docs define `important`/`caution`/`attention` as aliases of
  tip/warning/warning respectively, but these three keywords already exist as distinct GFM types (each with a different
  icon/colour) — "keep the GFM five as-is" takes priority, so these three were not put in the alias table.
  `[!important]`/`[!caution]` always resolve to the existing GFM entries, and `[!attention]` matches no type and remains
  an ordinary blockquote.
- A `[!anything]` not in the list is not recognised as a callout and the bracketed text stays as-is in the ordinary
  blockquote body (a scope decision not to invent types absent from the official docs).

### Syntax

The `+`/`-`/title following `[!type]` are independent of each other (confirmed in the official Obsidian docs — a title
alone without a marker is possible, and a marker alone without a title too):

- `> [!type]` — no marker/title. Rendered with the default type label (translated).
- `> [!type] Title` — a custom title only, no marker. **There is no fold UI at all** (`<details>` is not used at all —
  the same `<blockquote>` shape as GFM alerts, only the `data-label` attribute changes to the title).
- `> [!type]+ Title` (title optional) — rendered as `<details open><summary>...`, initially expanded.
- `> [!type]- Title` (title optional) — `<details><summary>...` (no `open`), initially collapsed.

A bare `> [!NOTE]` of the GFM five with no marker/title arrives already recognised by the `pulldown-cmark` parser itself
as a `Tag::BlockQuote(Some(kind))` AST event (`scanners.rs::scan_blockquote_tag` — if anything other than whitespace
follows the tag this recognition itself fails and it falls back to an ordinary blockquote). All callout recognition and
rendering, including this case, is gathered in one place in `rewrite_callout_buffer`. **As a result the GFM five with a
marker/title attached (like `[!note]+ Title`) are naturally recognised as Obsidian syntax too** — an intended behaviour
change that came with adding Obsidian support (previously anything after the tag was simply left as ordinary text).

The header label (the default type label or the custom title) is looked up by `render.rs::CALLOUT_KINDS` via the
plugin's own `Translator` for the UI language (`markdown.alert.<type>`, `lang/{en,ko,ja}.toml`) — the marker-less shape
cannot branch on language in CSS, so it is reflected via a `data-label` attribute + `content: attr(data-label)`, while the
`<details>` shape is reflected as an actual text node inside `<summary>` (either way a custom title, if present, replaces
the default label). Icons are planted in `background-image` as SVG data URIs of `tasty-icons`' canonical glyphs baked in
each kind's accent colour (`render.rs::alert_icon_data_uri`; the 15 types share the 7 existing semantic accents
(`accent_primary`/`accent_info`/`accent_success`/`accent_warning`/
`accent_attention`/`accent_danger`/`accent_agent`) — no dedicated colour tokens; overlapping combinations are told apart by
icon and label text).

Ordinary blockquotes (a tagless `>`, or a type not in the list) are unaffected. `data-label`/
`<summary>` text is planted only from actual parser events (`Tag::BlockQuote(Some(kind))`) or from parsing the first-line
text of a buffered blockquote, so writing a literal such as `<blockquote class="markdown-alert-note">` as raw HTML in the
body is never mistaken for a fake callout (because the approach trusts only parser events/buffered actual blockquote
content, rather than matching finished HTML strings).

### Nesting

When another callout/ordinary blockquote nests inside a callout (`> [!note]\n> > [!warning]\n...`),
`rewrite_callout_events` handles the inner one identically, recursively — perfect visual styling is out of scope
(e.g. no per-depth indentation adjustment), but the inner callout renders per its own type without a crash or text loss.

### sanitize

The `<details>`/`<summary>` tags were added to the `sanitize_html` whitelist — `details` with
`class`+`open`, `summary` with no separate attributes (the title goes in as an actual text node, so no attribute is needed).

## Bare URL autolink

`http://`/`https://` URLs written as plain text in the body without `<...>` angle brackets or `[text](url)` markdown
syntax are also converted to clickable links. `pulldown-cmark` 0.12.2 supports only CommonMark core's angle-bracket
autolinks and does not implement GFM's extended autolinks (including recognition of scheme-less bare URLs)
(`Options::ENABLE_GFM` turns on only alert blockquote tags), so `render.rs::autolink_bare_urls`/`split_bare_urls` scan the
event stream directly and split into `Tag::Link`. **This scope is `http(s)://` schemes only** — `www.`-prefix
(scheme-less hosts) and email autolinks are excluded (a separate TODO if the need is confirmed).

This pass is a stateful scan (not a simple stateless `map()`) — it explicitly excludes the following:

- Text already inside a `Tag::Link` (already explicitly linked, like `[https://x](https://x)`) — preventing duplicate links.
- Text inside `Tag::CodeBlock` (fenced/indented code blocks).
- Inline code needs no separate tracking — pulldown-cmark represents inline code content as a separate `Event::Code`
  variant in the first place, not `Event::Text`, so it is already structurally excluded.

Measurement confirmed that one visual URL really does arrive split into several `Event::Text` fragments — a single
unmatched `*`/`_` inside the URL that fails to pair as real emphasis is tokenised separately as a lone one-character
`Event::Text` (e.g. `.../foo*bar` → `Text("...foo")` + `Text("*")` + `Text("bar...")`). So this pass merges consecutive
`Event::Text` into one buffer until real markup (another tag start/`SoftBreak` etc.) intervenes, then scans URLs on that —
real markup boundaries are never joined.

Boundary handling:

- **Punctuation trimming**: a trailing `.`/`,`/`;`/`:`/`!`/`?`/quote/lone `*`/`_`/`~` at the end of a URL is removed one
  character at a time and left outside the link (`https://example.com.` → the `.` is outside the link).
- **Parenthesis balance**: only the counts of `(`/`)` **inside the matched URL itself** are compared — if parentheses balance
  within the URL as in wiki URLs (`Rust_(programming_language)`) the trailing `)` is kept, and if only a `)` the URL itself
  never had remains, as when a sentence wraps the URL in parentheses (`(https://example.com)`), it is left outside the link.
- **HTML entities**: entities such as `&amp;` are already decoded to actual characters by the pulldown-cmark parser before
  reaching `Event::Text`, so regardless of autolinking, `push_html` re-escapes them identically on the way out — this pass
  needs no separate entity handling.

The `dest_url` of a newly created `Tag::Link` is rewritten to the `#tasty-nav:link:<enc>` fragment by the same rule as
explicit markdown links — `autolink_bare_urls` only creates a `Tag::Link` with the original URL placed as-is in `dest_url`,
and `rewrite_link_event`, which passes once over the whole event stream at the end, converts explicit and auto-generated
links alike to nav-fragments without distinction (for the order see the comment in `unsafe_content_html`).

## Wikilinks

Obsidian-style `[[document]]`/`[[document|display text]]` syntax is recognised and converted to links
(`render.rs::resolve_wikilinks`/`split_wikilinks`/`wikilink_events`). Exactly the same architecture as bare URL autolink
(the section above) — a syntax the library does not know, so `Event::Text` is merged across event boundaries into one
buffer (for the same reason as `autolink_bare_urls`: one text can arrive split into several `Event::Text` fragments) and
scanned there, splitting into `Tag::Link`. `link_depth`/`code_block_depth` tracking is identical too — text already inside
an explicit link or inside a code block is untouched. The pipeline position is after `figurize_solo_image_paragraphs`,
right before `autolink_bare_urls` (see the `unsafe_content_html` comment) — both hand over a `Tag::Link` carrying the
original relative path as-is before `rewrite_link_event`, so the final rewrite to the nav-fragment
(`#tasty-nav:link:<enc>`) happens only once at the end (no wikilink-specific rewrite logic).

### Supported scope

- **File resolution**: `<document>.md` is looked up only in **exactly the same directory** (`base_dir`) as the current
  markdown file, as a filename matching exactly including case — the same directory rule as ordinary relative links
  (`classify_link`); the only difference is that a wikilink gives only an extensionless name, so `.md` is appended
  automatically. Existence is checked only once with a synchronous `std::path::Path::exists()` at render time (this crate
  already has the `fs.read` permission, so no permission expansion).
- **When found**: a `Tag::Link` of exactly the same shape as an ordinary relative link `[text](document.md)` is created and
  flowed into the existing pipeline as-is — a click follows the existing file-open path nav-fragment →
  `main.rs::dispatch_file_link` (no wikilink-specific click handling).
- **When not found**: the link itself is still created (the destination is not erased) — clicking follows
  `dispatch_file_link`'s existing "nonexistent files are logged and silently ignored" path as-is.
  It is only visually distinguished by wrapping in a `.tasty-wikilink-missing` span (dotted underline + `accent-danger`
  colour — see "Design token mapping" below). `span`/`class` are already opened in the `sanitize_html` whitelist
  (see the math rendering section), so no sanitizer change for this feature.
- **When `base_dir` itself is absent** (an unsaved buffer etc.) — always treated as "not found", the same as an ordinary
  relative link being treated as unresolvable in `classify_link`.
- **Display text**: in the `[[document|display text]]` form the text after `|` is used as link text (falling back to the
  document name if empty).
- **Path traversal prevention**: if the `<document>` part contains even one `/`, `\`, or `..` (not a proper single-segment
  name) it is not recognised as a wikilink and the original `[[...]]` text is left as-is (silently passes as a parse
  failure — no error).
- **No collision with footnotes (`[^name]`)**: with `Options::ENABLE_FOOTNOTES` active, footnotes leave the parser as
  separate `Event::FootnoteReference`/`Tag::FootnoteDefinition` events in the first place, not `Event::Text`, so they are
  not something this wikilink scanner can even see — verified not only by the structural argument but by a test that puts
  footnotes and wikilinks together in the same document and checks the actual event stream
  (`wikilink_does_not_collide_with_footnote_reference`).

### Unsupported (explicit scope exclusions)

- **Whole-vault recursive search** — nothing outside the same directory is searched.
- **Case-insensitive matching / aliases** — only the exact same filename is recognised.
- **`[[document#section]]` (heading-anchor combination)** — technically easy to implement given heading id
  auto-generation, but deliberately excluded from this scope.
- **`![[document]]` (embed syntax)** — not implemented.

## Footnote backlinks · accessibility

The default `pulldown-cmark` HTML writer for `Options::ENABLE_FOOTNOTES` (footnotes `[^name]`/`[^name]: ...`)
creates only the link from the reference point to the definition, and generates no backlink from the definition back to
the reference point nor any `aria-label`. `render.rs::rewrite_footnote_event` intercepts the actual
`Event::FootnoteReference`/`Tag::FootnoteDefinition` AST events (the same pattern as the callouts'
`rewrite_callout_events` — matching parser events themselves rather than finished HTML strings, so it is never confused
with fake footnote markup disguised as raw HTML) and plants the following directly:

- **A unique id per reference point** — `fnref-<safe-name>` (first reference); if the same footnote is referenced several
  times, sequence numbers `fnref-<safe-name>-2`, `-3`... follow. The reference `<a>` links to `#fndef-<safe-name>`
  (the definition).
- **Backlinks at the end of the definition** — inside the definition `<div id="fndef-<safe-name>">`, after the content,
  `<a href="#fnref-...">↩</a>` is added **as many times as there are references** (one backlink per definition would make
  it ambiguous which reference point to return to). The total reference count is counted in advance by
  `footnote_reference_totals` parsing `source` once more before the render run — a definition can come **before** its
  references in the source (a document where `[^a]: ...` precedes the `[^a]` references is valid too), so a single forward
  pass cannot know the final reference count at the point the definition ends.
- **`aria-label`** — references use `markdown.footnote.ref_aria` ("go to footnote N"); backlinks use
  `markdown.footnote.backlink_aria` ("return from footnote N to the text") for one reference and
  `markdown.footnote.backlink_aria_nth` ("return to the M-th reference of footnote N") for two or more, distinguishing which
  reference. Keys exist in all three `lang/{en,ko,ja}.toml` files. `sanitize_html` allows `aria-label` on the `a` tag only
  (narrowed to the actually needed `a`, not every tag).
- **id safety** — spaces/Unicode in footnote names cannot be used as HTML ids as-is, so they are encoded with
  `percent_encode_fragment` (the same helper as nav-fragments/icon data URIs) — a collision-free injective function, so
  different names never collapse to the same id.
- **Undefined references** (`[^missing]` with no matching definition) — the `pulldown-cmark` parser itself creates no
  `FootnoteReference` event and leaves `[`/`^missing`/`]` as plain text — a natural fallback to the original text without
  a crash.

## Heading id + table of contents (TOC)

Every heading (`h1`–`h6`) receives a GitHub-compatible auto-slug `id` — the explicit `# Title {#custom-id}`
syntax (`Options::ENABLE_HEADING_ATTRIBUTES`) is not supported (a design decision narrowing the scope to auto-generation
only). `render.rs::collect_headings` sweeps the source once collecting each heading's plain text (markup such as
code/links/emphasis/image alt stripped, text only), and `Slugger` turns it into a slug by lower-casing + keeping only
Unicode letters/digits/`-`/`_` + replacing spaces with `-` (non-ASCII text such as Korean is kept as-is —
`char::is_alphanumeric` is Unicode-aware). Duplicate slugs within the same document get `-1`/`-2` sequence numbers, and if
the slug is empty because it was all special characters it falls back to `heading` (so an id is never an empty string).
`render.rs::assign_heading_ids` then parses the document once more (both passes sweep the same `source`, so heading order
always matches) and assigns this result in order to each heading event's `id` field — pulldown-cmark's HTML writer always
outputs `Tag::Heading::id` when present regardless of options, so `ENABLE_HEADING_ATTRIBUTES` need not be turned on.
`sanitize_html`'s `generic_attributes(["id"])` already allows `id` on all permitted tags, so no sanitizer change was
needed either.

With one or more headings, a collapsible `<nav id="tasty-toc">` table of contents is inserted at the very top of the
document (right below the address bar, above the body) (`render.rs::toc_nav_html`) — an inline insertion, not a sticky
side panel (a design decision to avoid adding layout CSS/scroll synchronisation complexity). Each item is
`<a href="#slug">`, and clicks take the existing anchor-only exception path of `rewrite_link_dest` as-is (a dest starting
with `#` passes through without rewrite) — no new `#tasty-nav:` routing is made. Per-level indentation is expressed by the
`.tasty-toc-l1`..`l6` CSS classes (multiples of `--md-space-sm`). Collapse/expand is implemented by minimal JS in
`nav_script` (a trusted script, not user content) toggling the `tasty-toc-collapsed` class on `#tasty-toc` when
`#tasty-toc-toggle` is clicked, and the list has `max-height:280px;overflow-y:auto` so the panel does not grow without
bound in documents with many headings. Since `#tasty-addr-bar` is 40px sticky, every heading gets
`scroll-margin-top:calc(40px + var(--md-space-sm))` so a TOC-click jump does not hide the heading under that bar. A
document with no headings at all does not render the TOC area at all (so it does not break with an empty nav —
`render_document` skips the call entirely when the heading list is empty).

## Image captions

When a paragraph contains **only one** image (`![alt](src "title")`), the whole paragraph is promoted to
`<figure><img/><figcaption>{alt}</figcaption></figure>` (`render.rs::
figurize_solo_image_paragraphs`) — the alt text is always exposed as a caption instead of staying only inside the `alt`
attribute (invisible on screen when the image loads normally). **Policy: whenever alt text exists it is always promoted
automatically — no opt-in syntax.** An image without alt (`![](img.png)`) has nothing to caption, so it renders as before
(no regression).

The promotion condition is deliberately strict: if that paragraph has even a little inline content other than the image
(body text, a second image, a link wrapping the image `[![alt](img.png)](url)` etc.), it is not promoted and renders as
before (the inline `<img>` as-is). Reason: `Tag::Image` is an **inline** element inside `<p>`, and wrapping that single
event in `<figure>` (a block element) would produce invalid HTML with a block nested in inline context like
`<p><figure>...`, which the browser might close the `<p>` early in unpredictable ways — hence the approach of promoting the
**whole paragraph** containing only one image, and when that condition breaks, giving up the caption was judged safer than
producing invalid HTML.

The caption text is plain text concatenating only the `Text`/`Code` events inside the image alt span (markup such as
emphasis removed — the same way as heading text collection (`collect_headings`)). This text is emitted as an ordinary
`Event::Text`, so `push_html` HTML-escapes it just like body text — even if alt contains characters such as `<`/`>`/`&`
they appear in the caption only safely escaped. `<figure>`/`<figcaption>` themselves are injected via the "trusted
plugin-authored markup" pattern this file already uses (`Event::Html`, the same as `wrap_static_callout`'s
`<blockquote data-label="...">` insertion), so they were added to the `sanitize_html` whitelist as bare tags with no
separate attributes.

## Image load failure state UI

When an image fails to load through a path typo, a moved file, etc., the browser's default "broken image" icon is replaced
by tasty's own failure UI showing the path (`.tasty-img-error`) (`render.rs::
image_error_script`). If the document has no `<img` at all (most non-image documents) this script itself is not inserted
— the same conditional-insertion saving pattern as the code block copy button/mermaid/highlight.js.

- **Why a trusted script rather than an `onerror=` inline handler**: `sanitize_html` removes every inline event handler
  unconditionally (a core axis of XSS defence, no exceptions). Instead, the same pattern as the code block copy button —
  after sanitising, trusted plugin code attaches `addEventListener('error', ...)` directly to the DOM at render time.
- **Catching images that already failed**: the trusted script runs at the bottom of the document, so some images may have
  already fired their `error` event before the listener attached. So right after attaching the listener, each `<img>` is
  also checked for `img.complete && img.naturalWidth === 0` (loading finished but no actual pixels = failure; a case like
  `![alt]()` with an entirely empty `src` is naturally caught by this condition too).
- **Displayed path**: `img.getAttribute('src')` (the original relative path written in the markdown) is used as-is.
  `img.src` (the property) is the value already normalised to an absolute `file://` URI by `<base href>` (before the
  "Mermaid diagrams" section above, `render.rs::file_dir_uri`) and reads badly for humans.
- **Accessibility**: the placeholder is `role="img"`, and the original `alt`, if present, is preserved as-is as
  `aria-label` (if absent, the failure notice label itself falls back to the aria-label).
- **Relation to the remote-image blocking policy**: when the host's `allow_remote_content` policy blocks a remote image
  request, that request actually fails, so the `<img>`'s `error` event fires legitimately — not a false positive but an
  accurate failure indication. `sanitize_html`'s `url_schemes` allows only `http`/`https`/`mailto` and the `loading`
  attribute itself is not in the allowed attribute list (the `sanitize_html` section above), so `loading="lazy"` does not
  survive, and there is structurally no room to confuse "not yet attempted" from browser-native lazy loading with "load
  failed".
- **Duplicate-attach prevention**: `reload_webview` replacing the whole document on every reload is the same as the code
  block copy button (no structural path for listeners to accumulate per reload). The script itself also defends with two
  data attributes per `<img>`: `data-tasty-img-checked` (preventing duplicate listener attachment) /
  `data-tasty-img-failed` (making placeholder replacement idempotent, safe even if the listener path and the
  immediate-check path fire simultaneously).
- **Theme coupling**: the icon is planted as a data URI of the `tasty_icons::IMAGE` glyph baked with
  `theme.accent_danger()` (reusing the same `render.rs::alert_icon_data_uri` as GFM alert icons). Border/label colours use
  the same `danger` token and the path text the same `muted` token as `.tasty-state-detail` — the existing error-state
  colouring is reused as-is with no dedicated failure-UI tokens (see "Design token mapping" above).

**Verified on real hardware (this repo's dev machine, Linux/WebKitGTK, libwebkit2gtk-4.1)**: the document `render_document`
actually produced (one real 1×1 PNG + one nonexistent path, a real `file://` base URI) was loaded with
`WebKit2.WebView.load_html` and the actual browser fetch succeeding/failing observed as-is — the real image remained an
`<img>` (no regression), and only the nonexistent image was replaced by `.tasty-img-error`, with the original alt going into
`aria-label` and the original relative path (`missing.png`, not the normalised `file://` URI) going into the text exactly,
confirmed directly in the DOM. Manually re-injecting the same attach script once more into the same document did not increase
the placeholder count, verifying that the data-attribute guards actually work. macOS (WKWebView)/Windows (WebView2) cannot
run on this machine — only confirmed by code review that the implementation is based on the same standard DOM event
(`error`)/`HTMLImageElement` API (not verified on hardware).

## Find in page

Pressing `Ctrl+F`/`Cmd+F` while the document (webview content) actually has keyboard focus opens an in-document text
search bar (`render.rs::find_bar_html`/`find_in_page_script`) — it works purely with the trusted script embedded in the
markdown plugin document, without host API extension (the native find APIs
(`WebKitFindController`/`WKWebView.find`/WebView2 `Find`) were not adopted because the three engines differ in
regex/whole-word support, and returning the match count to the host would additionally need per-backend async signal
handling — a host API extension cost too high for this markdown-plugin-local feature).

The search bar (input + `n/m` counter + ▲▼ prev/next + close) floats at the top right of the document with
`position:fixed` (the same "sticky, non-modal, top-right" placement as the gallery `search_bar` specimen — no scrim),
hidden by default. Matches are found by walking the text nodes of `#tasty-md-body` with a DOM `TreeWalker`
(`NodeFilter.SHOW_TEXT`) and wrapped in `<mark class="tasty-find-hit">` — the current match additionally gets the
`tasty-find-current` class, distinguished by a different colour. Text nodes with a `<pre>`/`<code>` ancestor are excluded
from the scan (code blocks are out of search scope — a policy decision). On every search (input debounced 150 ms,
immediate on `compositionend`) the previous `<mark>`s are first restored to the original text (`Node.normalize()`) and
then re-scanned, so highlights do not accumulate. During IME composition (`compositionstart`~`compositionend`) no search is
triggered. `Esc` closes the bar and completely removes the highlights (DOM restored), `Enter`/`Shift+Enter` move to the
next/previous match (wrapping) + `scrollIntoView`.

**Conflict with the existing terminal search (`kb.find`)**: the host's global `find` keybinding used to open the
`search_bar` egui popup regardless of the focused surface kind — that popup's search logic (`run_search`) works only via
`find_terminal_by_id`, so on a markdown (webview) surface it was always an empty `0/0` overlay (a bug confirmed by
measurement). The `kb.find` branch in `src/adapters/ui/input/shortcuts/keybinding.rs` was fixed to open only when the
focused surface is a `Terminal` — other kinds do not consume this branch (returning false) and it passes on to the page's
own find-in-page (if any). With this change, `Ctrl+F` with a markdown document focused always goes to this section's
in-document search, and the terminal-only overlay does not appear.

## Design token mapping

`crates/tasty-plugin-markdown/src/render.rs::render_document` builds one complete HTML5 document
— it injects Theme tokens as CSS custom properties inside `<style>` (`theme_css`), and the whole document (address bar +
body) references those properties. The host only receives this document wholesale via `webview.set_url` and puts it on the
native WebView; it does not draw individual elements pixel by pixel — the table below is the CSS custom property ↔ Theme
token mapping.

|---|---|---|---|
| document background/foreground | `--md-bg` / `--md-fg` | `bg-app` (=crust) · `text-secondary` | the webview render path has no focus signal, so `bg-app` is the document's only background (the `surfaces.markdown.focused_bg` setting is not used on this path) |
| address bar | `#tasty-addr-bar` | `bg-sidebar` · 40px sticky top | `<input list>`+native `<datalist>` (recents)+Go `<button>` — all document HTML |
