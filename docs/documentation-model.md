# Tasty 문서 모델 (Documentation Model)

이 문서는 설계·명세·개발 문서의 위치와 연결 방법을 정한다. 새 문서를 만들거나 기존 문서를 고치기 전에 읽는다. 분류 이유는 [문서 구조 결정](adr/0049-documentation-structure-and-evidence.md)에 있다.

## 1. 핵심 원칙 — 동작이 1순위, 화면은 2순위

Tasty는 화면 없이도 동작한다. 기능 문서는 내부 동작을 먼저 설명하고, 그 동작을 화면에서 어떻게 사용하는지 연결한다. 프로젝트의 전체 원칙은 [identity.md](identity.md)를 따른다.

- 기획문서(behavior)는 기능이 무엇을 하는지 설명한다. 화면이 없는 실행에서도 유효한 내용이다.
- 화면정의서(screen)는 기능의 상태와 사용자 조작을 화면에 어떻게 표시하는지 설명한다. 해당 기획문서에 속한다.

기능 설명에는 에이전트가 사용하는 CLI·IPC 동작을, 화면 설명에는 키보드·마우스로 사용하는 방법을 적는다. 사용자와 에이전트의 행동을 구분하는 원칙은 두 문서 모두에 적용한다.

기능 하나에 화면은 없거나 여러 개일 수 있다. 화면 하나는 기획문서 끝의 `## 화면` 절이나 `screens/`의 별도 파일로 설명한다. 어느 형식을 쓰는지는 §3의 기준을 따른다.

## 2. 문서 지도 (전체 카테고리)

문서는 제품 명세와 개발·운영 가이드로 나눈다. 동작 설명에 화면 설명을 연결하는 §1의 구조는 제품 명세에 적용한다. 개발·운영 가이드는 목적에 맞는 별도 카테고리에 둔다.

### A. 제품 명세 — "tasty 가 무엇인가"

| 종류 | 위치 | 적을 내용 | 변경 방법 |
|---|---|---|---|
| 기획문서 | `docs/features/<f>/index.md` | 호스트가 제공하는 기능의 내부 동작 | 문서를 직접 갱신 |
| 화면정의서 | 기능 문서의 `## 화면` 절 또는 `docs/features/<f>/screens/<s>.md` | 화면 요소와 상태별 표시·조작 | 문서를 직접 갱신. 파일 분리 기준은 §3 |
| 번들 플러그인 | `docs/plugins/<id>/index.md`와 필요한 `screens/` | 플러그인이 제공하는 동작·화면 | features와 같은 구조로 갱신 |
| 횡단 규칙·흐름 | `docs/design/{policies,flows,systems}/` | 여러 기능에 공통인 규칙·흐름 | 문서를 직접 갱신 |
| 용어 | `docs/concepts/` | 프로젝트 공통 용어 | 문서를 직접 갱신 |
| 근거(ADR) | `docs/adr/` | 선택 이유·대안·보류·재검토 조건 | [ADR 작성 규칙](adr/template.md)에 따라 현재 유효한 선택과 근거를 유지 |
| 디자인 원본 | `design-system/…` (vendor) | 픽셀·토큰·컴포넌트 정의 | Claude Design에 design-request로 변경 요청 |

화면정의서는 요소 목록과 상태별 표시 관계를 적는다. 픽셀·토큰 값을 다시 정의하지 않고 `design-system/`의 디자인 원본을 연결한다. 값을 복사해 적으면 원본이 바뀔 때 설명 사본이 서로 달라질 수 있다.

### B. 개발·운영 가이드 — "tasty 를 어떻게 다루나"

| 종류 | 위치 | 적을 내용 | 독자 |
|---|---|---|---|
| 개발 가이드 | `docs/dev-guide/` | 빌드·커밋·릴리스·플러그인 개발·국제화·오류 처리·GPU·디버그 IPC·검증 | 개발자 |
| 아키텍처 | `docs/architecture/` | 크레이트 구조·데이터 흐름·유지해야 할 조건 | 개발자 |
| 자체 검증 | `docs/ai-verification/` | UI·렌더링 검증 절차 | 개발자 |
| 에이전트 가이드 | 별도 가이드는 미신설. 조회 문서는 [reference](reference/index.md) | IPC·CLI 조작 방법. 릴리스 파일에는 첨부하지 않음 | 사용자의 AI 에이전트 |
| 설치 | `docs/installation.md` | OS·아키텍처별 설치 방법 | 사용자·에이전트 |

호스트가 플러그인에 제공하는 런타임·권한·렌더링·번들 규칙은 개발 가이드에 둔다. 플러그인 자체의 기능을 설명하는 `docs/plugins/`와 구분한다. 개발·운영 문서는 코드와 절차를 기준으로 검토·교정하며, 디자인 도구를 도입했다는 이유로 처음부터 다시 쓰지는 않는다.

## 3. 폴더 구조 (중첩)

기능 하나는 폴더 하나에 둔다. 화면 설명은 그 폴더 안의 절 또는 파일이다.

```
docs/features/<feature>/
  index.md            # 내부 동작을 먼저 설명하고, 단일 화면은 끝의 `## 화면`에 작성
  screens/            # 화면 설명을 파일로 나눌 때만 생성
    <screen>.md
```

기본은 `index.md`의 절로 작성한다. 다음 중 하나에 해당할 때만 `screens/<screen>.md`로 나눈다.

1. 한 기능에 화면이 둘 이상이면 화면별로 파일을 나눈다.
2. 화면에 템플릿 항목 외의 고유 규칙이 있으면 별도 파일로 둔다. 렌더 경로, 스크롤·가상화, 조회·갱신, 상호작용, 입력 위젯 모양처럼 그 화면에만 적용되는 규칙이 해당한다.

템플릿 항목은 트리거·레이아웃·UI 요소 목록·상태별 표시·디자인 원본이다. 디자인 토큰 매핑이나 갤러리 예제로 연결하는 절도 템플릿 항목으로 본다. 토글에 따라 배치가 달라지는 것만으로는 고유 규칙으로 보지 않는다. 그 토글의 동작은 기능 문서에서 설명한다.

단일 화면을 `index.md`의 `## 화면` 절로 작성할 때는 다음 형식을 따른다.

- 머리 불릿의 `부모 기획`은 생략한다. 시각 소스·트리거 위치·상위 화면은 `## 화면` 바로 아래에 둔다.
- 화면 템플릿의 `##`를 `###`로, `###`를 `####`로 내린다. 절 이름은 유지한다.
- 기능 문서 머리의 `**화면**:`은 `#화면`을 연결한다. 다른 문서에서도 `features/<f>/index.md#화면`을 사용한다.

화면이나 고유 규칙이 추가되면 같은 기준으로 별도 파일로 나눈다. 줄어든 경우에는 절로 합칠 수 있다.

- headless 전용 기능은 화면 절과 `screens/`를 만들지 않고 머리에 `**화면**: 없음 — headless 전용`으로 적는다.
- 여러 화면은 `screens/`에 화면별 파일로 둔다.
- [기획 템플릿](features/_feature.template.md)과 [화면 템플릿](features/_screen.template.md)을 사용한다. 화면을 절로 넣을 때도 항목은 같고 제목 단계만 내린다.
- 번들 플러그인(`docs/plugins/<id>/`)도 같은 기준을 따른다.

## 4. 연결 개념 — 합성 화면은 "언급" 으로만 잇는다

사이드바·MainView·설정처럼 여러 기능을 모은 화면은 자기 영역만 설명한다. 다른 기능을 여는 요소에는 해당 문서를 연결하고 그 내용을 복사하지 않는다.

사이드바의 화면 설명은 다음처럼 쓴다.

```
## UI 요소 인벤토리
- 최상단: 아이콘·로고·접기 버튼
- 중단: 남은 높이를 사용하는 워크스페이스 영역
- 최하단 도구 버튼: features/tools-menu/ 참조
- 최하단 플러그인 버튼: features/plugin-system/index.md#화면 참조
- 최하단 설정 버튼: features/settings/screens/settings.md 참조
```

사이드바 문서에 도구 메뉴의 항목을 다시 적지 않고 버튼 설명에서 도구 메뉴 문서로 연결한다.

## 5. design ↔ code 연계 (claude design 협업)

`design-system/`은 Claude Design 산출물이다. 코드 작업자가 직접 수정하지 않는다. docs에는 화면 요소와 동작 관계를 설명하고 픽셀·토큰 정의는 디자인 원본으로 연결한다.

디자인 변경은 Claude Design에 요청한 뒤 받은 결과를 코드에 반영한다. 소스를 먼저 바꾸어 새 디자인 값을 정하지 않는다. 문서는 §6의 배치 규칙에 따라 동작을 features에, 디자인 원본 링크를 화면 설명에, 선택 이유를 ADR에 반영한다. 요청 제출과 결과 확인은 [디자인 변경 절차](dev-guide/design-change-workflow.md)를 따른다.

## 6. 작성 규칙 요약

### 문서의 역할과 말투

현재 기능과 규칙을 먼저 설명한다. 독자가 해야 할 일, 적용 조건, 결과를 구체적인 명사와
동사로 쓴다. 내부 비유나 조사 순서를 해독해야 결론을 알 수 있는 문장은 고친다.
한 문단에 현재 규칙, 과거 실험, 예외, 반박을 계속 덧붙이지 않는다.

소스 주석은 필요한 이유·제약·안전 조건만 짧게 남긴다. 과거 변경 일기, 코드 내용을 그대로 반복하는 설명, 중복 경고, 사라진 문서를 가리키는 주석은 삭제한다. 공개 API 계약·예제·라이선스와 검사에 필요한 예외 사유는 보존한다. ADR에서 선택의 이유를 설명하는 과거 근거와 일반 소스의 변경 일기는 구분한다.

- 현재 동작은 기능·설계 문서, 개발 절차는 개발 가이드, 중요한 선택의 이유는 ADR에 둔다.
- 구현 경로와 함수는 개발자에게 필요할 때 쓴다. 사용자 가이드에는 사용 방법을 설명한다.
- 진행 중인 계획과 작업 상태는 로컬 작업 문서에서 관리한다. 현재 미지원 범위는 문장으로 밝힌다.
- 문서 목록은 평문 불릿이나 번호를 쓴다. 진행 상태를 담는 Markdown 체크박스는 쓰지 않는다.
- 변경한 기능의 카테고리 인덱스를 갱신한다. 전체 인덱스는 카테고리가 바뀔 때 갱신한다.

### 경로와 코드 인용

저장소 경로를 인용하면 현재 파일을 가리켜야 한다. 이동했다면 인용도 고친다.
다른 저장소의 소스는 라이브러리 이름을 앞에 붙여 구분한다.
크레이트 문서의 `src/`는 그 크레이트를 기준으로 해석할 수 있다.
Markdown 상대 링크는 그 문서의 디렉터리를 기준으로 확인한다.
코드 위치는 줄 번호 대신 파일과 함수·타입·상수 이름으로 적는다.
현재 구현 인용은 이동·삭제를 따라 갱신한다. 과거 결정의 근거를 설명하는 인용은
결정 당시 상태임을 밝히고, 컴파일러 출력 견본의 줄 번호는 원문 내용으로 유지한다.
ADR References의 코드 인용은 별도 설명이 없으면 현재 구현 위치를 뜻한다.

Git에 없는 로컬 작업 폴더·티켓 번호·일회성 디자인 changelog를 영구 근거로 인용하지 않는다.
임시 작업 위치는 로컬 지침에서 정한다. 다음은 필요한 문서에 적을 수 있다.

- 빌드 절차로 재현되는 산출물 경로.
- 제품이 사용하는 사용자 홈과 런타임 경로.
- 파일 경로가 아닌 플러그인 ID·설정 키 등의 식별자.
- 제외 항목을 정의하는 `.gitignore` 자체.

금지 형태를 입력으로 사용하는 검사와 픽스처는 필요한 패턴만 예외로 둔다.
코드의 `TODO:`와 `TODO(범위):`는 할 일 표시로 사용할 수 있다.
다른 사람이 볼 수 없는 작업 티켓을 이유 대신 언급하지 않는다.

문서의 생성물 경로는 생성·소비 절차로 설명하고, 현재 저장소에 존재하는 근거 파일인 것처럼 링크하지 않는다.
크레이트 밖 문서에서는 어느 크레이트의 파일인지 전체 경로로 적는다.

경로 존재 검사는 인용 내용이 사실인지까지 확인하지 않는다.
백틱 안의 이름만으로 된 모든 인용을 자동 검사하는 것도 아니다.
함수와 파일을 함께 명시하고 실제 구현을 읽어 확인한다.

이력 재작성으로 측정 커밋에 접근할 수 없으면 같은 변경이 남아 있는지 patch-id와 실제 내용을 확인한다.
대응 커밋이 없다면 임의 해시로 바꾸지 말고 재현할 수 없음을 밝힌다.
현재 가드의 측정 기준처럼 재현 가능한 트리를 요구하는 값은 현재 트리에서 다시 측정한다.
얕은 clone의 객체 부재를 커밋이 없다는 증거로 쓰지 않는다.

### 링크와 표

헤딩을 바꾸거나 옮길 때 기존 인용을 검색하고 앵커를 확인한다.
헤딩 레벨만 바꾸면 보통 앵커는 같지만 같은 제목이 반복되면 번호 접미사가 달라질 수 있다.
강조와 문장부호가 있어도 렌더러가 만드는 앵커로 판단한다.
출발지와 대상이 모두 `site/content/`인 앵커는 사이트 빌드의 실제 HTML ID로 확인하며,
사이트 밖 GitHub 문서를 가리키는 앵커는 그 문서의 규칙으로 확인한다.

표 셀의 파이프 문자는 코드 표기 안에서도 이스케이프한다.
서로 다른 표 사이에는 빈 줄을 둔다. 소스에 내용이 보이는 것과 렌더 결과가 같은지는 별개다.
ADR 인덱스는 제목과 헤더에서 생성한다. 다른 인덱스가 파일명으로 링크하는 관례까지
ADR 제목 비교 규칙으로 바꾸지 않는다.

### 수치와 근거

수를 쓰기 전에 무엇을 세는지와 어떤 판단에 필요한지 정한다.
판단에 쓰지 않는 장식적인 개수는 덜어낸다.
현재 개수나 두 ref의 차이처럼 자주 바뀌는 값은 계산 명령 또는 정본 링크로 대신한다.
중요한 현재값을 계속 써야 한다면 소스와 문서가 맞는지 확인하는 수단도 함께 둔다.
과거 측정은 시점·커밋·검사 대상·계산 방법을 적고 현재 보장과 구분한다.
측정 이후 입력이 바뀌었다면 그 사실도 밝힌다.

값이 달라졌다면 대상이 변했는지, 세는 방법이 변했는지, 이전 값이 틀렸는지 구분한다.
서로 다른 대상을 센 수를 빼거나 부분 측정을 전수 측정처럼 쓰지 않는다.
기계나 실행마다 달라 재현할 수 없는 수는 그 이유와 다시 측정할 방법을 적는다.
계산 명령도 원본을 실제로 읽는지 확인한다. 같은 값에서 같은 값을 재구성한 식은 독립 검산이 아니다.
다른 문서의 선례를 인용할 때는 적용 조건과 제한도 함께 설명한다.
과거에 확인한 동작도 도구나 구현이 바뀌면 다시 확인해야 한다.

같은 사실이 여러 곳에 적혀 있으면 수정 전에 이름·값·경로로 인용을 찾고 변경 후 대조한다.
목록은 [중복 목록 관리](dev-guide/duplicated-sets.md)를 따른다.
사람이 읽는 문장 전체의 의미가 같은지는 자동 검사로 보장되지 않는다.

### 플랫폼과 검증 결과

실행해 확인한 사실, 소스에서 확인한 구조, 아직 확인하지 못한 범위를 구분한다.
플랫폼별 근거가 같으면 한 문장으로 쓰고, 다르면 각 OS의 근거와 미확인 범위를 적는다.
한 OS에서 실행한 결과를 세 OS에서 확인했다고 쓰지 않는다.
컴파일·유닛 테스트·통합 테스트·실제 UI 실행도 구분한다.
실행 경로는 [CI 가이드](dev-guide/ci-gates.md), 검출력 확인은
[가드 검증](dev-guide/guard-verification.md)을 따른다.

검사가 특정 사실을 보장한다고 쓸 때는 그 사실을 깨뜨린 변경을 실제로 검출하는지 확인한다.
확인하지 못했다면 기존 검사가 없다고 단정하지 말고 확인한 범위와 한계를 쓴다.
인용 경로의 존재나 테스트 실행 여부를 확인하는 가드가 산문의 주장 전체까지 검증하지는 않는다.
