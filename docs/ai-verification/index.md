# AI 자체 검증 지침

Tasty를 개발하는 에이전트가 UI·렌더링·입력을 직접 재현하고 확인하는 방법이다.

| 문서 | 내용 |
|---|---|
| [스크린샷](screenshot-methods.md) | 캡처 대상과 수단, ID 지정, 격리 실행, 픽셀 비교. native WebView는 OS 화면 캡처가 필요하다. [시각 판정 체크리스트](screenshot-methods.md#시각-판정-체크리스트)도 참고한다. |
| [IPC](ipc-usage.md) | IPC 조작, Enter 전송, 줄 단위 응답 읽기, 전용 PTY를 통한 대화형 작업 |
| [DPI 배율](dpi-scale-verification.md) | DPI가 1이 아닌 환경을 만들고 설정값과 실제 창 크기를 대조하는 방법 |
| [IME](ime-testing.md) | debug의 surface.ime_*로 한글·CJK 입력을 재현하는 방법과 한계 |

검증은 커밋 전에 직접 수행한다. 실행 환경은 [자체 검증 가이드](../dev-guide/self-verification.md)와 [격리 절차](../dev-guide/self-verification.md#독립-검증--개발도-agent-가-스스로-확인할-수-있어야-한다)를 따른다.

## 검증 절차를 나누는 기준

자동화 여부는 문서 전체가 아니라 각 단계의 입력과 판정 방법으로 판단한다. 배경 설명·참조표·이미 확인한 사실을 실행 절차로 세지 않는다.

- **시각·의미 판단**: preedit이 셀 그리드와 맞는지, 변경 영역이 의도대로 보이는지 등을 확인한다. 자동 검사가 없다는 이유만으로 절차가 잘못된 것은 아니다.
- **실행 준비**: Xauthority 전달, 창 ID 선택, 최신 플러그인 바이너리 확인, 저장한 PID로 정리 등이 해당한다. 준비가 틀리면 이후 결과도 유효하지 않다.
- **코드나 수치로 판정**: 상태 값·종료 코드·픽셀 값을 대조한다. 자동 판정이 가능하다는 사실과 CI에서 실제로 실행된다는 사실은 구분한다.

IME flush/clear의 기존 회귀 시험은 `tests/gui_tests.rs`에 있다. 자동 실행 여부와 수동 실행의 제약은 [CI 가이드](../dev-guide/ci-gates.md)의 사람이 돌리는 검사 절에서 확인한다. 검사 코드가 있어도 실행 환경을 갖추지 못해 끝나지 않았다면 통과로 보고하지 않는다.

## 문서 인용 검사와 실제 실행

명령이나 메서드가 존재하는지 확인한 것만으로 검증 절차를 실행했다고 볼 수는 없다. 실행한 명령, 대상 인스턴스, 결과와 로그를 따로 기록한다.

이름의 단순 존재 여부도 문맥에 따라 해석한다. 플러그인 메서드는 호스트 표에 없을 수 있고, 삭제된 명령을 설명하는 문서는 그 이름을 의도적으로 인용한다. 경로 검사는 파일 존재를 확인할 뿐 이런 문장의 의미까지 판단하지 않는다. 확인할 때는 CLI 도움말, IPC 등록 위치, 해당 플러그인과 주변 설명을 함께 읽는다.

### 재는 명령

아래 명령은 검토할 후보를 모은다. 결과 개수가 곧 유효한 절차나 위반 개수는 아니다.

```bash
# 최상위 번호 목록만 센다. 문단 안의 세부 단계는 포함하지 않는다.
grep -c '^[0-9]\+\. ' docs/ai-verification/*.md

# CLI 인용 후보. 각 형태를 해당 바이너리의 --help와 대조한다.
grep -rhoE '`tasty [a-z][a-z0-9-]*( [a-z][a-z0-9-]*)*' docs/ai-verification/*.md

# IPC 이름 후보. 등록 위치와 인용 문맥을 함께 확인한다.
grep -rhoE '`[a-z][a-z_]+(\.[a-z][a-z_]+)+`' docs/ai-verification/*.md
```

## 검증용 디스플레이 선택

GUI 검증 인스턴스는 기본적으로 셸이 상속한 디스플레이에 열린다. 여러 인스턴스를 사용자의 실제 화면에 띄우면 디스플레이 경합이 IPC 지연에도 영향을 줄 수 있다.

다음은 2026-09-06에 surface.list를 50ms마다 호출해 측정한 최대 왕복 시간이다. 현재 성능 보장값이 아니라 디스플레이를 분리해야 하는 이유를 보여 주는 관측이다.

| 조건 | load | 최악 왕복 |
|---|---|---|
| 인스턴스 18 개가 **실제 화면의 X 서버**를 함께 씀 | 39 | **5.79 s** |
| 같은 부하, 검증 인스턴스만 **전용 Xvfb** | 35 | 525 ms |
| 부하도 검증도 **같은 Xvfb 한 대** | 27 | 648 ms |
| 인스턴스는 안 늘리고 **CPU 만** 채움 | 33 | 372 ms |

당시에는 CPU 부하만 높였을 때보다 실제 화면의 X 서버를 공유했을 때 지연이 컸다. 한 Xvfb를 여러 인스턴스가 공유한 경우에는 같은 지연이 없었다. 다만 Xvfb는 렌더러도 소프트웨어이므로 X 서버와 하드웨어 GPU 중 어느 쪽이 원인인지는 이 측정으로 구분하지 못했다.

IPC 왕복·상태·타이밍처럼 사용자 화면 자체를 확인할 필요가 없는 검증은 전용 Xvfb에서 실행한다. 실제 화면을 쓰는 검증은 그 화면이 확인 대상일 때로 한정한다. Xauthority, 창 관리자 부재, 재렌더 조건은 [스크린샷 절차](screenshot-methods.md)를 따른다.
